# Правила проекта

Здесь — только правила. Зачем каждое и откуда оно взято —
`docs/PROCESS.md`. Над этим файлом — `docs/direction/DECISIONS.md`: при
расхождении прав он.

## Что это

DP_IDE (репозиторий DPmetaApp; D-165, D-167) — коммерческая мобильная
студия разработки на Android для любого пользователя (D-86, D-173):
первое — разработка с ИИ, второе — полуавтоматическая IDE для ручной
разработки; ничего, что не делает разработку эффективнее, и ничего
личного автора в сборке. Ядро — `dpai/`. Этапы — `ROADMAP/ROADMAP.md`.
Рабочие деревья, редактор, проверки, сборка, запуск/отладка и commit/PR
входят в продукт; тяжёлые графы не требуются.

DPmeta, DPpass и DPvisualisation вынесены с историей — самостоятельные
`dpsmpx/DPmeta` (D-178), `dpsmpx/DPpass` (D-174) и
`dpsmpx/DPvisualisation` (D-173). Канал к домашнему ПК — SSH поверх
включённого VPN, без DPpass (D-174). DP-Verify —
самостоятельный upstream и один из инструментов общей папки на target.
SocialMediaImage и DPprofile вне студии (D-87, D-154): их код — только в
`dpsmpx/SocialMediaImage` (DPprofile — его компонент), здесь копий и
связей нет; новую функциональность этого продукта не разрабатывать.
Сайт на паузе.

## Источник истины

- Старшинство: `docs/direction/DECISIONS.md` → этот файл → мастер-ТЗ
  `MESTER_TECHNICAL_TASK_ROADMAP.md` (D-25) → ТЗ → `ROADMAP/` → `TODO.md`
  → `docs/`. При расхождении прав старший; расходящийся документ
  исправляется. Решение меняется только новым решением в `DECISIONS.md`
  со строкой в истории.
- ТЗ — черновик версии 1.0 для фазы B, после влития — её контракт
  (D-25): меняется только вместе с решением.
- Подсистема `dpai/` — свой процесс (`DP_AI_Orcestrator:D-55`): её
  устройство решает `dpai/docs/direction/DECISIONS.md` (номера `D-NN`
  там свои, извне — `DP_AI_Orcestrator:D-NN`), правила — `dpai/CLAUDE.md`,
  проверки — `dpai/tools/verify/run.sh`. Решения этого журнала старше
  там, где речь о приложении целиком (одно приложение, имя, место,
  данные других систем).
- `README.md` — не источник истины и меняется только по запросу автора;
  его блок состояния пишет `tools/check/run.sh --write-status`.

## Запросы автора — сверять с решениями

- Слово автора — высший приоритет, но запрос до работы сверяется с
  `DECISIONS.md`, этим файлом, ТЗ, `ROADMAP/` и `TODO.md`.
- Расхождение с решением — спросить до работы: с чем расходится и какие
  варианты. Молча не выполнять и не «исправлять» запрос.
- Неясна важная деталь (что видит и что может сделать приложение,
  права и секреты, формат данных, что уходит в сеть) — спросить.
  Мелочи (имена в коде, раскладка внутри модуля) — решать и назвать в
  отчёте. Решённое не переспрашивать.
- Автор подтвердил решение, расходящееся с `DECISIONS.md`, — сначала
  новое решение там, потом работа.

## Перед правкой и после

- **Проверить — сделать или не трогать.** Нужного поведения или поломки
  и правда нет? Есть — ничего не менять и так и сказать; есть похожее —
  дополнить, а не писать второе.
- **Готово — остановиться.** Условие задачи выполнено и проверки прошли
  — работа кончена; следующий этап ROADMAP без поручения не брать.
  Обязательные документы (`TODO.md`, флажки ROADMAP, описание PR) — не
  лишнее.
- **Сбой инструмента — не сбой кода:** упавшая команда сперва
  разбирается по коду возврата и окружению (нет JDK, SDK, сети).
- **Красное до правки — не своё,** пока не доказано обратное: чужую
  поломку не чинить в своей задаче — записать в PR и `TODO.md`.
- **Класс задачи** — обычная, системная (сборка, общие модули, формат
  данных, безопасность) или рискованная (секреты, действия уровней 2 и 3,
  подпись, выпуск); что от класса зависит — `docs/PROCESS.md`.

## Правила кода

- Ядро одно — модули `dpai/` ниже `orchestrator` (D-28): `Outcome`,
  `Diagnostic`, `DiagCode`, `Clock`, `Secret`, ID, JSON, события, журнал
  берутся оттуда, второй раз не пишутся (проверка `core.single`).
  Правила кода подсистемы (`dpai/CLAUDE.md`, «Правила кода») действуют и
  для модулей DPmetaApp: время — `Clock`, случайность — `RandomSource`,
  неизвестное — `Measure.Unknown`, не ноль.
- Модули DPmetaApp — чистый Kotlin/JVM на ядре `dpai/`; Android-типы —
  только в оболочке; направления зависимостей — ТЗ, §6.2 (D-03);
  подсистема «AI» от модулей DPmetaApp не зависит.
- Состояние и метрики вычисляются при синхронизации и хранятся готовыми,
  с историей чисел (D-34); все пороги и веса — в `Rules.kt`, его смысл
  изменён — новая `RULES_VERSION` и запись в `docs/CHANGELOG.md`.
- Ожидаемые отказы — `Outcome` с `Diagnostic`; коды `DiagCode` только
  добавляются — в ядро и строкой в
  `dpai/tools/verify/registry/diag_codes.txt` (ТЗ, §6.9).
- Секрет — тип `Secret`; журнал — через `Logger` с редактированием;
  время — через `Clock`.
- Действие, меняющее что-то вне приложения, — команда `:core:actions` с
  уровнем и записью в журнал (D-07); уровень 3 — с красным
  предупреждением и вводом имени (D-37).
- Сеть — только адреса из списка `:core:net` (D-10); наружу не уходят ни
  телеметрия, ни отчёты о падениях: журнал отладки — только файлом в
  хранилище приложения (D-39); библиотек аналитики нет.
- Новая зависимость — только через каталог версий и со строкой в
  `docs/PROVENANCE.md`; без динамических версий.
- Предупреждения компилятора и Lint — ошибки; подавление — с причиной.
- Новый формат или новый баг разбора — новый образец в корпусе.

## Секреты и подпись

- В репозитории нет токенов, ключей API, паролей, `.env`, файлов ключей
  (`*.jks`, `*.keystore`, `*.p12`, `*.pfx`, `*.key`) — даже «тестовых»:
  образцы для проверки секретов собираются в тестах из частей.
- Ключ выпуска — только у автора; релиз подписывает автор (ТЗ, §12.4).
  Облачная сессия собирает только отладочный или неподписанный APK.
- Приложение коммерческое (D-173); выкладывает только автор (D-166).
  D-104 разрешает по явному поручению автора ручную выкладку APK в
  Releases закрытого dpsmpx/DPmetaApp: dev — prerelease с типом подписи,
  коммитом и SHA-256. Сессия не выкладывает в магазины и открыто, не
  меняет видимость репозитория; разрешён только APK workflow D-187. Порядок и проверки —
  docs/RELEASE.md. Отладочные сборки сессии — для устройств автора.

## Не терять работу между сессиями

- **Источник — актуальный `main` GitHub** (D-186). Невлитые ветки
  автора не трогать, если он прямо сказал их оставить.
- **PR больше не создавать** по поручению автора 22 ноября 2026.
  Незавершённое остаётся вне `main` до проверки. После завершённой
  задачи, зелёного `full --strict` и требуемой сборки APK — прямой
  коммит в `main`, с проверкой ожидаемого HEAD.
- Если полный строгий прогон технически недоступен — сообщить
  человеку о блокере и сохранить результат вне `main`, не называть
  частичный тест достаточным.
- **Агенты — не для проверок** (D-163): независимый проход по диффу
  делает сама сессия. По слову автора другие агенты могут участвовать
  строго по одному.

## Проверки

- `tools/check/run.sh static` — после любой правки.
- `tools/check/run.sh full` и `tools/check/run.sh full --strict` —
  перед прямой записью в `main`; полный прогон включает подсистему
  и `./gradlew build`. Пропуск недоступного шага в strict — ошибка.
- Правка `dpai/` — ещё `dpai/tools/verify/run.sh affected` и `full`
  по правилам подсистемы.
- `main` всегда зелёный: D-51 не отменяется. Нельзя считать
  `assembleRelease` заменой полного `full --strict`.
- По новому прямому поручению автора D-187 разрешён ровно `.github/workflows/apk.yml`:
  сборка APK с `full --strict`, SHA-256 и артефактом; PR не создаётся.
- Новое правило проверки — вместе с плохим и чистым образцом
  (`tests/test_check.py`).
