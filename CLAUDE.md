# Правила проекта

Здесь — только правила. Зачем каждое, откуда оно и как устроены
инструменты — `docs/PROCESS.md`. Над этим файлом —
`docs/direction/DECISIONS.md`: при расхождении прав он.

Репозиторий — система производства и проверки контента автора
`dpsmpx`. Главный принцип (Д1): **контент — производная проверенного
контекста автора и проектов, а не памяти конкретной сессии ИИ.**

## С чего начинать сессию

1. `docs/session/HANDOFF.md` — где остановилась прошлая сессия.
2. Вывод хука начала сессии: ветки с невлитой работой и открытые PR.
   Задача там уже начата — продолжать с той ветки, а не делать заново.
3. `docs/context/AUTHOR_MASTER_CONTEXT.md` — кто автор и что он делает.
4. Под задачу — `docs/direction/DECISIONS.md`, `TODO.md`, нужные
   документы из карты в `README.md`.

## Запросы автора — сверять с решениями

- Слово автора — высший приоритет, но запрос до работы сверяется с
  `DECISIONS.md`, этим файлом, `ROADMAP/`, `TODO.md` и `docs/`.
- Расхождение с решением или правилом — спросить до работы: с чем
  расходится и какие варианты. Молча не выполнять и не «исправлять».
- Неясна деталь, которая меняет результат (что увидит аудитория, имя,
  лицо, факты, площадка, деньги, право) — спросить. Мелочи (имена
  файлов, раскладка внутри задачи) — решать самому и назвать в отчёте.
- Автор подтвердил решение, расходящееся с `DECISIONS.md`, — сначала
  правка решения с записью в историю, потом работа.

## Сначала исследование, потом контент

- **Нет объекта — нет контента.** Любая работа над контентом — внутри
  `ContentItem` (`content/items/<id>/item.yaml`) с целью (`objective`),
  аудиторией и площадкой. Без цели контент не создаётся.
- Порядок не меняется: исследование → бриф → генерация → критика →
  ревизия → проверка → утверждение → экспорт
  (`docs/content/CONTENT_PIPELINE.md`). Генерация без брифа и
  публикация без `APPROVED` запрещены.
- Сначала проверить, нет ли уже нужного: похожий объект, шаблон,
  промпт или инструмент — дополнить существующее, а не завести второе.
- Варианты — только под заданную цель; десять вариантов «на всякий
  случай» не делаются. Выбирается вариант, лучше всех выполняющий
  цель, а не самый красивый.
- Материал пишется один раз — **каноном** (`canonical/vN.md`), формы
  площадок — его производные (`variants/`, Д22); числа, версии и адреса —
  подстановками из реестров (`{{fact:…}}`, Д28), а не руками.
  Зафиксированная версия канона не правится — только новой версией.
- Вывод ИИ — непроверенный (`trust: unverified`), пока не прошёл
  валидатор (`canonical seal`, `variant seal`, Д26).

## Факты и утверждения

- Неизвестное не придумывать. Недоступно — так и записать:
  `ACCESS = LIMITED`, `UNKNOWN / AUTH REQUIRED`. Пробел не
  заполняется догадкой.
- Утверждение о фактах — только из реестра `data/facts/facts.yaml`
  (класс `FACT` с источником и датой). `INTERPRETATION` и
  `HYPOTHESIS` не выдаются за `FACT` (`docs/content/CLAIM_POLICY.md`).
- Числа — с датой и источником; устаревшее число не повторяется.
- Оценка от ИИ («ИИ сказал, что проект хороший») — не доказательство и
  не контент. Превращать в проверенное наблюдение или результат.
- Запрещённые формулировки (anti-hype) — `data/facts/forbidden.yaml`;
  проверка — `tools/check.sh`.

## Идентичность и личные данные

- Источник истины о том, кто автор публично, — `docs/identity/`.
  Идентичность (имя, псевдоним, позиционирование, визуальный язык,
  аудитории, роли площадок) молча не меняется: правка решения в
  `DECISIONS.md` → запись в историю → проверка шаблонов и активных
  объектов (`docs/PROCESS.md`, «Изменение основ»).
- Имя — «Борис Давыдов / dpsmpx» (Д20), handle на площадках —
  `dpsmpx`. **На сайте имени нет — только `dpsmpx`** (Д37,
  `real_name: false`; сборка сайта проверяет). Имя — не разрешение на личное: работа, доход, учёба,
  семья, место — не материал для контента без отдельного решения.
- Образ автора — только с настоящей фотографии, помеченной
  `REFERENCE_IMAGE` (`assets/reference/`, `docs/PROVENANCE.md`).
  Генеративный «портрет автора» без сверки с фотографией и согласия
  автора не создаётся.

## Публикация

- Публикуется **только версия, одобренная автором** (Д12): одобрение
  записывается с хэшем текста и медиа; изменённое после одобрения не
  публикуется. Автопубликации нет, пока для класса нет решения.
- Сессия ИИ готовит, проверяет и показывает пакет (по умолчанию —
  dry-run), но **не одобряет за автора и не держит рабочих токенов**;
  рабочая публикация — с машины автора (`docs/content/PUBLISHING.md`).
- **Сайт (Д35, Д36):** хостинг — Beget, выгрузка — rsync из системы
  (`publish … --production`, `site deploy`). Выгружает только
  **локальная** сессия Claude Code и только после «да» автора на каждую
  команду: сначала показать `git diff` и `site deploy --dry-run`,
  закоммитить, потом спросить. Облачная сессия не выгружает никогда.
  Выпуск разрешён автором (Д34, `production.live: true`); `false` снова
  закрывает рабочую выгрузку. Выгружают только `site deploy` и
  `publish`: прямой rsync в `public_html/` в обход системы сессия не
  выполняет и автору не предлагает (Д35, инцидент 05.10.2026).
  Профили, удаление записей и всё вне официального API — руками
  автора; входа в аккаунты, автоматизации браузера и скрейпинга нет.
- Адресат публикации — только по явным id из
  `data/platforms/destinations.yaml`, никогда из имени или
  свободного текста (Д25).
- Чужие логотипы, изображения, шрифты, музыка — только по
  `docs/legal/RIGHTS_MATRIX.md`; у каждого ассета — запись
  происхождения (`docs/PROVENANCE.md`).

## Секреты

- В репозитории нет токенов, ключей, cookies, ID сессий, паролей,
  `.env`, закрытых приглашений и закрытых данных аккаунтов. Секреты —
  только локально, вне Git (`docs/SECURITY.md`). Проверка —
  `tools/check.sh` (`secrets`).
- Логи и выгрузки — с вычищенными секретами и личными данными.
- Выход сайта проверяет фильтр чувствительных данных (Д39,
  `data/policy/sensitive.yaml`): находка — ошибка сборки; исправлять
  источник, а не выход и не фильтр.

## Проверка перед коммитом

- `tools/check.sh` — все проверки: схемы объектов, состояния и гейты,
  реестр фактов, anti-hype, происхождение и хэши ассетов, ссылки в
  документах, секреты, канон и варианты, журнал публикаций, адресаты,
  матрица площадок, сборка сайта, тесты. Красное — не коммитить как
  готовое. Уровни: `--quick` — по ходу работы, `--affected` — перед
  коммитом куска, полный — перед «готово», `--release` — перед рабочей
  публикацией.
- GitHub Actions не используются (Д3): проверяет только
  `tools/check.sh` в сессии; итог — в описании PR.

## Не терять работу между сессиями

- Коммит и пуш — после каждого законченного куска и не реже раза в
  полчаса; незаконченное — с `WIP:` в заголовке.
- **PR — сразу после первого пуша** в рабочую ветку, черновиком, с
  «сделано / осталось», которое обновляется с каждым пушем. Отдельно
  не спрашивать.
- Перед концом сессии — обновить `docs/session/HANDOFF.md`.
- `TODO.md` — только незавершённые хвосты; решения — только в
  `DECISIONS.md`; история — в Git и PR.

## Где что лежит

- В корне — только точки входа: `README.md`, `CLAUDE.md`, `TODO.md`;
  из служебных — `.gitignore` и `.htaccess` (запрет отдачи корня
  репозитория с хостинга, Д35).
- Новый документ — в свой каталог по карте `README.md`; при переносе
  обновить все ссылки.
- `docs/audits/` — срезы на дату, не переписываются задним числом.
- **Готово — остановиться**: условие готовности выполнено, проверки
  зелёные — работа кончена; следующую задачу ROADMAP без поручения не
  брать. **Исключение — сайт (Д34):** пока автор не сказал «сайт готов»,
  каждая сессия продолжает разработку сайта в репозитории по списку
  «Сайт — в работе» (`ROADMAP/ROADMAP.md`, П2); выгрузка от этих слов
  не зависит — по правилам «Публикации».
- У задачи — объявленные границы (id в `ROADMAP/ROADMAP.md` или
  поручение). Постороннее в диффе — убрать, объяснить в PR или
  вынести в отдельную задачу.
