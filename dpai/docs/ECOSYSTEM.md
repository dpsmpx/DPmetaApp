# Экосистема и глобальный режим

Как оркестратор видит экосистему проектов и работает по ней (ТЗ, §5.3,
§43–§46, §148; этапы 15, 16). Экосистема необязательна: без неё
оркестратор работает как обычно.

## 1. Источник экосистемы

`ecosystem.EcosystemProvider`: проекты, их состояние, документы для
контекста и предложения задач. Реализации:

- `EcosystemProvider.None` — экосистема не подключена (`ECOSYSTEM_DISABLED`,
  не ошибка);
- `ManifestEcosystem` — манифест `dpai.ecosystem` v1 (§2).

Код DPmeta сюда не переносится (D-16): DPmeta выгружает манифест, адаптер
читает только его. Недоступный или испорченный манифест —
`ECOSYSTEM_UNAVAILABLE`; задачи, созданные вручную, идут дальше.

## 2. Манифест `dpai.ecosystem` v1

```json
{"format": "dpai.ecosystem", "version": 1, "projects": [
  {"key": "dplang", "name": "DPlang", "repository": "/src/dplang",
   "state": {"branch": "main", "verification": "red"},
   "documents": ["CONTRACT.md"],
   "suggestions": [{"key": "fix-contract", "title": "…", "objective": "…",
                    "priority": "HIGH", "operation": "fix"}]}]}
```

Чтение строгое (D-09): неизвестное поле, версия новее, повтор ключа
проекта — отказ. `state` — свободные пары строк: какие поля, решает
источник. `priority` — уровень `Priority`; `operation` — вид работы, по
нему прогон решает, разрешена ли она.

## 3. GitHub

`connectors.GitHubCommands` — команды официального клиента `gh`: создать
PR, узнать состояние PR, разобрать ссылку. Вход — у `gh` пользователя,
токенов оркестратор не хранит (D-14). Исполнение — процессом в дереве
задачи (`execution`). В V1 — PR и состояние, не замена GitHub
(`docs/direction/V1_SCOPE.md`, §3).

Экран PR (D-108, 9 ноября 2026): `orchestrator.github.GitHubDesk` — список
открытых PR (`gh pr list --json`), карточка (`gh pr view --json`:
описание, проверки `statusCheckRollup`, отзывы и комментарии), отправка
ветки задачи `task/<id>` в `origin` и PR в ветку интеграции. `gh` идёт
через агента target проекта в каталоге репозитория (как шаги проверки),
`git push` — Git того же target. Вывод `gh` — данные со стороны (T3):
строгий разбор по запрошенным полям, текст без управляющих знаков и знаков
смены направления, не длиннее 20 000 знаков; корпус — `tests/data/gh/`.
Отказы — понятной причиной: нет входа `gh` (`GITHUB_AUTH_EXPIRED`), нет
удалённого GitHub (`GITHUB_NOT_FOUND`), предел запросов, нет самого `gh`.
Отправка — действие уровня 1 (`DPmetaApp:D-36`) с окном «что уйдёт» и
строкой в журнале действий `actions/github.jsonl` (только добавление).
Повтор отправки не плодит PR — ответ адресом уже открытого.

DP-Verify — шаг профиля проверки проекта со своей командой
(`docs/SCHEDULER.md`, §8; D-16), отдельного адаптера не нужно.

## 4. Глобальный прогон

`orchestrator.ecosystem.EcosystemRun` (ТЗ, §45, §46): осмотр → выбор
следующей допустимой задачи → создание задачи в контуре проекта →
исполнение → проверка → запись итога → следующая.

Ограничители `RunPolicy`:

| Ограничитель | Что делает |
|---|---|
| `allowedProjects` | предложения других проектов пропускаются (`OPERATION_NOT_ALLOWED`) |
| `allowedOperations` | неразрешённый вид работы пропускается |
| `confirm` | задача из предложения создаётся только с подтверждения (V1) |
| `maxConcurrency` | не больше задач прогона одновременно |
| `maxTasks` | не больше задач за прогон (`RUN_BUDGET_EXHAUSTED`) |
| `maxTicks` | бюджет тактов (ресурсов) прогона |

Повторы и одобрения — политика задач и контура (`docs/SCHEDULER.md`, §5;
слияние — с одобрения). Порядок выбора: приоритет, затем проект и ключ
(D-22). Контекст задачи — документы проекта как данные с пометкой
происхождения и состояние экосистемы (`EcosystemSources`).

Итог — документ `dpai.ecosystem-results` v1: проект, предложение, задача,
состояние, вердикт и хеш отчёта проверки.

Отбор предложений — `EcosystemPlan`: одна логика для прогона, команды
`dpai ecosystem` и экрана приложения; у каждого предложения — решение
(можно или причина отказа: проект без контура, проект или вид работы вне
разрешённых, неизвестный приоритет) и команда постановки с ключом
`ecosystem:<проект>:<предложение>` — повторный прогон задачу не
дублирует (D-42). Части не из `[A-Za-z0-9_-]` или ключ длиннее 80 знаков
— `ecosystem.<40 hex>` (отпечаток обеих частей): контур принимает только
ключи `Command.KEY`. Прежний ключ с косой чертой контур отвергал — задача
из предложения не ставилась (найдено проверяющим D-106, 5 ноября 2026).

### 4.1 Точки запуска (D-97, часть 1)

Манифест — файлом: его строит `DPmeta:tools/manifest.py` (`DPmeta:C-13`),
например `python3 dpmeta/tools/manifest.py --root <клоны> --clone
DPmeta=dpmeta --out ecosystem.json` в каталоге DPmetaApp.

- `dpai ecosystem show <манифест> [--project ключ] [--operations docs,…]` —
  проекты, их состояние и предложения с решением; без сопряжения.
- `dpai ecosystem run <манифест> --project ключ [--operations docs,…]
  [--max N] [--yes]` — задачи из разрешённых предложений этого проекта
  ставятся контуру приложения через канал (D-47), каждая — после «да»
  человека; `--yes` подтверждает все. Без `--operations` — только `docs`
  (вид работы, который выгружает DPmeta); предел — 10 задач за прогон.
- В приложении: «Задачи» → «Экосистема…» (экран во весь экран) —
  источник манифеста (D-114): в DPmetaApp по умолчанию **реестр пульта**
  — оболочка `:shell` строит тот же `dpai.ecosystem` v1 из реестра и
  отмеченных клонов пульта (`DPmetaApp:core/formats`, `DpaiManifest`; те
  же правила, что у `manifest.py`, сверка —
  `DPmetaApp:tests/corpus/manifest`), без ПК и сети; запасной — файл,
  выбранный системным окном; в отдельной сборке «AI» — только файл.
  Смена источника, как смена файла, выключает политику прогона (§4.2).
  Проект этого контура — выбором (запоминается), задача из предложения —
  кнопкой «Поставить задачу…» и подтверждением; без отметки «Все виды
  работ» — только `docs`. На телефоне — `docs/DEVICE_CHECK.md`, §17.

Проверка: `EcosystemTest`, `EcosystemPlanTest`, `EcosystemCommandTest`,
`GitHubCommandsTest`.

### 4.2 Без подтверждения — политика прогона (D-106)

Политику включает только человек — в окне «Экосистема» приложения,
после окна с перечнем того, что она разрешает. Документ `dpai.auto-policy`
v1 (`AutoPolicy`):

| Поле | Смысл |
|---|---|
| `projects` | проекты манифеста, из которых ставить задачи; не пустой |
| `operations` | виды работ (`docs`, …); не пустой |
| `priorities` | приоритеты `CRITICAL`…`BACKGROUND`; не пустой |
| `maxPerDay` | не больше задач политики за 24 часа (1–20) |
| `maxOpen` | не больше открытых задач политики сразу (1–5) |
| `until` | срок, мс эпохи; нет поля — без срока |

Проход `AutoEcosystem.pass` — раз в час в такте службы контроллера,
сразу после включения и кнопкой «Пройти сейчас»: манифест — файл,
выбранный в окне (разрешение на чтение сохраняется), проект — проект
контура; отбор — `EcosystemPlan` и рамки политики; задача — та же
команда с ключом `ecosystem:<проект>:<предложение>`. След — документ
`dpai.ecosystem-auto` v1: `entries` — `at`, `project`, `suggestion`,
`task`, `policy` (отпечаток политики, 16 hex); последние 500 записей.
Запись делается до постановки — бронью без `task`, затем получает id.
Команда, ждущая очереди контура (`COMMAND_QUEUED`, D-94), остаётся
бронью: она занимает место в пределах, а id получает следующим проходом
по итогу команды с тем же ключом; записанный отказ контура убирает её из
следа, а бронь, о ключе которой контур сутки ничего не знает (команда до
него не дошла), снимается с предупреждением. Предложение, которое человек
уже поставил сам (ключ исполнен или ждёт очереди), политика не трогает и
своим не записывает. Без собранного контура проход не идёт. Выбран другой
файл манифеста — политика выключается: включить её заново.
Каждая задача политики — ещё строка журнала приложения и уведомление.
Копия настроек (D-51) и канал `dpai` (D-47) политику не переносят и не
задают. Угроза — T19 (`docs/SECURITY_MODEL.md`); проверка —
`AutoEcosystemTest`; на телефоне — `docs/DEVICE_CHECK.md`, §22.
