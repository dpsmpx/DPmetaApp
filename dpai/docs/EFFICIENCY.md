# Экономия контекста и токенов

Слой D-40 и D-41: больше полезной работы на единицу расхода подписки — без
обхода пределов провайдера (D-04, D-30) и без потери того, что нужно для
правильного решения. Аудит, с которого он начат, —
`docs/audits/2026-10-08-token-efficiency.md`.

Главная мера — не «меньше токенов», а **сделанные и проверенные задачи
на единицу расхода**: ход, сэкономивший токены и не прошедший проверку,
— потеря, а не экономия.

Принцип (слово автора, 8 октября 2026): **модель принимает
интеллектуальные решения, а среда не даёт ей без нужды тратить
интеллект.** Всё, что среда может узнать или сделать детерминированно, —
факты `git status`, итог и выжимка проверки, размер prompt, выбор модели
по классу, решение о продолжении, коммит, handoff, — делает оркестратор,
а модели достаются готовые факты и решения по существу.

## 1. Где тратится

Оркестратор не вызывает API модели сам: ход — процесс Claude Code
(D-32), и внутри хода инструменты, историю и кеш prompt ведёт Claude
Code. Оркестратор решает, **что и как часто** уходит в ход: prompt
(контекст задачи), продолжение или новая сессия, модель и усилие, повтор
после отказа. Поэтому рычаги слоя — на этих решениях, а измерение — по
итогу хода, который сообщает провайдер, и по самому потоку хода:
вызовы инструментов и их вывод оркестратор видит сам (D-41).

## 2. Учёт

Источники, которые никогда не смешиваются (D-13):

| Что | Источник | Мера | Событие |
|---|---|---|---|
| Prompt хода: знаки, токены, источники, не вошедшее, не посланное повторно, режим, маршрут | оркестратор | оценка (`ESTIMATED`) | `SESSION_PROMPT_PREPARED` |
| Ход: токены входа, выхода, чтения и записи кеша, размышления, контекст в конце хода, вызовы API, субагенты, длительность, модели и их окна, стоимость, было ли сжатие истории | провайдер (`result`, `docs/research/CLAUDE_CODE_CLI.md`, §11) | наблюдаемое; стоимость при подписке — оценка по прейскуранту | `SESSION_TURN_USAGE` |
| Инструменты хода: вызовы по инструменту, байты результатов в контексте модели, ошибки, повторы, файлов прочитано и изменено, вызовы и вывод субагентов | оркестратор по потоку (`tool_use`, `tool_result`, `parent_tool_use_id`) | байты — точно; токены — оценка; повторы — нижняя граница | `SESSION_TURN_TOOLS` |

Оценка токенов — UTF-8 байты / 3 с округлением вверх: с запасом и для
латиницы (~4 байта на токен), и для кириллицы (~5–6 байт на токен);
точный счёт знает только провайдер, и отчёт сравнивает оценку с ним.
Ход без итога (оборвался) — расход неизвестен, а не нулевой: суммы
сессии тогда — нижняя граница (`UsageTotals.unknownTurns`).

Сессия копит расход (`SessionRecord.usage`, снимок `dpai.sessions-state`
v3): из него строятся отчёт (§9) и решение о продолжении (§4).

**Повтор инструмента** — вызов с тем же входом (без описания), когда
между вызовами ничто не могло изменить результат: для чтения файла — ни
правки этого файла, ни команды с неизвестным действием (`Bash`,
инструменты MCP); для поиска — ни одной правки и такой команды. Та же
команда `Bash` дважды — не повтор: первая могла что-то изменить.
Сомнение — не повтор, поэтому счёт — нижняя граница. Субагенты ведут
свой контекст: их вывод в контекст хода не идёт (только итог инструмента
`Agent`) и считается отдельно. Замер есть и у хода без итога; пути
файлов в журнал не пишутся. Изображения в результатах не считаются.

## 3. Бюджет контекста

Источники контекста (`ContextSource`) — слои по уровню; prompt
(`PromptRenderer`) выводит их от устойчивого к меняющемуся:

| Слой | Уровень | Раздел prompt | Под давлением бюджета |
|---|---|---|---|
| L0 правила | — (оркестратор) | «Правила оркестратора» | всегда |
| L1 правила и решения | `GLOBAL`, `PROJECT` | сразу после правил | критично |
| — устройство репозитория | `REPOSITORY` | сразу после правил | выпадает с указателем |
| L2 задача | цель, следующее действие, `TASK` | «Задача» | критично |
| L3 состояние | `HANDOFF` | после задачи | критично |
| L4 знания | `DOCUMENT`, `CODE` (в том числе карта кода `code:map`, D-171) | после задачи | выпадают первыми, с указателем |
| L5 вывод инструментов | `TOOL` (итог проверки, §5) | после задачи | критично |
| L6 история | — (ведёт Claude Code) | — | §4 |

Бюджет (`ContextPolicy.budgeted`) — в оценочных токенах (§2) и вдобавок
к пределу знаков. Отбор — по `ContextPolicy.PRIORITY`: правила, задача,
handoff, итог проверки, затем репозиторий, документы, код. Не влезший
источник некритичного уровня — `CONTEXT_TRUNCATED` и строка в разделе
«Не вошло в контекст» с ключом и размером: исполнитель знает, чего не
видел, и найдёт сам. Критичный — отказ сборки `CONTEXT_BUDGET_EXCEEDED`:
правила и требования задачи не режутся молча. Тот же текст под вторым
ключом — один раз (`CONTEXT_DEDUPLICATED`, `sameAs`).

Размер бюджета задаёт оркестратор от окна модели (§10): окно минус
ответ, минус системный prompt и инструменты Claude Code, с запасом — и
лишь доля этого: остальное нужно ходу на собственную работу
(чтение файлов, вывод команд). Заполнять всё окно контекстом задачи —
лишить ход места для работы.

## 4. Продолжение и контрольные точки

Продолжают сессию той же задачи в двух случаях: ход прерван (handoff,
D-32) и ход заявил «готово», а проверка не прошла (§5) — тогда
следующая попытка продолжает ту же сессию провайдера: исполнитель помнит,
что сделал, и получает только то, что упало. Как продолжать, решает
`Continuation` по фактам журнала:

| Условие | Режим (`PromptMode`) | Сессия провайдера |
|---|---|---|
| первая попытка или нечего продолжать | `FULL` | новая |
| другой слот или target (файлы сессии — в каталоге слота на своём target) | `CHECKPOINT` | новая, с handoff |
| переполнение контекста (`CLAUDE_CONTEXT_OVERFLOW`) | `CHECKPOINT` | новая, с handoff |
| история не меньше `checkpointAt` окна (по умолчанию 0,6) | `CHECKPOINT` | новая, с handoff |
| сессия точно видела прежнюю версию контекста | `DELTA` | та же (`--resume`) |
| иначе | `FULL` | та же (`--resume`) |

«Точно видела» — все ходы сессии с последнего полного prompt сообщили
расход (§2), Claude Code не сжимал историю (`compact_boundary`), и
известна версия, ушедшая в её последний ход (метка `context` в
`SESSION_PROMPT_PREPARED`). В `DELTA` источник с тем же хешем не
посылается — строка в разделе «Без изменений с прошлого хода этой
сессии»; новое (handoff, выжимка проверки) и изменённое — целиком.
Сомнение — всегда полный prompt: лишние токены дешевле потерянного
контекста.

Контрольная точка — свежая сессия с handoff вместо `--resume`: каждый
вызов API в ходе перечитывает всю историю, и при большой истории
продолжение дороже нового начала с компактным состоянием. Handoff
(L3) — состояние для продолжения, а не стенограмма: причина, что
проверено, что упало (шаги и коды), изменённые файлы (`git status`),
ветка, рабочий каталог, следующее действие (`dpai.handoff` v3).

**Рабочий набор** (D-41) — чтобы свежая сессия не исследовала
репозиторий заново: файлы, которые сессии задачи читали и правили
внутри рабочего дерева (по вызовам инструментов, а не по словам модели;
изменённые — первыми, затем чаще читаемые; без уже названных `git
status`; до `maxFiles`), и итог последнего завершённого хода (до
`maxSummaryChars`, через `Redactor`, помечен «со слов исполнителя»). В
prompt они идут, только когда сессия провайдера не продолжается: при
`--resume` история их уже содержит. Набор держится в памяти контура;
после перезапуска — из последнего handoff задачи.

Переполнение контекста у провайдера (`Prompt is too long`) — ход
`INCOMPLETE` с `CLAUDE_CONTEXT_OVERFLOW`: handoff с причиной
`CONTEXT_OVERFLOW` и продолжение контрольной точкой — меньший контекст, а
не повтор того же.

## 5. Итог проверки

`OutputDigest` (`verification`) сжимает вывод непрошедшего шага: строки
ошибок (первые и последние до предела, повторы — один раз), итоговые
счётчики тестов и сборки, первые кадры стека после ошибки,
предупреждения, края вывода; середина — пометкой «пропущено строк: N».
ANSI-цвета убираются, длинные строки обрезаются с пометкой. Каждая
строка выжимки — строка вывода: ничего не пересказано и не выдумано.
`VerificationReport.failureDigest` собирает её для непрошедших
обязательных шагов с командой и кодом выхода — это источник `TOOL`
следующей попытки (§4). Прежние 20 последних строк (`tail`) остаются в
доказательстве шага: у Gradle это «BUILD FAILED … --stacktrace», а не
ошибка.

## 6. Кеш и повторы

- **Кеш prompt провайдера.** Кешем prompt управляет Claude Code; у
  оркестратора — порядок (устойчивое раньше, §3) и флаг
  `--exclude-dynamic-system-prompt-sections`: каталог, окружение и
  `git status` уходят из системного prompt в первое сообщение, и
  сессии разных рабочих деревьев перестают различаться системным prompt
  (аудит, W4). Попадания видны в расходе: чтение кеша против записи (§2).
- **Повтор постановки.** Незавершённая задача с тем же заголовком и целью
  (без регистра и лишних пробелов) — `TASK_DUPLICATE`: вторая задача не
  создаётся.
- **Повторы и гонки.** Уже были до D-40 и остаются: ключ идемпотентности
  сессии (`task:…:attempt:N`), запуска агента, handoff и одобрения — повтор
  такта, события или нажатия не даёт второго хода (ТЗ, §5.4).
- **Кеш результатов инструментов** у оркестратора не заведён: его
  инструменты — проверка и Git; проверку повторять на той же правке
  незачем, и это решает §5 (повтор — после правки), а не кеш. Кеш
  проверки по отпечатку дерева сделал бы упавший нестабильный тест
  «липким», а точный отпечаток требует индексировать рабочее дерево.
  Внутри хода кешем и повторами управляет Claude Code; оркестратор
  повторы измеряет (§2) — сжать вывод инструментов он не может.

## 7. Модель, усилие, субагенты

Класс задачи (`TaskClass`, политика задачи) → маршрут (`RoutingPolicy`):

| Класс | Модель | Усилие | Субагенты |
|---|---|---|---|
| `TRIVIAL`, `CLASSIFICATION`, `EXTRACTION`, `SUMMARIZATION` | `haiku` | `low` | нет |
| `REPOSITORY_RECON` | `sonnet` | `low` | нет |
| `NORMAL_ENGINEERING` (по умолчанию) | аккаунта | по умолчанию | да |
| `COMPLEX_DEBUGGING` | аккаунта | `high` | да |
| `ARCHITECTURE`, `CRITICAL_REVIEW` | `opus` | `high` | да |

- Явная модель или усилие задачи (`TaskPolicy.model`, `effort`) сильнее
  маршрута: без эскалации и удешевления (`route = pinned`).
- Эскалация: после каждой проваленной проверки — ступенью выше по
  `ladder` (`haiku` → `sonnet` → `opus`) и по усилию. Дешёвое — сначала,
  сильное — когда дешёвое не справилось. Модель аккаунта не угадывается —
  растёт только усилие.
- Запасная модель — ступенью ниже (`--fallback-model`): на случай
  перегрузки или модели, недоступной на плане подписки.
- Субагенты запрещаются классам, где параллельность не окупается
  (`--disallowedTools Agent`): лишний субагент — свой контекст и расход.
- Маршрут виден: модель, усилие и причина (`class`, `escalated:N`,
  `budget`, `pinned`, `legacy`) — в `SESSION_PROMPT_PREPARED`, модель хода
  по факту — в `SESSION_TURN_USAGE`.

Флаги `--effort`, `--fallback-model` и
`--exclude-dynamic-system-prompt-sections` проверены по справке 2.1.294;
старый Claude Code на target отвечает на неизвестный флаг «unknown
option» и выходит до вызова API — модель не тратится. Драйвер сессии
узнаёт флаг из stderr: ход — `CLAUDE_FLAG_UNSUPPORTED` без вины аккаунта,
оркестратор запоминает флаг для target, повтор идёт без него.

Длину ответа Claude Code флагом не ограничивает (`--max-turns` в 2.1.294
нет); пределы хода — усилие, `--max-budget-usd` политики задачи и
тайм-аут хода.

## 8. Режим бюджета

Пределы подписки — наблюдаемое (`rate_limit_event`, D-30): у подписки
слота, достигшей порога, — режим `FRUGAL`:

- бюджет контекста × `frugalScale` (0,6);
- классы из `downgradable` (мелкое и разведка) — на дешёвую ступень, пока у
  задачи нет провала; уведомление «Задача удешевлена» (`route = budget`);
- задачи ниже `deferBelow` (по умолчанию — `LOW` и `BACKGROUND`) ждут
  сброса окна с уведомлением «Задача ждёт»;
- архитектура, критичное ревью, трудная отладка и уже проваленное — без
  изменений: правильность на экономию молча не меняется.

Бюджеты в долларах на день или сессию не заведены: при подписке
стоимость — расчёт по прейскуранту, а ограничивают окна провайдера;
предел на ход — `--max-budget-usd` политики задачи.

## 9. Отчёт

`UsageReport` (`monitoring`) строится из состояния сессий и задач —
отдельного хранилища нет: `Orchestrator.usage()`, текст — `render()`.
Наблюдаемое и оценка — в разных разделах и так подписаны:

| Вопрос | Мера |
|---|---|
| Сколько ходов и вызовов API | `turns`, `apiCalls`; ходы без итога — `unknownTurns` (суммы — нижняя граница) |
| Сколько токенов входа, выхода, кеша | `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheCreationTokens`, `thinkingTokens` |
| Работает ли кеш prompt | `cacheReadShare` — доля входа из кеша |
| Какие модели и какая доля дорогих | `models`, `expensiveShare` |
| Сколько контекста слой не послал | `reusedTokens` (разница при `--resume`), `omittedTokens` (бюджет), `contextSavedShare` — оценка |
| Как часто контрольные точки и разница | `modes` (`FULL`, `DELTA`, `CHECKPOINT`) |
| Как маршрутизировались задачи | `routes` (`class`, `escalated`, `budget`, `pinned`, `legacy`) |
| Повторы, продолжения, сжатия, субагенты | `retries`, `continuations`, `compactedSessions`, `subagents` |
| Кто расходует больше всех | `topTasks` |
| Работа на расход | `tokensPerDoneTask` — грубая мера: задачи разные |
| Доля выполненных, средний ход, средний контекст в конце хода | `successShare`, `avgTurnMs`, `avgContextTokens` (наблюдаемое) |
| Сколько вывода инструментов вошло в контекст и какая доля входа это | `tools`, `toolTokens` (оценка), `toolShareOfInput` — доля впервые пришедшего: история перечитывается каждым вызовом API |
| Сколько работы впустую | `tools.total.duplicates`, `duplicateShare` — нижняя граница |
| Какие инструменты шумят | `topTools` — по выводу |
| Экономит ли рабочий набор исследование | `toolCallsByMode` — вызовов на сессию: `CHECKPOINT` против `FULL` |
| С какой попытки задачи проходят проверку и ревью | `passAtK` — по классу и модели последней рабочей сессии: pass@1, pass@3 (D-73, п. 4). Задача с итогом — `DONE` по проверке без ревью, принятого без итога, или `FAILED`; принятые без проверки и незавершённые не считаются (D-13). Попытка — `retries + 1`: повтор после отказа любого рода; повтор человеком счёт сбрасывает |

Сводка приложения показывает три меры — токенов на задачу, вход из
кеша, контекст не послан (оценка), — когда ходы уже были. Лента сессии
показывает итог инструментов каждого хода: вызовов, вывод (оценка),
повторов.

## 10. Настройка

Все пороги — в `EfficiencyPolicy` (`orchestrator.efficiency`), параметр
`Orchestrator`:

| Часть | Что задаёт |
|---|---|
| `context: ContextBudgetPolicy` | окно по умолчанию, резерв ответа, системный prompt и инструменты, запас, доля окна на контекст, нижний и верхний предел, множитель `FRUGAL` |
| `resume: ResumePolicy` | разница при `--resume`, порог контрольной точки, контрольная точка после переполнения |
| `routing: RoutingPolicy` | маршруты классов, ступени модели и усилия, порог эскалации, удешевляемые классы |
| `budget: BudgetPolicy` | режим `FRUGAL`, отложенные приоритеты |
| `workingSet: WorkingSetPolicy` | рабочий набор в handoff: путей не больше, длина итога хода (§4) |
| `codeMap: CodeMapPolicy` | карта кода в контексте хода (D-171): включена ли, предел вывода `git grep` и время, пределы текста карты |
| флаги | итог проверки в следующую попытку, handoff из фактов, общий кеш prompt, отказ повторной постановки, факты среды в prompt |

`EfficiencyPolicy.LEGACY` выключает всё — оркестратор ведёт себя, как до
D-40 (разделы prompt и выжимка проверки в отчёте — новые и в нём). Это и
базовая линия сравнения (§12), и рубильник.

## 11. Память

| Слой | Где | Сжатие | Чего нельзя |
|---|---|---|---|
| Долгая: решения, правила, устройство проекта | документы проекта, `CLAUDE.md` (их читает Claude Code), источники `GLOBAL`/`PROJECT` | правкой документов | писать туда стенограммы и эфемерное |
| Задачи: версия контекста, handoff, выжимка проверки, рабочий набор | `DocumentStore` (`dpai.context`, `dpai.handoff`) | новая версия вместо старой; handoff — поля, а не текст хода; итог хода — до предела | хранить переписку |
| Сессии: история диалога | сессия провайдера (Claude Code) | автосжатие Claude Code; контрольная точка (§4) | считать сжатую историю видевшей прежний prompt |
| Эфемерное: вывод процессов, текст модели | журнал агента и события `SESSION_OUTPUT` (обрезаны, D-37) | сегменты журнала | класть в контекст следующего хода |

Из эфемерного в память задачи попадает только выжимка (§5) и факты
`git status` — не сырой вывод.

## 12. Сравнение

`EfficiencyBenchmarkTest`: оркестратор, Git, проверка и разбор потока —
настоящие, Claude — заглушка, его расход — модель стоимости с явными
допущениями (цены ступеней модели 1 : 3 : 5, выход ×5, запись кеша
×1,25, чтение ×0,1; новая сессия изучает репозиторий заново,
продолжение — нет; каждый вызов API перечитывает контекст). Это
**симуляция**: она сравнивает решения оркестратора при одних допущениях,
а не измеряет модель. Прогон 8 октября 2026:

| Сценарий | До: выполнено, $ | После: выполнено, $ | Что сработало |
|---|---|---|---|
| 1. Мелкая задача | 1/1, 0,19 | 1/1, 0,06 | маршрут: дешёвая модель, малое усилие |
| 2. Обычная разработка | 1/1, 0,22 | 1/1, 0,22 | ничего: факты среды стоят ~250 токенов |
| 3. Анализ большого репозитория | 1/1, 0,53 | 1/1, 0,31 | бюджет контекста: документы сверх бюджета — указателями |
| 4. Шумный журнал проверки | 0/1, 0,76 | 1/1, 0,28 | выжимка вместо слепого повтора, продолжение той же сессии |
| 5. Повторный контекст | 1/1, 0,71 | 1/1, 0,53 | разница при `--resume`: ~600 токенов вместо ~20 000 |
| 6. Параллельные сессии | 4/4, 0,76 | 4/4, 0,65 | общий кеш системного prompt |
| 7. Долгая сессия | 0/1, 1,35 | 1/1, 1,44 | контрольная точка вместо переполнения |
| 8. Переполнение контекста | 0/1, 1,05 | 1/1, 2,06 | после отказа — свежая сессия, а не тот же объём |

Итого: до — 8 из 11 задач за 5,58 условных $, после — 11 из 11 за 5,55;
выполненных задач на условный доллар — 1,4 → 2,0. Тест требует, чтобы
«после» в каждом сценарии выполняло не меньше задач и не теряло больше
5 % работы на расход, а в сумме было лучше. Порядок величины выигрыша
даёт не один механизм, а сочетание: самый большой — там, где прежде
работа не доводилась до конца (сценарии 4, 7, 8). Цифры на настоящей
модели — замер на устройстве и ПК по `SESSION_TURN_USAGE` и отчёту §9.

## 13. Ограничения

- Выигрыш на настоящей модели — замер на устройстве и ПК; в облаке —
  сравнение на сценариях с моделью-заглушкой (симуляция, §12).
- Событие сжатия истории и отказ по размеру prompt узнаются по
  описанию, а не по записанному образцу
  (`docs/research/CLAUDE_CODE_CLI.md`, §11).
- Оценка токенов — с запасом, не счёт провайдера (§2).
- Поток с инструментами разработки построен по форме записанного
  образца (`tool-calls.jsonl`), а не записан: поля `tool_use.input` и
  `tool_result` сверить с настоящим ходом. Повторы — нижняя граница.
- Выигрыш рабочего набора модель стоимости (§12) не моделирует: он
  зависит от поведения модели и меряется на настоящей по
  `toolCallsByMode` (§9).
- Версия контекста, посланная в ход, держится в памяти контура; после
  перезапуска она узнаётся по документу задачи, только если он не
  обновлялся с того хода, — иначе продолжение идёт полным prompt (§4).
- Алиасы моделей (`haiku`, `sonnet`, `opus`) и уровни усилия — из
  справки Claude Code 2.1.294; доступность модели зависит от плана
  подписки, на неё — запасная модель (§7).
