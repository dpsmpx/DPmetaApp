# Модель безопасности

Что защищается, где границы доверия, какие угрозы и чем они закрыты.
Номера угроз — `T1`…; код и документы ссылаются на них (D-18). Угроза
без проверки — пожелание: у каждой указано, что её ловит или на каком
этапе появится проверка.

## 1. Что защищается

- Учётные данные аккаунтов провайдера, SSH-ключи, токены сервисов.
- Рабочие деревья и история репозиториев пользователя.
- Состояние оркестратора: задачи, события, контексты, handoff.
- Граница между проектами и между аккаунтами.
- Устройство и execution targets: от разрушительных команд без
  одобрения.

## 2. Границы доверия

| Источник | Доверие |
|---|---|
| Пользователь в интерфейсе приложения | доверенный; разрушительное — с подтверждением |
| Ядро оркестратора | доверенный код |
| Вывод Claude, предложенные им команды | недоверенный: проходит политику и одобрения |
| Содержимое репозиториев (README, код, issue) | недоверенный вход (ТЗ, §64) |
| Execution target | доверенный пользователем, но может быть недоступен или в чужом состоянии — всё сверяется |
| Внешние сервисы (GitHub, DPmeta) | данные, а не инструкции |

## 3. Уровни операций

| Уровень | Примеры | По умолчанию |
|---|---|---|
| `READ` | чтение файлов, статус | автоматически |
| `SAFE_WRITE` | правка в своём worktree, коммит в рабочую ветку | автоматически по политике |
| `SENSITIVE_WRITE` | push, PR, изменение настроек | подтверждение |
| `DESTRUCTIVE` | удаление файлов, сброс worktree | подтверждение и предпросмотр |
| `IRREVERSIBLE` | force push, удаление базы, отзыв учётных данных | явное одобрение с привязкой к хешу |

Предпросмотр (ТЗ, §69): область, затронутые объекты, риск, причина, хеш
предложения. Одобрение привязано к хешу (D-10): изменилось предложение —
одобрение недействительно (ТЗ, §5.4). `git reset --hard`,
`git push --force`, `rm -rf`, перезапись учётных данных не бывают
неявным следствием вывода AI (ТЗ, §70).

## 4. Угрозы

### T1 — Кража учётных данных

Вход claude.ai оркестратор не хранит и не передаёт: он лежит на target в
каталоге настроек слота и создаётся входом Anthropic (D-27). Ключи SSH
для targets — в Android Keystore, в базе — ссылка (D-14, ТЗ, §10).
Секрет не попадает в аргументы команды (они видны в списке процессов).
Ход на другом target (D-50) ходит к дереву по SSH своим ключом target
хода (на телефоне — в proot): этот ключ даёт оболочку на ПК, как и ключ
приложения, — на ПК он ограничивается частными сетями (`from=`; Windows —
D-68, Linux — D-84: дом, точка доступа телефона и VPN-сети; в чужой сети
с частными адресами `from=` её от домашней не отличает — вход только по
ключу), а вход claude.ai остаётся там, где выполнен.
Проверка: `SecretTest`; правило `provider-private` (`.credentials.json`,
токены подписки); хранилище ключей SSH — этап 3.

### T2 — Перехват сессии

Соединение с target — только по SSH с проверкой ключа хоста;
`ProviderSessionId` не даёт доступа сам по себе, но не публикуется в
уведомлениях и отчётах наружу. Клиент SSH запускается с
`StrictHostKeyChecking=yes` и `BatchMode=yes` (D-31): неизвестный или
сменившийся ключ хоста — отказ `SSH_HOST_KEY_REJECTED`, а не
молчаливое добавление; вход — только ключом. Имя хоста, пользователь и
пути, похожие на параметры `ssh`, отвергаются до запуска. Проверка:
`SshProcessHostTest`.

В приложении Android (D-35) — те же правила в `JschProcessHost`; ключ
входа — ECDSA P-256 в Android Keystore, закрытая часть не покидает
устройство. Ключ хоста нового target попадает в known_hosts приложения
только после того, как человек сверил отпечаток с тем, что показывает
сам target (`HostKeyProbe`); «доверять при первом подключении» нет.
Свой терминал (D-71) входит тем же путём (`JschConnect`). Проверка:
`JschProcessHostTest`, `JschShellTest`, `SshKeysTest`.

### T3 — Prompt injection

Содержимое репозитория и вывод инструментов — данные с пометкой
происхождения, а не инструкции оркестратора (ТЗ, §64). Действия,
предложенные моделью, проходят уровни операций (§3). Prompt строит
`PromptRenderer`: всё, кроме указаний оркестратора, — блоки данных с
пометкой происхождения, поддельный маркер конца блока обезврежен.
Ключ источника обезвреживается так же, как содержимое; данные проходят
`Redactor` (аудит `docs/audits/2026-10-07-security.md`, A-1, A-3).
Проверка: `ContextTest` на корпусе `tests/data/context-injection/`.

Сессия ревью (D-73) — только чтение: инструменты `Read`, `Grep`, `Glob`;
субагенты (`Agent`) и пишущие инструменты дерева на другом target
(`mcp__dpai__write`, `edit`, `run`, D-50) запрещены. Изменения задачи
идут в её prompt блоком данных `task-diff` (`REPOSITORY`) — через
`Redactor` и с обезвреженным маркером; ответ — только по `--json-schema`,
текст находок проходит `Redactor` и пределы длины, находки не по схеме
отбрасываются и считаются (`Review.parse`). Ревьюер решает лишь «повтор
или дальше»; слить по-прежнему может только человек (D-49).
Проверка: `ReviewFlowTest`.

### T4 — Вредоносное содержимое репозитория

Хуки Git, скрипты сборки, конфигурации инструментов в чужом
репозитории могут исполниться при проверке. Проверка проекта идёт в его
worktree на target, с профилем, явно разрешённым пользователем.
Коммит оркестратора — с `--no-verify`; каждая команда Git — с
`core.fsmonitor=false` и `core.hooksPath=/dev/null` — каталогом хуков вне
любого дерева: настройки и хуки репозитория, в том числе закоммиченные в
ветку, не исполняют код при командах оркестратора (A-2). Проверка:
`GitServiceTest`, `CompletionFlowTest`.

### T5 — Исполнение вредоносного скрипта

Команды, которые запускает оркестратор, — из профилей и политик, а не
из текста модели; запуск процессов — только в `execution` (D-03).
Проверка: `check_forbidden_apis.py`, правило `process-spawn`.

### T6 — Утечка между проектами

Граница проекта в контексте (ТЗ, §67); секреты проекта A не попадают в
задачу проекта B. Каталог агента на target — только владельцу (A-4).
Сервер дерева (D-50) читает и пишет только внутри дерева задачи, ссылки
— по настоящему пути; команды `run` границей не ограничены, как и
встроенный Bash.
Проверка: `ContextTest`, `IsolationTest` (A и B на одном target),
`WorkspaceMcpTest`.

### T7 — Путаница учётных данных между аккаунтами

Сессия несёт `accountId`, `credentialRef`, `executionTargetId`; сверка
перед запуском (ТЗ, §66). У каждого слота свой каталог настроек, вход
другим аккаунтом или вход не формой Claude останавливает слот,
перекрывающие вход переменные удаляются из окружения (D-29, D-30;
`docs/ACCOUNT_MODEL.md`, §4). Проверка: `AccountsTest`,
`SlotEnvironmentTest`; сверка перед запуском процесса — этапы 3, 6.

### T8 — Утечка секретов в журнал, диагностику, отчёт

`Secret` с закрытым `toString()`, `Redactor` для свободного текста,
диагностика редактируется при создании (D-14). Проверка: `RedactorTest`,
`DiagnosticTest`; тест утечки на диск — этап 2.

Свой терминал (D-71) несёт ввод человека на target и вывод программ
обратно — в том числе вход в Claude (`/login`, код из браузера) и
вставленный код. Поэтому экран и прокрутка назад — только в памяти
процесса приложения (`TerminalHub`), ввод и вывод не идут ни в журнал
приложения, ни в отчёт о сбое, ни в копию настроек; вкладки умирают с
процессом. Программа на target может попросить записать текст в буфер
обмена (OSC 52) — только после вопроса человеку, не больше 100 000
знаков; прочитать буфер обмена она не может (запрос «?» без ответа).
Вставка в терминал чистится от управляющих знаков и идёт в скобках 2004.
`claude` слота в терминале запускается без переменных, перекрывающих вход
(D-29). Снимок экрана тоже не должен уносить этот текст: окно терминала
стоит с `FLAG_SECURE`, и диалог, показывающий текст (OSC 52), — со своим
флагом (D-86); реестр таких экранов —
`tools/verify/registry/secure_screens.txt`. Проверка:
`TerminalEmulatorTest` (OSC 52 — только запись),
`KeyEncoderTest` (вставка не выходит из скобок), `TerminalLaunchTest`,
`check_secure_screens.py` (экран и его диалоги); запись в файлы вне
`storage` — правило `file-write` (модуль `terminal` файлов не пишет).

### T9 — Утечка через резервную копию

Секреты — отдельно и зашифрованно либо по явному согласию (ТЗ, §59).
Проверка — этап 2.

### T10 — Разрушительное действие без одобрения

Уровни операций (§3), привязка одобрения к хешу. `security.ApprovalLedger`:
одобрение — на хеш канонического предложения (действие, рабочее дерево,
аргументы), с временем истечения, одноразовое; нет одобрения —
`APPROVAL_REQUIRED`, другое предложение, истёкшее или повторное —
`APPROVAL_INVALID`. Разрушительные операции Git (`reset --hard`,
`clean -fd`, принудительный push, удаление ветки и дерева) строит только
`GitCommands` и только с одобрением. Проверка: `GitLogicTest`,
`GitServiceTest`; аудит — этап 18.

### T11 — Цепочка поставки

Зависимости — минимум (D-17), версии закреплены, у каждой — строка
`docs/PROVENANCE.md`; Gradle — со сверкой SHA-256 дистрибутива и
wrapper. Секреты в репозитории не хранятся. Проверка:
`check_dependencies.py`, `check_secrets.py`.

### T12 — Обход ограничений провайдера

Риск для пользователя (блокировка аккаунтов) и нарушение ТЗ, §10.
Только официальные интерфейсы, свои лимиты каждого аккаунта (D-04);
учётные данные claude.ai не собираются и не передаются (D-27); риски
подписок — `docs/ACCOUNT_MODEL.md`, §6.
Проверка: `check_forbidden_apis.py`, правило `provider-private`.

### T13 — Гость Linux в приложении — личность приложения

Гость Alpine под proot (D-75) работает под UID приложения: proot
перехватывает вызовы, но не изолирует. Всё, что гость открыл, открыто
от имени приложения. Защита: гостю — только нужные узлы `/dev`, без
`/sys` и `/dev/binder` (D-93); окружение Android гостю не передаётся
(`ProotHost`); файлы гостя хост пишет, не следуя ссылкам (аудит
безопасности 1 ноября 2026, A-3). Остаётся: гостю видны сеть и loopback,
в том числе канал `dpai` — он защищён подписью (D-92) и подтверждением
решающего на телефоне (D-91). Проверка: `ProotHostTest`,
`LinuxEnvironmentTest`.

### T14 — Подложенная копия настроек

Копия настроек (D-51) лежит в общих «Загрузках» и в Termux (D-54); их
может подложить другое приложение или сессия Claude в Termux.
Восстановление берёт из копии targets и ключи хостов как есть. Риск принят
автором 1 ноября 2026 (аудит безопасности, A-5): восстановление остаётся
одним шагом; ключ Termux подтверждается одноразовым кодом (D-54), остальные
— из копии. Восстанавливайте только свою копию.

## 5. Чего модель не обещает

- Защиты от пользователя с полным доступом к своему устройству и target.
- Безопасности кода, который Claude пишет: его проверяют профили
  проверки и ревью, а не оркестратор.
- Того, что провайдер не изменит интерфейс: изменение — новая запись в
  `docs/research/CLAUDE_CODE_CLI.md` и правка адаптера.

## 6. Как проверяется

| Что | Где |
|---|---|
| Секреты в репозитории | `tools/verify/check_secrets.py` |
| Запрещённые API и места | `tools/verify/check_forbidden_apis.py` |
| Редактирование секретов | `SecretTest`, `RedactorTest`, `DiagnosticTest` |
| Зависимости | `tools/verify/check_dependencies.py` |
| Глубокий аудит | `docs/audits/2026-10-07-security.md` (этап 18) |

### T15 — Диск приложения открыт менеджеру файлов

Диск приложения (D-96) отдаёт файлы приложения тому, кому человек открыл
его в системном выборе файлов, — и всему, что работает в том менеджере
файлов. Меры: закрыт по умолчанию, открыт — уведомление с «Закрыть»;
секретов на нём нет вовсе (токен канала `dpai`, каталоги слотов Claude,
`.credentials.json`, `.ssh`), их не открыть и по прямому пути; запись —
только в домашней папке Linux; символьные ссылки не проходятся.
Остаток риска: журнал контроллера (ход задач, ответы, итоги ходов) и
настройки (хосты, пользователи, ключи хостов) видит открытый менеджер.
Проверка: `AppDiskTest`.

### T16 — Ключ API-профиля: утечка и чужой адрес

Ключ API-профиля (D-98) даёт расход по счёту автора у провайдера. Пути
утечки: окружение процесса, журнал и диагностика, копия настроек, диск
приложения, адрес запроса и чужой сервер. Меры: ключ — `Secret`,
зашифрован ключом Android Keystore, в документе профиля — только ссылка;
`reveal()` — только в шифровании и в заголовке запроса (правило
`secret-reveal`); в окружение `claude` и гостя Linux ключ не передаётся
(D-29, D-98); запросы — только по списку `ProviderHosts`, свой адрес —
отметкой человека, без переадресаций; ключ — заголовком, не в адресе; по
HTTP ключ идёт только на это устройство; ответ провайдера — через
`Redactor`. Остаток риска: адрес на этом устройстве (`127.0.0.1`) слушает
и гость Linux — профиль с таким адресом и ключом отдаёт ключ тому, кто
слушает порт; ставьте ключ только своему серверу. Проверка:
`ProviderHostsTest`, `SlotEnvironmentTest`, `check_forbidden_apis.py`.

### T17 — Файлы автора в Linux-среде

Связанные папки (копией) и, в режиме «Доступ ко всем файлам», всё общее
хранилище телефона видны гостю Linux (D-99) — значит, и Claude, и коду
из npm и репозиториев, который там запускается: прочесть, изменить,
удалить. В хранилище лежат и копии настроек (`Download/dpai-backup`,
D-51), их гость может подменить (T14). Меры: режим всех файлов — только
переключателем, по умолчанию выключен; удаления из копии доходят до
папки автора только отдельной отметкой в окне плана; конфликт не
затирается; символьные ссылки копии не проходятся — ни данные
приложения в папку автора, ни запись за пределы копии; секреты
домашней папки Linux вкладка не показывает (D-96). Остаток риска: в
режиме всех файлов запись гостя в хранилище ничем не ограничена —
включайте его, когда нужен. Проверка: `FolderSyncTest`, `LocalTreeTest`.

### T18 — Локальная модель: сервер на этом устройстве и подсказки

Сервер llama.cpp (D-105) слушает `127.0.0.1` — это все приложения
телефона и страницы в браузере, а не только DPmetaApp; порт может
заранее занять чужой процесс (другое приложение, сервер разработки в
Linux приложения или в Termux, T13), и тогда чат и подсказки уйдут ему.
«Частная сеть» для профиля ПК — не «локально»: за адресом может стоять
прокси к облачной модели, а HTTP в Wi‑Fi идёт открытым текстом.
Подсказки получают состояние оркестратора — задачи, журнал, события.
Меры: у каждого запуска — случайный ключ API сервера (файлом с правами
владельца, не в аргументах) и свободный порт; веб-интерфейс и `/slots`
выключены; профиль «Телефон: llama.cpp» — свой, по сохранённому id, без
чужого ключа, сохраняется только после ответа сервера своим ключом на
`/v1/models` (порт — наш, модель загружена); пока сервер приложения не
запущен или профиль указывает не на его порт, профиль телефона подсказкам
и чату не отдаётся; ключ на диске приложения и во вкладке «Файлы» не
виден (D-96); подсказки берут только профили на этом устройстве или в
частной сети с отметкой своего сервера (D-98), и только выбранный
человеком или профиль телефона; данные — через строгий `Redactor`, с
меткой «данные, не инструкции» (T3), ответ — JSON по схеме, выбор — из
данного; модель ничего не делает сама. Остаток риска: приложение с тем же
доступом к loopback, узнавшее ключ из памяти процесса, — вне модели; сам
сервер ПК защищает его владелец. Проверка: `LocalAITest`,
`LinuxEnvironmentTest`; на телефоне — `docs/DEVICE_CHECK.md`, §21.

### T19 — Задачи из экосистемы без подтверждения

Политика прогона (D-106) ставит задачи из манифеста `dpai.ecosystem`, и
человек не читает их текст до постановки. Манифест — файл в хранилище
телефона: его может подменить приложение с доступом к файлам или чужая
правка в репозитории, из которого DPmeta его строит, — тогда цель задачи
(T3, prompt injection) уходит Claude без взгляда человека; сбойный
манифест может завалить очередь задачами. Меры: политики нет по
умолчанию; её включает и меняет только человек на экране, не канал
`dpai` и не копия настроек; она перечисляет проекты, виды работ и
приоритеты, а пустой список — ошибка, не «всё»; пределы за 24 часа и
открытых задач, срок действия; одно предложение — одна задача (ключ
D-42); каждая задача политики — запись с отпечатком политики, строка
журнала и уведомление; без подтверждения — только постановка: действия
вне приложения по-прежнему с подтверждением по уровням
(`DPmetaApp:D-36`, `DPmetaApp:D-37`), цель задачи — данные проекта, а не
инструкции оркестратору (T3). Другой файл манифеста выключает политику.
Остаток риска: подменённая цель в пределах разрешённых видов работ
исполнится до того, как человек увидит уведомление, — поэтому по
умолчанию в окне предложен только вид `docs`; документ политики — файл в
данных приложения, и процесс под его личностью (гость Linux приложения,
T13) может его записать в обход экрана — это в пределах того, что
принято в T13. Проверка: `AutoEcosystemTest`; на телефоне —
`docs/DEVICE_CHECK.md`, §22.

### T20 — Копия контура в облаке

Копия (D-107) уносит с телефона журнал контура: цели задач, тексты
handoff, пути, имена репозиториев и targets. Токен GitHub с правом
записи даёт доступ к репозиторию копий; утёкший пароль копии открывает
её любому, у кого есть файл; подменённая копия при восстановлении
заменила бы данные контура чужими (T14). Меры: шифрование на телефоне
до сети (PBKDF2-HMAC-SHA256, 600 000 повторов, AES-256-GCM, заголовок —
связанные данные), пароль не короче 12 знаков задаёт человек; репозиторий
— только приватный, адрес API — постоянный в коде; токен —
отдельный, на один репозиторий, под Keystore, только в заголовке
запроса; секретов, политики прогона (D-106), Linux-среды и журнала
отладки в копии нет; восстановление — только словом человека, с проверкой
каждого файла по оглавлению (пути внутри разрешённых каталогов, размеры,
SHA-256) и без удаления прежних данных. Остаток риска: слабый пароль
перебирается офлайн тем, кто получил файл, — поэтому предел снизу и
медленный вывод ключа; GitHub видит размер, время, имя устройства и
сообщение коммита копий; прежние копии под прежним паролем остаются в
истории репозитория. Чужую копию по тому же пути новая установка без
слова человека не заменяет.
Проверка: `CloudCopyTest`, `GitHubCopiesTest`; на телефоне —
`docs/DEVICE_CHECK.md`, §23.

### T21 — Модель, скачанная из сети

Файл GGUF с Hugging Face (D-110) — чужие данные: сервер llama.cpp разбирает
его в Linux-среде приложения, и ошибка разбора в llama.cpp — путь к коду
под личностью приложения (T13); подменённый по дороге файл или
переадресация на чужой адрес дали бы чужую модель; токен Hugging Face,
ушедший на хранилище файлов, — утечка. Меры: только `huggingface.co` и его
хранилище по HTTPS, переадресации — только на адреса списка; SHA-256 файла
сверяется со сведениями Hugging Face, не сошлось — файл удаляется; модель
выбирает человек; токен — только для закрытой модели и только по просьбе
при скачивании, под Keystore, в заголовке запросов к `huggingface.co`, не к
хранилищу и не в журнал; llama.cpp — из пакетов Alpine и обновляется
кнопкой «Поставить llama.cpp». Остаток риска: злонамеренная модель из
открытого репозитория, которую человек выбрал сам, — в пределах T13.
Проверка: тесты скачивания (D-110); на телефоне — `docs/DEVICE_CHECK.md`, §21.
