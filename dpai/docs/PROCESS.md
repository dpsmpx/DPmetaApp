# Процесс

Как в DP_AI_Orcestrator делается изменение, чем оно проверяется и как
обновляются зависимости. Короткая версия правил — `CLAUDE.md`.

## 1. Порядок изменения

1. **Решение раньше кода.** Найти решение, которое изменение
   затрагивает (`docs/direction/DECISIONS.md`), и раздел
   `docs/ARCHITECTURE.md` про модуль. Изменение, которое противоречит
   решению, начинается с нового решения D-NN (следующий свободный номер —
   в шапке журнала), а не с кода.
2. **Задача в рамках этапа.** Этап меняет только то, что в нём записано
   (`docs/direction/ROADMAP/README.md`); найденное «заодно» — строка в
   `TODO.md`, а не правка.
3. **Код, тест и документ — вместе.** Новый модуль или направление
   зависимости — таблица `docs/ARCHITECTURE.md`, §2; новый формат или
   поле — `docs/DATA_MODEL.md` и новая версия формата; новая угроза —
   `docs/SECURITY_MODEL.md`; новый предел — `docs/PERFORMANCE.md`; новая
   зависимость — §3 ниже; новый код диагностики или тип события — строка
   в `tools/verify/registry/` (D-05, D-12). Сменилось состояние этапа,
   критерий выхода, решение или пункт `TODO.md` —
   `python3 tools/verify/readme_progress.py` обновляет раздел «Прогресс»
   в `README.md` (руками его не правят).
4. **Проверки зелёные** (§2) — только тогда изменение готово.
5. **Коммит и пуш** — после каждого законченного куска (§4).

## 2. Проверки

### Запуск

```sh
tools/verify/run.sh static     # секунды: документы, модули, запрещённые API, секреты, контракты, формат
tools/verify/run.sh affected   # static + сборка и тесты затронутых модулей
tools/verify/run.sh full       # сборка и тесты, затем отдельные замеры; пропуск недоступного шага — ошибка
tools/verify/run.sh plan full  # что будет запущено и почему, без запуска
tools/verify/run.sh report     # итог последнего прогона в markdown — в описание PR
tools/verify/run.sh doctor     # окружение проверок: JDK, Python, git
```

Уровни — словарь ТЗ, §5.2 и DP-Verify, но своя реализация (D-16). Код
возврата: 0 — всё прошло; 1 — хотя бы один шаг упал; 2 — неверный
вызов. Журнал каждого шага — `build/verify/<шаг>.log`; итог —
`build/verify/report.json` и `build/verify/report.md`. На экран —
строки `✓`/`✗`, при отказе — хвост журнала.

`affected` выбирает модули по изменённым файлам относительно
`origin/main` (и незакоммиченным): изменённый модуль и все, кто от него
зависит по таблице `docs/ARCHITECTURE.md`, §2. Изменение сборки
(`build-logic/`, `gradle/`, `settings.gradle.kts`, `*.gradle.kts` в
корне) — все модули. Только документы — только `static`.

### Шаги

| Шаг | Что ловит | Решения |
|---|---|---|
| формат — `tools/verify/check_format.py` | не UTF-8, CR/CRLF, нет перевода строки в конце, хвостовые пробелы, табуляции, невидимые и двунаправленные символы | D-18 |
| порядок сборки и замеров — `tools/verify/verify_flow_test.py` | потеря замеров в full/affected, запуск после отказа сборки, скрытый отказ бюджета, устаревшее доказательство аудита | D-121 |
| ссылки — `tools/verify/check_docs.py` | ссылки на несуществующие документы, разделы, решения, угрозы, этапы, разделы ТЗ и тесты | D-19, все |
| модули — `tools/verify/check_modules.py` | модули и направления зависимостей не по таблице `docs/ARCHITECTURE.md`, §2; `android.*` вне `android`; `testkit` вне тестовых конфигураций; сторонняя библиотека во время выполнения; пакет исходника вне пакета модуля | D-02, D-17, D-21 |
| запрещённые API — `tools/verify/check_forbidden_apis.py` | системное время и случайность мимо `Clock`/`RandomSource`, сон, `GlobalScope`, `runBlocking` и печать вне `cli`, `printStackTrace`, запуск процессов вне `execution`, `reveal()` вне разрешённых мест, приватные адреса провайдера | D-03, D-04, D-07, D-14 |
| секреты — `tools/verify/check_secrets.py` | файлы ключей, закрытые ключи, токены провайдеров и сервисов | D-14 |
| API Android — `tools/verify/check_android_api.py` (`full`, при Android SDK) | вызов, поле или класс JDK из модулей приложения, которых нет в Android minSdk (`android.jar` 30); исключения — `tools/verify/registry/android_api_allow.txt` с причиной | D-28, D-34 |
| контракты — `tools/verify/check_contracts.py` | код диагностики или тип события удалён, переименован или не записан в реестр | D-05, D-12 |
| зависимости — `tools/verify/check_dependencies.py` | координаты и версии мимо каталога, версия без строки `docs/PROVENANCE.md`, сумма Gradle не та, workflow GitHub Actions | D-15, D-17 |
| README — `tools/verify/readme_progress.py --check` | раздел «Прогресс» отстал от плана, критериев, решений, `TODO.md`; этап «выполнен» при открытых критериях | — |
| сборка и тесты — `./gradlew build` | ошибки и **предупреждения** компилятора, модульные и межмодульные тесты | D-05 … D-23 |
| замеры — `:tests:integration:performanceTest --no-parallel --max-workers=1` | бюджеты хоста и нагрузка, отдельным вызовом Gradle после сборки; каждый раз заново | D-121 |
| cli — в `run.sh` (`full`) | собранная команда `dpai` запускается, коды выхода и вывод | D-02 |

`./gradlew build` выполняет обычные тесты, а бюджеты хоста — отдельная
задача `performanceTest` (D-121). Полный набор запускает `run.sh full`;
`affected` добавляет замеры, когда выбрал `:tests:integration:check`.
Падение замеров — падение проверки, пороги остались прежними. Для
ручного запуска после сборки:

```sh
./gradlew :tests:integration:performanceTest --no-parallel --max-workers=1
```

### Правила

- **Падающая проверка не ослабляется.** Тест и проверку чинят или
  меняют вместе с решением; отключить, пропустить, поднять порог «чтобы
  прошло» нельзя.
- **Исключение — с причиной и в одном месте:** разрешённые места в самих
  скриптах, `tools/verify/secrets_allow.txt`. Исключение без причины —
  ошибка обзора.
- **Новая проверка доказывает себя:** до включения в `run.sh` она ловит
  намеренно внесённое нарушение и проходит на чистом дереве; образцы —
  в самотестах `tools/verify/selftest.py`, их запускает `static`.
- **Сбой инструмента — не сбой кода.** Загрузка зависимостей через
  прокси отвечает `429 Too Many Requests` (6 октября 2026): шаг Gradle
  повторяется до 5 раз с растущей паузой (10…160 с), только если причина
  отказа в журнале временная — 429 или 5xx, обрыв или тайм-аут
  соединения, — нет постоянной (артефакт или версия не найдены, другой
  ответ 4xx, сертификат) и нет признаков сбоя кода: ошибки компилятора,
  упавшего теста или процесса тестов, ошибки в сценарии сборки
  (`tools/verify/gradle_log.py`). Обёртки `> Task … FAILED` и `Could not
  resolve …` Gradle пишет при любом отказе разрешения зависимостей — они
  не признак ни того, ни другого. Неопознанная причина — не повтор;
  повтор виден в отчёте. Красный тест не повторяется «на удачу».

## 3. Зависимости

Новая библиотека, плагин, версия или Gradle — по причине (уязвимость,
нужная возможность, требование платформы), а не «потому что вышло»
(D-17).

1. **Причина** — в описании изменения.
2. **Журнал изменений** между версиями прочитан: ломающие изменения,
   поведение по умолчанию, новые сетевые обращения и сбор данных.
3. **Лицензия** той версии, что берётся, — разрешает использование в
   закрытом личном приложении (D-101): Apache-2.0, MIT, BSD и подобные.
4. **Каталог** — версия только в `gradle/libs.versions.toml`.
5. **Запись** в `docs/PROVENANCE.md` в том же изменении.
6. **Gradle**: `./gradlew wrapper --gradle-version X --distribution-type
   bin --gradle-distribution-sha256-sum <сумма>`; сумма — из
   `services.gradle.org/distributions/gradle-X-bin.zip.sha256`; SHA-256
   нового `gradle-wrapper.jar` сверяется с `gradle-X-wrapper.jar.sha256`;
   обе суммы — в `docs/PROVENANCE.md`.

## 4. Работа между сессиями

Сессию обрывает лимит — без предупреждения; незапушенное пропадает.

- **В начале сессии** — хук DPmetaApp
  (`DPmetaApp:.claude/hooks/session-start.sh`, D-55) показывает ветки с
  невлитой работой; начатое продолжается с той ветки.
- **Коммит и пуш** — после каждого законченного куска и не реже раза в
  полчаса; незаконченное — коммитом `WIP:` со словами, что осталось.
- **Перед долгим** (сборка с загрузкой зависимостей, большой рефакторинг)
  — сначала запушить сделанное.
- **Перед сменой сессии** — состояние в `TODO.md` и файле этапа: что
  сделано, что дальше (ТЗ, §157, п. 16).

## 5. Перед слиянием

GitHub Actions не используется (D-15). Условие слияния в `main`:
`tools/verify/run.sh full` выполнен на последнем коммите и прошёл; итог
(`tools/verify/run.sh report`) — в описании PR (шаблон DPmetaApp
`DPmetaApp:.github/pull_request_template.md`, D-55). Засчитывается прогон
на ПК или в облаке; на телефоне (сборка в Termux) полный прогон не
обязателен и не засчитывается — там бюджеты устройства и
`docs/DEVICE_CHECK.md` (D-78).

## 6. Выпуск

Сборка воспроизводима (этап 20): архивы — без отметок времени файлов и с
устойчивым порядком записей (`dpai.kotlin-library`). Проверка —
`tools/verify/reproducible.sh`: две сборки коммита с нуля без кеша, и
SHA-256 каждого jar модуля, дистрибутива `dpai` и содержимого APK release
должны совпасть. У APK сравнивается содержимое без блока подписи
(`tools/verify/apk_digest.py`): подпись ECDSA от сборки к сборке разная.
Список хешей последней проверки — `build/reproducible/release.sha256`;
его прикладывают к контрольной точке выпуска.

Подпись выпуска Android: ключ (`.jks`) хранится у автора вне
репозитория и никуда не пересылается (ни в чат, ни в PR). Сборка берёт
его из свойств Gradle автора — `~/.gradle/gradle.properties`:

```properties
dpai.release.storeFile=C:/путь/к/ключу.jks
dpai.release.storePassword=…
dpai.release.keyAlias=…
dpai.release.keyPassword=…
```

Без этих свойств `assembleRelease` подписывает отладочным ключом — такой
APK только для замеров, не для раздачи.

Сценарий release — `DPmetaApp:tools/build-apk.sh release` — приложение
DPmetaApp с «AI» вкладкой (`DPmetaApp:D-53`), а `… release ai` — отдельная
сборка «AI» `android-app` (D-103) тем же ключом (D-31; на телефоне — ярлык
`apk-build` → «DPmetaApp — пульт и «AI»», в proot Alpine), как у
DPpass (D-97, ответ автора 2 ноября 2026): после сборки `apksigner verify`
— подпись v2/v3 и отпечаток SHA-256 сертификата; APK с отладочным ключом
(нет свойств `dpai.release.*`) сценарий удаляет и отказывает, если не задано
`DPAI_RELEASE_DEBUG_KEY=1` (замеры у себя); `dpai.release.certSha256` —
сверка отпечатка; рядом с APK — `SHA256SUMS`. Пароли — только в свойствах
Gradle: ни в командную строку, ни в вывод они не попадают.

Сборки облака (ветка `apk_debug`, §7) подписаны отладочным ключом облака: ключа
автора в облаке нет и быть не должно. Ключ автора — `dppass-dev`
(сертификат «DPpass Dev», PKCS#12) в Termux на телефоне; его свойства
`dpai.release.*` лежат в `~/.gradle/gradle.properties` Termux. Поверх
версии, подписанной им, APK облака ставятся только после переподписи на
телефоне: `tools/termux/resign-apk.sh` (он же — в ветке сборок) берёт те
же свойства, передаёт пароли `apksigner` через окружение и не меняет
содержимое APK — только подпись (схемы v2 и v3; `apk_digest.py` до и
после совпадает). Порядок — `docs/DEVICE_CHECK.md`, §1.2.
`dpai.release.certSha256` (необязательно) — SHA-256 сертификата или его
начало: скрипт отвергает подпись другим ключом.

## 7. Ветки и сборки

Слово автора (D-81); с 25 октября 2026 — правило всего репозитория
DPmetaApp (`DPmetaApp:D-33`): ветки сборок — его, подсистема кладёт
сборки в свой каталог, каталоги других подсистем переносятся из прежнего
коммита ветки без изменений. Сборки до 0.1.0-dev.5 — в ветке
`apk_debug` прежнего репозитория DP_AI_Orcestrator.

| Ветка | Что в ней |
|---|---|
| рабочие (`claude/…` и др.) | идёт работа; с невлитой работой их показывает хук начала сессии (§4) |
| `main` | весь код по каталогам модулей; вливается проверенная работа (§5) |
| `apk_debug` | все сборки APK, каждая в своём каталоге: `dpai/` — приложение, архив агента, `claude-proot.sh`, `resign-apk.sh`; `probe/` — пробник B2 (D-80): модуль удалён после пробы, каталог уходит со следующей сборкой приложения |
| `windows_debug`, `linux_debug` | сборки под Windows и Linux — когда появятся, по тому же правилу |

Ветка сборок — один коммит без истории, в ней только последние сборки:

1. Собрать из коммита `main` (полная проверка которого прошла).
2. В отдельном рабочем дереве (`git worktree add --detach`) — коммит-сирота
   (`git checkout --orphan`): каталоги сборок, в каждом `README.md` с
   коммитом `main`, версией и подписью и `SHA256SUMS`; общий `README.md`
   — что где лежит.
3. Сборка, которая не менялась, переносится из прежнего коммита ветки как
   есть — её суммы у автора остаются верными.
4. `git push --force origin HEAD:apk_debug` — прежние сборки уходят из
   ветки и из её истории.

Ветки сборок по версии не заводятся. Удалить ветку на GitHub политика
git облачной сессии не даёт (HTTP 403) — ненужную ветку удаляет автор на
GitHub; принудительный пуш ветки сборок разрешён (23 октября 2026).
