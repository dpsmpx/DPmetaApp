### 0.3. Подготовка ПК

Все команды для ПК — в Git Bash. Пути на телефоне начинаются с `/`, и
Git Bash переписывает их в пути Windows; отключите это один раз на
сессию терминала (`docs/TESTING.md`, §8):

```sh
export MSYS_NO_PATHCONV=1
mkdir -p ~/dpai-device-check && cd ~/dpai-device-check
adb devices
```

Ожидается строка с серийным номером и словом `device`. Если
`unauthorized` — подтвердите на телефоне «Разрешить отладку по USB».

На Redmi Note 13 через `adb` закрыты ввод (`adb shell input …`) и
изменение настроек (`adb shell settings put …`) — переключатель «Отладка
по USB (Настройки безопасности)» у вас не включается (D-33). Поэтому
прокрутки и переключатели в этой инструкции — руками; `am`, `dumpsys`,
`pidof`, `run-as` этим переключателем не закрыты и должны работать. Если
какая-то команда `adb` всё же ответит `SecurityException` — сделайте шаг
руками, как описано рядом, и запишите это в отчёт.

### 0.4. Если приложение упало

Признак: окно «Приложение остановлено» или приложение закрылось само.
Причина падения записывается в `files/last-crash.txt` приложения при
любой сборке, но прочитать файл можно только из debug-сборки
(`docs/TESTING.md`, §9). Стоит debug (§1.3) — хватит одной команды:

```sh
adb shell run-as com.dpsmpx.dpai cat files/last-crash.txt > last-crash.txt
```

Стоит ваш release (§1.4) — сначала поверх него debug, подписанный тем же
ключом (`…-debug-author.apk`, §1.2), затем та же команда и снова ваш
release; данные сохраняются.

Если на Redmi работает системный журнал, приложите и его:

```sh
adb logcat -d -b crash > logcat-crash.txt
```

В файле — тип ошибки и стек (имена классов); перед отправкой просмотрите
его. Замеры (§4) делаются только на release: после чтения файла верните
его.

Журнал самого приложения (D-43) — без `adb`: «Настройки AI» (значок
ползунков в заголовке, D-112) → «Журнал» → «В Загрузки» — файл `Загрузки/dpai-logs/dpai-log-<время>.txt` (журнал
целиком; в буфер обмена «Копировать» берёт начало и хвост; хранятся
последние 10 файлов). Текста модели и целей задач в нём
нет, но перед отправкой просмотрите и его.

### 0.5. Что никогда не присылать

Закрытые ключи (`~/.ssh/id_*`, ключи хостов без `.pub`), токены, файлы и
содержимое каталогов Claude (`~/.claude-slot-*`, `.credentials.json`,
`.claude.json`), полный вывод `claude auth status` (в нём email). В
отчёт идут только «да/нет» и поля, которые печатают команды этой
инструкции. Открытый ключ приложения не секрет, но и его присылать не
нужно.

## 1. Установка APK

### 1.1. Файлы и проверка SHA-256

Файлы лежат в ветке сборок `apk_debug` репозитория
`github.com/dpsmpx/DPmetaApp`, каталог `dpai/` (`DPmetaApp:D-33`: в
ветке — только последние сборки, у каждой подсистемы свой каталог).
Сборки до 0.1.0-dev.5 — в `apk_debug` замороженного DP_AI_Orcestrator.

| Файл | Зачем |
|---|---|
| `dpai-0.1.0-dev.10-debug.apk` | приложение для проверки; из него же читается `last-crash.txt` (§0.4) |
| `dpai-agent-0.1.0-dev.10.zip` | агент `dpai` для Termux и ПК: каталог `dpai/` с `bin/dpai` и `lib/` |
| `claude-proot.sh` | обёртка Claude Code для Termux (§5.3) |
| `resign-apk.sh` | переподпись APK вашим ключом выпуска на телефоне (§1.2) |
| `SHA256SUMS` | хеши файлов |
| `README.md` | описание сборки: коммит `main`, версия, подпись |

Release для замеров (§4) облако DPmetaApp не собирает: облачная сессия
собирает только отладочный или неподписанный APK (`DPmetaApp:CLAUDE.md`,
«Секреты и подпись»). Замеры на debug занижены — их не делать; release
собирается вашим ключом там, где ключ: на телефоне — ярлык `apk-build` →
«DPmetaApp — пульт и «AI»» (`DPmetaApp:tools/build-apk.sh release`, отдельная
«AI» — `… release ai`; без свойств
`dpai.release.*` — отказ; в конце — отпечаток сертификата и `SHA256SUMS`;
`docs/PROCESS.md`, §6).

Репозиторий приватный: ссылки `raw` без входа в GitHub отвечают 404,
поэтому `curl` из Termux не подходит. На ПК (вход в GitHub у `git` уже
есть):

```sh
git clone --depth 1 --branch apk_debug https://github.com/dpsmpx/DPmetaApp.git ~/dpai-device-check
cd ~/dpai-device-check/dpai
sha256sum -c SHA256SUMS
```

Файлы для Termux — на телефон в «Загрузки» (APK — тоже: переподписываются
на телефоне, где ваш ключ, §1.2):

```sh
adb push dpai-0.1.0-dev.10-debug.apk dpai-agent-0.1.0-dev.10.zip claude-proot.sh resign-apk.sh SHA256SUMS /sdcard/Download/
```

Ожидается `…: OK` для каждого файла. Любое `FAILED` — стоп: файл не тот,
скачайте заново; повторилось — FAIL пункта 1.1.

С телефона без ПК: в браузере откройте
`https://github.com/dpsmpx/DPmetaApp/tree/apk_debug/dpai`,
нажмите на файл и кнопку загрузки «Download raw file». Хеш на телефоне
сверяется в Termux (§5.2) после `termux-setup-storage`:

```sh
cd ~/storage/downloads && sha256sum -c SHA256SUMS --ignore-missing
```

Браузер может дописать к имени `(1)` — тогда переименуйте файл или
сравните строку `sha256sum <файл>` с `SHA256SUMS` глазами.

### 1.2. Уже установленная версия

**Стоит версия, подписанная вашим ключом выпуска** (сертификат «DPpass
Dev»; просмотрщик подписи показывает его как `807c…`). APK ветки подписаны отладочным ключом
облака (`docs/PROCESS.md`, §6) и поверх неё не встанут: Android ответит
«конфликт пакетов» (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`). Приложение не
удаляйте — пропадут targets и ключи; переподпишите APK вашим ключом на
телефоне. Ключ и пароли с телефона не уходят: `resign-apk.sh` (он же
`tools/termux/resign-apk.sh`) берёт путь, псевдоним и пароли из тех же
свойств `dpai.release.*` в `~/.gradle/gradle.properties`, что и Gradle, а
пароли передаёт `apksigner` через окружение, не командной строкой.

Нужен `apksigner`: в Termux — `pkg install apksigner`; или запускайте
скрипт там, где вы подписываете DPpass (proot Alpine с Android SDK:
скрипт найдёт `build-tools/*/apksigner` в `$ANDROID_HOME`). Файлы — в
«Загрузках» (§1.1):

```sh
cd ~/storage/downloads
sha256sum -c SHA256SUMS --ignore-missing
sh resign-apk.sh dpai-0.1.0-dev.10-debug.apk
```

Ожидается для каждого файла `✓ …-author.apk` и строки «сертификат
SHA-256» и «SHA-1»: одна из них начинается с тех же знаков, что показывает
просмотрщик у установленной версии (`807c…`). Чтобы скрипт сверял сам,
добавьте в `~/.gradle/gradle.properties` строку `dpai.release.certSha256=`
с SHA-256 сертификата или его началом: с ней чужой ключ — отказ, и файл
удаляется. Содержимое APK переподпись не
меняет — только подпись. Дальше ставьте `…-debug-author.apk` (§1.3). В отчёт — начало хеша
сертификата; ключ, пароли и `gradle.properties` — никогда (§0.5).

**Стоит сборка облака** (отладочный ключ облака). Отладочный ключ у
каждой облачной сессии свой: SHA-256 сертификата назван в `README.md`
каталога сборки (у 0.1.0-dev.1 … dev.5 — `60551def…`, у 0.1.0-dev.6 —
`a6f95acb…`, у 0.1.0-dev.7 и dev.8 — `005a23e4…`). Совпадает с установленной — APK ставится поверх как есть,
без переподписи (§1.3; с ПК — `adb install -r
dpai-0.1.0-dev.10-debug.apk`), targets, ключ приложения и закреплённые
ключи хостов остаются. Не совпадает — это «сборка с другой подписью»
ниже.

**В обоих случаях** после установки обновите агента на
каждом target тем же архивом, как в §5.4 (Termux) или §10 (ПК): версии
приложения и агента должны совпадать, иначе «Проверить» покажет
«обновить агента», а проба входа (D-69) ждёт сводку `dpai.auth-status`
от нового агента. Вход Claude в каталогах слотов сохраняется — заново
входить не нужно.

**Стоит сборка с другой подписью** — ни вашим ключом, ни отладочным
ключом облака. Проверьте, стоит ли приложение:

```sh
adb shell pm list packages com.dpsmpx.dpai
adb shell dumpsys package com.dpsmpx.dpai | grep -E "versionName|versionCode"
```

Пустой вывод первой команды — приложения нет, переходите к §1.3. Если
оно есть и установка поверх отвечает
`INSTALL_FAILED_UPDATE_INCOMPATIBLE` (на телефоне — «Приложение не
установлено» или «конфликт пакетов»), подписи разные: старое придётся
удалить.

При удалении пропадают данные приложения: targets, ключ приложения в
Android Keystore, закреплённые ключи хостов, журнал контроллера. После
установки ключ приложения будет новым — его снова нужно добавить в
`authorized_keys` на targets (§5.6), а старую строку убрать.

Если в старом приложении есть «Targets» → «Копия настроек» (D-51), до
удаления нажмите «Сохранить сейчас»: копия уйдёт в
«Загрузки/dpai-backup» и в Termux. После установки карточка
«Восстановление после переустановки» (D-54) даёт одну команду для
Termux: она заменяет ключ приложения в `authorized_keys`, и приложение
само возвращает targets и слоты из копии.

```sh
adb uninstall com.dpsmpx.dpai
```

Или на телефоне: долгое нажатие на значок «DP AI Orcestrator» →
«Удалить».

### 1.3. Установка

Ставится `dpai-0.1.0-dev.10-debug-author.apk` — переподписанный вашим
ключом (§1.2); без переподписи (стоит сборка облака с тем же ключом или
ничего) — `dpai-0.1.0-dev.10-debug.apk`. С ПК (переподписанный — сначала
`adb pull /sdcard/Download/dpai-0.1.0-dev.10-debug-author.apk`):

```sh
adb install -r dpai-0.1.0-dev.10-debug-author.apk
adb shell dumpsys package com.dpsmpx.dpai | grep -E "versionName|versionCode"
```

Ожидается `Success`, затем `versionCode=10` и `versionName=0.1.0-dev.10`.
Если `adb install` отвечает `INSTALL_FAILED_USER_RESTRICTED`, у Xiaomi
выключена «Установка через USB» в «Для разработчиков»; включить её без
аккаунта Mi часто нельзя — тогда ставьте с телефона.

С телефона: откройте `dpai-0.1.0-dev.10-debug-author.apk` (или без
`-author`) из «Загрузок», разрешите установку из этого источника, если HyperOS
спросит, и подтвердите установку. Версия — в «О приложении».

В Termux ещё прежний `dpai`, сопряжённый с приложением (D-47)? До §5.4
наберите `dpai status`: ожидается отказ «токен не подходит: dpai control
pair <новый код>», а не зависание (подпись D-92; итог — в §8.9 п. 8).

### 1.4. Release для замеров — сборка автора

Release нужен только §4 (замеры): debug медленнее, и его числа с
бюджетами не сравниваются. Облако release не собирает
(`DPmetaApp:CLAUDE.md`, «Секреты и подпись»): его собираете вы своим
ключом там, где ключ, — из того же коммита `main`, что в `README.md`
сборки (`docs/PROCESS.md`, §6):

```sh
cd DPmetaApp && ./gradlew :shell:assembleRelease
adb install -r shell/build/outputs/apk/release/shell-release.apk
```

Свойства `dpai.release.*` — те же, что для `resign-apk.sh`; без них
Gradle подпишет release отладочным ключом машины, и поверх вашей версии
он не встанет. Отдельная упаковка подсистемы снята D-201; ставится единый APK студии.
Нет release — §4 записывается «не проверено: нет release»; §3 идёт на
любой сборке.

## 2. Первый запуск и настройки HyperOS

### 2.1. Первый запуск

1. Откройте «DP AI Orcestrator».
2. Android 13+ спросит разрешение на уведомления — «Разрешить». (Отказ и
   возврат разрешения проверяются отдельно, §8.5.)
3. Ожидается: заголовок «AI · Сводка · демо», над содержимым любой
   вкладки — плашка «Демо: данные ненастоящие…» с «Начать» (к Targets,
   AI:A-17); внизу панель 48 dp из
   шести значков без подписей (D-61, D-112): плитки — «Сводка», список
   с отметками — «Задачи», компьютер — «Targets», облачко с вопросом —
   «Запросы» (число ждущих — значком), искра — «Модели», папка —
   «Файлы». Долгое нажатие на значок — его подпись; TalkBack читает
   «вкладка», название и «выбрано». «Журнал» — в «Настройках AI»
   (значок ползунков в заголовке; «Назад» — к вкладке). На
   «Сводке» — «Состояние: …» и карточки счётчиков, среди них «Активных
   сессий» — не меньше 20; числа меняются раз в секунду. Списка сессий
   на «Сводке» нет (D-65): задачи и их сессии — во вкладке «Задачи».

**Есть ли демо.** Демо — только пока в приложении нет target с каталогом
Claude. Ставили поверх версии со своими targets (§1.2) — приложение
сразу в режиме контроллера: заголовок «AI · Сводка» без «· демо». Тогда
выберите и запишите в отчёт:

- §3–§4 — «не проверено: контроллер, демо недоступно», переходите к §5;
- или на время §3–§4 уберите targets: «Настройки AI» → «Копии и восстановление» →
  «Сохранить сейчас», затем ⋮ → «Удалить…» у каждого target с каталогом
  Claude; после §4 — «Копия настроек» → «Загрузить…» → файл из
  «Загрузки/dpai-backup».

Оболочки Xiaomi ограничивают фон сильнее обычного Android (D-28). Пути
меню ниже — обычные для HyperOS; если пункт называется иначе, найдите
его поиском в «Настройках» и запишите в отчёт, как он называется у вас.

Для «DP AI Orcestrator» (долгое нажатие на значок → «О приложении», или

3. «Уведомления» — разрешены; для категорий «Запросы: нужен ответ»,

4. Список недавних приложений: долгое нажатие на карточку приложения →

## 3. Демо-режим без target

Демо — 20+ синтетических сессий на `MockRunner` с шагом раз в секунду
(D-34); журнал демо между запусками не хранится. Сборка — любая (debug
или ваш release, §1.4). Общее
правило: **FAIL** — падение (§0.4), окно «Приложение не отвечает»,
зависание больше 5 с, потеря выбранной вкладки там, где ниже ожидается её
сохранение; краткое (до секунды) мелькание индикатора загрузки после
поворота или возврата — ожидаемо: снимок экрана пересчитывается.

### 3.1. Сводка

На «Сводке» запишите N — число на карточке «Активных сессий»;
ожидается N ≥ 20 и меняющиеся счётчики. Затем «Задачи»: доска по
колонкам «… (число)», карточки «Демо-задача 1», «Демо-задача 2»…;
прокрутите доску до конца и обратно. Нажатие на карточку открывает чат
задачи: в заголовке — кружок состояния и имя, сверху справа «⚙» (лист
задачи) и «События» (лента событий хода); «←» и жест «назад»
возвращают к доске.

### 3.2. Быстрая навигация

За 30 секунд 20 раз переключите шесть вкладок в разном порядке;
10 раз откройте чат задачи с доски и сразу вернитесь жестом «назад». Ожидается: каждое нажатие отрабатывает сразу, нет падения и
окна «Приложение не отвечает».

### 3.3. Поворот

Включите автоповорот в шторке. На каждой вкладке и на открытом экране
сессии поверните телефон 5 раз. Ожидается: остаётся та же вкладка и та
же открытая сессия (состояние экрана сохраняется), счётчики и доска
продолжают обновляться с тех же значений — демо не начинается заново
(одна система на процесс).

### 3.4. Фон и возврат

На вкладке «Задачи» нажмите «Домой», подождите 10 с, вернитесь через
список недавних. Повторите 5 раз, в том числе с открытым экраном
сессии. Ожидается: та же вкладка и сессия, данные идут дальше.

### 3.5. «Не сохранять действия»

«Для разработчиков» → «Не сохранять действия» — включить (activity
уничтожается при уходе в фон, процесс остаётся жив). Повторите §3.4.
Ожидается то же, что в §3.4: вкладка и открытая сессия
восстанавливаются, счётчики не обнуляются. Затем переключатель
выключить.

### 3.6. Пересоздание процесса

```sh
adb shell pidof com.dpsmpx.dpai
```

Откройте вкладку «Задачи», нажмите «Домой» и убейте процесс в фоне:

```sh
adb shell am kill com.dpsmpx.dpai
adb shell pidof com.dpsmpx.dpai || echo "процесса нет"
```

Вернитесь через список недавних, снова `adb shell pidof com.dpsmpx.dpai`.
Ожидается: процесса не было, после возврата — новый PID; открывается та
же вкладка «Задачи»; демо — новое (журнал демо не хранится), и ранее
открытая сессия может оказаться пустой — это не ошибка. Ошибка —
падение или открытие не той вкладки.

Если `am kill` не убил процесс (PID тот же): «Для разработчиков» →
«Лимит фоновых процессов» → «Без фоновых процессов», переключитесь на
другое приложение и вернитесь; затем верните «Стандартное ограничение».
Запишите, каким способом получилось.

### 3.7. Убитый процесс и новый запуск

```sh
adb shell am force-stop com.dpsmpx.dpai
adb shell pidof com.dpsmpx.dpai || echo "процесса нет"
```

Без `adb`: «О приложении» → «Остановить». Откройте приложение значком.
Ожидается: обычный запуск на «Сводке», демо работает, падения нет.
Убийство во время настоящего хода — §7.3.

### 3.8. Длинная временная шкала

Оставьте приложение открытым на 5 минут, затем откройте чат любой
задачи, нажмите «События» (лента событий хода) и прокрутите её вниз и
вверх; «Чат» возвращает ленту сообщений. Ожидается: прокрутка без рывков
дольше доли секунды, нет падения.

### 3.9. Поиск (ТЗ, §75)

1. Сверху справа «Найти» → наберите две-три буквы из названия любой
   задачи на доске. Ожидается: через долю секунды после того, как вы
   перестали печатать, — список по видам («Задачи», «Сессии»,
   «События»…), у вида — число найденного. С контроллером, пока идёт
   такт, — до 2 с, и вместо событий может быть пометка «шёл такт
   контура»; повторный поиск через несколько секунд находит и события.
2. Нажмите задачу — открывается её лист; закройте. Снова «Найти» →
   нажмите сессию — открывается чат её задачи.
3. Одна буква — списка нет; бессмыслица (`ъъъъ`) — «Ничего не найдено».
4. Поверните телефон с открытым поиском — набранный текст на месте.

## 4. Замеры (этап 17)

Методика — как на Realme C21Y (`docs/PERFORMANCE.md`, §5), бюджеты —
`docs/PERFORMANCE.md`, §3: холодный старт до сводки ≤ 1,5 с, кадр сводки
≤ 16 мс при 20 активных сессиях. Только release (ваш, §1.4), демо-режим
(§2.1), экономия энергии выключена, другие приложения закрыты, телефон на
кабеле. Нет release или демо — §4 «не проверено» с причиной.

Запишите условия:

```sh
adb shell getprop ro.product.model
adb shell getprop ro.build.version.release
adb shell getprop ro.build.version.sdk
```

Версию HyperOS и частоту обновления экрана («Настройки» → «Экран» →
«Частота обновления»: 60 или 120 Гц) — из настроек. У Redmi Note 13
экран 120 Гц: при 120 Гц `dumpsys gfxinfo` считает кадр пропущенным
строже (срок кадра 8,3 мс против 16,7), поэтому долю «Janky» с Realme
(60 Гц) сравнивайте только при 60 Гц; перцентили в миллисекундах
сравнимы при любой частоте. Если есть время — повторите §4.2 при 60 Гц.

### 4.1. Холодный старт

Пять запусков с остановкой процесса перед каждым:

```sh
for i in 1 2 3 4 5; do
  adb shell am force-stop com.dpsmpx.dpai
  sleep 3
  adb shell am start -W -n com.dpsmpx.dpai/com.dpsmpx.dpai.android.MainActivity | grep -E "LaunchState|TotalTime"
  sleep 8
done | tee coldstart-redmi.txt
grep TotalTime coldstart-redmi.txt | awk '{print $2}' | sort -n | sed -n 3p
```

Ожидается `LaunchState: COLD` в каждом запуске (если `WARM` или `HOT` —
процесс не был остановлен, повторите). Последняя команда печатает
медиану `TotalTime` в миллисекундах. PASS — медиана ≤ 1500.

`TotalTime` — время до первого кадра activity. Сводка рисуется сразу
после первого шага демо; на глаз отметьте, виден ли индикатор загрузки
после появления окна и примерно сколько (нет / меньше 0,5 с / больше).
Условие бюджета «1000 задач в базе» на телефоне сейчас не создать —
запишите «демо, N активных сессий» с N из §3.1.

### 4.2. Кадры сводки

16 прокруток пальцем: на Redmi `adb shell input swipe` закрыт (D-33).
Списка сессий на «Сводке» больше нет (D-65), поэтому прокручивается
доска «Задачи» с 20+ демо-задачами — методика отличается от Realme
(там — список сессий на сводке), сравнение — с этой оговоркой
(`docs/PERFORMANCE.md`, §5). Одна прокрутка — уверенный взмах вверх или
вниз по доске, примерно раз в секунду, всего ~16 с; чередуйте
направление. В первом прогоне за 5 с ожидания после запуска откройте
«Задачи» — до `reset` счётчика кадров.

Первый прогон (холодный процесс):

```sh
adb shell am force-stop com.dpsmpx.dpai
adb shell am start -n com.dpsmpx.dpai/com.dpsmpx.dpai.android.MainActivity
sleep 5
adb shell dumpsys gfxinfo com.dpsmpx.dpai reset > /dev/null
echo "16 прокруток пальцем, затем Enter"; read
adb shell dumpsys gfxinfo com.dpsmpx.dpai > gfx-redmi-release-run1.txt
grep -E "Total frames rendered|Janky frames|50th|90th|95th|99th" gfx-redmi-release-run1.txt
```

Второй и третий прогоны — в том же процессе, без перезапуска; третий
считается «после прогрева»:

```sh
for n in 2 3; do
  adb shell dumpsys gfxinfo com.dpsmpx.dpai reset > /dev/null
  echo "прогон $n: 16 прокруток пальцем, затем Enter"; read
  adb shell dumpsys gfxinfo com.dpsmpx.dpai > gfx-redmi-release-run$n.txt
  grep -E "Total frames rendered|Janky frames|50th|90th|95th|99th" gfx-redmi-release-run$n.txt
done
```

Заполните таблицу как в `docs/PERFORMANCE.md`, §5:

| Сборка | Кадров | Пропущено (janky) | p50 | p90 | p95 | p99 |
|---|---|---|---|---|---|---|
| release, первый прогон | | | | | | |
| release, после прогрева | | | | | | |

PASS — p95 после прогрева ≤ 16 мс (на Realme: 11 мс). Первый прогон
записывается для профиля базовой линии (`TODO.md`, «Следующее»): на
Realme он был хуже из-за JIT; с 0.1.0-dev.5 профиль уже в
APK — первый прогон должен быть близок к прогону после прогрева. Если между установкой и замером телефон
ночь стоял на зарядке, система могла заранее скомпилировать приложение —
отметьте это.

## 5. Termux-target на том же телефоне

Те же шаги для человека — в самом приложении: «Настройки AI» → «Инструкция»
(пока targets нет — и на вкладке «Targets»)
(`SetupGuide` в `ui`; команды с кнопкой «Копировать», агент того же
выпуска — вложение APK, «Сохранить в Загрузки»). Правка шагов здесь —
правка и там.

Claude Code на телефоне работает только в Alpine внутри `proot-distro`
поверх Termux (D-33; `docs/research/CLAUDE_CODE_CLI.md`, §9, §10).
Приложение ходит к `sshd` Termux на `127.0.0.1:8022` по SSH (D-26, D-35)
и вызывает агента `dpai`, а агент запускает `claude` — обёртку
`tools/termux/claude-proot.sh`. На Realme C21Y эта схема проверена
(`docs/TESTING.md`, §8); здесь она повторяется на Redmi.

### 5.1. Termux

1. Ставьте Termux из F-Droid (`https://f-droid.org/packages/com.termux/`)
   или из выпусков GitHub (`https://github.com/termux/termux-app/releases`,
   файл `…arm64-v8a.apk`), не из Google Play. Если стоит Termux из Play —
   сначала удалите его. На Realme проверялся Termux 0.118 из F-Droid.
2. Для Termux — те же настройки, что в §2.2: «Автозапуск», «Нет
   ограничений», закрепить в недавних.
3. Android 12+ убивает лишние дочерние процессы приложений («phantom
   processes»), и Termux теряет `sshd`, JVM агента или proot с сообщением
   `[Process completed (signal 9)]`. На Android 14+ в «Для разработчиков»
   есть переключатель «Отключить ограничения для дочерних процессов»
   (англ. «Disable child process restrictions») — включите. Нет пункта —
   запишите версию Android и следите за этим сообщением в §7–§9.

### 5.2. Пакеты и Alpine

В Termux:

```sh
pkg update -y && pkg upgrade -y
pkg install -y openssh openjdk-21 git unzip proot-distro nodejs
proot-distro install alpine
termux-setup-storage
```

На вопросы `pkg` о файлах настроек отвечайте Enter (оставить как есть);
`termux-setup-storage` спросит доступ к файлам — «Разрешить».

### 5.3. Claude Code в proot

Если раньше ставился `npm i -g @anthropic-ai/claude-code` — уберите его,
иначе `$PREFIX/bin/claude` занят ссылкой npm:

```sh
npm uninstall -g @anthropic-ai/claude-code 2>/dev/null; rm -f $PREFIX/bin/claude
```

Musl-сборка — в `~/.local/share/claude-musl` (так её ищет обёртка):

```sh
mkdir -p ~/.local/share/claude-musl && cd ~/.local/share/claude-musl
npm pack @anthropic-ai/claude-code-linux-arm64-musl
tar xzf anthropic-ai-claude-code-linux-arm64-musl-*.tgz --strip-components=1
rm anthropic-ai-claude-code-linux-arm64-musl-*.tgz
ls -l claude
cd ~
```

Ожидается исполняемый файл `claude` (около 230 МиБ). Обёртка — как
`$PREFIX/bin/claude`:

Файл `claude-proot.sh` — из «Загрузок» (§1.1: `adb push` или браузер):

```sh
cd ~/storage/downloads && sha256sum -c SHA256SUMS --ignore-missing && cd ~
cp ~/storage/downloads/claude-proot.sh $PREFIX/bin/claude
chmod +x $PREFIX/bin/claude
claude --version
```

Ожидается `2.1.… (Claude Code)` — первый запуск proot может занять
несколько секунд. Если вместо версии — ошибка загрузки библиотеки
(`libstdc++`, `libgcc`), доставьте их в Alpine и повторите:

```sh
proot-distro login alpine -- apk add libgcc libstdc++
claude --version
```

Запишите версию Claude Code.

### 5.4. Агент `dpai`

Архив — из «Загрузок» (§1.1):

```sh
cd ~/storage/downloads && sha256sum -c SHA256SUMS --ignore-missing && cd ~
rm -rf ~/dpai && unzip -q ~/storage/downloads/dpai-agent-0.1.0-dev.10.zip -d ~
chmod +x ~/dpai/bin/dpai ~/dpai/claude-proot.sh
ln -sf ~/dpai/bin/dpai $PREFIX/bin/dpai
dpai version
dpai agent doctor
```

Ожидается: `dpai-agent-0.1.0-dev.10.zip: OK`; `dpai 0.1.0-dev.10`; одна
строка JSON, в которой `"ok":true`, `"agentVersion":"0.1.0-dev.10"`,
`"termux":true`, у `claude` — `"found":true` и версия, у `git` —
`"found":true`. Ссылка в `$PREFIX/bin` — чтобы дальше команда
набиралась просто `dpai …` (§7.7, §8). Сохраните строку для отчёта (в
ней нет секретов):

```sh
dpai agent doctor > ~/storage/downloads/doctor-termux.json
```

Полный путь агента для приложения — `/data/data/com.termux/files/home/dpai/bin/dpai`
(проверьте: `echo $HOME/dpai/bin/dpai`).

### 5.5. `sshd`, пользователь и ключ хоста

```sh
mkdir -p ~/.ssh && chmod 700 ~/.ssh
sshd -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no
pgrep sshd
whoami
for k in $PREFIX/etc/ssh/ssh_host_*_key.pub; do ssh-keygen -l -f "$k"; done
```

`sshd` слушает порт 8022, только по ключу — пароли выключены (как в
«Инструкции» приложения). `whoami` печатает имя вида `u0_a123` — это
«Пользователь» для приложения. Последняя команда печатает отпечатки
ключей хоста, по строке на тип: `256 SHA256:… (ECDSA)`, `… (ED25519)`,
`… (RSA)`. Экран с ними держите открытым — он нужен в §5.7.

Чтобы Termux не засыпал при выключенном экране (§9):

```sh
termux-wake-lock
```

В уведомлении Termux появится отметка о wake lock.

Приложение может запускать `sshd` само (D-46): в `~/.termux/termux.properties`
строка `allow-external-apps = true`, на вкладке Targets у локального
target — «Настройки target ▸» → «Разрешить» (запуск команд в среде Termux). Карточка Termux и
служба контроллера появляются только после §5.7, поэтому «Разрешить» и
проверку делайте после него: `pkill sshd` в Termux, через минуту на
карточке «sshd на порту 8022: слушает», в журнале приложения — строка
`[termux] … sshd запущен в Termux`.

Termux из Google Play (`googleplay.*`) разрешения `RUN_COMMAND` не
объявляет — приложение `sshd` не запустит (так и скажет на карточке).
Тогда — автозапуск при загрузке телефона: Termux из Google Play сам
выполняет скрипты `~/.termux/boot/`, например `~/.termux/boot/10-dpai-sshd`
(права `700`) с двумя строками: `termux-wake-lock` и
`pgrep -x sshd >/dev/null || sshd -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no`.

### 5.6. Ключ приложения в `authorized_keys`

1. В приложении: «Настройки AI» → карточка «Ключ приложения» → «Показать
   открытый ключ». Появится строка `ecdsa-sha2-nistp256 AAAA… dpai-android`.
2. Долгое нажатие на строку → выделить всё → «Копировать».
3. В Termux удалите прежние ключи приложения (после переустановки ключ
   новый, §1.2) и добавьте новый — только с самого телефона, как в
   «Инструкции» приложения: наберите `echo 'from="127.0.0.1,::1" `,
   вставьте строку (долгое нажатие → «Paste»), допишите
   `' >> ~/.ssh/authorized_keys`:

```sh
sed -i '/ dpai-android$/d' ~/.ssh/authorized_keys 2>/dev/null
echo 'from="127.0.0.1,::1" ВСТАВЛЕННАЯ_СТРОКА' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
tail -n 1 ~/.ssh/authorized_keys
```

Ожидается: последняя строка начинается с
`from="127.0.0.1,::1" ecdsa-sha2-nistp256 ` и кончается ` dpai-android`.

Удобнее набирать команды Termux с ПК (необязательно). Свой ключ ПК для
этого:

```sh
ssh-keygen -t ed25519 -N "" -f ~/.ssh/dpai_redmi
cp ~/.ssh/dpai_redmi.pub ~/dpai-device-check/ && cd ~/dpai-device-check
adb push dpai_redmi.pub /sdcard/Download/dpai_redmi.pub
```

В Termux:

```sh
cat ~/storage/downloads/dpai_redmi.pub >> ~/.ssh/authorized_keys
```

С ПК (вместо `u0_a123` — вывод `whoami`):

```sh
adb forward tcp:8022 tcp:8022
ssh -i ~/.ssh/dpai_redmi -p 8022 u0_a123@127.0.0.1
```

### 6.4. Свой терминал (D-71)

Терминал приложения входит на target тем же ключом и с тем же
подтверждённым ключом хоста, что контроллер; экран и история — только в
памяти приложения.

1. «Targets» → у «Termux» — «Терминал ▾» → «Оболочка». Ожидается: открывается чёрный
   экран с приглашением оболочки Termux, внизу ряд из девяти клавиш —
   ESC, CTRL, ALT, TAB, стрелки, «⋯» — весь на экране, без прокрутки;
   экранная клавиатура появляется по касанию экрана. В шторке —
   уведомление «Терминал: 1 вкладка».
2. Наберите `ls -la --color=always ~ && echo $TERM && stty size` и Enter.
   Ожидается: цветной список, `xterm-256color`, два числа (строки и
   столбцы) — столько, сколько помещается на экране.
3. Поверните телефон и снова `stty size`: числа поменялись; текст выше
   перенёсся по новой ширине, а не обрезан.
4. `top` (или `htop`, если стоит): экран обновляется, `q` выходит, после
   выхода прежний текст оболочки на месте. `vi ~/term-test.txt`: `i`,
   несколько слов, ESC (кнопка ряда), `:wq` — файл сохранён (`cat`
   его показывает); затем `rm ~/term-test.txt`.
5. CTRL (кнопка ряда), затем `c` на клавиатуре во время `sleep 100` —
   команда прерывается (`^C`). Стрелка ↑ — предыдущая команда.
6. Выделение: долгое нажатие на слове — слово выделено, у него ручки и
   панель «Копировать · Вставить · Выделить всё · Поделиться»; ручками
   выделение правится, у верхнего или нижнего края экрана история
   листается под пальцем; «Копировать» — текст в буфере. «⋯» → «Вставить»
   вставляет текст в строку оболочки (без выполнения). `seq 1 2000`,
   затем смахнуть вниз — история листается с инерцией; удержание ↑ в ряду
   — повтор, как на клавиатуре; смахивание вверх по ← — HOME, по TAB — `|`.
   `echo https://example.org`: касание адреса — «Скопировано: …»,
   второе касание — открывается браузер; выделенный адрес — в панели
   «Открыть ссылку» и «Копировать ссылку».
7. Щипок двумя пальцами меняет размер шрифта; `stty size` — новые числа.
8. Выход назад и снова «Targets» → «Терминалы (1)» (или касание
   уведомления «Терминал: 1 вкладка»): вкладка та же, история на месте.
   «Закрыть все» в уведомлении — сначала вопрос, после «Закрыть все» —
   вкладок нет, уведомление ушло. `exit` — строка «[соединение закрыто, код 0]» и
   кнопка «↻ Переподключить»; она открывает новую оболочку.
9. У «Termux» — «Claude в терминале». Ожидается: интерактивный Claude
   Code в каталоге слота: `/status` показывает вход (каталог — слота),
   рамки и цвета интерфейса рисуются ровно; `/exit` закрывает вкладку
   строкой «[соединение закрыто, код 0]».

10. Сессия в tmux (D-111). В Termux — `pkg install tmux`. У «Termux» —
    «Настройки target ▸»: «Держать сессию в tmux» включено. «Терминал ▾»
    → «Оболочка»: внизу зелёная строка tmux. `sleep 1000; echo готово`,
    затем режим полёта на минуту: строка «связь потеряна — вернусь, когда
    появится сеть»; сеть вернулась — «переподключаюсь…», и та же сессия
    (`sleep` идёт, история на месте). Закрыть приложение смахиванием из
    недавних и открыть терминал снова той же вкладкой: та же сессия.
    «Закрыть…» вкладки — вопрос «Сессия tmux на target завершится»;
    после — `tmux ls` в новой вкладке её не показывает. Без tmux на target
    (выключить настройку или удалить пакет) — вкладка как прежде, без
    tmux — строка «Нет tmux — …» с командами установки. Внутри tmux
    `echo привет` — кириллица, а не `____`. «Claude в терминале» при
    включённой настройке и без tmux на target: режим полёта и обратно —
    claude сам не запускается заново, строка «сессии tmux нет —
    «Переподключить» запустит программу заново». «Linux в приложении» →
    «Поставить tmux», затем две вкладки слота «в приложении» (оболочка и
    claude): закрытие одной не трогает другую; не запустился tmux под
    proot — строка «tmux не запустился — вкладка без него», вкладка
    работает. 24-битный цвет внутри tmux — по настройке tmux на target
    (tmux 3.2+: `set -as terminal-features ',xterm-256color:RGB'` в
    `~/.tmux.conf`), иначе 256 цветов.

PASS — 1–10 как описано. Что выглядит иначе (сдвинутые рамки, лишние
символы, не та клавиша) — в заметки отчёта, с тем, что было на экране.

`docs/research/SSH_ON_ANDROID.md`).

PASS — поток был и кончился с ходом, ход завершился один раз. Условно —
потока не было (строк `agent follow` нет), а ход завершился опросом:
запишите `dpai version` в Termux — агент прежней версии работает опросом,
так задумано. FAIL — ход не завершился или после него в Termux живёт
`agent follow` дольше минуты.

## 8. Уведомления (этап 12, D-36)

### 8.1. Каналы

«О приложении» → «Уведомления». Ожидаются категории: «Запросы: нужен
ответ», «Контроллер работает», «Сведения», «Ход работы», «Готово»,
«Система и сводки», «Предупреждения», «Нужно вмешательство», «Сбои»,
«Одобрения», «Безопасность»; после §16 — ещё «Диск приложения». По коду
важность: высокая — «Запросы: нужен ответ», «Нужно вмешательство»,
«Сбои», «Одобрения», «Безопасность»; средняя (звук) — «Предупреждения»;
низкая (без звука) — остальные; «Контроллер работает» — минимальная.
Запросы с кнопками ответа (одобрение слияния, «Задача без проверки»…)
приходят в «Запросы: нужен ответ».
Запишите, все ли категории видны и что HyperOS включил по умолчанию
(звук, всплывающие, экран блокировки).

### 8.2. Уведомление службы

В шторке — «DP AI: контроллер работает», «опрос targets и задач», кнопка
«Остановить». Нажатие на уведомление открывает то же окно приложения
(не второе). Нажмите «Остановить»: открывается приложение с вопросом
«Остановить контроллер?» — «Остановить». Уведомление службы пропадает и
не возвращается, а над сводкой — строка «Контроллер остановлен: такты не
идут, уведомлений нет.» с кнопкой «Запустить» (D-39). Нажмите
«Запустить»: уведомление службы вернулось. PASS — остановка держится,
пока не нажата «Запустить», и после неё служба снова работает.

### 8.3. При выключенном экране

Поставьте три задачи подряд: «Что сделать» — `Ответь одним словом: да`,
названия `Экран 1`, `Экран 2`, `Экран 3`. Сразу выключите экран кнопкой
питания. Задачи идут по одной (на target — одна сессия за раз).
Ожидается в течение 2–3 минут: три уведомления со звуком. На экране
блокировки текст скрыт — там «Запрос контура: нужен ответ» (A-12);
после разблокировки в шторке — «Задача без проверки: Экран 1»… Запишите,
сколько пришло и загорался ли экран. HyperOS может не показывать
уведомления DP AI на экране блокировки вовсе (§8.8) — тогда считайте их
в шторке после разблокировки и запишите это.

### 8.4. Проект с Git и кнопки одобрения

Кнопки одобрения появляются только у задачи проекта: после проверки и
коммита оркестратор просит одобрить слияние (D-10). В Termux:

```sh
mkdir -p ~/dpai-proj ~/dpai-trees && cd ~/dpai-proj
git init -q -b main
git config user.name "dpai device check"
git config user.email "dpai-check@example.org"
echo "проверка" > README.md
git add README.md && git commit -q -m "начало"
cd ~
```

«Targets» → у «Termux» — ⋮ → «Проект…»:

| Поле | Значение |
|---|---|
| «Каталог репозитория» | `/data/data/com.termux/files/home/dpai-proj` |
| «Каталог деревьев задач» | `/data/data/com.termux/files/home/dpai-trees` |
| «Ветка интеграции» | `main` |
| «Команда проверки (необязательно)» | `git status` |

«Сохранить». Новая задача: `Проект 1`, `Ответь одним словом: готово`.
Ожидается: ход в рабочем дереве, проверка `git status` проходит,
задача — «выполнена» в колонке «Готово»; запрос (D-49) «Слить в main:
Проект 1» с вариантами «Слить» и «Не сливать» — уведомлением, на вкладке
? «Запросы» и в `dpai requests`; счётчик «Запросы ждут ответа» — 1.

1. Нажмите «Слить» в уведомлении, не открывая приложение. Ожидается:
   запрос закрыт, «Запросы ждут ответа» — 0, в `main` — коммит задачи.
2. Задача `Проект 2`, то же; ответьте из Termux. `dpai` сопрягается с
   приложением один раз: «Настройки AI» → «Командная строка dpai» → «Показать
   код», в Termux `dpai control pair <код>` (§8.9 п. 8). Затем
   `dpai requests` и `dpai answer <запрос> decline`. Ожидается: «Запросы ждут ответа» — 0,
   `main` не изменился.
3. Задача `Проект 3`; до ответа удалите её ветку
   (`git -C ~/dpai-proj worktree remove --force <дерево>` и
   `git -C ~/dpai-proj branch -D task/<id>`), затем «Слить». Ожидается:
   новый запрос «Слить в main: Проект 3», в его тексте — «Слияние не
   удалось: …», кнопка «Повторить слияние» (A-30).
4. В Termux:

```sh
git -C ~/dpai-proj branch -a
git -C ~/dpai-proj log --oneline -5 main
git -C ~/dpai-proj worktree list
```

Пришлите вывод: в нём ветки задач и состояние `main`. Если Claude не
менял файлов, коммитов задачи нет и слияние ничего не меняет — это не
ошибка; проверяется путь кнопки.

5. Изменения задачи (D-42, п. 3): задача `Проект 4`, `Допиши в README.md
   строку «изменение»`. Во время хода — «Задачи» → карточка (откроется
   чат) → «⚙» → в листе задачи «Изменения» → «Показать». Ожидается: «Файлы (от main, …)» с
   `README.md` и в «Изменения» строка `+изменение` (зелёная). После
   проверки и коммита — «Обновить»: то же — до ветки задачи; в Termux
   `dpai task <id> diff` — то же текстом. После «Слить» — по-прежнему
   изменения задачи: база — до её слияния (D-72).

В конце пункта — «Targets» → «Убрать проект…» и в окне «Убрать»: дальше (§8.5–§9)
задачи снова идут без Git, и их итог — запрос «Задача без проверки».

### 8.5. Разрешение отозвано и возвращено (ТЗ, §96)

«О приложении» → «Уведомления» — выключить. Система может при этом
завершить процесс приложения — откройте его снова; если оно снова
спросит разрешение, ответьте «Не разрешать». Поставьте задачу

уведомлений нет, падения нет. Включите уведомления обратно, поставьте
`С уведомлениями` — уведомление пришло.

### 8.6. Cooldown Android 15

Только если `adb shell getprop ro.build.version.release` — 15 или выше;
на 13–14 пункт «не применимо». В Android 15+ система может приглушать
звук частых уведомлений одного приложения; оркестратор это не обходит:
частоту и так ограничивает ядро — не больше 6 показов в минуту, лишнее
уходит в сводку «Сводка: придержано уведомлений — N» (D-36; ТЗ, §36).

1. Найдите в «Настройках» (поиск «cooldown», «уведомлен») переключатель
   приглушения частых уведомлений; запишите, есть ли он и включён ли.
2. Поставьте четыре задачи `Ответь одним словом: да` подряд, сверните
   приложение и слушайте.

Ожидается: все четыре уведомления «Задача без проверки» в шторке, ни
одно не потеряно; при включённом cooldown второе и следующие тише
первого. Запишите, что слышали. Настройки нет в HyperOS — «не
применимо: нет настройки», с версией Android.

### 8.7. Doze принудительно (необязательно)

Поставьте две задачи `Ответь одним словом: да`, выключите экран и
переведите телефон в Doze:

```sh
adb shell dumpsys battery unplug
adb shell dumpsys deviceidle force-idle
```

Через 5 минут проверьте экран блокировки: пришли ли уведомления о
задачах. Затем верните:

```sh
adb shell dumpsys deviceidle unforce
adb shell dumpsys battery reset
```

Команды отклонены — «не проверено: adb закрыт», естественный Doze
проверяется в §9.

### 8.8. Запросы человеку: уведомление и окно поверх приложений (D-44)

Без target, в демо-режиме: «Настройки AI» → «Журнал» → «Отладка» → «Проверка
запросов» (с контроллером — там же).
Проверочный запрос ничего не меняет, ответ только записывается в
журнал. В демо запросы живут до перезапуска приложения, поэтому пункт 6
проверяется с контроллером (§5–§7, запрос «Задача без проверки»).

1. «подтверждение» → в шторке уведомление «Проверка запросов №N:
   подтверждение» с кнопками «Подтвердить» и «Отклонить»; на вкладке ?
   «Запросы» — та же карточка.
2. «Подтвердить» на заблокированном экране → телефон просит
   разблокировку; после неё — «Ответ «Подтвердить» отправлен», затем
   «Принято: Подтвердить — записано». Карточка исчезла с вкладки.
3. «вопрос» → три кнопки A, B, C; нажмите B → «Принято: Вариант B».
4. «нужен текст» → «Ответить» открывает поле ввода в шторке; пустой
   ответ не отправляется, текст — «Принято».
5. «опасное действие» → «Удалить» открывает приложение с диалогом
   «Подтвердить: Удалить?»; «Отмена» — запрос ждёт; «Удалить» — принято.
6. Повторное нажатие: после «Принято» кнопок в уведомлении нет. С
   контроллером: закройте приложение (смахнуть из недавних), откройте
   снова — ждущий запрос снова в шторке и на вкладке, срок прежний.
7. Нажатие на тело уведомления о задаче открывает её чат (или доску
   задач, если сессий ещё не было); проверочный — вкладку ? «Запросы».
8. «Окно поверх приложений» выключено → запросы только уведомлением.
   Включите выключатель без разрешения: подпись «Нет разрешения
   системы…», запросы — уведомлением, приложение не падает.
9. «Открыть настройку разрешения» → разрешите «Поверх других
   приложений», вернитесь, откройте любое другое приложение и создайте
   запрос: сверху появляется окно с текстом, задачей и вариантами;
   касания вне окна работают. «Удалить» в окне — сначала «Точно:
   Удалить?», вторым нажатием не раньше чем через полсекунды — принято, окно
   закрылось; два быстрых касания подряд ничего не делают, а через 5 с без
   второго нажатия кнопка снова «Удалить». «×» в строке-ручке («Скрыть окно») убирает
   окно, уведомление остаётся. В приложении DPmetaApp с истёкшим входом
   (`DPmetaApp:D-61`) второе нажатие опасного варианта не отвечает, а
   открывает вход по PIN и подтверждение на экране «AI» (D-104); не
   открылось (MIUI не пустила запуск из фона) — окно остаётся с подсказкой
   открыть приложение: проверить разрешение MIUI на всплывающие окна в фоне.
10. «Отклонить» на подтверждении — «Принято: Отклонить».
11. Включите «Короткий срок (1 мин)», создайте подтверждение, подождите
    две минуты: уведомление исчезло само, ответ на старую кнопку (если
    успели раскрыть шторку) — «Не принято: срок запроса истёк».
12. Создайте подряд «вопрос», «выбор» и «подтверждение»: три отдельных
    уведомления, ответ на одно не трогает другие.
13. Принятая команда (D-94), с контроллером: во время «Долгого хода»
    (§7.3) ответьте кнопкой в уведомлении на любой ждущий запрос.
    Ожидается: «Принято: <вариант>» и «применится после текущего шага
    контура — итог придёт уведомлением»; кнопки не возвращаются, итог —
    отдельным уведомлением через несколько секунд.
14. Ответ после убитого процесса: создайте запрос, затем
    `adb shell am kill com.dpsmpx.dpai` (или смахните приложение) и
    нажмите кнопку в уведомлении. Ожидается: ответ принят — запрос пропал
    из шторки и с вкладки ? «Запросы», итог пришёл уведомлением; служба
    «контроллер работает» снова в шторке.

Ожидается: всё так; запишите версию Android и HyperOS, что видели на
экране блокировки и было ли окно поверх полноэкранного приложения.

Redmi Note 13, HyperOS 2.0 (8 октября 2026): уведомления DP AI на
экране блокировки не показываются, хотя глобально и для приложения они
разрешены, — пункт 2 проверяется на разблокированном экране, требование
разблокировки там не видно. HyperOS может убить свёрнутое приложение
через несколько минут: в демо его журнал начинается заново (так
задумано), у контроллера работу держит служба переднего плана.

### 8.9. Действия с задачей (D-42)

С контроллером (§5–§7) и задачей `Ответь одним словом: да`:

1. «Задачи» → нажать карточку: у задачи без сессий — сразу лист с
   состоянием, моделью и бюджетом; у задачи с ходами — чат, лист — «⚙»
   сверху справа.
2. До запуска: «Модель, бюджет, ревью» — класс «простая» (`trivial`),
   модель `haiku`, «Сохранить» → «Принято»; у идущей задачи кнопки нет.
3. Во время хода: «Приостановить» → ход остановлен, на карточке
   «пауза», новых сессий нет; «Продолжить» → ход идёт дальше.
4. «Отменить задачу» → подтверждение → «отменена» (`CANCELLED`), сессия
   завершена.
5. «Повторить» у отменённой → снова в очереди. Область и зависимости
   при создании — п. 11.
6. После хода — в чате задачи (D-62): итог хода целиком (длинный ответ
   не обрезан), текст выделяется; после перезапуска приложения — на
   месте. В листе задачи («⚙» в чате) под причиной — строка «расход: ходов …» (вход,
   выход, кеш, стоимость); та же — в начале ленты чата («Расход: …»), ходы
   и стоимость — в `dpai status`. До первого хода строки нет.
7. «Настройки AI» → «Контур»: предел сессий 1 — вторая задача ждёт первую;
   у target («Настройки target ▸») выключить «Принимает новые задачи» — новая задача не
   начинается, включить — начинается.
8. Командная строка (D-47): «Настройки AI» → «Командная строка dpai» → «Показать
   код»; в Termux `dpai control pair <код>`, затем `dpai status`,
   `dpai task <id> hold`, `dpai task <id> cancel` (без `--yes` — отказ),
   `dpai requests`, `dpai answer <запрос> <вариант>`. Подпись (D-92):
   прежний `dpai` (0.1.0-dev.5) с новым приложением — понятный отказ, а не
   зависание. Это проверяется раньше, сразу после §1.3 и до §5.4 (там
   `dpai` обновляется), если прежний `dpai` был сопряжён: `dpai status`
   в Termux отвечает «токен не подходит: dpai control pair <новый код>»;
   итог запишите сюда, не успели — «не проверено». Расхождение часов — только с ПК: у Termux и
   приложения на одном телефоне часы одни. С ПК (агент из архива, §10):
   `adb forward tcp:47777 tcp:47777`, `dpai control pair <код>`, часы ПК
   сдвинуть на 5 мин — `dpai status` отвечает «отказ: подпись запроса не
   принята — токен отозван, часы расходятся больше чем на 2 мин или на
   порту не DPmetaApp»; без ПК — «не проверено».
   Решающее (D-91): у задачи без проверки `dpai answer <запрос> waive --yes`
   и `dpai task <id> waive --reason «…» --yes` — код выхода 3 и «решающее —
   только на телефоне»; тот же запрос снова в шторке (и окном поверх, если
   включено), «Принять без проверки» — с разблокировкой; задача не тронута,
   пока не нажато на телефоне. `dpai answer <запрос> later` — сразу.
   Экран блокировки: у уведомлений запросов и задач — только «Запрос
   контура: нужен ответ» / название канала, без текста (A-12).
9. С проектом (§10): в окне задачи «Изменения» → «Показать» — файлы с
   числом строк, новые файлы вне индекса, текст diff; после слияния —
   изменения ветки задачи. То же — `dpai task <id> diff` (`--stat` —
   только файлы). Без проекта — причина «у проекта нет репозитория».
10. «Настройки AI» → «Журнал» → «В «Загрузки»» → «сохранено: Загрузки/dpai-logs/…»; файл
    открывается в файловом менеджере, журнал в нём целиком.
11. «Новая задача» → «Дополнительно»: приоритет «высокий», класс «простая»,
    в поле области — файл README.md; в «Зависит от» отметить первую
    задачу → «Поставить». В
    окне новой задачи — «область: README.md» и «зависит от: …»; она не
    начинается, пока первая не «выполнена». До запуска — «Область и
    зависимости»: снять зависимость, «Сохранить» → «Принято», задача
    начинается. То же — `dpai task add «…» «…» --scope README.md
    --depends-on <id>` и `dpai task <id> depends` (без id — снять).
12. Быстрые действия на «Сводке» (ТЗ, §73):
    поставьте две задачи; «Пауза всем (2)» → подтверждение → «Пауза:
    принято 2 из 2», на карточках «пауза»; «Продолжить все (2)» — задачи
    идут дальше; нечего приостановить или продолжить — кнопки нет, «(0)» не
    видно (AI:A-6). «Ждёт вас» на сводке — список задач «заблокирована»,
    «провалена», «без проверки: нужна ручная проверка» и строки
    «Внимание», касание задачи открывает её лист; запросы — значок
    вкладки «Запросы» с числом. Счётчики — только ненулевые, расход —
    под «Расход ▸»; порог подписки — строкой «Порог N %», касание
    раскрывает выбор и передачу задач.
13. Поиск из `dpai` и коммит задачи: в проекте с Git (§8.4) после
    выполненной задачи — `git -C ~/dpai-trees/<дерево задачи> log -1
    --format=%h`; «Найти» в приложении и `dpai search <эти знаки>` находят
    его в «Коммиты» (COMMIT) со ссылкой на задачу. `dpai search
    <часть названия>` — те же виды, что «Найти».
14. «Запустить первой» (D-77): поставьте задач больше, чем мест, и у
    последней в очереди нажмите «Запустить первой» → «Принято»; как только
    место освободится, начинается она, а не та, что стояла раньше. У
    идущей задачи кнопки нет. То же — `dpai task <id> first`.

### 8.10. Действия с сессией (D-42)

Экран сессии — чат задачи (D-59, D-61): все сессии задачи в одной
ленте, ввод внизу, кнопки хода — рядом с полем ввода.

1. Во время хода откройте чат задачи: внизу ленты — кружок «работает …»
   (инструменты и команды хода на экран не выводятся, D-59); подробности
   хода — «События» сверху справа, лента обновляется.
2. «■» рядом с полем ввода → «Остановить ход?» → «Остановить» → задача
   на паузе, сессия завершена handoff.
3. Сообщение в сессию: текст в поле ввода, «Модель и усилие» → `haiku`,
   «Отправить» → новый ход той же сессии Claude (в «Событиях» — модель
   `haiku`).
4. «Свежая» (или «↻») → новый ход с handoff, без `--resume`.
5. После хода: в начале ленты чата — «Расход: ходов 1 · вход … · выход
   …», в листе задачи («⚙») — «расход:» по всем её сессиям; `dpai status`
   — то же у задачи в квадратных скобках (D-42, п. 4).
6. Быстрые действия (ТЗ, §74): «⚙» — лист задачи; «Контекст» в начале
   ленты — цель, следующее действие и источники последнего хода, касание
   источника показывает его текст; у задачи без хода — «контекст не
   собирался». На окне от 840 dp (планшет, альбомная ориентация; AI:A-24)
   лист задачи — панелью справа от чата, без окна поверх: «⚙» прячет и
   показывает её, «×» панели — прячет; «Открыть чат» в ней — только к
   другой сессии задачи.
7. «Прервать и перенести» в начале ленты (D-77; нужны два слота — на
   разных targets или на одном): во время хода нажмите → «Прервать ход и
   перенести?» → «Прервать и перенести» → «Принято»; ход остановлен,
   задача снова в очереди и начинается на другом слоте с handoff прежней
   сессии: в `dpai status --json` у новой сессии другой `slot`. Если
   другого слота нет — задача ждёт, в листе задачи «Ждёт: задача
   перенесена со слота …». То же — `dpai session <id> reassign`.

### 8.11. Ревью задачи (D-73)

Ревью идёт после проверки и коммита — нужен проект с Git (§8.4).

1. «Новая задача» → «Дополнительно» → «ревью кода» и «ревью
   безопасности» → «Поставить», цель — «добавь в README.md раздел
   «Проверка»». После хода и проверки идут сессии ревью, по одной: в
   начале ленты чата задачи — «ревью кода · …», затем «ревью
   безопасности · …» (все сессии задачи — в одной ленте, D-59); у задачи
   — «ревью». В листе задачи — «ревью кода: пройдено» (или
   «нужно исправить») с находками; после обеих ролей — запрос «Слить».
2. Сессия ревью только читает: пока она последняя, поле ввода чата
   выключено, в нём подсказка, почему сюда не пишут; у рабочей сессии
   поле и «Отправить» есть.
3. `dpai status` — у задачи «ревью CODE PASSED, SECURITY PASSED», у
   сессии ревью — «ревью CODE»; `dpai task <id> reviews` — итоги с
   находками.
4. Повтор по ревью (необязательно): задача «добавь функцию среднего
   значения списка без проверки пустого списка» с «ревью кода». Если
   ревьюер нашёл блокирующее — задача снова идёт той же сессией Claude,
   в её prompt — «Ревью нашло, что исправить»; в листе — «повторов: 1».
5. «Модель, бюджет, ревью» у задачи до запуска: класс `trivial` с
   ревью → «Сохранить» → отказ «у класса TRIVIAL ревью нет»; снять
   ревью → принято.

## 12. Прогоны выносливости на ПК (ТЗ, §116)

`EnduranceTest` гоняет контур в реальном времени на синтетических

## 15. Linux в приложении (D-75, шаг 5; D-90)

Alpine под proot в данных приложения — без Termux. Нужен телефон с
arm64 (Redmi Note 13 — да) и интернет для пакетов; около 15 мин.

1. «Targets» (или «Настройки AI») → «Linux в приложении ▸» → «Установить Alpine».
   Ожидается: «Установлено: файлов N, M МБ», затем строка «Установлено:
   alpine-minirootfs-3.24.3». Повторный запуск приложения — строка на
   месте, второй раз не устанавливается.
2. В поле «Пакеты» — `git nodejs npm` → «Поставить». Ожидается
   «Поставить: готово», в выводе — `OK: … MiB in … packages`. Ошибка
   подписи (`UNTRUSTED signature`) — FAIL: пакеты должны проверяться
   ключами Alpine.
3. «Терминал» → вкладка «Linux»:

```sh
cat /etc/alpine-release      # 3.24.x
cat /etc/resolv.conf         # nameserver — DNS сети телефона, не 1.1.1.1 и не 8.8.8.8
git --version && node --version
```

4. Claude Code и вход в каталог слота (D-27, D-29): на экране «Linux в
   приложении» — «Поставить Claude Code» (с 0.4.0-dev.11 DPmetaApp; нужно
   около 1 ГБ свободного места, несколько минут). Ожидается строка
   «Claude Code: 2.1.x (Claude Code)». Затем в терминале:

```sh
CLAUDE_CONFIG_DIR=/root/.claude-slot-1 claude    # внутри — /login, вход формой Claude
```

   Ожидается: вход прошёл; `exit` — вкладка пишет «соединение закрыто».
   Ошибка установки — в отчёт строки вывода под кнопкой (особенно про
   `link`, `EACCES`, место на диске).
5. Режим полёта → «Поставить» `htop`: понятная ошибка `apk` в выводе
   карточки, приложение не падает. Сеть обратно — `htop` ставится.
6. «Обновить всё» — «Обновить всё: готово».
7. Гость без `/sys` и с узкими `/dev` (D-93): в терминале `ls /dev` —
   только `null zero full random urandom tty ptmx pts fd stdin stdout
   stderr`, `ls /sys` — пусто или «нет такого каталога»; при этом п. 2–4
   работают (`npm`, `git`, Claude Code). Что-то нужное сломалось — в отчёт
   с текстом ошибки: это новое решение с узлом, названным явно.
8. `ln -sf /etc/hostname /etc/resolv.conf` в терминале, закрыть вкладку,
   открыть снова: `cat /etc/hostname` — прежнее имя, `/etc/resolv.conf` —
   снова файл с `nameserver` (A-3: запись DNS не идёт сквозь ссылку гостя).

9. Target «в приложении» (шаг 5): после п. 4 (Claude Code поставлен) —
   «Добавить слот «в приложении»». На вкладке Targets — «Linux в
   приложении · слот 1», строка «Alpine в данных приложения, без SSH».
   «Проверить» — агент отвечает; «Claude в терминале» → `/login` → вход;
   «Проверить вход» — слот доступен. Новая задача без проекта — ход идёт на
   этом слоте (сессия в чате, ответ Claude), а Termux и ПК не нужны.
10. Проект «в приложении»: в терминале Linux `apk`-командой карточки
   поставить `git`, затем `git clone <репозиторий> /root/repo`; у слота —
   «Проект»: репозиторий `/root/repo`, деревья `/root/trees`, проверка
   по желанию. Новая задача — дерево создаётся в `/root/trees`, ход идёт в
   нём, «Изменения» показывают diff, «Слить» сливает ветку задачи.
11. Linux не установлен, а слот «в приложении» в настройках есть
   (приложение переустановлено, настройки — из копии): на сводке заметка
   «Linux в приложении не установлен — ходов нет», остальные targets
   работают.

В отчёт: пункты 1–11 «да/нет», версию Alpine, строку `nameserver` (адрес
сети, а не публичный) и код выхода `apk` при ошибке.

## 19. Файлы пользователя (D-99, часть 3)

Папки, выбранные системным окном, — копией в Linux с синхронизацией;

7. «Копия» и «Папка» у карточки — списки файлов; текст открывается,

   файл виден в «Загрузках».
9. Выключить переключатель → новая вкладка терминала: `ls
   ~/storage/shared` — пусто или «нет такого каталога».
10. «Linux» → «Домашняя папка»: каталогов слотов `.claude-slot-*` и
    `.ssh` нет (D-96).
11. ✦ «Модели» → чат → 📎 → текстовый файл → вопрос «что в файле?» →
    ответ по содержимому; картинка или двоичный файл — отказ с причиной.
12. «Отвязать» у папки → карточка исчезла, копия в `~/files/` осталась.

В отчёт: пункты 1–12 «да/нет»; какой менеджер файлов и какая папка.

   хода — смахнуть приложение из недавних и открыть снова. Ожидается: ход
   досчитан или задача с понятной причиной и «Повторить», без зависшей
   сессии.
8. **GitHub.** В поле «Пакеты» — `github-cli` → «Поставить»; в терминале —

В отчёт: пункты 1–8 «да/нет»; версию Claude Code; время установки (п. 1)

## 25. PR на GitHub из «AI» (D-108, `DPmetaApp:D-80`; с 0.4.0-dev.12 DPmetaApp, комментарий и слияние — с 0.4.0-dev.13)

Нужно: проект «в приложении» или на другом target (§24, п. 5) с
удалённым `origin` на GitHub — тестовый репозиторий, — `gh` на этом
target и вход в нём (§24, п. 8). Около 15 мин.

   строка «на target нет gh — поставьте пакет github-cli…», приложение не
   падает.
2. **Без входа.** `github-cli` поставлен, `gh auth login` не сделан — «gh на
   target не вошёл в GitHub — в терминале target: gh auth login».
3. **Список.** После входа — открытые PR тестового репозитория: номер,
   заголовок, ветки, автор, проверки (✓ ✗ …), решение отзывов. «Обновить»
   — заново.
4. **Карточка.** Касание PR — описание, проверки по именам, отзывы и
   комментарии по времени; ссылка: первое касание копирует, второе

5. **Отправка задачи.** Задача проекта с изменениями (§24, п. 6) → в листе
   задачи «GitHub» → «Отправить ветку и открыть PR…». В окне — ветка
   `task/…`, `origin`, база, заголовок; «Отправить» — строка «PR: https://…»;
   на GitHub — ветка и PR. Повтор той же кнопки — тот же адрес, второго PR
   нет. Запись — в журнал действий приложения (`files/actions/github.jsonl`:
   строки `branch.push` и `pr.create` уровня 1).
6. **Комментарий (уровень 2).** В карточке PR — текст → «Отправить
   комментарий…»: окно показывает PR и текст, «Дальше — PIN» — системное
   окно PIN или отпечатка; после — «Комментарий: готово», комментарий в
   ленте карточки и на GitHub. Отмена PIN — «не подтверждено…», на GitHub
   ничего нет.
7. **Слить (уровень 3).** Красная «Слить…» → красное окно: ветки, коммит

   между показом и нажатием в ветку PR пришёл новый коммит — отказ GitHub
   (слияние только показанного коммита), строкой под кнопкой.

В отчёт: пункты 1–7 «да/нет», текст отказов, время списка и отправки.
Токены, вход и почта — не присылать (§0.5).

## 27. Служба агента на ПК (D-109, D-120; с 0.4.0-dev.21 DPmetaApp)

Нужно: ПК-target с агентом из архива этой сборки (§10 Linux или §11
Windows), Claude на ПК или в приложении. Около 20 мин.

1. **Linux: установка.** `~/dpai-agent agent service install` — строки
   «✓ записан …/dpai-agent.service», «✓ служба включена и запущена», в
   конце «служба: running, процесс N». «linger не включён» — выполнить
   `sudo loginctl enable-linger $USER` и повторить установку.
   `systemctl --user status dpai-agent` — `active (running)`.
2. **Ход через службу.** Задача на этот target с текстом по-русски → ход
   идёт, Claude отвечает (кириллица дошла, `claude` найден). На ПК:
   `systemctl --user status dpai-agent` — в дереве службы видны
   `dpai agent supervise` и `claude`; `systemctl --user show dpai-agent -p
   Environment` — ваш `PATH` и локаль UTF-8.
3. **Обрыв.** Во время хода выключить Wi-Fi телефона на 2 мин и включить —
   ход дошёл, события без пропусков. Выйти из всех сеансов на ПК (`exit`
   во всех SSH и локальных) — ход идёт (`systemctl --user status`).
4. **Перезапуск службы во время хода.** `systemctl --user restart
   dpai-agent` — ход не прервался; `agent service status` — `running`,
   новый процесс.
5. **Без службы.** `agent service remove` — «служба остановлена и снята»;
   новая задача — ход идёт, как раньше (запасной путь).
6. **Windows.** `agent service install` — «задача «dpai-agent» … запущена»,
   «служба: running»; Планировщик заданий — задача `dpai-agent`, «При входе
   в систему», «Выполняется»; окна консоли нет. Повторить п. 2–3 (вместо
   systemctl — Диспетчер задач: `javaw.exe`). Выйти из Windows и войти —
   задача снова «Выполняется». `agent service remove` — задачи нет.

В отчёт: пункты 1–6 «да/нет», текст отказов; ОС и версия systemd
(`systemctl --version | head -1`), значение `KillUserProcesses`.
