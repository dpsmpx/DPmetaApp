# Адаптивное подключение DPpass 0.5.0

Срез: 5 октября 2026.

## Цель

0.5.0 оптимизирует не пиковую скорость, а сохранность рабочего канала:
1. вероятность успешно передать данные;
2. стабильность RTT и jitter;
3. отсутствие длительных stall;
4. RTT;
5. скорость как вторичный параметр.

Изменение профиля не должно происходить из-за одного случайного неуспеха.

## Что взято из исследования Zapret2

Zapret2 использует автообучаемый hostlist: повторный сбой фиксируется для конкретного hostname, существует порог числа сбоев и временное окно; отдельно отслеживаются retransmission-события. После достижения порога хост попадает в auto-hostlist, а при нормальной работе счётчик сбрасывается. Точные значения upstream по умолчанию включают 3 сбоя в течение 60 секунд и 3 retransmission как одно failure event. Источник: github.com/bol-van/zapret2/config.default и github.com/bol-van/zapret2/nfq2/desync.c.

DPpass не переносит Linux NFQUEUE/raw-packet/desync механику. Его сетевой контракт — Android VpnService + TUN + процессное Xray-ядро; у него нет безопасного аналога interception raw packets из Zapret2. Вместо этого перенесён сам принцип адаптации: измерять результат, отделять устойчивый сбой от одиночной ошибки, запоминать контекст и автоматически менять стратегию.

## Модель

StabilitySample:
- success/failure health-check;
- время полезной probe;
- stall-флаг;
- время наблюдения.

StabilityStats:
- количество попыток и успехов;
- Bayesian-smoothed success rate;
- EWMA RTT;
- EWMA jitter как абсолютная разница соседних измерений;
- EWMA stall rate;
- bad streak;
- последнее наблюдение.

Итоговый stabilityScore:
- reliability: 58%;
- jitter: 22%;
- RTT: 15%;
- stall: 5%.

Это намеренно не throughput-first модель.

## Адаптивная петля

После первичного подключения Android-сервис каждые 15 секунд выполняет health probe через уже поднятый путь. Результат попадает в StabilityBook. Каждые четыре наблюдения состояние записывается в зашифрованное хранилище.

Recovery происходит только при наличии подтверждённой деградации:
- стандартный порог: минимум два плохих наблюдения и низкий score;
- тяжёлый случай: один плохой streak допускается только при очень низком score;
- старый session/TUN атомарно перестают считаться активными;
- ядро останавливается;
- строится новый план кандидатов;
- следующий профиль выбирается уже с учётом накопленного score.

Один неудачный probe не вызывает автоматическую смену профиля.

## Контекстное обучение

Состояние разделяется по грубому контексту:
- Wi-Fi;
- mobile;
- ethernet;
- unknown.

Если NetworkAssessment доступен, дополнительно используются его классы ограничений. Контекст не содержит hostname, IP, URL, payload, SSID, BSSID или идентификатор устройства.

При отсутствии точного контекста для профиля используется его последнее известное наблюдение как fallback. Это предотвращает холодный старт после смены сети, но не переносит приватные данные между контекстами.

## Автоматический domestic split

В формат конфигурации v2 добавлен routing.automatic_domestic = true.

После пользовательских правил DPpass автоматически проверяет:
- geosite:ru для доменного имени;
- geoip:ru для IP назначения.

Совпавшее назначение получает DIRECT.

Порядок принципиален: явное правило пользователя всегда имеет приоритет. Поэтому пользователь может принудительно отправить конкретный .ru ресурс в PROXY или BLOCK.

Таким образом пользователь больше не обязан вручную перечислять российские приложения. Перенос приложения на VpnService остаётся отдельным механизмом для явной per-app политики.

В Xray эти две проверки компилируются в отдельные routing rules, потому что несколько одновременно заданных условий одного Xray rule должны выполниться одновременно.

## Защита обучаемого состояния

StabilityBook записывает только агрегаты в ключ adaptive/stability. Android передаёт в DPpassCore не обычный FileBlobStore, а EncryptingBlobStore с AES-256-GCM и ключом из Android Keystore.

Дополнительные ограничения:
- максимум 128 контекстных записей;
- bounded counters;
- нет внешней телеметрии;
- нет сетевой синхронизации модели;
- нет удалённых управляющих директив;
- модель не меняет явные пользовательские правила.

## Почему не нейросеть

В 0.5.0 маленькая нейросеть не даёт доказуемого преимущества:
- выборка на одном устройстве мала;
- признаки сильно коррелированы;
- модель должна принимать решение в течение секунд;
- ошибочный inference может ухудшить стабильность;
- объяснимость и детерминизм важнее нескольких процентов потенциальной оптимизации.

Bayesian prior + EWMA + hysteresis создают полноценный online-learning контур с существенно меньшим риском и стоимостью.

Нейросетевой или bandit-слой имеет смысл после появления реальных обезличенных локальных измерений этапа 3 и контролируемого offline-тестового корпуса.

## Границы

0.5.0 не обещает:
- скрытие самого факта использования Android VPN от приложений;
- невозможность увидеть VPN transport через Android API;
- невозможность определить VPN по адресу выхода или сетевым fingerprint'ам;
- обход любого белого списка;
- идеальный RTT/jitter во всех сетях.

Эти свойства зависят от Android, сети, удалённого сервера и протокола.
