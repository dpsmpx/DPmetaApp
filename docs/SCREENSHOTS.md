# Снимки экранов на JVM

Настоящие экраны приложения `:shell` — пульт и окно «AI» — рисует
Robolectric с нативной графикой на синтетической экосистеме корпуса
(`tests/corpus/ecosystem`) и демо-системе подсистемы «AI». Телефон не нужен,
данных автора в снимках нет.

## Как снять

```sh
tools/screenshots.sh            # PNG — в docs/screenshots/
tools/screenshots.sh <каталог>  # PNG — в другой каталог (сверить, не трогая docs/)
```

Нужны JDK 21 и Android SDK — как для сборки APK. Robolectric и образ
«Android целиком» (213 МБ) Gradle берёт только по свойству
`dpmeta.screenshots`, со сверкой сумм в `gradle/verification-metadata.xml`;
в APK и в обычную сборку и проверки они не попадают. Происхождение —
`docs/PROVENANCE.md`. Старые PNG сценарий удаляет: снимок, которого тест
больше не делает, не остаётся молча.

## Что снимается

| Файл | Экран |
|---|---|
| `pult-summary.png` | Пульт, «Сводка» |
| `pult-projects.png` | Пульт, «Проекты» |
| `settings.png` | Документ настроек |
| `help.png` | Справка |
| `ai-summary.png` | Окно «AI», «Сводка» (демо) |
| `ai-tasks.png` | Окно «AI», «Задачи» (демо) |
| `workspace-simple.png` | Рабочий проект, простой вид, синтетическое локальное дерево |
| `workspace-full.png` | Тот же проект, полный вид |

Экран 360×800 dp, плотность xhdpi, SDK 36, светлая тема, русский язык.

`AppearanceTest` дополнительно рисует восемь вариантов оформления
(четыре темы × простой/полный вид) с крупным текстом и плотным режимом,
проверяет совпадение цветов пульта, IDE и нативной палитры. Отдельно
проверяется сохранение фона, текста и курсора настоящего адаптера Sora
после повторного `applyDefault` (это происходит при attach редактора). Запуск:

```sh
./gradlew :shell:testDebugUnitTest -Pdpmeta.screenshots --tests '*AppearanceTest'
```

В APK workflow обе проверки обязательны, PNG — отдельный артефакт
`DPmetaApp-interface-<коммит>`. Ошибка интерфейса не заменяет и не отменяет
`full --strict`: у каждой проверки свой завершающий guard. Для состояния
проекта используется текущий синтетический `projects.json`, без прежнего
формата реестра ролей.

## Как устроен тест

`shell/src/screenshots/kotlin/…/ScreenshotsTest.kt` — один тест: все
экраны снимаются по очереди в одном окне, каждый — своя композиция
(`key`). В песочнице Robolectric диспетчер Compose запоминает
Choreographer первого теста, и в следующих тестах эффекты (переход пульта,
вкладка «AI», загрузка данных) не идут — отдельные тесты давали один и тот
же снимок. Перед снимком главный цикл прокручивается шагами по 50 мс с
настоящим ожиданием между ними: данные «AI» грузятся в фоновых потоках по
настоящему времени.

## Пока не снимается

- Редактор с открытым файлом и взаимодействие с IME. Цвета его настоящего
  адаптера проверяет AppearanceTest; ввод и восстановление — на телефоне.
- Другие размеры экрана и ориентации. Текущая матрица оформления проверяет
  четыре темы, крупный текст и плотный режим на 360×800 dp.

Тесты виджета на минимальном Android 11 запускаются отдельно:
`./gradlew :shell:testDebugUnitTest -Pdpmeta.screenshots=true -Pdpmeta.test.sdk=30 --tests '*StudioWidgetTest'`.
По умолчанию используется API 36; свойство выбирает один из двух
закреплённых образов со сверкой Gradle, загрузка самим Robolectric запрещена.


## Достоверность кадров

Изменения Snapshot отправляются явно, Choreographer приостановлен и получает
ограниченные шаги времени: индикатор загрузки не зацикливает тест. Перед
сохранением проверяется, что выполнена композиция выбранного экрана; разные
экраны и варианты оформления не могут повторять один PNG. Рабочий проект
использует синтетическое дерево и ту же инициализацию состояния редактора,
которую выполняет MainActivity, без запуска служб и команд.

Два класса выполняются отдельными процессами тестов. В артефакте обязательны
16 PNG и оба JUnit-отчёта; ошибка любого класса или недостающий кадр не дают
успешного интерфейсного результата. Он проверяется отдельно от полного
`full --strict`. Ввод, IME и восстановление открытого редактора — сценарии
физической приёмки, а не доказанные этими снимками свойства.

## Подготовка образа и сетевые отказы

Перед тестами workflow и `tools/screenshots.sh` вызывают
`python3 tools/prepare-screenshots.py`. Задача `:shell:prepareRobolectricImage`
копирует закреплённый образ в каталог `robolectric-image` сборки модуля `shell` после проверки
контрольной суммы Gradle. Тестовая задача зависит от этой подготовки, поэтому
прямой вызов Gradle тоже использует проверенный образ и offline Robolectric.

HTTP 429, 502, 503 и 504 при подготовке допускают всего три попытки с паузами
15 и 30 секунд. Ошибки контрольных сумм, компиляции и прочие отказы не
повторяются. Сами тесты автоматически не повторяются. Логи каждой попытки
сохраняются: локально — `build/reports/robolectric-preparation/`, в workflow —
в артефакте интерфейса. При отказе CI сохраняет отчёты проверок и диагностику
конфигурационного кэша даже после ошибки выгрузки снимков. Условие успеха
остаётся прежним: оба класса тестов и 16 PNG.

Для образов API 30/36 Gradle использует зеркало Maven Central Google;
его exclusive-фильтр охватывает только `org.robolectric:android-all-instrumented`.
Остальные зависимости сохраняют прежние репозитории. Сверка JAR/POM
использует прежние суммы из репозитория проекта, Robolectric остаётся offline.

Workflow восстанавливает только скачанные файлы этого модуля из GitHub
Actions Cache. Ключ включает ОС, каталог версий и реестр сумм; нет
частичного совпадения ключей. Сохранение разрешено только после успешной
проверенной подготовки образа, даже если позднее упал тест интерфейса
или отдельный замер производительности. Результаты проверок, конфигурационный
кэш и признак успешного теста не кешируются. Восстановленный файл снова
проходит обычную проверку Gradle в новом job. Ошибка сервиса кэша видна
в логе и допускает обычную загрузку с зеркала; отказ подготовки образа
или тестов по-прежнему блокирует успешный UI-результат и выпуск.
