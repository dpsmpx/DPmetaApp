# Универсальные инструменты разработки

Этап 2 D-196 / `DP_AI_Orcestrator:D-223`, пакет dev.49. Инструменты
расширяют прежний каталог, не запускают свой shell, worker или модель.
Рабочий проект → «Автоматизации» → «Исследование проекта». Краткий
результат показывается там же; доказательства раскрываются и копируются.
Доступны общий API, подписанный `dpai automation` и шаги сценариев.
Как у прежнего каталога, это основное дерево выбранного рабочего проекта;
занятое дерево задачи сохраняет доступ только через своего владельца.

## Возможности и доказательства

| Инструмент | Что делает | Что не доказывает |
|---|---|---|
| `development.structure` | Число файлов, языки по расширениям, папки build-файлов, хеш метаданных и пределы обхода | Метаданные — не атомарный снимок содержимого и не компиляторный граф |
| `development.find_files` | Ранжирует пути по словам задачи/имени, до 40 результатов | Текстовое совпадение — не семантическая связь |
| `development.symbol` | Символы документа, определения, ссылки, входящие/исходящие вызовы действующей LSP; `impact` добавляет кандидаты модулей и тестов | Полнота индекса и отсутствие внешних связей не известны |
| `development.impact` | Текущий Git, буквальные Gradle project-ссылки, потенциальные зависимости/циклы, транзитивные кандидаты тестов; точные ревизии доступных профилей проверки | Динамические DSL, комментарии и неявные зависимости требуют компилятора/полного профиля; выбор кандидатов не заменяет обязательные проверки |
| `development.diff` | Реальный diff от точного HEAD, включая staged, до 50 разрешённых путей; новые/конфликтные файлы отдельно | Новые файлы не входят в patch; снимок не атомарен |
| `development.history` | Существующие запуски CHECK/BUILD: id, commit, время, исход, длительность и хеш сохранённого вывода | История не является новым запуском |
| `development.diagnostics` | Нормализует сообщения компилятора/проверки и traceback из истории либо выбранного журнала; группирует по устойчивым отпечаткам, сравнивает запуски и ищет похожую историю | Первый ERROR — кандидат, совпадение шаблона — гипотеза; последующий успешный запуск не доказывает конкретное исправление |
| `development.tests` | Читает JUnit XML: фактические testcases, сбои, пропуски, seed, расхождения счётчиков, изменения результатов относительно базы | Свежесть, одинаковая среда и нестабильность теста автоматически не подтверждаются |
| `development.quality` | Нормализует SARIF 2.1.0 настроенного анализатора: инструмент/версия, правило, важность, место и сообщение | Успешное чтение отчёта не заменяет запуск анализатора |
| `development.measurements` | Точное десятичное сравнение замеров с commit, одинаковыми environment/method/единицами | Причинность и достоверность предоставленной методики не подтверждаются |
| `development.artifact` | Реальные байты, размер, SHA-256 и проверка ожидаемой суммы | Подпись, установка и запуск проверяются прежними инструментами |
| `development.duplicates` | Точные совпадения целых текстовых файлов по SHA-256 | Совпадение не доказывает ненужность компонента или безопасность удаления |

Семантика используется только через LSP/компиляторный backend. Операции
недоступной службы возвращают отказ; regex не подменяет её ответ. Файл
должен быть открыт, сохранён и иметь переданный SHA-256; текст службы
сверяется до и после запроса, файл перечитывается после него. Черновик
не перезаписывается. Иерархия вызовов требует `callHierarchyProvider`;
запрос ограничен четырьмя подготовленными вариантами и пятью запросами
по пять секунд. Для SSH используется настроенный профиль анализатора;
встроенная LSP редактора относится к Linux приложения.

## Запуск и анализ — разные операции

CHECK/BUILD, FAST/NORMAL/FULL, проверки тулчейна и зависимости уже
подключены к каталогу. Сохранённые профили приоритетнее готовых.
В профиле CHECK можно подключить зрелые unit/integration/e2e/smoke,
property/fuzz/совместимость, анализаторы безопасности, секретов, лицензий,
API и производительности. Параметры/seed — через существующие варианты
профиля; вывод и окончательный код остаются в его истории. Генераторы,
минимизаторы, санитайзеры и профилировщики работают своими командами на
target; инструменты студии не выдают встроенный парсер за их реализацию.
Семантические quick-fix, формат и переименование используют существующий
редактор и защищённый план WorkspaceEdit, копию, diff и проверки версий.

Типичный сценарий: структура → влияние → настроенный быстрый профиль →
диагностика/отчёт; перед контрольной точкой — обязательный полный профиль.
Если он не настроен, каталог прямо сообщает причину. Кандидаты тестов не
дают разрешения пропустить полную проверку. Полноценная общая политика
проверок этапа 6 и стратегия контекста этапа 3 остаются следующими этапами.

SUCCEEDED у инструмента чтения означает, что **анализ выполнен**, а не что
проект собран или тесты прошли. FAILED/SKIPPED в отчёте сохраняются;
чтение не записывает PASSED задачи и не обходит DONE. Сценарий из чтений
может завершить чтения успешно, но не становится приёмкой изменений.

## Форматы и воспроизведение

`run_automation` получает id/revision из свежего описания и параметры-
строки. Например, `development.tests`: `path=app/build/test-results/test/TEST-example.xml`,
`baseline=reports/baseline.xml` при наличии базы. Для диагностики без path
используется история выбранного kind; run/baseline — точные id или
последний/предыдущий. С path читается один явный журнал; run и baseline
в этом режиме не принимаются. Исходные большие журналы не включаются
в контекст: возвращаются хеши, места и ссылки на историю/путь отчёта.

JUnit разбирается SAX с запретом DTD/ENTITY, внешних сущностей и сети,
глубиной до 64 и до 5000 testcases. Одинаковые suite/name не выбираются
молча. Пропуски и flaky-события не превращаются в обычные пройденные
тесты. Отсутствующие/противоречивые счётчики оставляют неполноту явной.
SARIF 2.1.0 — до 50 runs, ограниченный JSON; успешность invocation и
свежесть отчёта различаются. Неизвестная версия — отказ.

Замеры — `dpai.measurements` v1:

```json
{"format":"dpai.measurements","version":1,"commit":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","environment":"host-and-device-id","method":"warm-run-3","metrics":{"buildMillis":{"value":12.1,"unit":"ms"}}}
```

До 40 метрик; наборы и единицы должны совпасть. Точность/масштаб чисел
ограничены, разница вычисляется десятично. Образцы форматов синтетические:
`dpai/ui/src/test/resources/development/`.

## Границы и приёмка

Обзор: 5000 файлов, 1000 каталогов, глубина 24. Секреты и типовые
служебные/генерируемые каталоги (.git, build, .gradle, node_modules,
venv и другие из ApiProjectFiles.hidden) скрыты. Граф: до 200 build-файлов, 256 КиБ на файл,
2 МиБ суммарно и 1000 буквальных связей. Повторы: текстовые файлы
32 байта–128 КиБ, 4 МиБ чтения. Отчёт XML/JSON/журнал — до 2 МиБ,
артефакт — до 64 МиБ; FileTree/SSH может иметь меньший собственный предел.
Чтение отчёта разрешает build-вывод, но не секреты и прочие закрытые
каталоги. Символические ссылки и выход за дерево запрещает прежний FileTree.

Обработка проверяет отмену и монотонный бюджет 60 секунд. Уже начатое
блокирующее чтение завершается по прежнему таймауту транспорта; отмена
проверяется после него. Git для этих чтений ограничен 20 секундами на
команду. Показаны фазы чтения/анализа и число просмотренных файлов;
выдуманных процентов нет. Результат — валидный JSON до 24 тысяч знаков,
с явным усечением и неизвестной полнотой. Хеш метаданных не называется
хешем прочитанного содержимого. Разбор не создаёт второй кэш зависимостей.

Автоматические регрессии: DevelopmentToolsTest, DevelopmentReportsTest,
CallHierarchyTest, GitLogicTest, DevelopmentFlowTest. На телефоне/ПК
проверяются настоящие службы, отчёты реальных проектов, отмена SSH,
русский/английский интерфейс и работа внутри установленного APK.
