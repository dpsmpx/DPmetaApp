# Модель аккаунтов

Слоты аккаунтов AI-провайдера, их учётные данные, возможности и выбор.
Код — модуль `accounts` (этап 5); автомат — `core`, `AccountLifecycle`
(этап 1).

## 1. Слоты и пределы

Число слотов в модели не ограничено (ТЗ, §9). Параллелизм ограничен:
лимитами провайдера, числом execution targets, CPU и памятью, сетью,
политикой пользователя, доступными учётными данными. Слот — аккаунт,
который пользователь законно контролирует; оркестратор не обходит
лимиты и не маскирует идентичность (D-04).

Разделение сущностей (ТЗ, §10):

| Сущность | Что | Где хранится |
|---|---|---|
| `AIAccount` | слот: провайдер, метка, возможности, политика, состояние | база оркестратора |
| `Authentication` | способ входа (ключ API, вход по подписке через CLI) | база — вид и ссылка |
| `Credential` | сам секрет | хранилище ОС (Android Keystore, хранилище target); в базе — только `credentialRef` |
| `ExecutionSession` | применение учётных данных в одной сессии | процесс на target; секрет — в окружении процесса, не в аргументах и не в журнале |

## 2. Автомат состояний

Начальное — `AUTH_REQUIRED` (учётные данные ещё не проверены).
`DISABLED` выходит только явной операцией: включение → `AUTH_REQUIRED`.

| Из | В (обычный переход) |
|---|---|
| `AUTH_REQUIRED` | `AVAILABLE`, `ERROR`, `DISABLED` |
| `AVAILABLE` | `BUSY`, `COOLDOWN`, `RATE_LIMITED`, `AUTH_REQUIRED`, `ERROR`, `DISABLED` |
| `BUSY` | `AVAILABLE`, `COOLDOWN`, `RATE_LIMITED`, `AUTH_REQUIRED`, `ERROR`, `DISABLED` |
| `COOLDOWN` | `AVAILABLE`, `AUTH_REQUIRED`, `ERROR`, `DISABLED` |
| `RATE_LIMITED` | `COOLDOWN`, `AVAILABLE`, `AUTH_REQUIRED`, `ERROR`, `DISABLED` |
| `ERROR` | `AVAILABLE`, `COOLDOWN`, `AUTH_REQUIRED`, `DISABLED` |
| `DISABLED` | — (явно: `AUTH_REQUIRED`) |

- `AVAILABLE` — может принять ещё одну сессию; `BUSY` — достигнут
  предел параллельных сессий по политике аккаунта;
- `COOLDOWN` — пауза после ошибок или по политике распределения;
- `RATE_LIMITED` — провайдер сообщил о пределе; выход — через
  `COOLDOWN` или по времени, указанному провайдером.

## 3. Возможности

Возможности слота (ТЗ, §51): модель, программирование, рассуждение,
длительная работа, инструменты, удалённое исполнение, структурированный
вывод. Задача объявляет `requiredCapabilities`; планировщик выбирает
только совместимые слоты (`docs/SCHEDULER.md`, §4).

## 4. Изоляция

Каждая сессия несёт `accountId`, `credentialRef`, `executionTargetId`;
перед запуском они сверяются (ТЗ, §66). Учётные данные слота B не
попадают в сессию слота A, даже на одном target. Способ изоляции на
target (отдельное окружение процесса, `--bare` с ключом в окружении,
отдельный каталог настроек CLI) — отложенное решение этапа 5
(`docs/direction/DECISIONS.md`, «Отложено»).

## 5. Журнал

Каждое изменение состояния слота — событие (`ACCOUNT_STATE_CHANGED`,
`ACCOUNT_RATE_LIMITED`, `ACCOUNT_AUTH_REQUIRED`) без секретов (D-14).
