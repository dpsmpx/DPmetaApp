# Automation Engine: контракт этапа 1

Решения D-195 и DP_AI_Orcestrator:D-222. Реестр, схемы и прежние
исполнители описаны в [каталоге](AUTOMATIONS.md).

Сценарий — последовательность ссылок на инструменты и их точные ревизии,
с параметрами из схемы. Нет собственного shell, неявного изменения
профиля, передачи секретов и повышения полномочий. Запуск сценария
не сохраняет свои параметры как новый последний выбор ручного профиля:
следующий шаг проверяет ту же конфигурацию и точные входы сценария. Инструмент сам
проверяет проект, target, занятость, черновики и прежнее подтверждение.

Сценарии хранятся вне рабочего дерева. Импорт всегда выключен; включение
делает человек. Обнаружение возможностей использует нынешние профили,
файлы стека и готовность окружения. Инструменты можно выключить явно.

Триггеры: вручную, ИИ, событие, до/после сборки, изменение файлов,
до коммита, до принятия правок ИИ и расписание. Это входы существующей
службы/операции, не отдельный системный планировщик. Фоновый запуск
не наследует полный доступ чата и может ждать подтверждения человека.

До запуска записываются событие и RUNNING; перед каждым шагом — его
номер. После сбоя такой запуск становится INCOMPLETE и сам не повторяет
изменения. Повторное событие возвращает прежний результат. Повторный
вход того же сценария без изменения отпечатка состояния блокируется.
Ошибочный обязательный шаг останавливает последовательность.

Ограничения: один активный сценарий проекта, до 20 шагов, ограниченные
время и результаты. Отмена передаётся прежнему исполнителю; неподтверждённая
остановка не выдаётся за завершение. Сохранение факта запуска обязательно:
отказ записи предотвращает эффект. Смена проекта, target, параметров или
команды требует новой ревизии. Результат содержит доказательства каждого
шага и не объявляет задачу ИИ выполненной.

Критерии автоматической приёмки: все четыре источника, CLI и API идут
одним контрактом; сценарий действительно выполняет шаги; повтор, цикл,
отзыв разрешения, подмена ревизии, отмена, повреждение и отказ хранилища
имеют регрессии; расписание проверяется управляемыми часами без ожидания.
На устройстве отдельно проверяются фон Android, интерфейс подтверждений,
SSH и восстановление установленной release-сборки.

## Использование

Рабочий проект → «Автоматизации» → «Сценарии». Создайте шаблон,
выберите точные ревизии и параметры; импорт сохраняется выключенным.
Пример формата — `dpai/automation/src/test/resources/workflows/v1.json`:
нулевые хеши в образце заменяются актуальными из каталога. Включите
сценарий явно. Отключение разрешено во время исполнения и блокирует
следующий шаг; «Остановить» передаёт отмену текущему исполнителю.

В API-чате `list_workflows` показывает только этот проект/target;
`run_workflow` требует включённый триггер AI. Модель не импортирует,
не включает и не меняет сценарии. CLI после прежнего сопряжения:

```text
dpai automation <ProjectId> list
dpai automation <ProjectId> describe --stdin
dpai automation <ProjectId> run --stdin
dpai automation <ProjectId> workflows
dpai automation <ProjectId> import --stdin
dpai automation <ProjectId> workflow-run --stdin
dpai automation <ProjectId> status --stdin
dpai automation <ProjectId> stop --stdin
```

`--stdin` принимает один объект JSON. Для run — id, revision, parameters
по `describe`; для workflow-run — id, revision и необязательный event.
Передайте стабильный event в сохранённом JSON, чтобы повтор запроса при
потере ответа не повторил шаги. Без event создаётся новый явный запуск;
после неопределённого ответа сначала сверьте историю. Для status/stop —
run из квитанции 202. Список workflows принимает offset и возвращает
nextOffset; страницы учитывают размер ответа и не пропускают записи. Код выхода 3 означает
«ещё выполняется/ожидает», 1 — отказ или неопределённый итог; HTTP 200
не превращает FAILED в успех. После перезапуска процесса status можно
сверить объектом {"workflow":"id","run":"event из квитанции"} с долговечным результатом. CLI не переключает
проект и не содержит флага обхода подтверждений; запрос виден в рабочем
проекте независимо от выбранной вкладки.

## Границы этапа

События журнала именуются `studio.<event_type>` в нижнем регистре,
подчёркивания заменены точками. FILES_CHANGED — успешное сохранение
редактором, применение LSP и запись проектным API, а не внешний watcher
произвольных изменений терминала. Расписания работают в существующей
foreground-службе, включая API-проект без CLI-контура; требуют включённого
приложения/службы и разрешений Android. Пропущенные интервалы не создают
лавину запусков. В занятом дереве задачи BEFORE_ACCEPT/BEFORE_COMMIT
используют только штатные verification.* через её владельца; неподходящий
сценарий блокируется с причиной. В основном свободном дереве доступны все
DIRECT-инструменты. Вложенный профиль сборки не вызывает заново свои hooks.

До 100 сценариев, 20 шагов и 1000 ожидающих событий проекта. Есть общий
бюджет времени и ограниченные доказательства; полный вывод остаётся в
истории инструмента. Фоновый сценарий не наследует «Полный доступ» чата.
Отдельный DAG/маршрутизатор агентов, роли моделей, ИИ-аудит и сравнительные
испытания A–D относятся к этапам 2–10 и этим пакетом не заменяются.
