# Восстановление

Как оркестратор переживает сбои, не теряя критичного состояния и не
выдавая догадку за знание. Код — `orchestrator` и `storage` (этапы 2,
13). Принцип: состояние либо восстанавливается правильно, либо явно
становится `UNKNOWN` или конфликтом — но не ложным (ТЗ, §102).

## 1. Перезапуск

```
старт ─► снимок + хвост журнала (storage)
      ─► сессии в рабочих состояниях → RECOVERY_PENDING
      ─► проба target ─► проба процесса ─► сверка
```

Исходы сверки (ТЗ, §54, §55): процесс жив → `RUNNING`; мёртв →
`FAILED` (затем повтор или переназначение по политике); завершился, пока
приложения не было → `COMPLETED` с подтягиванием событий; неизвестно →
остаётся `RECOVERY_PENDING` с записью `STATE_CONFLICT` до следующей
пробы или решения пользователя.

## 2. Сверка

Если представление оркестратора и target расходятся (оркестратор:
`RUNNING`, target: процесса нет), одно не выбирается наугад: создаётся
`STATE_CONFLICT`, исходы — `RESOLVED_RUNNING`, `RESOLVED_FAILED`,
`RESOLVED_COMPLETED`, `UNKNOWN` (ТЗ, §55).

## 3. Потерянные события

Номер события в потоке без пропусков (D-12). Пропуск (100, 101, 102,
104) обнаруживает `SequenceTracker`: событие 104 не применяется, пока
не получены 103 или снимок с target; повтор события с тем же id —
идемпотентен; тот же номер с другим событием — конфликт (ТЗ, §56).

## 5. Сироты

Периодический поиск: сессии, worktree, процессы, задачи, уведомления,
блокировки, снимки без владельца (ТЗ, §119). Безопасная починка — сама;
остальное — запрос пользователю. `OrphanScan` (`orchestrator.recovery`)
сам возвращает аренды слотов и рабочие деревья конечных и неизвестных
сессий и возвращает задачу `RUNNING` без живой сессии в `READY`; живая
сессия без аренды и запуск агента без сессии — вопрос пользователю
(`ORPHAN_FOUND`). Уведомления без предмета снимает `NotificationEngine.resolve`;
блокировок и снимков без владельца в V1 нет: блокировка — аренда, снимок
один на проекцию.

## 7. Код

`orchestrator.recovery`: `Reconciler` (ТЗ, §54, §55: `markPending`,
`reconcile` с исходом `RESOLVED_RUNNING`, `RESOLVED_FAILED`,
`RESOLVED_COMPLETED`, `UNKNOWN` и диагностикой `STATE_CONFLICT`),
`OrphanScan`, `WorktreeProbe`. Чтобы продолжить идущий ход после
перезапуска, сессия пишет в журнал позицию в потоке агента (heartbeat с
`agentSequence`), а раннер подхватывает её (`ClaudeRunner.adopt`). Итог
хода, завершившегося без приложения, собирается из журнала агента.

Сам контур — `Orchestrator`: при создании над непустым журналом
аккаунты, сессии, задачи и деревья поднимаются проекциями
(`AccountsProjection`, `SessionsProjection`, `TasksProjection`,
`WorktreesProjection`; дерево задачи узнаётся по ветке `task/<id>`) —
из снимков и хвоста журнала, если контуру дано хранилище снимков
(журнал сегментами, D-37), иначе из всей истории потоком, а `recover` проводит сверку
со всеми targets и подхватывает идущие ходы; задачи реагируют на исход
сверки, как на опрос. Так перезапускается контроллер приложения
(`LiveSystem`, D-35): `LiveSystemTest`, `restartAdoptsRunningTurnFromJournal`.

## 6. Деградация

Частичный отказ не останавливает всё (ТЗ, §80): без Git — просмотр
задач, сессий, истории; сломаны уведомления — планировщик работает;
нарушена целостность хранилища — разрушительные записи останавливаются.
Состояния самодиагностики: `Healthy`, `Degraded`, `Recovery`,
`Blocked`, `StorageError`, `ExecutionUnavailable`, `SecurityLockdown`
(ТЗ, §79).
