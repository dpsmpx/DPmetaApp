# Android APK из DPmetaApp: in-app Linux, SSH и Termux

Состояние: 22 ноября 2026. Контекст: D-202 (специальный Termux-target удалён),
D-216 (готовность проверяется запуском), D-217 (SDK принадлежит target), D-12
(выдача APK с контрольной суммой). Это реализация **обычного SSH-target**,
а не восстановление Android intent-моста Termux.

## 1. Сборка в Termux на том же телефоне

1. DPmetaApp → «Настройка» → «Termux: сборка APK на этом телефоне».
   Сначала установите пакеты, затем сохраните актуальный `dpai-agent.zip`
   встроенной кнопкой «Сохранить» и разрешите Termux доступ к общей папке
   (`termux-setup-storage`). Все команды человек запускает в Termux сам.
   Перед распаковкой архив сверяется с SHA-256 вложения текущего APK;
   подменённый или старый архив не устанавливается.
2. Команда из инструкции устанавливает `dpai`-агент текущей версии,
   добавляет **только открытый** ключ DPmetaApp в `authorized_keys`,
   запускает второй `sshd` на `127.0.0.1:8023` без паролей и печатает
   отпечатки ключей хоста. Пароли, закрытые SSH-ключи и ключ подписи APK
   не переносятся между приложениями.
3. DPmetaApp → «Targets» → «Добавить» → «Termux · телефон». Имя пользователя
   берите из `id -un` в Termux; адрес, команда агента и каталог слота
   Claude (`~/.claude`) выставляются заготовкой. Этот каталог нужен
   нынешнему формату проекта, но ручная сборка не требует входа в Claude.
   При первом подключении сравните ключ хоста с выведенным
   Termux. Кнопка «APK-среда» проверяет запуск `java`, `javac`, `git`,
   `aapt2` и наличие Android SDK в окружении *нелогиновой SSH-команды*.
4. Репозиторий должен находиться **на этом target**: например,
   `git clone` внутри Termux в `~/Projects/…`, после чего создайте
   проект в DPmetaApp для Termux target и его каталога. Сборка остаётся
   обычным профилем CHECK/BUILD с тем же Git-preflight, журналом и
   отменой. APK в дереве отображается в «Артефакты» и скачивается через
   SFTP, после чего действуют прежние установка и подпись.
5. Android может остановить фоновый Termux; для длительного Gradle-процесса
   настройте ограничения батареи и при необходимости вручную используйте
   `termux-wake-lock`. DPmetaApp не запускает Termux тайно и не включает
   бессрочную фоновую службу без действия пользователя.

### Android SDK и ARM64

Обычный Linux SDK от Google включает host-инструменты под ПК, поэтому
не доказывает пригодность для Android/aarch64. Для Java нужен Termux
`openjdk-21` и **реальный** успешный `java -version`. Для ресурсов —
нативный Termux `aapt2` и, где версия AGP принимает, свойство Gradle
`android.aapt2FromMavenOverride=$PREFIX/bin/aapt2`. Android platform
(`android.jar`), подходящие build-tools и лицензии SDK устанавливаются
отдельно; `ANDROID_HOME` должен быть виден SSH-командам. Проба AAPT2
не заменяет проверку конкретной версии AGP. C++/NDK дополнительно
требуют рабочую ARM64 toolchain для Android host; скачанный Linux x86_64
NDK сам по себе непригоден. Некоторые проекты могут не собираться в
Termux и после успешной Java-пробы. Итогом служит только код Gradle и
проверенный APK; «готово» по наличию пакета не объявляется.

### Проверка на устройстве

- Текущий Termux подписан официальным источником, `id -un`, `java -version`,
  `javac -version`, `aapt2 version` успешны.
- SSH с ключом приложения на 127.0.0.1:8023, host key проверен; парольный
  вход отключён, внешний сетевой интерфейс не прослушивается.
- `dpai-agent agent doctor` сообщает ту же версию, что DPmetaApp.
- «APK-среда»: Java, JDK, Git, AAPT2 и SDK не помечены успешными по одной
  записи в пакетной базе. Ошибки видны поимённо.
- `BUILD`: Gradle действительно завершился 0, SHA-256 файла сверена;
  SFTP-скачивание, установка и подпись проверены отдельно.
- Остановка и повторная сборка, отключение Termux во время SSH и смена
  host key завершаются диагностикой, не автоодобрением.

## 2. Настольный SSH-target

ПК Linux/Windows уже поддерживается: агент, проверенный ключ хоста,
рабочее Git-дерево и Android SDK принадлежат ПК. При этом файл APK
скачивается обратно по SFTP. Важное отличие от Termux — Android SDK/NDK
для обычных x86_64 машин распространены официально; не нужно подменять
host binaries ARM64-вариантами.

## 3. Почему Alpine под proot не равен Termux

Установка пакета JDK в Alpine подтверждает наличие файлов, но при отказе
`mprotect`/`execmem` в SELinux-домене процесса `untrusted_app` JVM может
не запуститься даже с `-Xint`. `proot` не даёт процессу новые SELinux-права.
Прежняя ошибка о PaX не доказывает присутствия PaX. Встроенная проба
Java и память объясняет такой отказ до запуска Gradle; она не снимает
системную политику Android.

Termux использует собственные пакеты, собранные для Android/Bionic, и
собственный префикс `/data/data/com.termux/files/usr`. Его пакеты нельзя
просто скопировать в `/data/data/com.dpsmpx.dpai`: они зависят от путей,
ABI, модели запуска и прав другого приложения. DPmetaApp не может
получить UID Termux или исполнять его процессы напрямую без особого
взаимодействия/подписи. Снижать `targetSdk` до устаревшего уровня ради
обхода ограничений Android не является принятым решением и противоречит
задаче современной Android IDE.

Возможное будущее **полностью автономного native-in-app builder** требует
отдельной проверки на устройствах: Bionic/ARM64 пакетов, совместимой JVM,
native AAPT2, SDK/NDK host tools, платформенных файлов, подписи и
изоляции каталога. Пока нет работающего, проверенного стека на телефоне,
DPmetaApp не выдаёт этот режим за доступную сборку. Рабочий путь — SSH
к Termux или ПК; он не требует root и не нарушает D-202.
