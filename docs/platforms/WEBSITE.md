# Сайт dpsmpx.com

**Сайт в разработке (Д34):** сессии развивают его в репозитории
(staging), пока автор не скажет «сайт готов»; список работ —
`ROADMAP/ROADMAP.md`, П2, «Сайт — в работе». **Выгрузка разрешена**
(Д34, `production.live: true`) и от этих слов не зависит. Хостинг —
Beget, выгрузка — rsync (Д35); выгружает автор или локальная сессия
Claude Code после его «да» (Д36). Домен зарегистрирован 05.10.2026
(ОР-11 закрыт); HTTPS — после сертификата (`TODO.md`).

Центральная точка публикации и постоянный архив автора (Д21, Д32;
постановка §4–7, §25, §32–35, §48, §79–85, §94, §117–118). Исследование —
`docs/research/publishing/WEBSITE.md`; генератор — `tools/cs/site/`;
тема — `website/`; настройки — `data/website/site.yaml`.

## Модель

| Поле | Значение |
|---|---|
| Audience | все аудитории (`CONTENT_STRATEGY.md`, §2): профессиональная и соавторы — «кто это», игроки — проекты, разработчики — записи |
| Purpose | ответить за секунды: кто этот человек, что он делает, какие проекты главные, почему следить (§6); хранить всё опубликованное (§25) |
| Primary content | PERSON (главная, «обо мне»), PROJECT (страницы проектов), все опоры в ленте `/news/` |
| Secondary content | фиды, `/api/v1/` для своих клиентов |
| Length | запись — сколько нужно; главная — экран-два без свалки (§6, §117) |
| Visual format | тёмная тема из токенов бренда (Д9), IBM Plex; изображения записей — экспорт объектов; OG 1200×630 — формат `og_image` (будущий, `verified: false`) |
| CTA | дневник, видео, подписка на фиды |
| Posting rhythm | каждая запись площадок рождается здесь (POSSE) |
| Discoverability | поиск (title, description, canonical, sitemap, структурированные данные), ссылки с площадок на канонический адрес |
| Retention mechanism | фиды Atom/RSS/JSON, архив, страницы проектов |
| Cross-platform role | **источник**: площадки ссылаются на сайт; сайт не зависит от площадок (§118) |

## Структура (после исследования)

```
/                       главная (RU)              /en/                  главная (EN)
/about/                 обо мне (CI-0001)         /en/about/
/projects/              проекты                   /en/projects/
/projects/<id>/         страница проекта (факты)  /en/projects/<id>/
/news/                  лента: новости, дневник, статьи, релизы — категории
/news/<slug>/           запись (адрес не меняется)
/tags/<метка>/          записи по метке
/feed.xml /rss.xml /feed.json   фиды
/sitemap.xml /robots.txt /404.html
/api/v1/index.json /api/v1/projects.json /api/v1/news.json
/media/<объект>/…  /fonts/…  /style.css  /favicon.svg
/.htaccess              заголовки и 404 для Apache (Beget, Д35); /_headers — для Cloudflare Pages и Netlify
```

§5: «devlog», «articles», «releases» — категории одной ленты; «media»,
«downloads» — появятся, когда будет что показать (снимки игры в
реестре, выпуск); «contact» — блок на главной и в «обо мне».

## Имя автора (Д37)

На сайте автор — только `dpsmpx`: заголовок главной, `<title>`, подвал,
JSON-LD (`Person`, `CreativeWork`, `BlogPosting`), фиды и API. Имя из
AU-NAME выводится только при `real_name: true` в `site.yaml` — новым
решением автора. При `real_name: false` сборка ищет слова имени из
AU-NAME (RU и EN) в каждом файле сайта; совпадение — ошибка сборки, и
её видят проверка `site`, предпросмотр и выгрузка. Так имя не попадёт на
сайт и через текст варианта (`{{fact:AU-NAME}}`) или alt изображения.
Текст на картинках проверка не читает — подпись изображений сайта
«dpsmpx» сверяется глазами (критика, К1).

## Адреса (§79)

Канонический адрес — `https://dpsmpx.com` + путь; на площадках —
он же (`link: canonical` в варианте), без меток отслеживания (`utm.enabled:
false`, §80). Адрес записи (`/news/<slug>/`) не меняется после
публикации; смена — только с перенаправлением со старого.

## SEO и вид в соцсетях (§81–82)

`<title>`, `description`, `rel=canonical`, `hreflang` RU/EN, Open Graph
(`og:title`, `og:type`, `og:image`, `og:url`, `og:description`,
`og:locale`), `twitter:card`, JSON-LD (`Person`, `WebSite`,
`BlogPosting`, `CreativeWork` проекта), `/sitemap.xml` с `lastmod` и
парами `hreflang` (`xhtml:link` у каждого адреса пары и `x-default`),
`/robots.txt`, фиды. `lastmod` — дата самого нового источника страницы:
записи или свидетельства факта, который на ней выведен; источника с
датой нет — `lastmod` не пишется. Значок `/favicon.svg` — «d» и
точка-акцент из токенов бренда, без шрифтов. Проверка `site` собирает
обе версии, читает фиды и JSON, ищет битые внутренние ссылки, проверяет
доступность и CSP каждой страницы, наличие значка и файла заголовков
хостинга.

## Доступность (П2-10, П2-14)

- `<html lang>`; ссылка «к содержимому» (`#main`) первой по Tab; видимый
  фокус (`:focus-visible`, акцент `human`); у текущего раздела меню —
  `aria-current="page"`; переключатель языка с `lang` и подписью.
- Один `h1` на странице: заголовок страницы; разметка вариантов даёт
  только `##`/`###` (`h2`/`h3`).
- У каждого изображения — `alt`. Для медиа вариантов это `media_alt` —
  по строке на файл `media`, с подстановками фактов (Д28); alt входит в
  хэш одобрения, его меняет только новая фиксация варианта. Нет
  `media_alt` — ошибка сборки.
- Телефон — проверка на 390 px: без горизонтальной прокрутки, пункты
  меню не рвутся, цели касания меню и списков ссылок — не ниже 24 px
  (WCAG 2.2, 2.5.8; ссылки внутри предложений — исключение).

## Заголовки безопасности (П2-12, Д35)

Файл — по `hosting` в `site.yaml`: для Beget (Apache) — `/.htaccess`
(`Header always set …` внутри `<IfModule mod_headers.c>`,
`Options -Indexes` — без списка файлов каталогов, где нет своей страницы,
`ErrorDocument 404 /404.html`, `AddDefaultCharset utf-8`, типы
`woff2`/`svg`); для Cloudflare Pages и Netlify — `/_headers`, правило
для `/*`. Набор один: `Content-Security-Policy` (только свои файлы: `script-src 'none'`,
`style-src 'self'`, `img-src 'self'`, `font-src 'self'`,
`frame-ancestors 'none'`; JSON-LD — блок данных, не исполняется),
`X-Content-Type-Options: nosniff`, `Referrer-Policy:
strict-origin-when-cross-origin`, `Permissions-Policy` (камера,
микрофон, геолокация, оплата, USB — выключены), `X-Frame-Options: DENY`,
`Cross-Origin-Opener-Policy: same-origin`; у staging ещё
`X-Robots-Tag: noindex, nofollow`. Политика — в `tools/cs/site/build.py`
(`SECURITY_HEADERS`) рядом с генератором: что страница может содержать,
решает он. Проверка `site` ловит встроенные скрипты, стили, обработчики
`on…=` и внешние ресурсы страниц; проверка `siteshots` отдаёт тот же
набор заголовков с локального сервера и ловит нарушения политики в
настоящем браузере (§ «Визуальная регрессия»). На рабочем сайте
заголовки отдаёт хостинг. Beget `Header` к статике применяет: на `/`
приходит весь набор (05.10.2026, `http://dpsmpx.com/`; впереди стоит
nginx, `.htaccess` всё равно действует). Список файлов каталогов у Beget
выключен и без `Options -Indexes` (`/fonts/`, `/api/` — 403).

## Визуальная регрессия (П2-17)

Проверка `siteshots` (`tools/cs/site/shots.py`, съёмщик
`tools/render/site_shots.js`) — как проверка изображений: собирает
staging, поднимает локальный сервер с заголовками сайта (CSP и др.) и
снимает в Chromium каждую страницу (и `/404.html`) на ширине **390** и
**1280 px**. По раскладке:

| Уровень | Что |
|---|---|
| ошибка | прокрутка вбок; элемент за краем экрана; сломанное изображение; нарушение CSP; ошибка в консоли; несработавший запрос; не загружен IBM Plex Sans; не один `h1`; цель касания меньше 24 px на телефоне (меню, списки ссылок, подвал) |
| предупреждение | текст мельче 12 px |

Снимки — в каталоге сборки build/site-shots/staging (`<страница>-<ширина>.png`,
не в Git) — для глаз: смотреть после каждой правки темы или шаблона.
Команда — `python3 -m tools.cs site shots`; в `tools/check.sh` проверка
входит в полный уровень и `--affected` (правки сайта, темы, контента,
фактов), в `--fast` пропускается (нужен Node.js с Playwright и
Chromium). Попиксельного сравнения с эталоном нет намеренно: снимки
меняются с каждой правкой текста, а правила ловят именно поломки
вёрстки.

## Выпуск и выгрузка (§48, Д35, Д36)

Предпросмотр (`python3 -m tools.cs preview <объект|кампания> --serve`) —
staging-сборка в корне `build/preview/<id>/`, страница со всеми
вариантами — `/_preview/`; сайт ссылается на свои файлы от корня, поэтому
открывается через локальный сервер (`site serve`, `preview --serve`;
нет адреса — `/404.html` с кодом 404, как на хостинге), а не из `file://`.

```
commit → python3 -m tools.cs check → site build --env staging → предпросмотр (site serve, preview --serve)
       → publish <объект> website.ru --to site-production --production (сборка + rsync + проверка по HTTP + журнал)
       → site deploy --dry-run → site deploy        (тема и код сайта без новой записи)
```

- **Запись** (новая или изменённая): `publish … --to site-production
  --production` — одобрение, сборка с записью, rsync, проверка страницы
  по HTTP (canonical на месте), запись в журнал.
- **Тема и код сайта** без новой записи: `site deploy --dry-run` (что
  изменится: rsync `--dry-run --itemize-changes`), затем `site deploy` —
  та же production-сборка из журнала; проверка `site` до выгрузки,
  главные страницы по HTTP — после; событие — `build/logs/deploy.jsonl`.
- rsync: `--checksum --delete-delay --delay-updates` (файлы встают на
  место в конце), `--filter=P /.well-known/` (не удалять), SSH с
  `BatchMode=yes`; путь обязан кончаться `public_html/`. Адрес —
  переменная автора `CS_PROD_SITE_DEPLOY_TARGET`, ключ — его SSH
  (`docs/operations/CREDENTIALS.md`, «Сайт: Beget»); в Git — только имя
  переменной. rsync на сервере Beget есть: пробный прогон у автора
  прошёл (05.10.2026).
- Первая выгрузка — сначала `site deploy --dry-run`: в `public_html/`
  Beget кладёт `cgi-bin/` и `index.php` — выгрузка их удалит;
  `/.well-known/` не трогается.
- Корень репозитория — не сайт: его `.htaccess` запрещает отдачу всего
  (Д35). Если корень по ошибке окажется в `public_html/`, Apache ответит
  403 (проверено на Apache 2.4; если хостинг запрещает `Require` в
  `.htaccess` — 500, файлы тоже не отдаются). У Beget впереди nginx, но
  `.htaccess` к статике применяется (заголовки на `/`, 05.10.2026), так
  что запрет, вероятно, сработает; на самом Beget он не проверялся.
- Выгружают только `site deploy` и `publish` (Д35): все запреты ниже
  стоят внутри них, а источник — всегда свежая сборка. Ярлыки и скрипты
  только вызывают эти команды; прямой rsync в `public_html/` в обход
  системы запрещён — 05.10.2026 так ушёл корень репозитория
  (`docs/audits/2026-10-05-SITE_LEAK_INCIDENT.md`).
- Запреты: выпуск закрывает `production.live: false` (сейчас `true`,
  Д34) и статус адресата `site-production`, отличный от `active`; нет
  адреса или путь не на `public_html/` — отказ; сборка с ошибками
  проверки `site` не выгружается; облачная сессия — никогда; локальная —
  только после «да» (Д36). Пробный прогон (`--dry-run`) не смотрит на
  `live` и вид сессии, но тоже требует адрес. Причины отказа печатают
  `site deploy` и `health`.
- Откат: `git revert` правки и снова `site deploy` (сборка выводится из
  модели и журнала); снять запись — `publish --delete` (автор).
