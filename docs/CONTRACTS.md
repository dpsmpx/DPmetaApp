# Контракты между репозиториями

Что один репозиторий ждёт от другого. Контракт — не новое правило
DPmeta: у каждого есть владелец, и правится он там. Здесь — то, что
обычно видно только с одной стороны, собранное в одно место с
доказательствами.

Поля: **вид** (M-03), **владелец** (где правится), **потребители**,
**что передаётся**, **устойчивость**, **что ломает**, **чем проверяется**,
**доказательства**.

## C-01 — Galdhold не зависит от DPlang

- **Вид:** наблюдение.
- **Владелец:** оба — каждый своей стороной: `Galdhold:Р18` (Galdhold не
  зависит от DPlang ни при сборке, ни при исполнении; до DPlang 1.0 код
  не переносится; после — подсистема за подсистемой, каждая отдельным
  решением в Galdhold) и `DPlang:Р21`, `DPlang:Р22`, `DPlang:Р31` (язык не
  блокирует игру; перенос — только решением в журнале Galdhold и после
  аудита; этот репозиторий решений за игру не принимает).
- **Что передаётся:** ничего, кроме знания. DPlang берёт из Galdhold
  правила и счёт конструкций, но не код (`DPlang:CLAUDE.md`, «Защита и
  оригинальность»); компилятор пишется на C++20 «в подмножестве
  VoxelRPG» (`DPlang:Р34`) — правило стиля, не зависимость.
- **Устойчивость:** до DPlang 1.0 — абсолютная; после — отдельными
  решениями в Galdhold.
- **Что ломает:** зависимость сборки Galdhold от DPlang; задача в
  Galdhold «ради будущего переноса» (`Galdhold:Р18`, «Что это значит
  сейчас»).
- **Чем проверяется:** обзором при архитектурных правках Galdhold
  (`Galdhold:Р18`); у DPlang — правилом «решений за VoxelRPG не принимать»
  (`DPlang:CLAUDE.md`).
- **Доказательства:** формулировки сторон совпадают по сути;
  `SocialMediaImage:docs/identity/PROJECT_MAP.md` (§4) и
  `SocialMediaImage:IC-06` переносят то же в публичный образ. Расходится
  только имя: DPlang пишет об игре как о VoxelRPG (SQ-03), Galdhold пишет
  адрес DPlang как `dpsmpx/C-` (SQ-01).

## C-02 — Скриптовый язык Galdhold и назначение DPlang

- **Вид:** открытый вопрос — RISK-02.
- **Суть.** `Galdhold:Р17` откладывает выбор скриптового языка между
  «подмножеством DPlang со встраиваемым детерминированным исполнителем» и
  малым DSL; задача Galdhold «Детерминированный скриптовый язык» выбирает
  вариант 3 — «когда собственный язык стабилен — его встраиваемый
  исполнитель вместо отдельного DSL» — и перечисляет, что для этого
  нужно от DPlang (исполнитель в процессе движка на Android ARM64 и
  Windows x64, песочница, счёт шагов). `DPlang:Р27` и
  `DPlang:docs/direction/VISION.md` (§2) говорят обратное: язык — «не DSL,
  не скриптовый слой; программы — native-приложения, а не программы
  внутри интерпретатора». В журнале DPlang требования Galdhold не
  записаны ни решением, ни открытым вопросом.
- **Что уже смягчает.** Galdhold знает, что встраиваемого режима нет
  (ответ автора 3 октября 2026), и держит запасной путь: DSL за тем же
  контрактом хоста или модули на DPlang через C ABI после 1.0.

## C-03 — Поставка DP-Verify в репозитории

- **Вид:** наблюдение (по проекту DP-Verify; потребителей ещё нет).
- **Владелец:** DP-Verify — `DP-Verify:docs/direction/TECHNICAL_TASK.md`
  (§6.1, §7, §9, §11), решения `DP-Verify:V-02`, `DP-Verify:V-03`,
  `DP-Verify:V-15`, `DP-Verify:V-16`, `DP-Verify:V-17`.
- **Потребители по плану:** DPpass — пилот, этап 6; Galdhold — этап 7;
  DPlang — версия 1.1; DPlearn — «когда выйдет 1.0» (`DPlearn:TODO.md`).
- **Что передаётся:**
  - копия в `tools/dpv/` (`dpv`, `dpverify/`, `kit/`, `VERSION`,
    `MANIFEST.sha256`); правка копии на месте — находка, изменения
    приходят новой поставкой (`DP-Verify:V-02`, `DP-Verify:I-07`);
  - профиль проекта `tools/dpverify.toml`, схема 1 (`DP-Verify:V-03`);
  - `report.json`, схема 1; коды возврата 0–3 (ТЗ, §9.2, §9.4);
  - строка в `PROVENANCE.md` проекта (`DP-Verify:I-09`);
  - окружение: `python3` ≥ 3.11 и `git` (`DP-Verify:F-13`, `DP-Verify:V-01`) —
    так в контейнере сессий; всё, что нужно командам профиля, ставит хук
    начала сессии проекта (`DP-Verify:I-10`).
- **Устойчивость:** в 1.x схема профиля не меняется, поля `report.json`
  только добавляются, id проверок не переименовываются и не удаляются
  (`DP-Verify:N-09`); подключённые репозитории — на одной минорной версии
  (`DP-Verify:I-12`).
- **Чего контракт не делает:** зависимости исполнения — копия работает
  без сети и без клона DP-Verify; обязанности подключаться — подключение
  начинается с решения в журнале принимающего репозитория
  (`DP-Verify:I-01`), проект сильнее профиля (`DP-Verify:I-08`).
- **Что ломает:** номера решений принимающих репозиториев, закреплённые
  в плане (RISK-03); лицензия принимающего репозитория, несовместимая с
  `DP-Verify:V-15` (RISK-01); устаревшие сведения о принимающих
  репозиториях в плане (SQ-07, SQ-08).
- **Чем проверяется:** самотестами DP-Verify и пробой на клонах
  (`DP-Verify:docs/audits/STAGE2_TRIAL.md`); пути в чужих репозиториях
  DP-Verify не сверяет (`DP-Verify:V-17`) — их сверяет `tools/xref.py`.

## C-04 — Факты о проектах — из их репозиториев

- **Вид:** наблюдение; последний пункт — рекомендация.
- **Владелец:** каждый проект — о себе (M-02).
- **Потребители:**
  - **DPprofile** — история: факт ссылается на источник из реестра и на
    точное место (`путь@sha`, коммит, релиз); факты не переписываются;
    из других репозиториев — только идентификаторы и выжимки до 300 знаков
    (`DPprofile:D-04`…`DPprofile:D-06`); полная проверка сверяет ссылки с
    клонами источников (`DPprofile:tools/verify/fetch_sources.sh`);
  - **SocialMediaImage** — публичные утверждения: класс, источник, коммит,
    дата и срок перепроверки (`SocialMediaImage:data/facts/facts.yaml`);
    решения проектов не переписываются, расхождение — находка в
    `SocialMediaImage:docs/identity/IDENTITY_CONFLICTS.md`.
- **Что передаётся:** факты, вехи, номера решений, публичные описания —
  с местом и коммитом. Без кода и внутренних документов (C-05).
- **Неявное допущение:** история `main` в репозиториях-источниках не
  переписывается — иначе ссылки DPprofile `путь@sha` перестают
  разрешаться. Сейчас это так: везде вливание через PR, принудительных
  пушей в `main` в правилах нет. Явно нигде не записано.
- **Рекомендация:** записать это допущение в правилах репозиториев,
  которые служат источниками (строка «`main` не переписывается»);
  решают сами репозитории.
- **Наблюдение:** реестр DPprofile покрывает Galdhold, DPlang, DPpass,
  профиль и публичные проекты (S-00…S-22); DP-Verify, DPlearn,
  SocialMediaImage, DP_game_market_analytic_system и DPmeta в нём нет —
  по правилу DPprofile «закрытые репозитории, которых нет в реестре, — до
  отдельного решения» (`DPprofile:docs/direction/SCOPE.md`). Карта проектов
  SocialMediaImage тоже знает только часть (SQ-12).

## C-05 — Закрытый код не выходит наружу

- **Вид:** наблюдение.
- **Владельцы:** каждый закрытый проект — `Galdhold:Р12`, `DPlang:Р5`,
  `DP-Verify:V-15`, а также правила `CLAUDE.md` DPpass, DPprofile,
  DPlearn и SocialMediaImage.
- **Суть:** код и внутренние документы закрытого репозитория не
  копируются в другой и не вставляются в сторонние сервисы; другие
  репозитории берут только факты, номера и короткие выжимки со ссылкой
  (`DPprofile:D-05`; `SocialMediaImage:CLAUDE.md`, «Закрытые проекты»;
  `DPlang:CLAUDE.md` — «Код VoxelRPG сюда не копируется»). Исключение —
  поставка DP-Verify: «свой код автора» в закрытые репозитории автора
  (`DP-Verify:V-15`; см. RISK-01).
- **Для DPmeta:** то же правило (M-02): здесь только номера, пути,
  короткие цитаты и выводы.
- **Онлайн-компилятор DPlang** (C-09) держится того же: компиляция на
  сервере, а не сборка компилятора в браузере, потому что WASM — это
  передача двоичной сборки каждому посетителю (`DPlang:Р49`, со ссылкой
  на `DPlang:Р4`, `DPlang:Р5`, `DPlang:Р39`).
- **Нарушение 05.10.2026.** Ярлык на телефоне автора выгрузил на хостинг
  сайта весь рабочий каталог SocialMediaImage вместо сборки. Кода
  закрытых проектов там нет по правилу самого SocialMediaImage, но были
  внутренние оценки и факты с `public: false` о Galdhold и DPlang, а
  также личные данные автора. Каталог очищен восстановлением; разбор —
  `SocialMediaImage:docs/audits/2026-10-05-SITE_LEAK_INCIDENT.md`
  (SQ-19, RISK-08).

## C-08 — Формат карт и имена тайлов Andors-Love

- **Вид:** наблюдение.
- **Владелец:** Andors-Love — `src/types.h` (`enum Tile`), `src/world.cpp`
  (разбор), `tools/check_maps.py` (проверка), README, «Формат карты»;
  имена основных слотов тайлов — `Andors-Love:src/gfx/tiles.cpp`.
- **Потребитель:** TrueJointTileMaker — режим карты: коды клеток в порядке
  `enum Tile`, восемь видов объектов, хвост строки объекта сохраняется
  как есть. С 5 октября 2026 оригинал 0.6.0 на PascalABC.NET лежит в
  `pascal/` и служит эталоном (`TrueJointTileMaker:pascal/TJTMMap.pas`),
  а редактор переносится на C++ и SDL2 (`TrueJointTileMaker:docs/porting.md`).
- **Записан у потребителя:** «Формат карт — договор с игрой: перенос
  обязан читать и писать все карты … байт в байт»
  (`TrueJointTileMaker:CLAUDE.md`, «Правила»); имена основных слотов в
  `data/tiles/*.png` — «договор с `src/gfx/tiles.cpp` игры»
  (`TrueJointTileMaker:docs/porting.md`, «Корпус Andors-Love»).
- **Устойчивость:** версии формата нет; совместимость держится тем, что
  TrueJointTileMaker повторяет `enum Tile` и сверен на всех 50 картах
  («байт в байт», `TrueJointTileMaker:README.md`).
- **Чем проверяется у потребителя:** тесты переноса читают корпус —
  клон `main` Andors-Love (`ANDORS_LOVE_DIR`), который ставит хук начала
  сессии TrueJointTileMaker; без корпуса тесты пропускаются, а не падают
  (`TrueJointTileMaker:docs/porting.md`). Это зависимость проверки, не
  сборки: редактор собирается и работает без клона игры.
- **Сверено 5 октября 2026:** семь кодов клеток и их символы совпадают
  (`Andors-Love:src/types.cpp` ↔ `TrueJointTileMaker:pascal/TJTMMap.pas:84`,
  `TILE_CHARS = '.#~T,=:'`); виды объектов совпадают;
  `tools/check_maps.py` — 50 карт, всё сходится. Описание формата у
  владельца неполное: в README нет символа `:` (стоячая вода, проходима),
  который знают парсер, проверка и редактор и использует карта `canal`
  (SQ-16). У потребителя устарело имя скрипта проверки игры —
  `tools/gen_maps.py` вместо `tools/check_maps.py` (SQ-20).
- **Что ломает:** новый код клетки или вид объекта в игре без правки
  редактора — редактор прочтёт неизвестный символ как стену и при
  пересохранении испортит карту.

## C-09 — Онлайн-компилятор DPlang и страница на dpsmpx.com

- **Вид:** наблюдение; согласование сторон — открытый вопрос (RISK-09).
- **Владелец:** DPlang — компилятор, контракт, версии, диагностика,
  детерминизм (`DPlang:Р49`, «Граница ответственности»). Там же
  названы ещё две стороны: SocialMediaImage — страница, редактор,
  HTTP-клиент, показ диагностики; «инфраструктура» — точка входа, TLS,
  внешний rate limit, оркестрация worker-ов, мониторинг — без
  репозитория-владельца.
- **Потребитель:** страница сайта `dpsmpx.com`, которую по плану DPlang
  делает SocialMediaImage «по контракту» (`DPlang:ROADMAP/ROADMAP.md`,
  «Онлайн-компилятор (Р49)»).
- **Что передаётся:** программа на DPlang → диагностика. Только
  компиляция, программы не исполняются. JSON с версией API в адресе
  (`/api/v1/...`), отдельной от версий компилятора и языка;
  детерминированная часть ответа одна и та же при одинаковом входе и
  версии. Код и сборка компилятора наружу не уходят — компиляция на
  сервере (C-05).
- **Когда вступает:** запуск выключен (`available: false`) до отдельного
  решения автора по `DPlang:Р5`, проверки имени у поверенного
  (`DPlang:Р39`) и выполнения DoD сервиса (`DPlang:Р49`).
- **Устойчивость:** контракт записан стороной DPlang —
  `DPlang:docs/service/integration.md` и `DPlang:docs/service/README.md`
  (`78defb1`, 7 октября 2026; в `715ab0c` их ещё не было): версия API в
  пути `/api/v1/`, адрес API задаёт инфраструктура при развёртывании,
  страница сначала спрашивает `available` и не показывается, пока сервис
  выключен, CSP страницы `connect-src` — адрес API. Стороны
  SocialMediaImage нет; инфраструктура — RISK-09.
- **Вторая сторона о связи не знает.** В SocialMediaImage нет ни
  решения, ни задачи, ни строки в карте проектов о странице компилятора
  (сверено по `main` `9f93695` и ветке `claude/youthful-planck-pyi7tw`;
  на `main` `04b8ded` — так же).
  Принятое там расходится с ожиданием DPlang:
  - адрес `/api/v1/` на dpsmpx.com уже занят статическим API сайта —
    `/api/v1/index.json`, `projects.json`, `news.json`
    (`SocialMediaImage:Д32`, `SocialMediaImage:docs/platforms/WEBSITE.md`);
