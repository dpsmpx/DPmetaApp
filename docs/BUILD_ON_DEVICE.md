# Сборка APK внутри DPmetaApp

Основной DPmetaApp — мобильная студия с `targetSdk 28`: Android-проекты
собираются прямо в приложении, в собственном Alpine Linux под proot,
без отдельного Termux и обязательного SSH-target. Реальный запуск JVM
и Gradle всё ещё требует проверки на целевом телефоне (`DPmetaApp:D-189`).

## 1. Установить основной APK студии

В GitHub Actions DPmetaApp (`.github/workflows/apk.yml`) после зелёного
`full --strict` доступны два APK:

- `primary/DPmetaApp.apk` — **основная сборка**, `targetSdk 28`,
  позволяющая Android запускать программы из каталога Linux приложения;
- `modern/DPmetaApp-modern-target.apk` — дополнительная сравнительная
  сборка, `targetSdk 36`, с ограничением запуска из каталога данных.

У обоих APK неизменные `applicationId=com.dpsmpx.dpai`, название
`DP_IDE`, ключевая схема и `minSdk 30`. Смена `targetSdk` приложения-IDE
**не задаёт** `targetSdk` собираемых ею Android-проектов: каждый проект
выбирает свой целевой API в собственном Gradle-файле.

Основной вариант `primary` не предназначен для Google Play. У него более мягкие
ограничения Android на выполнение загруженного кода и иная модель
разрешений. **Оба артефакта Actions подписаны отладочным ключом**:
они не устанавливаются поверх APK с подписью владельца без пересборки
с тем же ключом. Нельзя удалять установленное приложение с данными
ради перехода на этот вариант без резервной копии!

Сборка основного APK на машине с JDK 21 и Android SDK:

```sh
DPAI_RELEASE_DEBUG_KEY=1 sh tools/build-apk.sh release
```

Для сравнительной сборки с `targetSdk 36`:

```sh
DPAI_TARGET_SDK=36 DPAI_RELEASE_DEBUG_KEY=1 sh tools/build-apk.sh release
```

Устаревшее `DPAI_ON_DEVICE_BUILD=1` остаётся совместимым, но больше
не нужно: `28` используется и при обычном `./gradlew :shell:assembleRelease`.

Для настоящего обновления приложения используйте существующий ключ
выпуска владельца (без `DPAI_RELEASE_DEBUG_KEY=1`) и сверку сертификата.

## 2. Подготовить инструменты на телефоне

1. В DPmetaApp установите **Linux в приложении**. Это собственная среда
   приложения; пакет Termux не нужен.
2. Выберите **«Установить Android-native JDK 21»** в Linux приложения
   или вызовите `environment.android_jdk` из чата. Это OpenJDK под
   **Android ARM64/Bionic**, как в Termux/AndroidIDE, но со своим
   каталогом `/opt/dpai-jdk21` в Linux DPmetaApp. Пакет `openjdk21-jdk`
   из Alpine — другая (musl) сборка HotSpot; для мобильного APK-пути
   больше не используется. Отдельное приложение Termux не требуется.

   Источник: [MobileStudio OpenJDK 21.0.14 ARM64/Bionic](https://github.com/MobileStudio-AndroidIDE/MobileStudio_AndroidIDE/releases/tag/jdk21-android-21.0.14),
   `jdk21-android-arm64.tar.gz`, закреплённый SHA-256
   `8746f96a348c34b1e21508128478cb613de05f9d0aa9befad2967f83a9542680`.
   Это сторонняя сборка OpenJDK, не дистрибутив Google и не официальный
   бинарный релиз проекта OpenJDK. Приложение проверяет сумму до
   распаковки и реально запускает `java` и `javac` до сообщения об успехе.
   Системные библиотеки `/system`, `/apex`, `/linkerconfig` пробрасываются
   гостю для Android linker64; `/sys` и `/dev/binder` не открываются.
3. Выполните `environment.probe` для `java` и `jdk`.
   Важно: наличие файлов не доказывает запуск JVM. При необходимости
   рантайм пробует совместимые `-XX:-UseCompressedOops -Xint`, но они
   включаются **только если обычный Java не стартует**. Если оба варианта
   дают ошибку, установщик возвращает отказ с живым stderr; Gradle
   не запускается. Если preflight пишет `targetSdk=36`, установлен старый
   APK: синхронизация `main` **не** обновляет APK на телефоне.
4. Запустите **Android SDK…** в том же Linux приложения. Этот мастер
   также ставит и проверяет Android-native JDK перед sdkmanager. Согласие
   на лицензию выбирает человек. Приложение ставит Google cmdline-tools
   **20.0**, `platforms;android-37.0`, `build-tools;36.1.0` и на ARM64
   статическую `aapt2` от AndroidIDE-Dev v35.0.2 и совместимые
   `zipalign`/`aidl`/`aapt`/`split-select` из AndroidIDEOfficial v34.0.4,
   с отдельными SHA-256. Gradle
   автоматически получает `android.aapt2FromMavenOverride`.
5. Запустите `environment.probe` для `android_sdk` либо проверку SDK
   после мастера. При ошибке не начинайте сборку; проверьте конкретный
   отсутствующий инструмент, свободное место и поддерживаемый процессор.

Пакеты, Gradle-кеши и Android SDK занимают гигабайты памяти телефона.
Для проекта с JNI/C++ дополнительно нужен **совместимый ARM64 NDK**:
официальный набор Google включает host-компиляторы x86_64 и не подходит
для выполнения на ARM64. Его наличие/совместимость проверяется отдельно,
сейчас универсальной автоматической поставки NDK нет. Это относится и к
самостоятельной пересборке DPmetaApp, в которой есть JNI.

## 3. Собрать проект

1. Откройте проект в IDE на локальном target **Linux приложения**.
2. Откройте раздел **Сборка** → шаблон **APK Android** (ставит
   `./gradlew --no-daemon assembleDebug` и потребность в Android SDK).
3. Проверьте команду и путь проекта, сохраните профиль, запустите.
4. При успехе откройте **Артефакты** и установите/экспортируйте APK;
   перед установкой сравните подпись с уже установленной версией.

Этот путь предназначен для проектов с Gradle/Android Gradle Plugin.
Наличие SDK и JVM проверяется до запуска, ошибки Gradle остаются в
истории сборки, самодельный «успех» при ошибке JVM не выдаётся.

Если до обновления был установлен Alpine `openjdk21-jdk`, удалять его
не обязательно: после успешной установки Android-native JDK его
`bin` приоритетнее в `PATH`, `JAVA_HOME` указывает на новый runtime.
Работа этого пути на Redmi Note 13 должна быть подтверждена физически;
облачная компиляция Kotlin/Android не равнозначна проверке ELF/Bionic
внутри proot на телефоне.

## 4. Физическая приёмка

На целевом устройстве нужны фактические результаты:

- `targetSdkVersion` установленного приложения действительно 28;
- `java -version`, `javac -version`, проба компиляции и `aapt2 version`;
- скачивание зависимостей Gradle, сборка Android-проекта **с ресурсами**;
- подпись APK, установка и запуск, повторная сборка после правки кода;
- отдельно — Gradle+NDK проекта с JNI, если планируется нативная разработка.

Если любой шаг не работает, локальная сборка **не считается готовой**.
GitHub Actions остаётся доступным как облачный способ собрать APK без
SSH-target, но не заменяет цель автономной сборки на самом телефоне.
