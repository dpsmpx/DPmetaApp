# Сборка APK внутри DPmetaApp

Основной DPmetaApp — мобильная студия с `targetSdk 28`: Android-проекты
собираются прямо в приложении, в собственном Alpine Linux под proot,
без отдельного Termux и обязательного SSH-target. Реальный запуск JVM
и Gradle всё ещё требует проверки на целевом телефоне (`DPmetaApp:D-189`).

## 1. Установить основной APK студии

В GitHub Actions DPmetaApp (`.github/workflows/apk.yml`) после зелёного
`full --strict` доступны два APK:

- `primary/DPmetaApp.apk` — **основная сборка**, `targetSdk 28`,
  позволяющая Android запускать программы из каталога Linux приложения;
- `modern/DPmetaApp-modern-target.apk` — дополнительная сравнительная
  сборка, `targetSdk 36`, с ограничением запуска из каталога данных.

У обоих APK неизменные `applicationId=com.dpsmpx.dpai`, название
`DP_IDE`, ключевая схема и `minSdk 30`. Смена `targetSdk` приложения-IDE
**не задаёт** `targetSdk` собираемых ею Android-проектов: каждый проект
выбирает свой целевой API в собственном Gradle-файле.

Основной вариант `primary` не предназначен для Google Play. У него более мягкие
ограничения Android на выполнение загруженного кода и иная модель
разрешений. **Оба артефакта Actions подписаны отладочным ключом**:
они не устанавливаются поверх APK с подписью владельца без пересборки
с тем же ключом. Нельзя удалять установленное приложение с данными
ради перехода на этот вариант без резервной копии!

Сборка основного APK на машине с JDK 21 и Android SDK:

```sh
DPAI_RELEASE_DEBUG_KEY=1 sh tools/build-apk.sh release
```

Для сравнительной сборки с `targetSdk 36`:

```sh
DPAI_TARGET_SDK=36 DPAI_RELEASE_DEBUG_KEY=1 sh tools/build-apk.sh release
```

Устаревшее `DPAI_ON_DEVICE_BUILD=1` остаётся совместимым, но больше
не нужно: `28` используется и при обычном `./gradlew :shell:assembleRelease`.

Для настоящего обновления приложения используйте существующий ключ
выпуска владельца (без `DPAI_RELEASE_DEBUG_KEY=1`) и сверку сертификата.

## 2. Подготовить инструменты на телефоне

1. В DPmetaApp установите **Linux в приложении**. Это собственная среда
   приложения; пакет Termux не нужен.
2. Запустите **Android SDK…** в том же Linux приложения. Установщик
   сначала разворачивает изолированный Termux-совместимый префикс из
   официального bootstrap с фиксированной SHA-256 и устанавливает
   **Android/Bionic OpenJDK 21** вместе с зависимостями. Это не использует
   установленный Termux и не заменяет Alpine, в котором работают другие
   инструменты. Пакетный менеджер Termux запускается с реальным UID приложения:
   его `pkg`/`apt-get` запрещает эмуляцию root, хотя `apk` Alpine продолжает работать
   под PRoot `-0`. `pkg` выбирает живое зеркало Termux; если bootstrap
   не содержит `pkg`, используется `apt-get` со строгой проверкой обновления
   индексов. Для Bionic под PRoot гостю пробрасывается **только** системный
   DNS-сокет Android `/dev/socket/dnsproxyd`, а не весь `/dev/socket`:
   `/etc/resolv.conf` Alpine применяется к musl, но не к Bionic. Сбой вида
   `Something wicked happened resolving` прежде не давал получить индекс
   пакетов, после чего `apt` сообщал `Unable to locate package openjdk-21`.
   `openjdk21-jdk` из Alpine не является JDK для APK-сборки.
3. Дождитесь `DPAI_NATIVE_JDK_OK` (реально запущены `java` и `javac` и
   выполнена компиляция/запуск пробного класса). После успешной установки
   ярлыки `java` и `javac` в `~/tools/bin` ведут к Bionic JDK, поэтому
   эти команды в новом терминале Linux больше не должны запускать
   Alpine HotSpot. Уже имеющиеся пользовательские ярлыки не заменяются;
   при конфликте печатается `DPAI_NATIVE_JDK_PATH_CONFLICT`.
   При ошибке сначала сохраните вывод установки и `environment.probe`
   для `android_java`, `android_javac`, `memory`. Сообщение HotSpot
   `Failed to mark memory page as executable` не доказывает PaX;
   успешная проба `mprotect` также не доказывает запуск JVM. Если
   preflight пишет `targetSdk=36`, установлено другое приложение:
   обновление Git-исходников не меняет APK на телефоне.
4. В рамках того же **Android SDK…** примите лицензию Google; после JDK
   приложение устанавливает Google cmdline-tools
   **20.0**, `platforms;android-37.0`, `build-tools;36.1.0` и на ARM64
   статическую `aapt2` от AndroidIDE-Dev v35.0.2 и совместимые
   `zipalign`/`aidl`/`aapt`/`split-select` из AndroidIDEOfficial v34.0.4,
   с отдельными SHA-256. Gradle
   автоматически получает `android.aapt2FromMavenOverride`.
5. Запустите `environment.probe` для `android_sdk` либо проверку SDK
   после мастера. При ошибке не начинайте сборку; проверьте конкретный
   отсутствующий инструмент, свободное место и поддерживаемый процессор.

Пакеты, Gradle-кеши и Android SDK занимают гигабайты памяти телефона.
Для проекта с JNI/C++ дополнительно нужен **совместимый ARM64 NDK**:
официальный набор Google включает host-компиляторы x86_64 и не подходит
для выполнения на ARM64. Его наличие/совместимость проверяется отдельно,
сейчас универсальной автоматической поставки NDK нет. Для самой DPmetaApp
есть отдельный путь: мастер SDK устанавливает Alpine clang/lld/compiler-rt
и Android sysroot, после чего JNI и PRoot собираются на ARM64 без NDK с ПК.
Это не универсальная замена NDK для других C/C++ проектов.

## 3. Собрать проект

1. Откройте проект в IDE на локальном target **Linux приложения**.
2. Откройте раздел **Сборка** → шаблон **APK Android** (ставит
   `./gradlew --no-daemon assembleDebug` и потребность в Android SDK).
   Приложение также распознаёт `assembleDebug`, `assembleRelease`,
   `testDebugUnitTest` и APK/AAB-артефакты в ранее сохранённых профилях,
   даже если в их старой версии отсутствует поле `needs`.
3. Проверьте команду и путь проекта, сохраните профиль, запустите.
4. При успехе откройте **Артефакты** и установите/экспортируйте APK;
   перед установкой сравните подпись с уже установленной версией.

### Самосборка DPmetaApp из последнего PR

1. После установки новой студии повторно выполните «Android SDK…»: кроме
   SDK/JDK нужны библиотека совместимости JVM, sysroot и нативные компиляторы.
   Проверьте `java`, `javac`, `android_sdk` через штатную диагностику.
2. Откройте существующий проект DPmetaApp на target «Linux приложения»
   и его **основное дерево**. Профили и привязку не удаляйте.
3. В «Сборка» выберите шаблон **DPmetaApp**, проверьте и сохраните профиль.
   Он выполняет release-сборку, показывает APK в артефактах и явно использует
   отладочную подпись. Для обновления студии автор переподписывает результат
   прежним ключом; ключ в репозиторий не передаётся.
4. Нажмите **Собрать последний PR**. Через `gh` на target автоматически
   выбирается самый новый открытый PR origin, включая черновики, загружается
   его точный HEAD и обновляется ветка существующей привязки. Затем запускается
   выбранный BUILD. Поле `main` вручную заменять не нужно. Только подготовка
   исходников — отдельная кнопка **Подтянуть последний PR**.
5. Для приватного репозитория заранее войдите через `gh auth login` в терминале
   Linux приложения. Сохраните правки редактора: коммит не обязателен.
   Совместимые локальные изменения и новые файлы сохраняются и входят в сборку.
   При реальном пересечении Git укажет файлы и остановит обновление, защищая
   также игнорируемые файлы. Свои коммиты в обновляемой ветке не стираются;
   при расхождении истории подготовка остановится. Если открытых PR нет — текущая ветка
   сохраняется, обычная кнопка сборки работает с ней.

Прерывание подготовки не запускает её заново при восстановлении. Ошибка записи
новой привязки сохраняет паузу контура до повторной успешной записи.

Этот путь предназначен для проектов с Gradle/Android Gradle Plugin.
Наличие SDK и JVM проверяется до запуска, ошибки Gradle остаются в
истории сборки, самодельный «успех» при ошибке JVM не выдаётся.
Для Android-профиля обязательны одновременно `java`, `javac` из
изолированного Android/Bionic JDK, `sdkmanager`, платформа SDK, build-tools,
ARM64 `aapt2` и `zipalign`. При отсутствии компонентов не следует
устанавливать Alpine `openjdk21-jdk`: используйте мастер «Android SDK…».
Запуск JDK под PRoot на каждом телефоне требует проверки на устройстве;
успех GitHub Actions не заменяет эту проверку.

### Копирование ошибок и результатов

С dev.45 в «Сборке» и «Проверках» кнопка **Копировать результат** берёт
итог и весь доступный вывод одним текстом. **Копировать вывод** берёт
весь сохранённый текст поля, включая часть, скрытую сворачиванием или
ограничением показа истории. Текст также выделяется долгим нажатием.
Такие же действия доступны для установки SDK/пакетов, зависимостей,
диагностики окружения, Git, APK/сертификатов и отладки.

Существующие маски `<redacted>` сохраняются: копирование не запрашивает
скрытые значения. Результат остаётся на экране после копирования; буфер
помечается чувствительным, без второго подтверждения поверх системного
окна Android 13+. Копируется доступная сохранённая часть журнала, а не
утраченные строки сверх пределов его хранения.

### Сохранённые компоненты и прогресс

С dev.46 Gradle и пакетные кэши общие для Linux, IDE, терминала и пульта;
прежний Gradle из Bionic home учитывается. Проверенные архивы установщиков
сохраняются; снимок Alpine не удаляет скачанные пакеты. Установка показывает
этапы, реальные проценты и известные счётчики. Полные пути, приоритет своих
переменных, обрыв и ручная очистка — [сохранение компонентов](COMPONENT_CACHE.md).
`NO-SOURCE`, `UP-TO-DATE`, `FROM-CACHE`, `SKIPPED` означают штатные состояния
задачи Gradle; предупреждения совместимости описаны в
[dev.46](releases/0.4.0-dev.46.md), сырой вывод остаётся копируемым.

## 4. Физическая приёмка

На целевом устройстве нужны фактические результаты:

- `targetSdkVersion` установленного приложения действительно 28;
- `java -version`, `javac -version`, проба компиляции и `aapt2 version`;
- скачивание зависимостей Gradle, сборка Android-проекта **с ресурсами**;
- подпись APK, установка и запуск, повторная сборка после правки кода;
- отдельно — Gradle+NDK проекта с JNI, если планируется нативная разработка.

Если любой шаг не работает, локальная сборка **не считается готовой**.
GitHub Actions остаётся доступным как облачный способ собрать APK без
SSH-target, но не заменяет цель автономной сборки на самом телефоне.
