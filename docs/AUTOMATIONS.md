# Каталог автоматизаций

Первый пакет этапа 1 ТЗ автоматизации (D-172,
`DP_AI_Orcestrator:D-215`). Каталог объединяет описание существующих
инструментов; их исполнители, настройки и файлы хранения прежние.

В IDE откройте рабочий проект → «Автоматизации». Каталог относится к
основному дереву: выбранное дерево задачи переключается явно, кнопкой.
Есть фильтр источника, параметры профиля, зависимости и уровень действия.
«Настроено» означает наличие описания, а не уже пройденную проверку
тулчейна: штатный worker проверяет её перед выполнением.

Четыре источника:

- Команды пульта из прежнего `commands.toml`. Открывается прежний экран
  команд с выбором клона, проверкой пакетов, подтверждением и журналом.
- CHECK/BUILD/RUN и операции зависимостей проекта. CHECK/BUILD можно
  вызвать прямо; RUN сохраняет реальный терминал, зависимости — своё
  подтверждение. Сохранённый профиль приоритетнее готового варианта.
- FAST/NORMAL/FULL из профиля проверки задачи. Ненастроенный уровень
  назван недоступным; приложение не придумывает для него команду.
  Проверка задачи остаётся в её прежнем интерфейсе.
- Диагностика Alpine и прежние операции менеджера пакетов. Диагностика
  читает локальную базу и потребности только выбранного проекта, без
  сети и запуска процессов. Изменения пакетов открывают «Окружение».

## API-модель

В проектном чате доступны `list_automations`, `describe_automation` и
`run_automation`. По умолчанию список короткий — только DIRECT;
`includeUi=true` добавляет действия человека, `source` фильтрует источник.
Если `nextOffset`/`nextParameterOffset` не null, есть следующая страница.
Параметры — варианты существующего профиля; без них используются текущие
настройки. Строка shell из запроса модели не исполняется.

Для вызова нужны id и ревизия из свежего описания. Изменение проекта,
target, команды, окружения или выбранных вариантов меняет ревизию.
Вызов использует фиксированный снимок; старое описание получает отказ.
Секретные варианты не включаются в схему API; сами исходные argv,
окружение и настройки SSH тоже не отправляются каталогом.

Отсутствие прав, занятое дерево, черновики и незавершённое восстановление
не обходятся. Сеанс, у которого сменился target, требует открытия заново.
Отмена проверяется до подготовки и перед start; запущенная команда
останавливается прежним механизмом, с сохранением паузы до подтверждения.
API и UI не создают второй worker или планировщик.

## Результат

Оболочка показывает `OperationResult`: статус, id, происхождение,
диагностику, данные и доказательства исполнения. Неудачная проверка —
FAILED, даже когда её полный вывод получен. У профиля сохраняются id
реального запуска, хеш вывода и ссылка на прежнюю историю.

Длинный ответ сокращается с `payloadTruncated` и `payloadHash`, без
обрыва JSON. Полный вывод профиля остаётся в его истории. Диагностика
окружения не пробует компиляторы: `commandsProbed=false`; факт наличия
объявленных зависимостей не доказывает успешную сборку.

UI-вызов живёт вне экрана в LongJobs. После перезапуска start не
повторяется: сведения о сборке/проверке — в прежней истории; диагностику
можно запросить снова. Результаты чтения не объявляют задачу завершённой.
