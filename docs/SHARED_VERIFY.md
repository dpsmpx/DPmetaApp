# Общие инструменты DP-Verify

## ПК и Termux по SSH

D-138: «AI» → target → «Настройки target» → «Общие инструменты
DP-Verify…». Сначала обновите агент dpai до версии приложения; нужны
Python 3.11+, Git и на Windows Git Bash. Проба состояния не использует
GitHub-аккаунт. Укажите абсолютный путь папки и программу Python, затем
подключите её после PIN/биометрии. Уже существующая Git-копия проходит
те же проверки origin/main и full, что новая.

Агент поставляет контроллер из своего JAR, публикует его целым файлом
с SHA-256 в имени вне папки инструментов и сохраняет прежние версии для
запущенных процессов. Неизвестные правки контроллера не затираются.
Аккаунт передаётся только по stdin SSH/контроллера; на ПК не сохраняется
и инструментам не выдаётся. Запоздалая синхронизация не отменяет
одновременное отключение: одна операция настройки на agent home,
остальные получают «занято», а status доступен.

Фон включается отдельным флажком после подключения. Раз в минуту
служба пробует синхронизацию; lease защищает запущенные инструменты.
Смена адреса, SSH-пользователя, ключа хоста, агента или пути требует
подключения заново. После остановки службы нужен новый вход; отдельного
токена в настройках нет. Отключение сохраняет папку и историю.
Приёмка Windows 11 и телефона остаётся в TODO.

## Linux в приложении

DP-Verify — отдельная изменяемая Git-папка `/root/dp-verify` в Linux
приложения. Она подключается к новым ходам Claude/Codex/Gemini target
«в приложении». Ручная настройка других target также доступна через
`dpai tools configure`; Windows-контроллер и CLI реализованы по D-137,
экран настройки удалённых target — следующий пакет. Проверка Windows 11
автора остаётся в TODO.

Windows lease проверен тем же межпроцессным набором под Windows Python
3.13.1 в Wine 10: параллельное чтение, writer, освобождение после аварии,
живая дочерняя проверка после аварии обёртки и отказ повреждённому
маркеру; также проверены буквальные аргументы Python и выбор Git Bash.
Wine не заменяет приёмку Git for Windows, ACL и разных сессий на ПК автора.

## Подключение

1. Подключить GitHub-аккаунт в пульте. Нужен доступ к DP-Verify,
   включая запись для публикации проверенных изменений.
2. В «AI» открыть Linux в приложении, установить среду при необходимости.
3. В карточке «Общие инструменты DP-Verify» нажать «Установить и подключить…»,
   подтвердить системный вход. Установятся Python/Git и сертификаты;
   первая копия пройдёт полный штатный прогон до подключения.
4. Следующий ИИ-ход получит путь и инструкции. Для проверок — `dpv` на PATH;
   другие инструменты — через `DP_VERIFY_CONTROLLER run`, правки — `edit`.

Синхронизация получает изменения GitHub и отправляет проверенные локальные
изменения прямо в main без PR/force. Автокоммиты отмечены
`DPmetaApp <dpmetaapp@localhost>`; Git config пользователя не меняется.
Разошедшаяся история требует ручного разбора: обе копии сохраняются.

## Фон и состояние

После подключения фон включён. Существующая служба контроллера повторяет
синхронизацию раз в минуту, даже без настроенных ИИ-слотов. Долгая проверка
идёт отдельно от такта ИИ; повторная установка или синхронизация параллельно
не запускается. Открытая idle-сессия не удерживает lease. Запущенный
инструмент откладывает обновление до свободной попытки.
Без ИИ-слотов служба поддерживает CPU на время установки/проверки,
а в ожидании следующей попытки отпускает wakelock; Android может отложить
минутный опрос спящего устройства.

Приложение использует существующий токен пульта под Keystore. После явного
входа по PIN/биометрии право DP-Verify остаётся только в памяти службы:
фон работает и после блокировки телефона. Остановка/перезапуск службы,
выключение фона, смена или удаление аккаунта отзывают право; для следующих
попыток нужен новый явный вход кнопкой «Синхронизировать…». Запоздалое
окно прежнего входа право не восстановит. Уже начатая операция может
закончиться со своим токеном. Дополнительного сохранения на диск нет;
прочие функции пульта сохраняют прежний срок Keystore. Если служба не
запущена, право отзывается после операции. Автоматического окна входа
из фона нет. Остановленная пользователем служба сама не поднимается;
после её явного запуска попытки возобновляются. Android может завершить
процесс/ограничить фон; непрерывная работа без службы не обещается.

Токен не записывается в папку/настройки DP-Verify, URL или аргументы процесса.
Он передаётся контроллеру через stdin, затем сетевому Git и credential
helper в окружении. Helper обслуживает только точный официальный HTTPS-путь,
HTTP redirects отключены. Проверки и ИИ этот секрет не наследуют. Это
защита от случайной утечки; процессы одного Android UID не изолированы
друг от друга и не считаются враждебными друг другу.

Состояние и SHA видны в карточке. Полный вывод неудачной проверки остаётся
в `/root/.dpmetaapp-verify/state/validation.log`, без токена аккаунта в
окружении валидатора. «Отключить» снимает подключение с новых ИИ-ходов
и фон, сохраняя папку и Git-историю. Уже запущенный ход заканчивает работу
со своей настройкой.

## Проверка на устройстве

Автоматические тесты проверяют реальные Git-репозитории, конкурентные
процессы и credential helper без сети; компиляция/Lint проверяют Android.
11 ноября 2026 код `1648084b83e5` прошёл DPmetaApp `full --strict` (26/26,
159 самотестов) и dpai `full`, включая Android API и отдельные последовательные
замеры. Контроллер/аккаунт — 41 тест, отзыв права в памяти — 3 теста.
В APK подтверждены `0.4.0-dev.23`, versionCode `40023`; контроллер в debug
и release совпадает с исходником, реализация права в памяти включена в debug.
Физическая приёмка ещё нужна:

- Первая установка, SHA проверенной версии, новый ход каждого исполнителя.
- Занятый инструмент откладывает sync; idle-сессия допускает обновление.
- Изменение с каждой стороны проходит full; конфликт/ошибка сохраняет данные.
- Фон после пяти минут и блокировки телефона; новый вход после остановки
  службы/перезапуска APK/смены аккаунта; отказ запоздалому окну входа.
- Отключение сохраняет папку и не подключает её к следующему ходу.

Решения: D-89…D-95, `DP_AI_Orcestrator:D-122`, `DP_AI_Orcestrator:D-126`.
