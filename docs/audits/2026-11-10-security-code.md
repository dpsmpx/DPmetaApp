# Аудит безопасности и ошибок кода — 10 ноября 2026

Вид: **наблюдение** на дату и **рекомендации**; задним числом не правится
(`CLAUDE.md`, «Где что лежит»). Решения — за автором; принятое
записывается в `docs/direction/DECISIONS.md` и журналы подсистем.

**Срез.** `main`, коммит `7c73993b` (9 ноября 2026). Все пути — от корня
репозитория DPmetaApp.

**Зачем.** Запрос автора 9 ноября 2026: полный глубокий аудит проекта —
информационная безопасность и прочие ошибки кода; итог — документом в
отдельной ветке без файлов проекта.

**Как проверялось.** Чтение кода (без сборки и без прогона тестов);
утверждения о поведении библиотек и ОС, на которых держатся две главные
находки, проверены опытом (раздел 7, «Опыты»). Уже известное по `TODO.md` и
прежним аудитам заново не открывалось — только там, где заявленная
защита на деле обходится; такие пункты помечены «заявлено — в коде».
Что прочитано целиком, что выборочно и что не смотрелось — раздел 7:
объём репозитория (около 180 тыс. строк, 6 подсистем) больше одного
прохода, и «не найдено» там, где чтение было выборочным, не значит
«нет».

**Шкала.** Высокая — обход заявленной границы безопасности с понятным
сценарием и без особых условий. Средняя — обход с условиями
(скомпрометированная сессия модели, действие человека) или ошибка,
которая молча искажает данные. Низкая — усиление защиты, надёжность,
расхождение кода с документом. Инфо — наблюдение без требования правки.

## 2. Корень: `core/`, `app/`, `shell/`, `cli/`

### K-01 — Средняя — «основная ветка» клона берётся из того, что пишет гость (обход меры T19)

- **Где.** `core/git/src/main/kotlin/com/dpsmpx/dpmeta/git/Clones.kt:156-166`
  (`fetch`), `:231-239` (`mainOf`);
  `app/src/main/kotlin/com/dpsmpx/dpmeta/app/data/PultRepository.kt:198-239`
  (`ecosystemManifest`), `:436` (`trustHost`).
- **Заявлено** (`dpai/docs/SECURITY_MODEL.md`, T19): реестр и очередь
  DPmeta для манифеста «AI» читаются из клона DPmetaApp «только на
  коммите, который назвал GitHub при последней синхронизации пульта
  (`ls-remote`, голова хранится в данных пульта, не в клоне), а не по
  ссылкам клона».
- **В коде.** SHA действительно берётся из ответа `ls-remote`, но *для
  какой ветки* — решает `mainOf(repo)`: сначала `dpmeta.main` из
  `.git/config` клона, затем цель `origin/HEAD`, затем `main`. И конфиг,
  и ссылки клона гость Linux пишет (`D-72`; комментарий в `fetch`:
  «конфиг клона правит и git гостя»). Дальше
  `mainSha = remoteRefs.firstOrNull { it.name == R_HEADS + main }` →
  `trustHost(sha)` → `fileAt(host, sha, REGISTRY)` и очередь.
- **Сценарий.** Сессия модели под prompt injection в `/root/repos`:
  (1) пушит в `dpsmpx/DPmetaApp` ветку `x` со своим
  `dpmeta/tools/ecosystem.toml` и очередью DPmeta — это её обычная
  работа; (2) `git config dpmeta.main x` в клоне (ссылка `origin/x` там
  уже есть после `git fetch`). При следующей синхронизации пульт
  запишет «доверенной головой» голову ветки `x`; сверка объектов по
  хешу (`verified`) проходит — объекты настоящие. Манифест `dpai.ecosystem`
  собирается из подложенных реестра и очереди; при включённой политике
  прогона (`D-106`) цели задач уходят в работу без взгляда человека.
  Выход из proot не нужен — в отличие от остатка, принятого в T13.
- **Рекомендация.** Имя основной ветки брать из ответа GitHub при каждом
  обновлении — `HEAD` из `ls-remote` (как уже сделано в `clone()`,
  строки 134-137) — и хранить рядом с доверенным SHA в данных пульта;
  `dpmeta.main` и `origin/HEAD` клона оставить только для показа
  документов. Добавить образец в `ClonesTest`: подменённый `dpmeta.main`
  не меняет доверенную голову.
- **Уверенность.** Подтверждено чтением кода; на устройстве не
  воспроизводилось.

### K-02 — Средняя — `url.*.insteadOf` в конфиге клона уводит обновление мимо пропуска сети (D-10)

- **Где.** `core/git/…/Clones.kt:161-173`.
- **Заявлено** (KDoc класса): «Сеть — только через `gate`… адрес
  проверяется до любого обращения JGit»; в `sync` — «у `git://`, `file:`
  и локальных путей JGit свои сокеты — мимо пропуска HTTP», поэтому
  схема адреса проверяется.
- **В коде.** Проверяется адрес-аргумент. Но `git.fetch().setRemote("origin")`
  строит адрес из `RemoteConfig` клона, а тот применяет подстановки
  `url.<база>.insteadOf` из того же `.git/config`. Строка
  `[url "git://host/"] insteadOf = https://github.com/` превращает
  проверенный `https://github.com/…` в `git://host/…`: JGit берёт
  `TransportGitAnon` — собственный сокет, `GatedFactory` о нём не знает.
  Так же достижимы `amazon-s3://` (свой `HttpURLConnection`, тоже мимо
  фабрики) и локальный путь. `Isolated` закрывает пользовательский и
  системный `gitconfig`, но не конфиг самого клона. `lsRemoteRepository`
  подстановок не применяет — расходятся «спросили у GitHub» и «скачали
  оттуда, куда указал конфиг».
- **Сценарий.** Тот же гость. Процесс приложения открывает соединение с
  произвольным хостом вне списка `:core:net` и принимает оттуда объекты
  и ссылки `origin/*`. Токен при этом не утекает (у `git://` нет
  учётных данных, чужой `https` пропуск по-прежнему режет), но
  инвариант `D-10` «приложение ходит только по списку» нарушен, а
  вместе с K-04 под ударом оказывается разбор XML в транспорте S3.
- **Рекомендация.** Не обновлять по имени `origin`: передавать адрес
  явно (`setRemote(remote.toString())` — у адреса-строки JGit
  подстановок не делает, проверено) и перед вызовом сверять схему
  итогового `URIish`; либо перед `fetch` удалять из конфига клона
  секции `url.*`. Образец в `ClonesTest`.
- **Уверенность.** Подстановка и выбор `TransportGitAnon` проверены
  опытом на JGit 5.13.3 (раздел 7); `amazon-s3` и локальный путь — по
  составу библиотеки, без прогона.

### K-05 — Низкая — надёжность — непечатный `ETag` навсегда ломает запросы адреса

- **Где.** `core/net/src/main/kotlin/com/dpsmpx/dpmeta/net/Net.kt:136,146`;
  `UrlTransport.kt:15-17`, `JdkTransport.kt:25-27`.
- **Что.** `Net.get` кладёт в кэш любой `ETag` ответа 200. Следующий
  запрос добавляет `If-None-Match` с этим значением, а транспорт
  отказывает на любом заголовке с непечатным знаком (`VALUE_INVALID`) —
  до сети дело не доходит, запись в кэше не обновится никогда
  (`StoredEtagCache` хранит её между запусками).
- **Рекомендация.** Проверять `etag` тем же `printable` перед
  `cache.put`; отказ транспорта по заголовку `If-None-Match` — повод
  выбросить запись и повторить без неё.

### K-06 — Низкая — надёжность — кэш ETag растёт без предела

- **Где.** `core/sync/src/main/kotlin/com/dpsmpx/dpmeta/sync/StoredEtagCache.kt:22-30,45-53`.
- **Что.** Документ `etags` хранит тела всех когда-либо запрошенных
  адресов (включая коммиты по SHA и записи прежних токенов — отпечаток
  токена входит в ключ) и переписывается целиком при каждом сохранении;
  вытеснения нет. `Base64.getDecoder().decode` в `init` на испорченной
  строке бросает `IllegalArgumentException` — синхронизация падает
  отказом «прервана» при каждом запуске, пока данные не стёрты.
- **Рекомендация.** Предел числа и объёма записей с вытеснением старых;
  при смене токена — чистка; испорченная запись — пропуск, а не
  исключение.

### K-07 — Низкая — ошибка — исключения JGit мимо `Outcome`

- **Где.** `core/git/…/Clones.kt:353-363` (`withRepo`), `:318-328`
  (`file`, `size`), `:257-267` (`last`).
- **Что.** `withRepo` ловит `IOException` и `JGitInternalException`.
  `Repository.resolve("…origin/$branch^{tree}")` на имени с `^`, `~`,
  `:`, `@{` бросает `RevisionSyntaxException` (наследник
  `IllegalArgumentException`); `ObjectLoader.getBytes()` на большом
  объекте — `LargeObjectException` (`RuntimeException`). Предел размера
  стоит только у `localDocument` (2 МБ); `CloneReader.file` читает
  документы процесса без предела. Сейчас это гасят `runCatching` выше
  по стеку — человек видит «INTERNAL_ERROR: имя класса» вместо причины,
  а один огромный файл в клоне роняет всю синхронизацию.
- **Рекомендация.** В `withRepo` — ещё `IllegalArgumentException` и
  `LargeObjectException` с понятным отказом; `size()` перед `file()` в
  `CloneReader`.

### K-08 — Низкая — надёжность — регулярные выражения из данных

- **Где.** `core/model/…/Registry.kt:39`, `core/formats/…/ProcessFormats.kt:55`,
  `core/formats/…/PanelFormat.kt:109`, `app/…/screens/Panels.kt:31`.
- **Что.** Шаблон номера решения приходит из реестра (а до первой
  синхронизации — из клона, который пишет гость:
  `PultRepository.localRegistry`) и компилируется как есть, затем
  применяется к каждой строке документа. Шаблон с вложенными повторами
  подвешивает разбор. Там же `COMMENT = <!--.*?-->` с
  `DOT_MATCHES_ALL` — квадратичное время на документе с множеством
  незакрытых `<!--`.
- **Рекомендация.** Предел длины и состава шаблона (как `GLOB` у
  панели), разбор — с пределом времени вне главного потока.

### K-09 — Инфо — блокировка приложения скрывает окна прозрачностью

- **Где.** `app/src/main/kotlin/com/dpsmpx/dpmeta/app/AppLock.kt:52-79`;
  `PultActivity.kt:87,188-193,210-221`.
- **Что.** До входа окно пульта и «AI» уже создано и собрано, спрятано
  `alpha = 0`, поверх — `LockActivity`. Содержимое остаётся в дереве
  представлений (его читают службы специальных возможностей), а между
  `onResume` окна и показом экрана входа окно принимает касания. На
  Android 11–12 снимок в «недавних» остаётся прежним (документ это
  называет). `entrySync` запускает синхронизацию с токеном до ввода PIN,
  если ключ Keystore ещё открыт разблокировкой телефона, — так и
  задумано (`D-59`), но «вход на всё приложение» сеть не закрывает.
- **Рекомендация.** По желанию: до входа не вызывать `setContent`
  (или ставить `FLAG_NOT_TOUCHABLE` вместе с прозрачностью).

## 3. Подсистема «AI» (`dpai/`)

### A-01 — Средняя — диск приложения: секреты прячутся по списку имён, и список неполон

- **Где.** `dpai/ui/src/main/kotlin/com/dpsmpx/dpai/ui/AppDisk.kt:43-53`
  (`hidden`); `dpai/android/…/AppDiskProvider.kt`.
- **Заявлено.** «Секретов на диске нет вовсе: ни в списках, ни по прямому
  пути» (`AppDisk`, `D-96`); уведомление: «Файлы DPmetaApp видны
  менеджерам файлов (без секретов)».
- **В коде.** Скрыты `control-token`, `.ssh`, `.credentials.json`,
  каталоги слотов `.claude-slot-N`/`.codex-slot-N`/`.gemini-slot-N` и
  `.config/llama`. Не скрыты обычные места секретов в домашней папке
  гостя, где работают модели и терминал: `.config/gh/hosts.yml` (токен
  `gh`), `.git-credentials`, `.netrc`, `.npmrc`, `.pypirc`,
  `.codex/auth.json` и `.gemini/` вне слотов, `.claude.json`,
  `.gnupg/`, `.bash_history`/`.ash_history`, `.env`. Те же имена
  `dpai/tools/verify/check_secrets.py` уже считает секретными для
  репозитория.
- **Сценарий.** Диск открыт человеком (отметка живёт до «Закрыть», срока
  нет) — любой менеджер файлов, которому раз выдан доступ к корню,
  читает токен GitHub гостя. Блокировка приложения (PIN) этот путь не
  закрывает.
- **Рекомендация.** Перевернуть правило для домашней папки гостя: всё,
  что начинается с точки, скрыто, кроме короткого списка разрешённого;
  плюс срок жизни отметки «открыт».
- **Уверенность.** Подтверждено чтением кода; есть ли такие файлы у
  автора — зависит от того, как в госте настроен вход в GitHub.

### A-02 — Низкая — канал `dpai`: политика задач и новые задачи — не «решающее»

- **Где.** `dpai/orchestrator/…/control/ControlApi.kt:261-268`

- **Что.** По `D-91` канал не отличает автора от сессии под prompt
  injection, поэтому «да» на слияние и исключение задачи подтверждаются
  на телефоне. Но `task.policy` с `reviews: []` (снять все роли ревью,
  `D-73`), смена `taskClass`, `task.add` с произвольной целью,
  `task.move` на другой target и `control.session-limit` проходят сразу.
  Политику идущей задачи менять нельзя (`EDITABLE`), так что своё ревью
  сессия не снимет, — но снимет у задач в очереди и поставит новые без
  ревью.
- **Рекомендация.** Ослабление проверки (меньше ролей ревью, класс ниже)
  и перенос на другой target из канала — тоже через подтверждение на
  телефоне; усиление — сразу.

### A-03 — Низкая — диск приложения: усечение файла раньше проверки настоящего пути

- **Где.** `dpai/android/…/AppDiskProvider.kt:115-147` (`openDocument`).
- **Что.** `Os.open` с `O_CREAT|O_TRUNC` выполняется до сверки
  `readlink(/proc/self/fd/N)`. `O_NOFOLLOW` защищает только последнюю
  часть пути; подмена промежуточного каталога ссылкой между `path()` и
  `open` (гонка, T15) даст отказ — но файл по ту сторону ссылки уже

## 4. DPpass (`dppass/`)

### 4.1. Оболочки для ПК

### L-01 — Высокая — к JVM с `CAP_NET_ADMIN` подключается любой процесс пользователя

- **Где.** `dppass/desktop/build.gradle.kts:34-40`
  (`applicationDefaultJvmArgs` — без `-XX:+DisableAttachMechanism`);
  `dppass/desktop/package/dppass-launch` (последняя строка — `setpriv …
  --ambient-caps=-all,+net_admin … dppass-desktop`); для сравнения —
  `dppass/tools/desktop/windows_package.py:71` и
  `dppass/docs/SECURITY_MODEL.md:614`: у Windows флаг есть.
- **Заявлено** (`dppass/docs/SECURITY_MODEL.md`, T17): «процессы того же
  пользователя не подключаются к нему отладчиком и не читают его память
  (у цели больше возможностей)».
- **В коде.** Про `ptrace` и `/proc/<pid>/mem` это верно. Но HotSpot сам
  принимает подключение от процесса с тем же uid: сигнал `SIGQUIT`
  (для него возможности цели не важны) и сокет `/tmp/.java_pid<pid>`.
  `jcmd <pid> JVMTI.agent_load <файл.so>` загружает произвольную
  библиотеку в процесс окна.
- **Сценарий.** Любая программа под учётной записью пользователя
  (расширение, скрипт сборки, пакет npm) ждёт запущенный DPpass и
  исполняет код с `CAP_NET_ADMIN`: маршруты, правила nftables,
  интерфейсы, перенаправление трафика всего ПК. Пароль администратора не
  спрашивается — его уже ввели при запуске. `auth_admin_keep` в
  `com.dpsmpx.dppass.policy` ещё и позволяет несколько минут запускать
  окно без пароля.
- **Рекомендация.** `-XX:+DisableAttachMechanism` в
  `applicationDefaultJvmArgs` (заодно `-XX:-UsePerfData` — не оставлять
  `/tmp/hsperfdata_*`); проверка `DesktopLaunchTest` — что флаг есть в
  сценарии запуска, как `windows_package.py` сверяет флаги запускателя.
  Подумать об `auth_admin` вместо `auth_admin_keep`.
- **Уверенность.** Подтверждено опытом (раздел 7): OpenJDK 21, цель —
  с `CapEff = net_admin` под `setpriv` с теми же ключами, подключение
  — тем же uid без возможностей; `/proc/<pid>/environ` при этом
  недоступен, а `jcmd` отвечает. Сама загрузка библиотеки
  (`JVMTI.agent_load`) не выполнялась — это штатная команда того же
  канала.

### P-01 — Средняя — ошибка — обновление подписки пишет список по устаревшему снимку

- **Где.** `connection/src/main/kotlin/com/dpsmpx/dppass/connection/Subscriptions.kt:243-306`
  (`refresh`); `Activation.kt:95` (`state` без замка).
- **Что.** `refresh()` читает состояние, уходит в сеть и активацию (до
  десятков секунд) и в конце записывает **весь** список:
  `commit(st.copy(items = st.items.map { … }))`. Замка в
  `SubscriptionService` нет. Правка, сделанная за это время на экране,
  затирается фоновым обновлением (`SubscriptionJobService`): удалённая
  подписка возвращается, выключенный идентификатор устройства
  (`x-hwid`) снова включён и уйдёт поставщику — без следа на экране.
- **Рекомендация.** Один `Mutex` на службу подписок и на
  `activate`/`rollback`/`restore`; после сети перечитывать состояние и
  менять только свою запись. Тест: правка во время приостановленной
  загрузки.
- **Уверенность.** Подтверждено чтением кода; окно — время загрузки, на
  практике не воспроизводилось.

### P-02 — Средняя — переподключение закрывает TUN раньше, чем поднят новый

- **Где.** `app/src/main/kotlin/com/dpsmpx/dppass/app/DPpassVpnService.kt:229-234`
  (`restart`: `shutdown()` → `start()`), `:850-869` (`shutdown`:
  `tunnel?.close()`), `:830-835` (`fail` → `stopSelf()`).
- **Что.** Любое переподключение — по наблюдателю сети, раздаче,
  обновлению подписки — сначала закрывает интерфейс VPN. Пока новое
  подключение проходит проверку здоровья, трафик приложений идёт мимо
  туннеля; неудача оставляет телефон без туннеля вовсе. В T4
  (`docs/SECURITY_MODEL.md`, «Трафик мимо туннеля») этого остатка нет.
- **Рекомендация.** Поднимать новый интерфейс до закрытия прежнего
  (`VpnService.Builder.establish()` заменяет интерфейс без разрыва) или
  держать блокирующий TUN на время переподключения; до тех пор —
  записать остаток в T4 и сказать на экране про системную «Блокировать
  соединения без VPN».
- **Уверенность.** Подтверждено чтением кода; длительность окна на
  устройстве не измерялась.

### P-03 — Средняя — ошибка — дескриптор TUN теряется при отмене и при неожиданном исключении

- **Где.** `app/…/DPpassVpnService.kt:319-375` (`connect`), `:254-264`
  (`connectOrFail`).
- **Что.** `establish()` возвращает `handle`, но `try`, который закрывает
  его при отмене, начинается позже — после `NetworkCheck.regime`,
  `core.share.current()` и приостанавливающего `tetherForConnect()`.
  Отмена в этом промежутке, как и любое исключение, пойманное
  `connectOrFail` (`fail()` дескриптор не закрывает), оставляет
  интерфейс VPN без ядра: у приложений нет сети, пока дескриптор не
  соберёт сборщик мусора.
- **Рекомендация.** `try/finally` сразу после `establish()`: всё, что не
  передало `handle` сеансу, закрывает его.
- **Уверенность.** Подтверждено чтением кода.

### P-04 — Средняя — устройство раздачи: пароль уходит шлюзу любой сети

- **Где.** `app/src/main/kotlin/com/dpsmpx/dppass/app/RelayNetworks.kt:59-105`
  (`locate`, `check`); `connection/…/Relay.kt:358-371` (`Socks5Login.check`).
- **Заявлено** (`docs/SECURITY_MODEL.md`, T15): «спрашивается только шлюз
  своих сетей, и отвечает лишь вход, знающий логин и пароль».
- **В коде.** У устройства без сохранённого адреса кандидаты — шлюзы
  всех подключённых сетей. Каждому отправляются логин и пароль SOCKS5
  (RFC 1929, открытым текстом), а «вход найден» — это два байта ответа
  сервера: знать пароль ему не нужно. Шлюз чужой сети (кафе, гостиница),
  слушающий порт раздачи, получает пароль и становится «устройством
  раздачи» — трафик идёт через него.
- **Рекомендация.** Искать только в сети, где устройство было сопряжено
  (запоминать BSSID или подсеть и адрес); взаимная проверка —
  запрос-ответ на общем секрете вместо пароля в открытом виде; до тех
  пор — поправить текст T15.
- **Уверенность.** Подтверждено чтением кода; канал без шифрования в T15
  признан, подмена шлюзом — нет.

## 5. Сайт и инструменты (`socialmediaimage/`, `dpvisualisation/`, `dpmeta/`, `dpprofile/`, `tools/`)

### S-01 — Низкая — команда выгрузки сайта читается из файла репозитория

- **Где.** `socialmediaimage/tools/cs/site/deploy.py:161-167`.
- **Что.** При `deploy.kind: command` список аргументов из

### S-02 — Низкая — у сайта нет ни перевода на HTTPS, ни HSTS

  список путей — в `tools/check`.

## 6. Что проверено и в порядке

- **Манифесты Android** (`shell/`, `app/`, `dpai/android/`): наружу —
  только вход лаунчера и `AppDiskProvider` под `MANAGE_DOCUMENTS`;
  приёмники и службы не экспортированы; резервные копии и перенос
  выключены целиком (`data_extraction_rules.xml`); открытого HTTP нет
  (`usesCleartextTraffic` не задан).
- **Токен пульта** (`SecretStore`): AES-256-GCM, ключ Keystore с
  требованием входа, IV от Keystore, шифротекст в `noBackupFilesDir`;
  поле ввода — «пароль», без `rememberSaveable`.
- **Сеть корня** (`:core:net`): список адресов, запрет учётных данных в
  адресе, переадресации выключены в обоих транспортах, текст исключений
  с заголовками в диагностику не идёт; пути GitHub кодируются по
  частям, `..` отвергается.
- **Клоны**: каждое HTTP-соединение JGit и переадресации — через пропуск;
  отключить проверку TLS из конфига нельзя (`Verified`); удаление без
  перехода по ссылкам; чтение на доверенном коммите со сверкой хеша
  каждого объекта (`fileAt`) — сама сверка сделана верно, слабое место
  — выбор коммита (K-01).
- **Канал `dpai`**: HMAC-SHA256 над методом, путём, временем, значением
  и телом; сравнение за постоянное время; окно времени и запрет повтора;
  отказ запросам с `Origin` и чужим `Host` (DNS rebinding); пределы
  заголовков, тела, соединений и времени.
- **Облачная копия**: PBKDF2-HMAC-SHA256 (600 000, пределы при чтении),
  AES-256-GCM, заголовок — связанными данными; пути архива — только в
  разрешённых корнях, без `..`; политика прогона в копию не идёт.
- **Адреса провайдеров** (`ProviderHosts`): HTTPS; HTTP — только частные
  адреса числом, с ключом — только loopback.
- **SSH**: `StrictHostKeyChecking=yes`, `BatchMode=yes`, `--` перед
  хостом; кавычки POSIX корректны.
- **Запуск DPpass для Linux** (`dppass-launch`): `PKEXEC_UID` и
  переменные окна проверяются, окружение сбрасывается, ограничивающий
  набор — одна возможность, `no-new-privs` — кроме L-01.
- **Сайт**: CSP `script-src 'none'` и своя для раздела экосистемы;
  просмотрщик (`dpvis.js`, `dpvisualisation/viewer/`) — только
  `textContent`, без `innerHTML`, `eval` и внешних адресов; разметка
  канона экранирует текст и ссылки; корневой `.htaccess` закрывает
  репозиторий.
- **Инструменты на Python** (все подсистемы, кроме копии DP Verify):
  процессы — списком аргументов, `shell=True`, `eval`, `pickle`,
  небезопасного `yaml.load` и отключённой проверки TLS нет.
- **Сборка**: суммы Gradle-обёртки, command-line tools, minirootfs и
  proot закреплены; ключей и токенов в дереве нет.

**Опыты.**

1. *JGit и `insteadOf`* (K-02). JGit 5.13.3: в конфиг нового репозитория
   записаны `remote.origin.url = https://github.com/dpsmpx/DPmetaApp.git`
   и `url."git://127.0.0.1:9/".insteadOf = https://github.com/`.
   `RemoteConfig(…, "origin").getURIs()` → `git://127.0.0.1:9/dpsmpx/DPmetaApp.git`;
   `Transport.open(repo, "origin")` → `TransportGitAnon`; `fetch` —
   `Connection refused` от этого адреса. `Transport.open(repo,
   "https://github.com/…")` — `TransportHttp`, без подстановки.
2. *Подключение к JVM с возможностью* (L-01). OpenJDK 21: процесс Java
   запущен `setpriv --reuid=65534 --inh-caps=-all,+net_admin
   --ambient-caps=-all,+net_admin --bounding-set=-all,+net_admin
   --no-new-privs --reset-env`; `/proc/<pid>/status` — `CapEff:
   0000000000001000`. Из процесса с тем же uid и пустым набором
   возможностей: чтение `/proc/<pid>/environ` — отказ; `jcmd <pid>
   VM.version` — ответ JVM.

## 8. С чего начать

1. **L-01** — одна строка во флагах JVM и проверка в тесте запуска.
2. **K-01** и **K-02** — одно изменение в `Clones.fetch`: имя основной
   ветки и адрес — из ответа GitHub и аргумента, не из конфига клона; два
   образца в `ClonesTest`; заодно **K-04** и **K-07**.
3. **P-03**, затем **P-02** и **P-04** — жизненный цикл TUN и поиск
   устройства раздачи; **P-01** — замок на службе подписок.
4. **A-01** — правило «скрыто всё с точки» для домашней папки гостя.
5. **K-03** — страницы или честный отказ «список неполон».
6. **B-01** — сверка зависимостей до первого выпуска с ключом автора.
7. Остальное — по мере работы в соответствующих модулях; **A-02**,
   **S-01** и **B-04** требуют решения автора, а не только правки.
