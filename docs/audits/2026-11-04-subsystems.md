## 2. Ещё не решено — оценка

### 2.1. Verification — DP-Verify

- **Сейчас.** Отдельный закрытый проект: 1.0.0-rc2, этапы 0–7, выпуск 1.0.0
  — этап 8 (`DPmeta:docs/ECOSYSTEM.md`). Копия — в `dppass/tools/dpv/`
  по его лицензии (D-47); `tools/check/` корня — по его идеям, без кода
  (D-16); пульт читает его итог `dpv report` в разделе «Проверки» PR
  (F-15).
- **Отношение.** Инструмент проверок на машине разработки и в сессиях,
  не функция телефона: в APK ему делать нечего.
- **Рекомендация:** отдельный проект; приложение читает его отчёты
  (уже так) и после 1.0 подключает его обязательный набор вместо своих
  общих проверок (`TODO.md`, «DP Verify 1.0»). Домен Verification —
  «показывать итог проверок», а не переносить DP-Verify.

### 2.2. Market — DP_game_market_analytic_system

- **Сейчас.** Python, CLI `dpm`, SYSTEM 0.3.0 (pre-release), 358 тестов;
  последний коммит — 16 октября 2026 (`DPmeta:docs/ECOSYSTEM.md`).
  Наблюдения → факты → метрики → гипотезы → решения; не скрейпер и не
  обёртка над LLM. Место в реестре — `core`.
- **Отношение.** Самостоятельная аналитическая система; в приложении нужен
  разве что итог — `DecisionReport` и фаза работы (ТЗ, приложение А:
  `DP_game_market_analytic_system:docs/HANDOFF.md`, журнал `ADR-\d+`).
- **Рекомендация:** наблюдаемый проект, как DPlearn: карточка, фазы,
  решения; перенос кода не нужен — на телефоне анализ рынка не
  запускается. Если анализ нужен в приложении — запуск `dpm` в
  Linux-среде приложения (`DP_AI_Orcestrator:D-75`) по команде, а не
  перенос на Kotlin.

### 2.3. Monetization — DPmonetization

- **Сейчас.** «Strategic Project Intelligence»: анализ портфеля — стадии и
  шлюзы готовности, ценность, монетизация. В `main` — прерванный каркас
  ядра без тестов, README из одного заголовка, нет `CLAUDE.md` и журнала
  решений (`DPmeta:SQ-22`); работы нет с 5 октября 2026. Место —
  `support`.
- **Отношение.** Его план (реестр проектов по фактам DPmeta, отчёты
  DP-Verify и DP_game_market_analytic_system, стадии готовности) почти
  целиком совпадает с тем, что DPmetaApp уже делает или делает на
  этапе 4: состояние проектов, метрики и история чисел (D-34),
  статистика (ТЗ, §8).
- **Рекомендация:** не заводить вторую систему портфеля: стадии и шлюзы
  готовности — метриками этапа 4 DPmetaApp (`Rules.kt`), а
  DPmonetization — архивом или идеей со ссылкой. Если монетизация —
  отдельная цель (цены, доходы), — отдельный вопрос о её данных.

## 3. Общее для подсистем на Python

SocialMediaImage, DPvisualisation, DPmeta и DPprofile переехали кодом
(D-43), но их инструменты — Python, и в APK они не входят. В приложении
уже есть своя Linux-среда (Alpine в proot, `DP_AI_Orcestrator:D-75`,
`DP_AI_Orcestrator:D-82`), где работают `claude`, Codex и Gemini.

**Рекомендация:** «что может работать в приложении» (D-35) для них —
запуск их же команд проверки и сборки в Linux-среде приложения по
кнопке, а не перенос на Kotlin: один код, одна проверка, без второго
источника истины. На Kotlin — только чтение их данных пультом (схема,
факты, прогресс), как уже сделано для README и ROADMAP. Это отдельное
решение автора; выгрузки сайта оно не открывает (D-40, D-48).
