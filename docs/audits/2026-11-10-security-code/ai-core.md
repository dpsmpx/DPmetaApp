## Находки (итоговый вид; пополняется по модулям)

Пути — от корня репозитория. Опыты — `scratchpad/exp-core/R.java` (перенос шаблонов `Redactor` на `java.util.regex`), `P.java` (модель стоимости пути в `JsonParser`).

### C-01 — Средняя — утечка секретов (T8): правило «имя=значение» не видит имён с `_` перед словом
- Место: `dpai/core/src/main/kotlin/com/dpsmpx/dpai/core/diagnostics/Redactor.kt:115-119`.
- Цитата: `"(?i)\\b(password|passwd|pwd|secret|…|token|…|api[_-]?key|…)" + "(\\s*[=:]\\s*)(\"?)(?!<redacted)[^\\s\"&,;]+"`.
- Что не так: `\b` — граница слова, а `_` — знак слова. В `DB_PASSWORD=…`, `GITHUB_TOKEN=…`, `OPENAI_API_KEY: …`, `my_secret=…`, `aws_secret_access_key = …` перед `PASSWORD`/`TOKEN`/`API_KEY`/`secret` границы нет, а с начала имени (`DB_`, `GITHUB_`) ни одна альтернатива не начинается — пара не распознаётся. Опыт: `DB_PASSWORD=hunter2` → без изменений; `OPENAI_API_KEY: abc` → без изменений; `my_secret=abc` → без изменений (и STANDARD, и STRICT). Спасают только «известный вид» токена или длина 32+ (24+ в STRICT) с цифрой.
- Сценарий: шаг проверки или Claude печатает окружение/`.env` (`env`, `printenv`, `cat .env`, трассировка CI) — строки `ИМЯ_PASSWORD=короткий пароль` уходят в `TARGET_PROCESS_OUTPUT` журнала (`AgentRuntime.kt:242`), в журнал приложения, в облачную копию контура, в `Diagnostic` (сообщения исключений).
- Рекомендация: убрать `\b` в пользу `(?<![A-Za-z0-9])` и разрешить префикс имени: `(?<![A-Za-z0-9])([A-Za-z0-9_.-]*?(?:password|…))`; добавить образцы `DB_PASSWORD=`, `GITHUB_TOKEN=`, `X_API_KEY:` в `RedactorTest`.
- Уверенность: высокая (воспроизведено опытом на тех же шаблонах). По документам не известно: `SECURITY_MODEL.md` T8 называет `Redactor` защитой без оговорок.

### C-02 — Средняя — утечка секретов (T8): секретное поле JSON не распознаётся по имени ключа
- Место: `…/diagnostics/Redactor.kt:62-76` (`redactLine`, `redactValues`) и шаблон `SECRET_PAIR` (115-119).
- Цитата: `is JsonObject -> JsonObject(v.fields.mapValues { redactValues(it.value) })` — имя ключа в правку не участвует; в сыром тексте между именем и `:` стоит кавычка, и `(\s*[=:]\s*)` не совпадает.
- Что не так: `{"password":"hunter2"}`, `"api_key": "abcdef12345"`, `{"token":"…"}` проходят без изменений и как строка JSON (`redactLine`), и как свободный текст (`redact`). Опыт: обе формы — без изменений в STANDARD и STRICT.
- Сценарий: ответ API/конфиг/вывод инструмента в JSON с коротким секретом (пароль БД, PIN, токен < 32 знаков, токен из одних букв) → журнал событий хода, уведомление (STRICT), диагностика.
- Рекомендация: в `redactValues` для ключей из списка секретных имён (по тому же списку, сравнение без регистра, по подстроке) заменять строковое значение целиком; в `SECRET_PAIR` допустить `"?` между именем и разделителем.
- Уверенность: высокая (опыт). По документам не известно.

### C-03 — Низкая — утечка секретов (T8): правило пары вырезает только первое «слово» значения
- Место: `…/diagnostics/Redactor.kt:118` (`[^\s"&,;]+`), `:114` (`BEARER`).
- Что не так (опыт): `Authorization: Basic dXNlcjpodW50ZXIy` → `Authorization: <redacted> dXNlcjpodW50ZXIy` (вырезано слово `Basic`, логин:пароль в base64 остался — он обычно короче 32 знаков); `Cookie: sid=abc123; csrftoken=zzz999` → `Cookie: <redacted>; csrftoken=zzz999`; `token: my secret words` → `token: <redacted> secret words`; `passphrase: …`, `pass=…` — имён в списке нет.
- Сценарий: трассировка HTTP (`curl -v`, журнал прокси) в выводе шага проверки.
- Рекомендация: отдельные правила для `Authorization:\s*\S+\s+\S+` (любая схема) и для заголовков `Cookie`/`Set-Cookie` (до конца строки); добавить `pass(phrase)?`.
- Уверенность: высокая (опыт). По документам не известно.

### C-04 — Низкая — утечка секретов (T8): эвристика «путь» и требование цифры пропускают настоящие ключи
- Место: `…/diagnostics/Redactor.kt:83-91` (`looksLikeToken`), `:79` (исключение `sha256:`).
- Цитата: `if ('/' in v && v.split('/').all { it.length < 24 || TYPED_ID.matches(it) || UUID.matches(it) }) return false`; `if (!strict && !v.any(Char::isDigit)) return false`.
- Что не так: (а) base64 со `/` считается путём, если каждый кусок короче 24: 40-значный секретный ключ AWS со `/` ближе к середине (≈12 % ключей) не вырезается ни в STANDARD, ни в STRICT (опыт: `wJalr…/K7MDENG…/…KEYz` — без изменений, в том числе после `aws_secret_access_key = `, см. C-01); (б) STANDARD не трогает последовательность 32+ из одних букв (опыт: `hf_` + 34 буквы — без изменений; токены Hugging Face и часть base64 без цифр); (в) любая последовательность сразу после `sha256:` не проверяется вовсе — префикс выключает правило; (г) параметр запроса `key=` (Gemini API кладёт ключ так) в списке имён отсутствует — короткий ключ в URL не вырезается (настоящий `AIza…` ловит правило известных видов).
- Рекомендация: «путь» признавать только если в сегментах нет знаков `+`/`=` и строка не похожа на base64 (длина кратна 4, высокая энтропия), либо начинается с `/`, `./`, `~`, буквы диска; для `sha256:` требовать ровно 64 hex; в STANDARD не требовать цифру у последовательностей 40+.
- Уверенность: высокая по коду и опыту; оценка 12 % — расчёт. По документам не известно.

### C-05 — Средняя — отказ в обслуживании: строгий разбор JSON квадратичен по «длина ключа × число элементов»
- Место: `dpai/core/src/main/kotlin/com/dpsmpx/dpai/core/serialization/JsonParser.kt:98` и `:129`; вход — `Redactor.redactLine` (`Redactor.kt:65`) на каждой строке вывода процесса (`dpai/orchestrator/src/main/kotlin/com/dpsmpx/dpai/orchestrator/agent/AgentRuntime.kt:242`), предел строки — 1 МиБ (`dpai/execution/…/LocalProcessHost.kt:81`).
- Цитата: `val childPath = JsonPath.field(path, key)` … `items += value(JsonPath.index(path, items.size), depth)` — строка пути собирается заранее для каждого поля и каждого элемента, хотя нужна только при ошибке.
- Что не так: строка `{"<ключ 500 000 знаков>":[1,1,1,…250 000 раз…]}` (1 МиБ) требует 250 000 копирований по 0,5 МБ: модель `P.java` — 20–40 с процессора на сервере, на телефоне — минуты; для документа у предела по умолчанию (16 Ми знаков) — часы. Вложенные длинные ключи (64 уровня) дают ещё и сотни МиБ живых строк пути.
- Сценарий: тест/скрипт репозитория (T4, T5) печатает такие строки в stdout шага проверки или хода — поток чтения вывода агента на target занят разбором, ход и проверка стоят; строк можно напечатать сколько угодно.
- Рекомендация: путь вести стеком сегментов и собирать строку только в `fail`/при дубле ключа; в `redactLine` — предел размера для попытки разбора.
- Уверенность: высокая по коду; время — по модели, не по самому классу (скомпилированного ядра в контейнере нет). По документам не известно (`PERFORMANCE.md` не сверял).

### C-06 — Низкая — целостность журнала: начало запечатанного сегмента и стык между сегментами не сверяются
- Место: `dpai/storage/src/main/kotlin/com/dpsmpx/dpai/storage/journal/EventJournal.kt:154-167` (`forEachRecord`), `:528-555` (`scan(bytes, null)`), `:557-563` (`firstHeader`).
- Цитата: `val expected = loaded.lastOrNull()?.let { … } ?: start ?: firstHeader(line)`; проверяется только `if (last + 1 != nextFirst) throw …`.
- Что не так: для собственного (не из копии) сегмента номер и `prev` первой записи берутся из неё самой: (а) номер первой записи не сравнивается с номером в имени файла (сравнение есть только у копии, `:334`) — сегмент, у которого пропало начало (остались записи k…N), читается как целый, записи с начала сегмента молча отсутствуют в проекциях; (б) `prev` первой записи сегмента N+1 не сверяется с хешем последней записи сегмента N — подменённый целиком средний сегмент с верными номерами проходит. Заявлено (KDoc, стр. 28-31): «цепочка хешей ловит и порчу, и перестановку, и потерю записи в середине», «номера и цепочка хешей сквозные».
- Последствия: потеря подтверждённых записей (D-24) в этом случае не обнаруживается; от намеренной правки цепочка без ключа не защищает в любом случае (хеш пересчитывается) — это вопрос только случайной порчи/неполной копии.
- Рекомендация: в `forEachRecord` и `open` требовать `first.position == firstOf(name)` и нести хеш последней записи предыдущего сегмента в `scan(bytes, start)`.
- Уверенность: высокая по коду; теста на «сегмент без начала» не искал. По документам не известно.

### C-07 — Низкая — устойчивость: имя `…​.seg-` без цифр или с 20+ цифрами роняет открытие журнала исключением
- Место: `…/journal/EventJournal.kt:355` и `:314`.
- Цитата: `it.removePrefix(prefix).all(Char::isDigit)` (для пустого хвоста `all` истинно) → `firstOf(name) = name.substringAfterLast(SEGMENT_MARK).toLong()`.
- Что не так: файл `live.journal.seg-` или `live.journal.seg-99999999999999999999` в каталоге журнала даёт `NumberFormatException` из `open` — не `Outcome`, оболочка (`ui/LiveSystem.kt:132`) ждёт `Outcome` или `JournalSegmentUnreadable`.
- Рекомендация: фильтр `Regex("\\d{1,18}")`, остальное — диагностика.
- Уверенность: высокая по коду; файл такой появится только от руки/сбоя (низкая вероятность).

### C-08 — Низкая — гонка: `position` и `lastHash` журнала читаются без монитора, снимок берёт их двумя чтениями
- Место: `…/journal/EventJournal.kt:80`, `:100`, `:220-224`; `dpai/storage/src/main/kotlin/com/dpsmpx/dpai/storage/snapshot/Snapshots.kt:87-88`.
- Цитата: `Snapshot(projection.name, journal.position, journal.lastHash, projection.encode(state))`; в `rotateIfFull`: `baseHash = lastHash; offset = position; records.clear()`.
- Что не так: журнал пишут два потока (такт и `accept`, D-94 — так сказано в KDoc `view()`); `append` между чтением `position` и `lastHash` даёт снимок «позиция P, хеш записи P+1», а чтение `position` между `offset = position` и `records.clear()` — удвоенный номер. Такой снимок при восстановлении отвергается («хеш записи журнала не совпал») — полный пересчёт всей истории; сам пересчёт корректен.
- Рекомендация: один синхронизированный метод `head(): Pair<Long, ContentHash>`; геттеры — под монитором.
- Уверенность: средняя — гонка видна по коду, кто именно зовёт `snapshotOf` из другого потока, чем пишущий, не проверял (`Orchestrator.kt` — область другого прохода).

### C-09 — Низкая — хранилище: `DocumentStore` без взаимного исключения по ключу; `keys()` не видит документ, от которого остались только `.tmp`/`.prev`
- Место: `dpai/storage/src/main/kotlin/com/dpsmpx/dpai/storage/document/DocumentStore.kt:39-43`, `:45-62`.
- Цитата: `val tmp = "$main$TMP"` (одно имя на все записи ключа); `fun keys() = vfs.list(dir).filter { KEY.matches(it) }`.
- Что не так: (а) две одновременные записи одного ключа делят `key.tmp`: первый `rename` уносит наполовину записанный вторым потоком файл в основной, второй `rename` падает — основная версия испорчена, чтение молча откатывается на `.prev` (потерянное обновление с предупреждением); (б) сбой между двумя переименованиями (`main → .prev`, `tmp → main`, fsync каталога — только после обоих) оставляет `key.tmp` и `key.prev` без `key`: `read(key)` документ найдёт, а `keys()` — нет, и чтение его не «чинит» (не переименовывает), так что перечисление по `keys()` теряет документ до следующей записи.
- Рекомендация: монитор на запись (хотя бы по ключу); в `keys()` учитывать имена с суффиксами; в `read` довершать прерванную замену.
- Уверенность: (б) — высокая по коду; (а) — гипотеза: надо проверить, пишут ли один ключ два потока (`android/Controller.kt:93`, `Orchestrator` c `documents`).

### C-10 — Инфо — резервные копии ядра: `BackupService` в `src/main` никем не вызывается; в нём есть дефекты
- Место: `dpai/storage/src/main/kotlin/com/dpsmpx/dpai/storage/backup/Backups.kt:43-49`, `:121-144`.
- Что не так: (а) поиск по `src/main` всех модулей `dpai` — ни одного `BackupService(`: заявленная в `SECURITY_MODEL.md` T9/ТЗ §59–61 копия каталога данных в продукте идёт другим кодом (`sync/CloudArchive`, оболочка), а этот класс покрыт только тестами; (б) `vfs.read(...) ?: ByteArray(0)` (стр. 44): файл, пропавший между `list` и `read` (ротация журнала, замена документа между двумя `rename`), попадает в копию пустым, манифест сходится, а после восстановления документ — `STORAGE_CORRUPTED` (`.prev` в копию не идёт), журнал — без записей сегмента; (в) восстановление не трогает подкаталог `journal-copies` (D-95): `apply` видит только файлы каталога, и при следующем `EventJournal.open(keepCopies = true)` «пропавшие» более новые сегменты вернутся из копий (стр. 363-372 журнала) — старая копия смешается с новой историей либо журнал не откроется без карантина.
- Рекомендация: если класс остаётся — пропавший файл считать ошибкой копии, копию снимать при остановленной записи, каталог копий сегментов восстанавливать/очищать вместе с журналом; иначе — удалить или пометить как неиспользуемый.
- Уверенность: (а) высокая (grep); (б), (в) — по коду, без прогона.

### C-11 — Низкая — одобрения: одноразовость живёт только в памяти экземпляра `ApprovalLedger`
- Место: `dpai/security/src/main/kotlin/com/dpsmpx/dpai/security/Approval.kt:37-55`; создание — `dpai/ui/src/main/kotlin/com/dpsmpx/dpai/ui/LiveSystem.kt:247` (`GitCommands(ApprovalLedger())` на каждую сборку контура).
- Цитата: `private val used = HashSet<ApprovalId>()`.
- Что не так: использованные одобрения не пишутся ни в журнал, ни в документ; после перезапуска процесса или пересборки контура (D-94) тот же `Approval` до `expiresAt` снова пройдёт `consume`. Заявлено (KDoc, стр. 27-36): «Одноразовое… Использованное одобрение запоминается».
- Сценарий (гипотеза): одобрение слияния выдано, процесс убит после `consume`, но до записи исхода; после запуска сохранённое `PendingMerge` с тем же `Approval` исполняется ещё раз. Проверить в `orchestrator/Merges.kt`, хранится ли `Approval` в состоянии дольше одного вызова.
- Рекомендация: признак «использовано» — событием журнала (восстанавливается проекцией) или срок одобрения — секунды с привязкой к монотонным часам процесса.
- Уверенность: по коду `ApprovalLedger` — высокая; эксплуатируемость — гипотеза.

### C-12 — Низкая — уведомления: время показа — настенное; перевод часов назад глушит уведомления
- Место: `dpai/notifications/src/main/kotlin/com/dpsmpx/dpai/notifications/NotificationEngine.kt:112-126`, `:163-166`.
- Цитата: `while (recentPosts.isNotEmpty() && now - recentPosts.first() >= 1.minutes) recentPosts.removeFirst()`; `shown.values.removeIf { r.at - it.second >= policy.aggregationWindow }`.
- Что не так: `at` — `clock.now()` контроллера (`Orchestrator.kt:1742`). Если часы устройства ушли назад на Δ (ручная правка, поправка сети после неверной даты), разности отрицательны: `recentPosts` не чистится — после 6 показов все категории, кроме `APPROVAL`/`SECURITY`, уходят в `Held`, а `flush` тоже ждёт `rateAllows` — `FAILURE`/`BLOCKED`/`WARNING` молчат до Δ + 1 мин; записи `shown` не стареют — повтор по ключу (включая новый запрос `APPROVAL` по тому же предмету) идёт как беззвучный `Update`.
- Рекомендация: при `now < отметки` считать отметку устаревшей (сбрасывать очередь) либо вести окна по `Clock.monotonicNanos()`.
- Уверенность: высокая по коду; теста на перевод часов назад не видел. По документам не известно.

### C-13 — Инфо — личные данные: «отпечаток» аккаунта — несолёный SHA-256 от email
- Место: `dpai/security/src/main/kotlin/com/dpsmpx/dpai/security/AccountIdentity.kt:23-27`.
- Цитата: `val canonical = "dpai.account-identity\n" + (orgId ?: "") + "\n" + (email?.trim()?.lowercase() ?: "")`.
- Что не так: при отсутствии `orgId` отпечаток — хеш известной строки и email: проверяется перебором адресов (словарь) — это псевдоним, а не «без личных данных» (D-30, D-69); отпечаток уходит в журнал и облачную копию. Разделитель `\n` не экранируется (коллизия `orgId="a\nb"` — теоретическая: поля от CLI Claude).
- Рекомендация: HMAC с ключом установки (хранится рядом с токеном канала) или хеш канонического JSON с солью.
- Уверенность: высокая по коду; риск низкий (личное приложение).


### C-14 — Низкая — числа: принятое разбором число может не записаться обратно (исключение вместо `Outcome`)
- Место: `dpai/sessions/src/main/kotlin/com/dpsmpx/dpai/sessions/UsageJson.kt:61`, `:95`, `:204` (запись), `:219-223` (чтение); ограничение — `dpai/core/src/main/kotlin/com/dpsmpx/dpai/core/serialization/JsonValue.kt:30-32`.
- Цитата: `"costUsd" to (… JsonNumber(it.value.toPlainString()) …)`; `require(GRAMMAR.matches(literal) && literal.length <= 1000) { "не число JSON" }`.
- Что не так: разбор принимает порядок до ±9999 (`1e-2000` — допустимое число), `decimal()` отдаёт его как `BigDecimal`, а запись идёт через `toPlainString()` — строка длиной в тысячи знаков, и конструктор `JsonNumber` бросает `IllegalArgumentException`. ### C-18 — Средняя — потеря данных автора: `FolderSync.apply` исполняет план, не сверяя, что файл не изменился после плана
- Место: `dpai/files/src/main/kotlin/com/dpsmpx/dpai/files/FolderSync.kt:121-190` (особенно `:135-146`, `:151`, `:158`); вызов — `dpai/android/src/main/kotlin/com/dpsmpx/dpai/android/UserFiles.kt:304-324` (план и исполнение — два отдельных вызова, между ними — экран с планом).
- Цитата: `fun toRemote(item: SyncItem, counted: SyncAction) = run(local.read(item.path, MAX_FILE_BYTES)) { bytes -> run(remote.write(item.path, bytes)) { rm -> next[item.path] = BaseEntry(…, rm, item.local ?: rm)`.

- `storage/journal/EventJournal.kt`: запись — после `force(true)`, первый файл — с fsync каталога; хеш записи — по каноническому телу с номером и `prev`; порча в середине активного файла — отказ до подтверждения карантина; оборванный хвост — в карантин-файл; запись после отказа закрыта (`broken`), прежний экземпляр — `close()`; пропажа первого/среднего сегмента по номерам ловится.

- `storage/snapshot/Snapshots.kt:110-115`: снимок другой проекции, длиннее журнала или с чужим хешем записи не применяется.
