### P-01 — Средняя — ошибка (гонка состояния; последствие для приватности)

- **Место:** `dppass/connection/src/main/kotlin/com/dpsmpx/dppass/connection/Subscriptions.kt:243-306` (`refresh`), `:226-229` (`edit`), `:148-151` (`commit`); `dppass/connection/src/main/kotlin/com/dpsmpx/dppass/connection/Activation.kt:95` (`var state`), `:149`, `:237-241`; вызовы — `dppass/app/src/main/kotlin/com/dpsmpx/dppass/app/SubscriptionJobService.kt:37`, `dppass/app/src/main/kotlin/com/dpsmpx/dppass/app/ui/SubscriptionsScreen.kt:284,299,338,350,366`.
- **Что не так.** `refresh()` берёт снимок `st` в начале, уходит в сеть и активацию (до десятков секунд) и в конце пишет весь список по устаревшему снимку:
  ```kotlin
  val st = when (val s = state()) { … }            // 250-253
  …сеть, разбор, активация…
  val saved = commit(st.copy(items = st.items.map { if (it.id == id) kept else it }, activeId = activeId))  // 302
  ```
  Ни в `SubscriptionService`, ни в `ActivationService` нет ни замка, ни одного потока-исполнителя (в `connection/` замки есть только у `Usage`, `Analyzer`, `Policy`, `Regime`, `Adaptive`, `SplitFallback`). `ActivationService.state` — обычное поле без `@Volatile`; номер ревизии читается до приостановки (`:149`), а пишется после.
- **Сценарий.** Фоновое автообновление (`SubscriptionJobService`, поток `Dispatchers.IO`, раз в час проверка срока) идёт невидимо. Пока оно ждёт ответ поставщика, пользователь на экране подписок: удаляет подписку, выключает «идентификатор устройства» (`setDeviceId(false)`), меняет срок или имя. Правка записана, а через секунды затёрта `commit` из `refresh`. Итог: удалённая подписка возвращается и остаётся применённой; выключенный `x-hwid` снова включён и уходит поставщику при следующем обновлении — без следа на экране. То же между ручным обновлением и фоновым; у `ActivationService` — две активации подряд с одним номером ревизии и потерянной записью истории.
- **Рекомендация.** Один `Mutex` на `SubscriptionService` (и на `ActivationService.activate/rollback/restore`); в `refresh` после сети перечитывать состояние и менять только свою запись (`state().items.map { … }`), а не писать снимок целиком. Тест: правка во время приостановленного `fetch`.
- **Уверенность:** подтверждено чтением кода (вероятность мала — окно равно времени загрузки).
- **Известно по документам:** нет.

### P-02 — Средняя — безопасность (T4: трафик мимо туннеля)

- **Место:** `dppass/app/src/main/kotlin/com/dpsmpx/dppass/app/DPpassVpnService.kt:229-234` (`restart`), `:850-869` (`shutdown` закрывает TUN), `:266-328` (работа до `establish`), `:830-835` (`fail` → `stopSelf`); автоматические причины — `:624` (наблюдатель), `:685` (интерфейсы раздачи), `dppass/app/src/main/kotlin/com/dpsmpx/dppass/app/SubscriptionJobService.kt:48`.
- **Что не так.** Любое переподключение — это «закрыть TUN, потом поднять новый»:
  ```kotlin
  lifecycle.withLock {
      shutdown()                                   // session.stop(); tunnel.close()
      if (restarts.decrementAndGet() == 0) start() // … позже AndroidTunnelProvider.establish
  }
  ```
  Между `tunnel?.close()` и новым `establish()` выполняются `core.restore()`, поиск устройства раздачи (сетевой ввод-вывод, до 1,5 с на сеть), `localProxy.prepare()`, сборка `TunnelSpec`. Всё это время интерфейса VPN нет, и трафик приложений идёт по сети оператора с настоящим адресом. Если после этого ни один кандидат не прошёл, `fail()` останавливает сервис: уведомление исчезает, устройство остаётся без туннеля.
- **Сценарий.** Действий пользователя не нужно: подтверждённая деградация сервера (`adaptive_reconnect`), смена набора интерфейсов раздачи, фоновое обновление подписки с изменившимся сервером. Каждое даёт окно открытого трафика; при неудаче нового подключения — открытый трафик до тех пор, пока пользователь не заметит. Закрывает это только системный режим «Блокировать соединения без VPN», которого приложение не требует и не подсказывает.
- **Рекомендация.** Поднимать новый TUN до закрытия прежнего (повторный `establish()` того же приложения заменяет интерфейс без разрыва) и закрывать старый дескриптор после; при отказе автоматического переподключения держать TUN поднятым без ядра (трафик закрыт) до решения пользователя — как уже сделано на время перебора кандидатов. Как минимум — записать окно в `SECURITY_MODEL.md`, T4, и подсказать системную блокировку на экране.
- **Уверенность:** подтверждено чтением кода; длительность окна на устройстве не измерялась.
- **Известно по документам:** нет. T4 этого остатка не называет; `docs/research/ANDROID_NETWORK_MODEL.md:46` упоминает lockdown только как системную настройку.

### P-03 — Средняя — надёжность (утечка дескриптора TUN)

- **Место:** `dppass/app/src/main/kotlin/com/dpsmpx/dppass/app/DPpassVpnService.kt:319-328` (TUN поднят), `:347-348` и `:698-707` (`tetherForConnect` с `delay`), `:350-375` (единственное место, где `handle` закрывается при отмене), `:254-264` (`connectOrFail`).
- **Что не так.** `handle` закрывается только в `catch (e: CancellationException)` вокруг `core.connect(...)`. Но между `establish()` и этим `try` есть точка приостановки:
  ```kotlin
  val share = if (shareSettings?.enabled == true) shareSettings.spec(tetherForConnect()) else null   // 348 → delay(1500)
  val job = currentCoroutineContext().job
  val report = try { … } catch (e: CancellationException) { handle?.close(); throw e }
  ```
  Отмена во время `delay` (включена раздача, пользователь нажал «Отключить» или пришло переподключение) уходит мимо `handle?.close()`. То же при любом не-`Cancellation` исключении после `establish()`: `connectOrFail` зовёт `fail()`, а `handle` не закрывает. Поле `tunnel` ставится только при принятом сеансе (`:387`), поэтому `shutdown()` этот TUN не видит.
- **Сценарий.** Сервис остановлен, статус «не подключено», а интерфейс VPN жив и забирает трафик в дескриптор, который никто не читает: у приложений в туннеле нет сети, пока сборщик мусора не финализирует `ParcelFileDescriptor` или пока туннель не поднимут заново.
- **Рекомендация.** Обернуть всё от `establish()` до принятия сеанса в `try/finally` с признаком «сеанс принят» (`if (!accepted) handle?.close()`); то же в `connectServerless`.
- **Уверенность:** подтверждено чтением кода; что интерфейс живёт до финализации — свойство `ParcelFileDescriptor`, на устройстве не проверялось.
- **Известно по документам:** нет.

### P-04 — Средняя — безопасность (T15; заявлено одно, в коде другое)

- **Место:** `dppass/app/src/main/kotlin/com/dpsmpx/dppass/app/RelayNetworks.kt:46-51` (`gateways`), `:59-93` (`locate`), `:96-105` (`check`); `dppass/connection/src/main/kotlin/com/dpsmpx/dppass/connection/Relay.kt:358-371` (`Socks5Login.check`); заявление — `dppass/docs/SECURITY_MODEL.md:537-538`.
- **Что не так.** Заявлено: «спрашивается только шлюз своих сетей, и отвечает лишь вход, знающий логин и пароль». В коде устройство без явного адреса ищется на шлюзе любой сети Wi-Fi, Bluetooth или Ethernet с частным IPv4, а «вход найден» — это два байта ответа сервера:
  ```kotlin
  output.write(byteArrayOf(AUTH_VERSION, u.size.toByte()) + u + byteArrayOf(p.size.toByte()) + p)   // логин и пароль открыто
  …
  return if (status[1].toInt() == 0) Result.ACCEPTED else Result.REJECTED
  ```
  SOCKS5 (RFC 1929) проверяет только клиента. Сервер ничего не доказывает: «принято» может ответить кто угодно. Сохранённое устройство к сети не привязано.
- **Сценарий.** Устройство раздачи выбрано, телефон оказался в чужой сети Wi-Fi (кафе, гостиница). При подключении — и при автоматическом перезапуске сервиса (`START_STICKY`, always-on) — DPpass шлёт логин и пароль входа раздачи шлюзу этой сети. Шлюз, который перенаправляет все TCP-порты на свой SOCKS5 и отвечает `01 00`, получает пароль и становится «устройством раздачи»: весь трафик туннеля идёт через него открытым SOCKS (адреса назначения, DNS, незашифрованный HTTP), а на экране — «подключено».
- **Рекомендация.** Взаимная проверка для сопряжённых устройств (D-56 уже даёт общий секрет: запрос-ответ HMAC до отправки пароля); для введённых вручную — не искать шлюз автоматически в сети, где устройство не подтверждено, либо запоминать признак сети при добавлении. Как минимум — исправить формулировку T15 и предупредить на экране, что в чужой сети пароль уйдёт её шлюзу.
- **Уверенность:** подтверждено чтением кода.
- **Известно по документам:** частично. T15 признаёт, что канал без шифрования и безопасна только своя сеть; что «своя сеть» кодом не проверяется и что ответ входа ничего не доказывает — не записано.

### P-05 — Низкая — безопасность (подделка строк журнала; заявлено одно, в коде другое)

- **Место:** `dppass/subscriptions/src/main/kotlin/com/dpsmpx/dppass/subscriptions/ShareLinks.kt:123,142,150,153,165,190,258,345`; `dppass/subscriptions/src/main/kotlin/com/dpsmpx/dppass/subscriptions/Pipeline.kt:84-88`; `dppass/subscriptions/src/main/kotlin/com/dpsmpx/dppass/subscriptions/Metadata.kt:73-77`; `dppass/diagnostics/src/main/kotlin/com/dpsmpx/dppass/diagnostics/Log.kt:106-118`; `dppass/diagnostics/src/main/kotlin/com/dpsmpx/dppass/diagnostics/DeviceLog.kt:183-187`; запись в журнал — `dppass/connection/src/main/kotlin/com/dpsmpx/dppass/connection/Core.kt:518`.
- **Что не так.** KDoc `ShareLinkParser`: «сообщения не содержат значений параметров и самой ссылки». В коде в сообщения идут значения (`"type=$type"`, `"mode=${q["mode"]}"`, `"fp=$f"`, `"security=$s"`) и имена параметров из ссылки (`unknown.sorted().joinToString()`), а в `SUBSCRIPTION_DIRECTIVE_IGNORED` — всё, что стоит до двоеточия в любой строке `#…` тела. Это недоверенный текст после %-декодирования, без предела длины и без фильтра управляющих символов. `Logger` и `FileLogSink.format` перевод строки не экранируют:
  ```kotlin
  for ((k, v) in e.fields) append(' ').append(k).append('=').append(v)
  ```
- **Сценарий.** Поставщик (или тот, кто подменил ответ) кладёт в ссылку параметр с `%0A` в имени или значении `type` — в журнале устройства появляется поддельная строка события с любым текстом; журнал копируют в поддержку. Строка `#<1 МБ текста>: x` даёт находку и строку журнала на мегабайт. Секрет, оказавшийся на месте имени параметра в испорченной ссылке, попадёт в сообщение (дальше — только `Redactor`).
- **Рекомендация.** В `Logger.log` заменять управляющие символы в значениях полей (`\n` → `\\n`) и ограничивать длину поля; в сообщениях разбора цитировать только имена из закрытого набора вида `[a-z0-9_.-]{1,32}`, прочее — «параметр №k»; число и длину имён в `ignored` ограничить.
- **Уверенность:** подтверждено чтением кода.
- **Известно по документам:** нет.

### P-08 — Низкая — надёжность (порча записи хранилища)

### P-11 — Инфо — безопасность (T7; заявлено шире, чем сделано)

- **Место:** `dppass/app/src/main/kotlin/com/dpsmpx/dppass/app/AppPrefs.kt:22,78-82,107`; `dppass/app/src/main/kotlin/com/dpsmpx/dppass/app/DeviceLog.kt:71-83`.
- **Что не так.** T7: «данные в `noBackupFilesDir`; AES-256-GCM». Список сайтов «Напрямую с разбиением» (`split_sites`) и выбор приложений режима без сервера лежат открытым текстом в `shared_prefs/ui.xml`. Журнал устройства — открытый файл с именами серверов (уровень `STANDARD`); выключение журнала закрывает файл, но уже записанные `current*.log` и `previous*.log` не стирает.
- **Сценарий.** Без root другим приложениям это недоступно, резервные копии выключены — практический риск мал; важно только для того, кто полагается на формулировку T7.
- **Рекомендация.** Перенести `split_sites` в зашифрованную запись рядом с политикой пользователя либо уточнить T7; при выключении журнала предлагать стереть файлы.
- **Уверенность:** подтверждено чтением кода.
- **Известно по документам:** нет.

### P-12 — Инфо — качество (разные правила для недоверенных имён)

- **Место:** `dppass/subscriptions/src/main/kotlin/com/dpsmpx/dppass/subscriptions/ShareLinks.kt:530`; `dppass/config/src/main/kotlin/com/dpsmpx/dppass/config/DocumentMapper.kt:373`; для сравнения — `dppass/subscriptions/src/main/kotlin/com/dpsmpx/dppass/subscriptions/Metadata.kt:86`, `dppass/connection/src/main/kotlin/com/dpsmpx/dppass/connection/Subscriptions.kt:406`.
- **Что не так.** Имя подписки и `profile-title` проверяются `isISOControl()` (C0, DEL, C1), имя сервера из ссылки и документа — только `code < 0x20`. Символы направления письма и нулевой ширины (U+202E, U+2066, U+200B) проходят везде. Имя сервера видно в уведомлении (`DPpassVpnService.kt:951`), в окнах подтверждения и в журнале.
- **Сценарий.** Поставщик задаёт имя, которое на экране читается иначе, чем записано. Только подмена вида, не поведения.
- **Рекомендация.** Одна функция проверки имени в `core/` для всех четырёх мест: `isISOControl` плюс категории Unicode `Cf`, `Zl`, `Zp`.
- **Уверенность:** подтверждено чтением кода.
- **Известно по документам:** нет.

### P-13 — Инфо — безопасность (вторая линия редактирования)

- **Место:** `dppass/diagnostics/src/main/kotlin/com/dpsmpx/dppass/diagnostics/Redactor.kt:51-59,70-72`.
- **Что не так.** В шаблоне ссылки часть до `@` не может содержать `/`. У `ss://` она — обычный base64, где `/` бывает; тогда всё до первого `/` считается хостом и остаётся в тексте, а под метку уходит только остаток. Короткие (меньше 24 символов) пароли вне пары `ключ=значение` редактор не узнаёт вовсе.
- **Сценарий.** Гипотеза: нужна строка журнала, куда ссылка попала целиком. Сообщения разбора ссылок самих ссылок не цитируют, такого пути я не нашёл.
- **Рекомендация.** Для схем `ss|vless|trojan|hysteria2|hy2|socks5` редактировать всё после `://` до пробела независимо от формы; добавить случай в `RedactorTest`.
- **Уверенность:** гипотеза — поведение шаблона подтверждено чтением, путь утечки не найден.
- **Известно по документам:** нет.

## Что проверено и в порядке

- **Инъекции в конфигурацию Xray нет:** JSON строится деревом значений, строки экранирует `Json.Writer` (`core/Json.kt:296-310`); правила доменов и геокодов — с явными префиксами `full:`/`domain:`/`keyword:`/`geosite:` после проверки значений (`XrayCompiler.kt:872-876`).
- **Проверка сертификата не отключается:** `allow_insecure` в документе и `allowInsecure`/`insecure` в ссылке — отказ (`DocumentMapper.kt:216-222`, `ShareLinks.kt:126-128,191-194`); компилятор не пишет ослабляющих полей (`XrayCompiler.kt:446-468`); журнал ядра выключен (`:193`).
- **Пределы недоверенного входа:** размер до разбора, глубина JSON, длина строк, число профилей и правил (`ConfigLoader.kt:36-41,76-79`, `Format.kt:32-39`); тело подписки ограничено во время чтения, в том числе после распаковки gzip (`Https.kt:108-121`); `fm`/`extra` — глубина 8 (`ShareLinks.kt:513-517`); QR — предел файла и пикселей (`QrPicture.kt:21-44`). Шаблонов с катастрофическим откатом в `Redactor`, `ShareLinks`, `Relay` не нашёл.
- **Подписка не управляет клиентом:** директивы не применяются, маршрутизация и DNS поставщика — только при привязке, выбор приложений и `bypassLan` остаются пользователя (`Metadata.kt`, `Pipeline.kt:263-286`, `ProviderPolicy.kt:30-34`); `happ://crypt` и `happ://routing/off` не принимаются (`Import.kt:70-77`, `HappRouting.kt:87-93`).
- **Загрузка подписки:** только `https`, переадресация вручную и только на `https`, не больше 3, своих `TrustManager` нет (`Https.kt:44,62-73`); `network_security_config.xml` — без открытого HTTP, только системные CA.
- **Хранилище:** AES-256-GCM, случайный nonce 96 бит на запись, имя записи в связанных данных, ключ данных обёрнут неизвлекаемым ключом Keystore, новый ключ поверх существующих записей не создаётся (`Storage.kt:142-200`, `Keys.kt:88-125`, `KeystoreKeyWrapper.kt`); ключи записей проверяются до обращения к файлам (`Storage.kt:30-37`); данные и ключ — в `noBackupFilesDir` (`AppGraph.kt:68-74`).
- **Резервные копии выключены:** `allowBackup="false"`, `fullBackupContent="false"`, `data_extraction_rules.xml` исключает все домены.
- **Экспортированные компоненты:** `MainActivity` (`MAIN`, `SEND text/plain`, `SEND image/*`), три сервиса под системными разрешениями, приёмники не экспортированы, `ContentProvider`, `FileProvider`, `WebView` и схем deep link нет; видимость пакетов — только `<queries>` с `MAIN/LAUNCHER`.
- **`PendingIntent`:** все `FLAG_IMMUTABLE`, с явным компонентом (`DPpassVpnService.kt:957-968`, `ServerSwitch.kt`, `ExpiryAlarms.kt:307`, `UsageAlerts.kt`, `DPpassTileService.kt:105`).
- **Чужие данные из «Поделиться»:** текст — с пределом длины, только через распознавание и подтверждение (`MainActivity.kt:146-149`, `ImportFlow.kt:67-85`); URI картинки читается только как изображение, наружу не отдаётся.
- **Секреты:** `Secret.toString()` — метка; `reveal()` в `app/` — только экраны раздачи и локального прокси и выдача входа при сопряжении; `CompiledConfig.toString()` без содержимого (`Engine.kt:87`); экспорт по умолчанию — с метками (`ConfigWriter.kt:23-28`); копия журнала — через `STRICT` и с пометкой «чувствительное» на Android 13+ (`DeviceLog.kt` в `diagnostics` и в `app`).
- **Сопряжение (D-56):** обязательство хозяина до раскрытия числа гостя, сравнение за постоянное время (`MessageDigest.isEqual`), код из обоих ключей и чисел, HKDF + AES-256-GCM со стенограммой в связанных данных, проверка кривой ключа, кадры не больше 1024 байт (`Pairing.kt`). Подбор кода под чужой ключ не получается ни в одном порядке сообщений.
- **Локальные входы ядра:** раздача и локальный прокси — с паролем (100 бит) и случайным портом из `SecureRandom`; локальный прокси несовместим с TUN (`XrayCompiler.kt:118-122`); вход раздачи закрыт для адресов самого телефона и для loopback назначения (`:510-522,763-770,985-988`).
- **Случайность:** везде `SecureRandom` (`DeviceId`, `ShareSettings`, `RelayService`, `Pairing`); `java.util.Random` и времени как зерна не нашёл.
- **Широких `catch (Exception)` с потерей отмены корутин нет:** `DPpassVpnService.kt:254-264` и `Orchestrator.kt:265-270` отмену пробрасывают, сеанс ядра при отмене посреди проверки здоровья останавливается.
- **Текст поставщика на экране:** `announce` и прочее проходят `Presentation.plain` (`Presentation.kt:313-316`); ссылки поддержки открываются только с `https://` (`SubscriptionsScreen.kt:372-379`).
- **Цепочка поставки:** версии закреплены в одном каталоге, динамических версий нет, репозитории — Google и Maven Central (`FAIL_ON_PROJECT_REPOS`), проверка SHA-256 артефактов включена (316 записей; подписи не проверяются — так и записано), сумма дистрибутива Gradle задана.
- **Замеченное и безвредное:** `Char.isDigit()` в `\u`-последовательностях JSON, группах IPv6 и `%XX` пропускает не-ASCII цифры, но результат всегда каноничен (`Json.kt:175`, `Address.kt:67`, `ShareLinks.kt:609`).
