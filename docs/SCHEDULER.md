# Планировщик и задачи

Задачи, их автомат, зависимости, приоритеты и выбор исполнителя. Код —
модуль `tasks` (этап 7); автомат задачи — `core`, `TaskLifecycle`
(этап 1). Планировщик детерминирован (D-22): одинаковые вход и время
дают одинаковое решение.

## 1. Автомат задачи

Состояния доски ТЗ, §41 и цепочка проверки ТЗ, §32 (D-23). Начальное —
`BACKLOG`; конечные — `DONE`, `FAILED`, `CANCELLED`.

| Из | В (обычный переход) |
|---|---|
| `BACKLOG` | `QUEUED`, `CANCELLED` |
| `QUEUED` | `READY`, `BLOCKED`, `BACKLOG`, `CANCELLED` |
| `READY` | `RUNNING`, `QUEUED`, `BLOCKED`, `CANCELLED` |
| `RUNNING` | `WAITING`, `BLOCKED`, `IMPLEMENTED`, `READY`, `FAILED`, `CANCELLED` |
| `WAITING` | `RUNNING`, `BLOCKED`, `READY`, `FAILED`, `CANCELLED` |
| `BLOCKED` | `READY`, `QUEUED`, `FAILED`, `CANCELLED` |
| `IMPLEMENTED` | `VERIFYING`, `COMPLETION_UNVERIFIED`, `CANCELLED` |
| `VERIFYING` | `VERIFIED`, `READY`, `COMPLETION_UNVERIFIED`, `FAILED`, `CANCELLED` |
| `VERIFIED` | `DONE`, `READY` |
| `COMPLETION_UNVERIFIED` | `VERIFYING`, `DONE`, `CANCELLED` |
| `DONE`, `FAILED`, `CANCELLED` | — |

Явные операции (не обычный переход, D-11):

| Операция | Переход |
|---|---|
| повтор упавшей задачи | `FAILED` → `QUEUED` |
| возобновление отменённой | `CANCELLED` → `BACKLOG` |
| переоткрытие выполненной | `DONE` → `BACKLOG` |

Смысл:

- `QUEUED` — принята в очередь, зависимости ещё не выполнены или нет
  ресурсов; `READY` — может быть назначена прямо сейчас;
- `RUNNING` → `READY` — сессия закончила ход без результата (предел,
  handoff): задача ждёт следующего исполнителя (ТЗ, §28);
- `IMPLEMENTED` — исполнитель сообщил о завершении; это заявление, не
  результат (D-23);
- `VERIFYING` → `READY` — проверка не прошла, нужна работа; это неудачная
  попытка (§5): пауза перед следующим ходом, предел попыток, а тот же
  провал (тот же хеш отчёта) раз за разом — `LOOP_DETECTED`; следующий
  ход получает выжимку того, что упало, и продолжает ту же сессию
  провайдера, а маршрут модели поднимается на ступень (D-40,
  `docs/EFFICIENCY.md`, §4, §7);
- `COMPLETION_UNVERIFIED` — проверку не удалось выполнить; `DONE` из
  него — только с записанным исключением политики (инвариант
  `docs/DATA_MODEL.md`, §5; запись исключения — этап 10).

## 2. Зависимости

Граф задач — DAG (ТЗ, §17, §42). Задача становится `READY`, только
когда все её зависимости в `DONE`. Цикл — `DEPENDENCY_CYCLE` с перечнем
задач цикла (ТЗ, §120); задачи цикла не планируются. Отношения: «зависит
от», «блокирует», «связана с» (не влияет на порядок).

## 3. Приоритет

Базовые уровни: `CRITICAL`, `HIGH`, `NORMAL`, `LOW`, `BACKGROUND` (ТЗ,
§18). Вычисленный ключ упорядочивания — кортеж, сравниваемый
лексикографически:

1. ручной приоритет пользователя, если политика его разрешает;
2. базовый уровень с поправкой на старение (ожидание дольше порога
   поднимает уровень, ТЗ, §84);
3. влияние на блокировку: сколько задач ждут эту;
4. приоритет проекта;
5. время постановки в очередь (раньше — выше);
6. `TaskId` — устойчивая развязка равенства.

Число в формулах не прячется за плавающей точкой: только целые и явные
пороги, чтобы порядок был воспроизводим.

## 4. Выбор исполнителя

Для задачи в `READY` планировщик выбирает аккаунт и target (ТЗ, §50,
§51, §85):

- только совместимые возможности (`requiredCapabilities`);
- аккаунт в `AVAILABLE`, без cooldown и rate limit; лимиты не обходятся
  (D-04);
- при равенстве — меньшая текущая нагрузка, затем меньше недавних
  ошибок, затем устойчивый ключ;
- давление ресурсов (память, CPU, батарея) откладывает задачи ниже
  порогового приоритета (ТЗ, §47);
- внутренние пределы: параллельные сессии, запуски в минуту, повторы на
  задачу, переподключения (ТЗ, §82);
- пересечение областей (ТЗ, §31): у задачи может быть заявленная область —
  пути, которые она затронет (`TASK_SCOPE_CHANGED`). Перед запуском контур
  сверяет её с областями идущих задач (`OverlapPolicy`): общий файл —
  задача ждёт (`SERIALIZE`; критичный файл сборки, зависимостей или
  миграций — `REJECT`, тоже ждёт, с предупреждением), общий каталог —
  запуск с предупреждением (`WARN`). Уведомление — при смене вердикта.
  Область неизвестна — пересечения не проверяются (D-13): `OverlapTest`.

## 5. Повтор и петли

Повтор — по классу причины в диагностике (D-05; ТЗ, §21):

| Класс | Действие |
|---|---|
| `RETRYABLE` (сеть, временная недоступность, rate limit) | повтор с паузой по политике, не больше `maxRetries` |
| `NON_RETRYABLE` (ошибка компиляции того же кода, неверный ввод) | без слепого повтора; `BLOCKED` или задача-исправление |
| `UNKNOWN` | один повтор, затем `BLOCKED` |
| аутентификация | запрос входа; аккаунт → `AUTH_REQUIRED`; вход восстановлен («Вход Claude») — задача продолжается сама, как ответ «Повторить» (ревью A-45) |
| конфликт слияния | `BLOCKED` до вмешательства или задачи-зависимости |
| испорченный worktree | процедура восстановления (`docs/RECOVERY.md`) |
| target недоступен до начала хода (повторяемый сетевой отказ) | не попытка задачи: `READY` с паузой `Orchestrator.TARGET_RETRY`, без счёта повторов и петли (ревью A-50) |
| запуск не удался до хода (дерево, контекст, отказ драйвера) | попытка задачи по классу причины: пауза или `BLOCKED` с запросом, а не новый запуск каждый такт (ревью A-47) |
| ход упёрся в предел подписки | факт предела `REACHED` у подписки, даже без `rate_limit_event` с отказом (ревью A-49) |
| работа проверена, а коммит не удался | `BLOCKED` с запросом, не `DONE` и не слияние ветки без работы (ревью A-52) |

Защита от петель (ТЗ, §22, §121): ключ «задача + хеш промпта + хеш
состояния + код отказа»; N повторов одного ключа — `LOOP_DETECTED`,
ресурсы дальше не тратятся. Так же ловятся: нет изменений файлов, нет
новых событий, повтор одной ошибки, повторные откаты, повторная смена
аккаунта.

## 6. Бюджет задачи

Для каждой задачи: максимальная длительность, повторы, продолжения и
(где провайдер поддерживает) расход — `--max-budget-usd` у Claude Code
CLI (ТЗ, §86; `docs/research/CLAUDE_CODE_CLI.md`).

## 7. Код

Модуль `tasks` (этап 7): `Tasks` — решения над состоянием (`create`,
`addDependency` с обнаружением цикла, `enqueue`, `promote`, `ready`,
`plan`, `start`, `implemented`, `continueLater`, `attemptFailed`,
`explicit`), `apply` сворачивает события в `TasksState`; `TaskCodec` —
события в `dpai.event` (поток — задача) и снимок `dpai.tasks-state` v1;
проекция журнала — `orchestrator.tasks.TasksProjection`.

- Старение: каждый `SchedulerPolicy.agingStep` ожидания с постановки в
  очередь поднимает уровень на один, вплоть до `CRITICAL` (ТЗ, §84).
- План назначений: задачи по порядку, каждой — первый target с нужными
  возможностями и свободным местом (`Tasks.TargetOffer`); задача без
  подходящего target ждёт, не занимая места других.
- Повтор: `RETRYABLE` — пауза `retryBackoff · 2^(n−1)`, не больше
  `maxRetries`, затем `FAILED` (`RETRY_LIMIT_REACHED`); `UNKNOWN` — один
  повтор, затем `BLOCKED`; `NON_RETRYABLE` и ошибка входа — `BLOCKED`.
- Петля: тот же ключ отказа `loopThreshold` раз — `BLOCKED`
  (`LOOP_DETECTED`); продолжений больше `maxContinuations` — `BLOCKED`
  (`CONTINUATION_LIMIT_REACHED`).
- Зависимость упала или отменена — зависимые `BLOCKED`
  (`DEPENDENCY_FAILED`).

## 8. Проверка и завершение

`IMPLEMENTED` — заявление исполнителя (D-23); `CompletionFlow` модуля
`orchestrator` сразу проверяет рабочее дерево по профилю проекта
(`verification.Verifier`) и записывает итог `Tasks.recordVerification`:

| Итог проверки | Задача |
|---|---|
| `PASSED` (падения из базовой линии названы, но не регрессия) | `VERIFIED` |
| `FAILED` — новая ошибка обязательного шага | `READY` после паузы — нужна работа; попытка считается (§5) |
| `INCOMPLETE` — нет профиля, шаг не выполнен, тайм-аут | `COMPLETION_UNVERIFIED` |

В `DONE` — только `Tasks.complete`: из `VERIFIED` — с записанной успешной
проверкой, из `COMPLETION_UNVERIFIED` — с исключением политики (кто и
почему, `VERIFICATION_WAIVED`). Прямой переход в `DONE` отвергается
(`VERIFICATION_REQUIRED`).

Профили `FAST`/`NORMAL`/`FULL` (static/affected/full, ТЗ, §33) задаёт
пользователь в настройках оркестратора, а не репозиторий (T4); внешний
DP-Verify — шаг профиля со своей командой (D-16). Уровни: `plan` —
`Verifier.plan`, `baseline` — `Verifier.baseline`, `report` —
`VerificationReport.render` и формат `dpai.verification-report` v1;
`doctor` target — `docs/EXECUTION_MODEL.md`, §1.2.
