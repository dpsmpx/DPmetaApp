# Решения

Здесь записано, **что решено и почему**. Это источник истины: если
другой документ расходится с решением, прав этот документ, а
расходящийся исправляется. Решение меняется только правкой здесь — с
записью в историю (раздел 4), а не молча в другом месте.

Нумерация: `Д<n>` — принятые решения, `ОР-<n>` — открытые решения,
которые принимает только автор. Пока ОР не решено, действует его
«правило до решения».

## 1. Модель системы

```
человек: идентичность и намерение
  ↓
исследование ─→ проверенный контекст (identity, facts, platforms, strategy)
  ↓
ContentItem: цель · аудитория · площадка · утверждения · доказательства
  ↓
бриф → генерация → критика → ревизия → проверка (гейты) → APPROVED
  ↓
экспорт под площадки → публикует автор → метрики → выводы → решения
```

Контекст копится в репозитории; сессия ИИ его читает и пополняет, но
не является его хранилищем.

## 2. Принятые решения

### Д0. Правила работы
- **Решение.** Краткие правила — `CLAUDE.md`; пояснения — `docs/PROCESS.md`;
  иерархия: `DECISIONS.md` → `CLAUDE.md` → остальное. Принципы взяты из
  инженерной культуры `dpsmpx/Galdhold` (сверка с решениями, «готово —
  остановиться», PR сразу, TODO только для хвостов, аудиты на дату),
  предметная структура — своя.
- **Почему.** Эти правила у автора уже работают и знакомы ему; копия
  файлов перенесла бы чужой предмет (игра, сборка, Vulkan).

### Д1. Контент — производная проверенного контекста
- **Решение.** Единица работы — `ContentItem` (`docs/content/CONTENT_MODEL.md`)
  с целью, аудиторией, площадкой, утверждениями и доказательствами.
  Контент создаётся только из него; факты — только из реестра
  `data/facts/facts.yaml`.
- **Почему.** Иначе каждая сессия заново «вспоминает» автора, и ошибки
  памяти уходят в публичный образ.
- **Следствия.** Состояния и переходы проверяются инструментом;
  `PUBLISHED` недостижим без `APPROVED`.

### Д2. Репозиторий закрытый; личных данных сверх опубликованного нет
- **Решение.** Репозиторий `dpsmpx/SocialMediaImage` — закрытый. В нём
  хранится только то, что автор сам опубликовал, и производные от
  этого; закрытые сведения (документы, договоры, переписка, данные
  аккаунтов) — у автора, вне Git.
- **Почему.** Исследование собирает сведения об авторе в одном месте —
  такая сводка ценнее для злоумышленника, чем разрозненные посты.
- **Следствия.** Опубликованные автором, но личные сведения (работа,
  доход, учёба) фиксируются только как «есть такая публикация», без
  повторения деталей.

### Д3. GitHub Actions не используются; проверяет `tools/check.sh`
- **Решение.** Все проверки — локально: `tools/check.sh`. CI нет.
- **Почему.** Так решено автором для его закрытых репозиториев
  (Galdhold Р12, DPlang Р3): минуты Actions в закрытом репозитории
  платные. Перенесено по аналогии 4 октября 2026; автор может
  пересмотреть.
- **Следствия.** Поиска секретов GitHub в закрытом репозитории личного
  аккаунта нет — его заменяет проверка `secrets` в `tools/check.sh`.

### Д4. Позиционирование автора
- **Решение.** Рабочая формулировка: **независимый разработчик, который
  строит сложные нативные системы — движок, игру, язык — с ИИ как
  инженерным инструментом и под собственным архитектурным
  управлением; память проекта живёт в Git, решениях и проверках, а не в
  сессии ИИ.** Короткая строка — `docs/direction/CONTENT_STRATEGY.md`, §1.
- **Почему.** Гипотеза постановки («independent developer building
  complex native software and game systems with AI-assisted
  engineering») проверена по источникам (`docs/audits/INITIAL_AUDIT.md`,
  §3): подтверждается кодом и историей Galdhold, DPlang, профилем
  GitHub и собственными текстами автора (Telegraph, 04.10.2026).
  Отличие — не «пишу с ИИ», а инженерная система вокруг ИИ.
- **Следствия.** Главный нарратив — результат и метод; «ИИ похвалил» —
  не нарратив. Смена позиционирования — изменение основ (`PROCESS.md`).

### Д5. Иерархия проектов
- **Решение.** Primary — Galdhold (игра и движок внутри него).
  Secondary — DPlang; метод ИИ-разработки (как опора контента, не
  проект). Background — TrueJointTileMaker, Andors-Love, PixRogue,
  DP_Ecosystem, инструменты. Archive — ранние закрытые репозитории
  2023–2024. Подробно — `docs/identity/PROJECT_MAP.md`.
- **Почему.** Вес — по доказуемости и зрелости: Galdhold прошёл этапы
  1–4 и проверялся на телефонах; DPlang — на v0.0, компилятора-выпуска
  нет.
- **Следствия.** DPlang в контенте — «в разработке», без обещаний
  возможностей; Background — только как история пути.

### Д6. Политика утверждений
- **Решение.** Три класса: `FACT` (подтверждено источником и датой),
  `INTERPRETATION` (вывод автора из фактов, подаётся как мнение),
  `HYPOTHESIS` (предположение, подаётся как план или вопрос).
  Утверждения высокого риска (числа, «собственный», «работает на»,
  сравнения, сроки) — только `FACT`. Подробно —
  `docs/content/CLAIM_POLICY.md`.
- **Почему.** Доверие технической аудитории теряется на одном
  преувеличении и восстанавливается долго.

### Д7. Anti-hype
- **Решение.** Запрещены превосходные степени без доказательства
  («лучший», «уникально в мире», «никто не делает», «в N раз быстрее»),
  пересказ похвалы ИИ как доказательства и сравнение с чужими проектами
  в заголовках. Список — `data/facts/forbidden.yaml`, проверка —
  автоматическая.
- **Почему.** Аудит канала (`docs/audits/2026-10-04-SOCIAL_AUDIT.md`)
  показал, что заметная часть постов — оценки от ИИ; сильный контент
  даёт читателю сделать вывод самому.

### Д8. Языки
- **Решение.** Русский — Telegram, VK, YouTube, TikTok (текущая
  аудитория; TikTok — Д19); английский — GitHub. Английский для игровых
  площадок — по ОР-7.
- **Почему.** Аудитория каналов сейчас русскоязычная; GitHub —
  международный.

### Д9. Визуальный язык: бренд автора отдельно от брендов проектов
- **Решение.** У автора — свой визуальный язык
  (`docs/brand/VISUAL_SYSTEM.md`): графит, семантические цвета (человек
  — коралловый `#FF7A59`, ИИ — бирюзовый, проверено — зелёный), IBM Plex. Проекты
  входят в работы автора «в рамке» — своим снимком или знаком, не
  перекрашиваясь в цвета автора.
- **Почему.** Автор — над проектами; смешение брендов сделало бы
  Galdhold «темой автора», а автора — «логотипом игры».
- **Следствия.** Нет «ИИ-эстетики»: неонового мозга, робота,
  голограмм. ИИ показывается как инструмент в цепочке работ. Настоящий
  код закрытых проектов в изображениях не используется (Galdhold Р12).

### Д10. Образ автора — только с настоящей фотографии
- **Решение.** Портрет — только с фотографии, предоставленной автором
  и помеченной `REFERENCE_IMAGE`; допустимы кадрирование и тоновая
  обработка. Генерация лица ИИ «по описанию» и изменение черт — нет.
- **Почему.** Подмена внешности — риск доверия и правил площадок
  (YouTube требует раскрывать реалистичный синтетический контент).
- **Следствия.** Портрет без записи `REFERENCE_IMAGE` в
  `docs/PROVENANCE.md` не проходит гейт Provenance; источник
  фотографии — Д18.

### Д11. Изображения первой фазы — программная композиция
- **Решение.** Изображения собираются детерминированно: спецификация
  композиции → HTML/SVG → Chromium → PNG (`tools/render/`). Генеративные
  модели — только для фонов и иллюстраций без людей, с записью
  провайдера, модели и версии промпта.
- **Почему.** Воспроизводимость, ясные права, нет риска чужого
  сходства; в сессии нет модели генерации изображений.
- **Рассмотрено и отклонено:** генерация всего изображения моделью —
  невоспроизводимо, искажает текст, права на выход зависят от сервиса.

### Д12. Публикуется только одобренное автором; учётные данные — только у автора
- **Решение** (пересмотрено 04.10.2026, прежняя редакция — в истории, §4).
  Публикация на площадки — через их **официальные API** адаптерами
  системы (`docs/content/PUBLISHING.md`) и только той версии, которую
  **одобрил автор**: одобрение записывается с хэшем текста и медиа
  варианта; изменённая после одобрения версия не публикуется.
  - По умолчанию — **пробный прогон** (dry-run): всё готовится и
    проверяется, показывается адресат, наружу не уходит ничего.
    **Безопасный режим** — только тестовые адресаты (тестовый канал,
    staging сайта). Рабочая публикация — явный флаг и рабочий адресат
    с явными id (Д25).
  - **Автопубликации нет** ни для одного класса контента, пока для
    класса не принято отдельное решение здесь (`data/policy/publication.yaml`
    — список классов пуст).
  - **Учётные данные** — только на машине автора: вне Git и вне
    облачных сессий ИИ; у сессии ИИ рабочих токенов нет (Д26,
    `docs/operations/CREDENTIALS.md`). Исключение — выгрузка сайта
    (Д36): её запускает локальная сессия Claude Code на машине автора
    после его «да» на каждую команду; облачная — никогда.
  - Профили, удаление записей и всё, чего нет в официальном API,
    делает **автор руками** по пакету публикации (ручной путь, Д33).
    Входа в аккаунты через браузер, автоматизации браузера и
    скрейпинга нет.
- **Почему.** Решение автора 4 октября 2026 (постановка платформы,
  `docs/direction/PLATFORM_VISION.md`, §19, §30; ответ на вопрос
  сессии). Ошибка публикации необратима — поэтому одобрение конкретной
  версии, идемпотентность и журнал (Д24); учётные данные — главный
  риск безопасности — поэтому отдельная граница на площадку и
  окружение и ни одного токена в сессии ИИ.
- **Следствия.** Первая площадка с реальным адаптером — Telegram (бот
  публикует в канал); остальные — по фазам `ROADMAP/ROADMAP.md`.
  Возможности площадок — `docs/platforms/PUBLISHING_CAPABILITY_MATRIX.md`.

### Д13. Размеры экспорта — из официальных источников, с датой проверки
- **Решение.** Требования площадок — в `data/platforms/export_specs.yaml`:
  у каждого — источник, класс источника и дата проверки. Неофициальное
  помечается `verified: false`.
- **Почему.** Требования меняются; захардкоженный размер устаревает молча.

### Д14. Вариация — не эксперимент
- **Решение.** Варианты для выбора (A–D) и контролируемый эксперимент
  (гипотеза, метрика, площадка, решение) — разные сущности
  (`docs/content/EXPERIMENTS_AND_ANALYTICS.md`).
- **Почему.** Выбор по вкусу, записанный как «тест», даёт ложное знание.

### Д15. Метрики — ручной импорт, без сбора с площадок
- **Решение.** Метрики загружаются выгрузкой (CSV) из аналитики площадок
  в `data/metrics/`; скрейпинга и API с ключами нет до отдельного решения.
- **Почему.** Без доступа к аккаунтам и без хранения токенов (Д12, Д2).

### Д16. Имя игры — Galdhold
- **Решение.** Новый контент называет игру **Galdhold**; «VoxelRPG» —
  только как прежнее имя («Galdhold, прежде VoxelRPG») на переходный
  период и в записях о прошлом.
- **Почему.** Решение автора 4 октября 2026 (Galdhold, Р20).

### Д17. Закрытые проекты наружу — только фактами и снимками игры
- **Решение.** Из Galdhold и DPlang в контент и сюда идут факты, вехи,
  снимки игры и публичные описания — не код, не выдержки, не снимки
  редактора и не внутренние документы.
- **Почему.** Galdhold Р12 («ни строки кода наружу»), DPlang — закрытый
  проект с проприетарной лицензией.

### Д18. Лицо автора — в личном бренде; источник — его фотография
- **Решение.** Автор показывает лицо в личном бренде. Решение автора
  4 октября 2026: прислал фотографию со словами «Референс моего образа»
  (закрывает ОР-2). Фотография —
  `assets/reference/author/2026-10-04-author-reference-01.jpg`,
  `REFERENCE_IMAGE` (`docs/PROVENANCE.md`, A-001).
- **Почему.** Человек — главный объект личного бренда
  (`docs/brand/VISUAL_SYSTEM.md`); фотографии автора на открытых
  площадках до этого не было (`docs/audits/2026-10-04-SOCIAL_AUDIT.md`, §9).
- **Следствия.**
  - Обработка — только кадрирование и тон (Д10); черты лица не
    меняются, генерация «по мотивам» не делается.
  - Домашний интерьер на фото — личное (Д2): в работах фон не должен
    читаться — плотное кадрирование и затемнение.
  - Каждая работа с портретом утверждается автором отдельно (гейт
    Brand, `QUALITY_MODEL.md`).
  - Кто сделал снимок, неизвестно; права фотографа для публичного
    использования подтверждает автор (`docs/legal/RIGHTS_MATRIX.md`).

### Д19. TikTok `@dpsmpx` — площадка автора в системе
- **Решение.** Аккаунт `https://www.tiktok.com/@dpsmpx` входит в
  систему (идентичность, ссылки, модель площадки
  `docs/platforms/TIKTOK.md`, перечисление площадок в схемах, формат
  `tiktok_vertical`). Роль — короткие вертикальные клипы из настоящего
  рендера (RESULT, PROJECT, RELEASE), из того же материала, что YouTube
  Shorts; язык — русский (язык аккаунта `ru`, Д8). Отдельный ритм не
  заводится.
- **Почему.** Просьба автора 4 октября 2026 (передана в
  `docs/session/HANDOFF.md`). Роль выведена из стратегии: TikTok — та же
  вертикальная форма, что Shorts; доказательство — настоящий рендер
  (`CONTENT_STRATEGY.md`, §3). Срез — `docs/audits/2026-10-04-TIKTOK_AUDIT.md`.
- **Следствия.** Публикует только автор (Д12). Официальные размеры
  TikTok даны для рекламы — формат `verified: false` (Д13). Роль и язык
  автор может пересмотреть — правкой этого решения.

### Д20. Имя автора открыто: «Борис Давыдов» рядом с `dpsmpx` (закрывает ОР-1)
- **Решение.** Публичная идентичность — имя **Борис Давыдов** (EN
  **Boris Davydov**) рядом с псевдонимом **`dpsmpx`**. Псевдоним остаётся
  handle на всех площадках; имя его не заменяет. Главная сущность
  сайта — «Борис Давыдов / dpsmpx» (`PLATFORM_VISION.md`, §94).
  Написание: кириллица — подпись статей Telegraph автора (поле
  `author_name` «Борис Давыдов» со ссылкой на `t.me/dpsmpx`, публичный
  API Telegraph, 04.10.2026); латиница — из постановки автора. Факт —
  AU-NAME (`data/facts/facts.yaml`).
- **Почему.** Решение автора 4 октября 2026 (ответ на вопрос сессии
  по ОР-1). Имя уже связано с проектом публично (статьи Telegraph,
  IC-03); заявка в Роспатент опубликует его в реестре.
- **Следствия.**
  - IC-03 закрыт; статьи Telegraph не переподписываются.
  - Имя — не разрешение на личное: работа, учёба, город, семья — по
    ОР-8, как раньше (Д2).
  - Затронутые объекты (`PROCESS.md`, §4): CI-0001 — подпись
    изображения пересматривается на ревизии (`TODO.md`); промпты и
    шаблоны больше не запрещают имя.
  - Решение необратимо по сути (имя, раз связанное с проектами, не
    «забирается»); отмена — только правкой здесь и не удаляет уже
    опубликованное.

### Д21. Сайт `dpsmpx.com` — центральная точка публикации и архив
- **Решение.** Собственный сайт автора — **источник истины для
  публикаций и постоянный архив**; соцсети — каналы распространения
  ниже по потоку (`PLATFORM_VISION.md`, §4, §25, §118). Адрес рабочего
  сайта — **`https://dpsmpx.com/`** (решение автора 04.10.2026).
  Языки (дополняет Д8): русский — основной (новости, дневник); главная,
  «обо мне» и страницы проектов — ещё и на английском, как языковой
  вариант одной канонической версии (Д22). Устройство —
  `docs/platforms/WEBSITE.md`.
- **Почему.** Площадки меняют API, правила и доступность; контент и
  история публикаций, которые живут только на них, автору не
  принадлежат. Свой сайт и Git-репозиторий переживут любую площадку
  (§120).
- **Следствия.**
  - Домен на 04.10.2026 **не зарегистрирован** (RDAP Verisign — 404,
    DNS — NXDOMAIN): регистрация и хостинг — ОР-11. До этого — staging
    (локальная сборка, закрыта от индексации).
  - Точка входа (`CONTENT_STRATEGY.md`, §6): после запуска сайта — сайт;
    до запуска — README профиля GitHub и закреплённая запись канала.
  - Сайт не зависит от соцсетей: на нём нет встраиваний, без которых
    страница не работает; ссылки на площадки — только исходящие.

### Д22. Канонический контент независим от площадок; варианты — производные
- **Решение.** Материал создаётся один раз как **каноническая версия**
  объекта (`content/items/<id>/canonical/vN.md`): смысл, факты, ссылки,
  медиа — без разметки площадок. Версии нумеруются (v1, v2…);
  зафиксированная версия не меняется — правка = новая версия, разница
  видна (`diff`). **Вариант площадки** (`variants/<площадка>.<язык>.md`)
  — производная с `source_version`: своя длина, порядок, CTA, формат
  медиа. Русский и английский — языковые варианты одного канона, а не
  два источника истины. Подробно — `docs/content/CANONICAL_MODEL.md`.
- **Почему.** Постановка, §1, §9–10, §26–27, §78. Копия одного текста на
  пять площадок уже запрещена (гейт Platform); канон делает «одна
  истина — разные формы» (`CONTENT_STRATEGY.md`, §5) проверяемым.
- **Следствия.** `ContentItem` расширен до `content_item/v2` (Д31);
  `copy/` объектов v1 — это варианты без канона, переносятся
  миграцией. Цепочка «факты → канон → генерация → правки человека →
  вариант → публикация» восстанавливается по файлам и журналу (§89).

### Д23. Модульный монолит; адаптеры площадок заменяемы; ядро — офлайн-первым
- **Решение.** Одна программа — пакет `tools/cs` с модулями `core/`
  (модель, валидатор, движок публикации, журнал), `adapters/` (по
  адаптеру на площадку за общим интерфейсом `PlatformAdapter`) и
  `site/` (генератор сайта). Ядро не знает площадок по имени: всё
  площадочное — в адаптере и в `data/platforms/`. Создание, факты,
  правка, версии, предпросмотр и сборка сайта работают без сети.
  Микросервисов, распределённой очереди, Kubernetes, облачного бэкенда
  нет (§115).
- **Почему.** `docs/research/publishing/SYSTEM_DESIGN.md`, §1: нагрузка —
  единицы операций в день, команда — один человек; распределённость
  даёт только цену. Сменился API площадки — меняется её адаптер, а не
  модель, кампании, сайт или аналитика (§69).
- **Следствия.** Новый модуль — в существующий пакет, а не второй
  инструмент (`CLAUDE.md`). Граница «ядро не импортирует адаптеры
  площадок» проверяется тестом.

### Д24. Публикация транзакционна и идемпотентна
- **Решение.** Каждая публикация проходит prepare → validate →
  запись `PUBLISHING` → publish → verify → запись `PUBLISHED` или
  `FAILED` в **журнал публикаций** (`data/publications/<окружение>.jsonl`,
  только дописывание). Ключ идемпотентности — хэш объекта, варианта,
  версии варианта, адресата и окружения; есть `PUBLISHED` по ключу —
  повтор не публикует. Исход неизвестен (обрыв после отправки) —
  `UNKNOWN`: повтор только после проверки на площадке или решения
  автора. Повторы — только временных ошибок, с экспоненциальной
  задержкой и потолком попыток, каждая — в журнале. Ошибки площадок
  приводятся к кодам (`AUTH_EXPIRED`, `RATE_LIMITED`, `MEDIA_REJECTED`,
  `INVALID_CONTENT`, `PERMISSION_DENIED`, `PLATFORM_UNAVAILABLE`,
  `INVALID_DESTINATION`, `OUTCOME_UNKNOWN`, `UNKNOWN_PLATFORM_ERROR`).
  Состояния публикации и состояния контента — разные (§14).
- **Почему.** §15–18, §47, §56. Площадки не дают транзакций, нативная
  защита от дублей есть только у VK (`PLATFORM_APIS.md`, §7).
- **Следствия.** Лимиты и повторы — у каждого адаптера свои (§57).
  Недоступная площадка не трогает канон: публикация ждёт (§67).
  Устройство — `docs/content/PUBLISHING.md`.

### Д25. Окружения, режимы и адресаты
- **Решение.** Окружения: **development** (только имитации площадок),
  **staging** (тестовые адресаты: закрытый тестовый канал, staging
  сайта), **production**. Режимы запуска: **dry-run** (по умолчанию:
  всё готовится, проверяется и показывается, наружу — ничего),
  **safe** (только staging-адресаты), **production** (явный флаг).
  Адресат — запись в `data/platforms/destinations.yaml` с явными id
  (канал, аккаунт, площадка), окружением, брендом и **ссылкой** на
  учётные данные (`credential_ref`), а не значением. Перед публикацией
  адаптер сверяет, от чьего имени и куда идёт запрос, с этими id;
  адресат не выводится из имени пользователя или свободного текста.
- **Почему.** §51–55, §105. Одна ошибка адресата (личный канал вместо
  проектного, рабочий вместо тестового) необратима.
- **Следствия.** Учётные данные staging и production не совпадают
  (проверка `destinations`); разработка по умолчанию идёт в staging.

### Д26. Вывод ИИ — непроверенный вход; роли
- **Решение.** Любой текст и медиа от ИИ — `trust: unverified`, пока не
  прошёл валидатор (`ContentValidator`: поля, факты, ссылки,
  запреты, ограничения площадки, происхождение). Роли: читатель,
  редактор, рецензент, публикатор, администратор; **автор** —
  все роли; **сессия ИИ** — генератор и рецензент: пишет черновики и
  критику, готовит пакет, но не одобряет, не держит рабочих токенов и
  не публикует в рабочие адресаты. Агенты — без права записи в
  рабочий слой публикации (§86).
- **Почему.** §45, §86–87; ошибки ИИ уже были главной находкой аудита
  канала (Д7).
- **Следствия.** Одобрение и рабочая публикация отказывают, если
  запущены из сессии Claude Code (это защита от случайности, а не
  граница безопасности: граница — токенов в сессии нет). Исключение —
  выгрузка сайта из локальной сессии после «да» автора (Д36); одобрение
  по-прежнему только у автора.
  `docs/content/GOVERNANCE.md`.

### Д27. Бренды автора и проектов в публикации разделены
- **Решение.** Бренды — `data/identity/brands.yaml`: автор, Galdhold,
  DPlang (дальше — новые проекты), у каждого тон, визуальный стиль,
  разрешённые и запрещённые темы, CTA, официальные ссылки. Объект
  выбирает режим **PERSONAL / PROJECT / MIXED** и бренды; адресат
  принимает только свои бренды (`accepts_brands`): новость DPlang не
  уйдёт в дневник Galdhold, личный пост — в будущий официальный канал
  проекта.
- **Почему.** §91–94; развитие Д9 (бренд автора отдельно от брендов
  проектов) на публикацию.
- **Следствия.** Сайт связывает бренды вокруг автора (Д21), не
  превращаясь в портал проекта.

### Д28. Факты подставляются из источников; зависимости и устаревание
- **Решение.** Числа, даты, версии, ссылки в тексте — подстановки
  `{{fact:ID}}`, `{{link:ID}}`, `{{release:…}}` из реестра фактов, ссылок
  и релизов (`data/releases/`), а не переписанные руками значения.
  Каждая каноническая версия и вариант при фиксации записывают
  зависимости с отпечатками (факты, ассеты, версия канона); изменился
  источник — объект **STALE**, одобрение по хэшу недействительно.
- **Почему.** §21–24: ИИ не придумывает метрики, даты, релизы и числа;
  смена версии или ссылки должна находить всё производное.
- **Следствия.** Опубликованное устаревшее не переписывается молча —
  проверка `stale` называет его, решает автор (новая версия или
  оставить как историю).

### Д29. Аналитика: нормализованная модель; метрики не определяют истину
- **Решение.** Метрики приводятся к событиям `Impression, View, Click,
  Reaction, Comment, Share, Subscriber, Conversion, Retention` с
  привязкой к кампании, объекту, варианту, площадке и публикации.
  Источник данных — по Д15 (ручной импорт выгрузок); сбор через API
  площадок — отдельное решение фазы 10. Вывод «почему» — всегда
  `INTERPRETATION`; рекомендация системы не меняет стратегию: смена
  стратегии — правка здесь с одобрения автора.
- **Почему.** §58–62; Д14, Д15.
- **Следствия.** Эксперименты — как раньше (Д14), с привязкой к
  публикациям.

### Д30. Архив, резервирование и экспорт
- **Решение.** Канон, медиа, происхождение и журнал публикаций живут в
  Git; сайт — постоянный архив опубликованного. Соцсети — не
  резервная копия. Резервирование: Git на GitHub + локальная копия +
  внешняя копия у автора; выгрузка всей базы в переносимом виде —
  `python3 -m tools.cs bundle`. Сценарии восстановления —
  `docs/operations/DISASTER_RECOVERY.md`.
- **Почему.** §25, §65–66, §109–110, §118, §122: главная собственность
  автора — база знаний, контент, медиа, происхождение и история
  публикаций.

### Д31. Версия схемы и явные миграции
- **Решение.** У каждого файла данных — версия схемы (`schema:
  content_item/v2` = `content_schema_version` 2). Переход — только
  явной миграцией (`python3 -m tools.cs migrate`, сначала пробный
  прогон), без тихих разрушающих изменений; старые версии читаются,
  пока не перенесены.
- **Почему.** §111–112. До запуска рабочего сайта формат может меняться
  быстрее; после — только миграциями.

### Д32. Сайт — статический, собирается инструментами системы
- **Решение.** Сайт — статические файлы, которые собирает генератор
  `tools/cs/site` из той же модели (проекты, факты, канон, журнал
  публикаций); тема — `website/`. Фиды Atom (`/feed.xml`), RSS
  (`/rss.xml`), JSON Feed (`/feed.json`); `/sitemap.xml`, `/robots.txt`;
  статический `/api/v1/` (проекты, записи) для своих клиентов. Staging
  закрыт от индексации. Хостинг — Beget, выгрузка rsync (Д35; прежняя
  рекомендация Cloudflare Pages снята 04.10.2026).
- **Почему.** `docs/research/publishing/WEBSITE.md`: статика решает
  задачу дешевле, проще и безопаснее CMS и своего бэкенда (§32–33);
  свой генератор — одна модель и одни проверки вместо двух; выход
  переносим.
- **Следствия.** Разделы «дневник», «статьи», «релизы» — категории одной
  ленты `/news/` (адрес записи не зависит от раздела).

### Д33. Возможности площадок — данные; у каждой площадки — ручной путь
- **Решение.** Что площадка позволяет — `data/platforms/capabilities.yaml`
  (уровни FULLY_AUTOMATED, SEMI_AUTOMATED, MANUAL_APPROVAL_REQUIRED,
  MANUAL_ONLY, UNSUPPORTED) и таблица
  `docs/platforms/PUBLISHING_CAPABILITY_MATRIX.md`. Для каждой площадки
  есть **ручной путь**: пакет публикации (текст, медиа, адресат,
  чек-лист), по которому автор публикует сам; после ручной публикации
  адрес записывается в журнал (`publish --record-manual`). Скрейпинг и
  обход ограничений площадок — нет (§90).
- **Почему.** `PLATFORM_APIS.md`: VK даёт права на стену по запросу,
  YouTube и TikTok без аудита публикуют приватно, личный профиль
  Telegram — только руками.
- **Следствия.** Изменение API — правка данных и адаптера, а не
  архитектуры (§3, §69).

### Д34. Сайт разрабатывается в репозитории, пока автор не скажет «сайт готов»
- **Решение.** Сайт `dpsmpx.com` — **постоянная задача**: каждая сессия
  продолжает его разработку в этом репозитории (генератор `tools/cs/site/`,
  тема `website/`, данные `data/website/`, страницы из канона и фактов),
  пока автор явно не скажет **«сайт готов»**. Работа идёт в staging:
  сборка `build/site/staging`, `python3 -m tools.cs site serve`,
  предпросмотр. Рабочий выпуск (выгрузка на хостинг, публичный адрес,
  ссылки на сайт из профилей) — только после слов автора «сайт готов» и
  ОР-11 (домен и хостинг).
- **Почему.** Решение автора 4 октября 2026: «Уже разрабатывай сайт
  внутри репозитория, пока я не скажу тебе что сайт готов, работай с ним
  в репозитории».
- **Следствия.**
  - Исключение из правила «следующую задачу ROADMAP без поручения не
    брать» (`CLAUDE.md`): задачи сайта (фаза П2, список «Сайт — в
    работе» в `ROADMAP/ROADMAP.md`) сессия берёт без отдельного
    поручения; остальные правила (решения, факты, одобрение, Д12) — как
    всегда.
  - Что сделано и что осталось по сайту — в `ROADMAP/ROADMAP.md`, П2, и
    в `docs/session/HANDOFF.md` каждой сессии.
  - Тексты сайта — по-прежнему контент: production показывает только
    одобренное автором (Д12, Д21); staging — всё, с плашкой «черновик».
  - Решение закрывается одной фразой автора «сайт готов» — тогда
    запись в историю (§4), П2 — к выпуску (П2-01, П2-02, П2-05).

### Д35. Рабочий сайт — на Beget; выгрузка — rsync из системы публикации
- **Решение.** Рабочий сайт `dpsmpx.com` — на виртуальном хостинге
  **Beget** (оплачен автором на 2 года). Выгрузка — **rsync по SSH**
  готовой production-сборки в каталог сайта на Beget
  (`~/dpsmpx.com/public_html/`) командой из `data/website/site.yaml`
  (`environments.production.deploy`); её запускает система:
  `publish <объект> website.* --to site-production --production` (новая
  или изменённая запись — с одобрением и журналом) или
  `site deploy` (тема и код сайта без новой записи; выгружается та же
  production-сборка из журнала). Адрес выгрузки
  (`логин@сервер:путь`) — в переменной окружения автора
  `CS_PROD_SITE_DEPLOY_TARGET`, SSH-ключ — только на его машине; в Git
  — ни того, ни другого. Заголовки и страница 404 — `.htaccess`
  (Apache), а не `_headers`. Сборка в Git не хранится; GitHub Actions
  и bare-репозиторий на сервере не используются.
- **Почему.** Ответы автора 4 октября 2026 на вопросы сессии: «beget,
  сайт уже куплен на 2 года», выгрузка — «rsync из publish». Рассмотрены
  и отклонены: публичный репозиторий + Actions (противоречит Д3 и Д12;
  открыл бы весь репозиторий, а сайт — малая его часть) и push в
  bare-репозиторий с хуком (сборку пришлось бы коммитить; push обходил
  бы одобрение и журнал, Д12, Д24).
- **Следствия.**
  - ОР-11: хостинг выбран. Домен — автор сообщил, что зарегистрирован;
    реестр `.com` на 04.10.2026, 19:16 UTC, его не видит (RDAP Verisign
    и rdap.org — 404, DNS — NXDOMAIN): сверить в панели Beget, ОР-11
    открыт по домену и DNS.
  - Первая выгрузка — по Д34, после слов автора «сайт готов»: до них в
    `site.yaml` `production.live: false`, и выгрузка отказывает.
  - Работают ли директивы `Header` (CSP и др.) для статики на Beget —
    **UNKNOWN** (в базе знаний Beget описан `ErrorDocument`, про
    `mod_headers` нет): проверить `curl -I` после первой выгрузки (П2-02).
  - `docs/platforms/WEBSITE.md`, `docs/operations/CREDENTIALS.md`
    («Сайт: Beget»).

### Д36. Выгрузку сайта запускает локальный Claude Code после «да» автора
- **Решение.** Рабочую выгрузку **сайта** (`publish … website.* --to
  site-production --production`, `site deploy`) может запустить
  **локальная** сессия Claude Code на машине автора — только после
  явного подтверждения автора на каждую команду. Подтверждение — запрос
  разрешения Claude Code: правила `ask` в `.claude/settings.json` на
  `python3 -m tools.cs publish`, `python3 -m tools.cs site deploy`,
  `rsync`, `ssh`, `scp`, `sftp`; запрет чтения `~/.ssh/**`. Перед
  выгрузкой сессия показывает, что изменится (`git diff`,
  `site deploy --dry-run`). Облачная сессия (`CLAUDE_CODE_REMOTE`) не
  выгружает никогда: ключа у неё нет, и система отказывает. Без
  изменений остаётся: одобряет версии только автор (`approve` — в его
  терминале, Д26); без действующего одобрения вариант на production не
  попадает (Д12); рабочая публикация на другие площадки и удаление
  рабочих публикаций из сессии ИИ запрещены.
- **Почему.** Ответ автора 4 октября 2026 на вопрос «кто запускает
  рабочую выгрузку»: «Claude Code локально с «да»».
- **Следствия.**
  - Исключение из Д12 и Д26 только для класса «выгрузка сайта»:
    `data/policy/publication.yaml`, `local_session_production: [website]`.
  - Граница честно: ключ на машине автора технически доступен
    локальному агенту. Правила `ask` по документации Claude Code
    спрашивают в любом режиме (и в auto, и в bypassPermissions; в
    `dontAsk` такая команда запрещается), но сверяют текст команды, а не
    программу — это защита от случайности, а не граница безопасности.
    Рекомендовано: отдельный SSH-ключ только для Beget; `BatchMode` —
    без интерактивных паролей.
  - `CLAUDE.md` («Публикация»), `docs/content/PUBLISHING.md`,
