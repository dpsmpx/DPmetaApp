# Решения

Здесь записано, **что решено и почему**. Это источник истины: если другой
документ расходится с решением, прав этот документ, а расходящийся
исправляется. Решение меняется только правкой здесь — новым решением со
ссылкой «заменяет D-NN» и строкой в разделе «История», а не молча в
другом месте.

Правила журнала (как в process-kit DP-Verify,
`DP-Verify:docs/direction/TECHNICAL_TASK.md`, §10.2):

- номер — `D-NN` латиницей, не переиспользуется и не меняется;
- поля — «Статус», «Решение», «Почему», «Проверка»; решение без проверки
  — пожелание; «Отклонено» и «Следствия» — когда есть что сказать;
- чужой номер — с именем проекта: `DPpass:D-12`, `DPmeta:C-05`.

Поля, сплошную нумерацию и ссылки держит `tools/check/run.sh` (проверки
`process.decisions` и `docs.refs`).

## Какой документ за что отвечает

| Документ | Отвечает на вопрос |
|---|---|
| `docs/direction/DECISIONS.md` | что решено и почему — источник истины |
| `CLAUDE.md` | краткие правила, обязательные в каждой сессии ИИ |
| `MESTER_TECHNICAL_TASK_ROADMAP.md` | мастер-ТЗ автора: порядок экосистемы (фаза A — законченные системы, фаза B — приложение) и что приложением быть не должно; старше ТЗ (D-25) |
| `docs/direction/TECHNICAL_TASK.md` | что строится в версии 1.0 и как проверяется готовность — черновик для фазы B, контракт версии после влития (D-25) |
| `ROADMAP/ROADMAP.md` | этапы, их порядок и состояние |
| `TODO.md` | незаконченное: хвосты, вопросы за автором, подтверждённый долг |
| `docs/PROCESS.md` | зачем каждое правило процесса и откуда оно взято |
| `docs/PROVENANCE.md` | происхождение всего чужого: зависимостей, данных, идей |
| `docs/direction/REQUEST.md` | постановка автора — требования, не решения |
| `README.md` | вход для человека; не источник истины |

Порядок старшинства при расхождении: `DECISIONS.md` → `CLAUDE.md` →
мастер-ТЗ `MESTER_TECHNICAL_TASK_ROADMAP.md` (D-25) → ТЗ → `ROADMAP/` →
`TODO.md` → `docs/`. Код, который решение ещё не догнал, —
не противоречие, а открытый пункт `TODO.md`.

**Статус «предложено (этап 0)»** — решение записано сессией вместе с ТЗ
по постановке автора; оно принимается, когда автор вливает PR с ТЗ, а
ответы на вопросы ТЗ (§19) могут его изменить — тогда новым решением.

## Решения

### D-01 — Назначение: личный пульт автора; о проекте прав его репозиторий

**Статус.** Принято — ответ автора 25 октября 2026. Предложено (этап 0),
5 октября 2026; назначение — из постановки автора
(`docs/direction/REQUEST.md`, Т1, Т7). Частично заменено D-27 (10
октября 2026): не пульт над внешними программами, а одна среда — системы
активных репозиториев переносятся внутрь в фазе B; до переноса источник
истины о проекте — его репозиторий, как здесь.

**Решение.** DPmetaApp — мобильный пульт одного пользователя, автора,
над экосистемой его репозиториев: показывает состояние проектов, ход
разработки, сайт, аккаунты Claude и статистику и запускает действия.
Источник истины о проекте — его репозиторий (журнал решений, код,
проверки); приложение хранит только наблюдения о нём и выводимое из них
(D-04) и не заводит вторых, расходящихся копий решений, стадий и задач.

**Почему.** Так устроена вся экосистема: о себе прав сам репозиторий
(`DPmeta:M-02`), а DPmeta — знание между репозиториями, а не власть над
ними (`DPmeta:M-01`). Пульт, который хранил бы «своё» состояние проектов,
стал бы ещё одним устаревающим источником.

**Проверка.** ТЗ, §3 («Не источник истины»); в модели данных нет полей
«статус проекта» и «стадия» как записей — только наблюдения и
производное (тесты `:core:metrics` с этапа 2).

**Отклонено.** Своя база задач и стадий в приложении с синхронизацией в
обе стороны — расходилась бы с журналами проектов.

### D-02 — Платформа — Android, нативно на Kotlin; iOS, веб и компьютер — не в 1.0

**Статус.** Принято — ответ автора 25 октября 2026: «да. Веб версия
будет уже после выпуска 1.0». Предложено (этап 0), 5 октября 2026;
«мобильное приложение» — из постановки автора.

**Решение.** Версия 1.0 — нативное Android-приложение на Kotlin для
телефона автора. iOS, веб-версия и приложение для компьютера в 1.0 не
делаются.

**Почему.** Телефон автора — Android с Termux: с него уже выгружается
сайт (`SocialMediaImage:tools/termux/dpsmpx-site-deploy.sh`). Опыт
экосистемы — Android: DPpass (Kotlin) и Galdhold (APK). iOS требует
платной программы Apple даже для своего устройства дольше семи дней —
ТЗ, §12. Нативное приложение даёт Keystore, биометрию, WorkManager,
виджет и интенты Termux без прослоек.

**Проверка.** ТЗ, §3 и §17 (L-01); в `settings.gradle.kts` (этап 1) — нет
целей, кроме JVM и Android.

**Отклонено.** Кроссплатформенные каркасы (Flutter, React Native) — лишний
слой без второй платформы; веб-приложение (PWA) — нет Keystore, Termux и
надёжного фона; Kotlin Multiplatform с iOS сейчас — объём без
пользователя (ядро на чистом Kotlin, D-03, оставляет этот путь открытым).

### D-03 — Ядро — модули на чистом Kotlin/JVM; Android — оболочка

**Статус.** Принято — ответ автора 25 октября 2026. Предложено (этап 0),
5 октября 2026.

Частично заменено D-28 (10 октября 2026): ядро — модули `dpai/` ниже
`orchestrator`; модули `:core:*` ТЗ, §6.2 — только то, чего в нём нет.

**Решение.** Логика — модули `:core:*` на чистом Kotlin/JVM без
Android-типов; `:app` — оболочка: интерфейс, хранилище ключей, фон,
интенты. Модуль `:app` подключается к сборке, только если найден Android
SDK; ядро собирается и тестируется без него. Раскладка модулей и
направления зависимостей — ТЗ, §6.2.

**Почему.** Сессии разработки идут в облачном контейнере без Android SDK —
ядро должно проверяться там целиком. Тот же приём работает в DPpass
(`DPpass:CLAUDE.md`, «Что это»; `DPpass:settings.gradle.kts`): ядро
проверяется на хосте, Android — только оболочка.

**Проверка.** С этапа 1: `tools/check/run.sh full` собирает и тестирует
ядро без SDK; проверка модулей — Android-типы только в `:app`,
направления зависимостей — по ТЗ, §6.2.

**Отклонено.** Один Android-модуль со всей логикой — не проверить в
облачной сессии без SDK и эмулятора.

### D-04 — Хранятся наблюдения; состояние и метрики выводятся; числа правил — в одном месте

**Статус.** Заменено D-34 (ответ автора 25 октября 2026). Предложено
(этап 0), 5 октября 2026.

**Решение.** Приложение хранит только наблюдения — неизменяемые записи
того, что получено из источника на момент `as_of`. «Кто работает»,
вопросы, метрики и тревоги вычисляются чистыми функциями из наблюдений и
правил; вычисленное — кэш, удаляемый без потерь. Все пороги, окна и веса
— в одном файле `Rules.kt` с `RULES_VERSION`; изменение смысла — новая
версия и запись в `docs/CHANGELOG.md`.

**Почему.** Так в трёх системах экосистемы: статус обучения — следствие
событий (`DPlearn:D-01`); выводы рынка — функции слоёв выше
(`DP_game_market_analytic_system:docs/ARCHITECTURE.md`); ядро
DPmonetization — чистые функции от данных, правил и даты среза
(`DPmonetization:tools/dpmon/__init__.py`). Это даёт воспроизводимость
(одни наблюдения — одни числа) и честную историю: смена правил
пересчитывает всё, а не только новое.

**Проверка.** С этапа 2: тест детерминизма `:core:metrics` (ТЗ, N-01,
A-03); проверка: числовые пороги вне `Rules.kt` в `:core:metrics` — находка.

**Отклонено.** Хранить вычисленное состояние и обновлять его — дрейф и
невозможность пересчёта.

### D-05 — Реестр проектов — из DPmeta; неизвестный формат — явная ошибка

**Статус.** Принято — ответ автора 25 октября 2026; дополнено D-35.
Предложено (этап 0), 5 октября 2026. Частично заменено D-43 (25 октября
2026): реестр — `dpmeta/tools/ecosystem.toml` здесь, после переезда
DPmeta. Дополнено D-46 (25 октября 2026): поле каталога подсистемы и
место `periphery` — образцом в корпусе.

**Решение.** Список проектов, их прежние имена, журналы решений и шаблоны
номеров приложение берёт из `DPmeta:tools/ecosystem.toml` (`schema = 1`);
поверх — локальные настройки показа (ТЗ, F-02). Другая схема или
неизвестный ключ — ошибка `REGISTRY_SCHEMA_UNSUPPORTED` на экране и
работа на последнем распознанном реестре. Любой формат проекта, который
не распознан, — «не распознано» с местом, а не догадка.

**Почему.** Реестр уже есть, его ведёт DPmeta и сверяет своими
проверками; второй реестр в приложении разошёлся бы с первым. Молча
показанные другие числа — урок страницы прогресса (`DPmeta:C-10`, «Что
ломает»).

**Проверка.** С этапа 2: корпус разборщика реестра (схема 1 с полем
`place` всех значений `control`, `core`, `sync`, `support`, `archive` —
`DPmeta:M-10`, `DPmeta:M-12`, D-26, D-27; прежнее `meta` и неизвестное
значение `place` — «не распознано»; неизвестный ключ;
другая схема); тест «нераспознанное не превращается в ноль».

**Отклонено.** Список проектов в коде приложения — новый проект
появлялся бы только с выпуском.

### D-06 — Изменения в других репозиториях — только их процессом

**Статус.** Заменено D-36 (ответ автора 25 октября 2026). Предложено
(этап 0), 5 октября 2026; «полный контроль» — из постановки автора,
форма — сессии.

**Решение.** Приложение не правит журналы решений, `CLAUDE.md`, `TODO.md`
и `main` других репозиториев напрямую и не переписывает историю.
Изменения идут так: поручение сессии Claude Code того репозитория
(маршрут, ТЗ F-22, F-25), комментарий, ревью или issue; вливание PR —
только действием автора уровня 2 (D-07), способом, не переписывающим
историю `main`.

**Почему.** У каждого репозитория свои правила и проверки, а решение
меняется только записью в его журнале (`DPmeta:E-01`). История `main`
не переписывается — на этом держатся ссылки `путь@sha` DPprofile
(`DPmeta:C-04`). Прямая правка в обход сессии и проверок — тот же класс
ошибки, что выгрузка в обход системы (`DPmeta:RISK-08`).

**Проверка.** С этапа 5: в `:core:actions` нет команд записи файлов в
репозитории и force-обновления ссылок; проверка запрещённых вызовов в
`tools/check` (ТЗ, A-06).

**Отклонено.** Редактор файлов репозиториев в приложении с коммитом в
`main` — обходит проверки и сессии.

### D-07 — Уровни действий 0–3, подтверждения и журнал действий

**Статус.** Принято — ответ автора 25 октября 2026; уровень 3 заменён
D-37. Предложено (этап 0), 5 октября 2026.

**Решение.** Каждое действие относится к уровню: 0 — чтение; 1 —
обратимое и видимое (комментарий, ревью, issue, запуск маршрута) —
одно нажатие с показом, что уйдёт; 2 — значимое (влить или закрыть PR,
удалить влитую ветку, выгрузка сайта ярлыком) — экран «что изменится» и
биометрия или PIN устройства; 3 — запрещено и в коде отсутствует
(перезапись истории, удаление репозитория, настройки и защита веток,
мутирующие вызовы Admin API, rsync и ssh, одобрение контента за автора).
Каждое действие уровня 1 и 2 пишется в журнал действий только на
добавление. Перечень — ТЗ, §6.5.

**Почему.** «Полный контроль» с телефона — это и полная цена ошибки
одним касанием. Уровни делают цену видимой; журнал отвечает на «что я
сделал из приложения» без памяти. Образец — правила `ask` для выгрузки в
SocialMediaImage (`SocialMediaImage:Д36`).

**Проверка.** С этапа 5: тесты политики `:core:actions` (уровень 2 без
аутентификации не исполняется; запись в журнал на каждое действие);
проверка запрещённых вызовов в `tools/check` (ТЗ, A-06).

### D-08 — Аккаунты Claude — только официальными способами: ключи API и маршруты

**Статус.** Принято — ответ автора 25 октября 2026; дополнено D-38.
Предложено (этап 0), 5 октября 2026; «несколько аккаунтов Claude» — из
постановки автора. Изменяющие вызовы Admin API не нужны — D-44. Вызовы
Claude API — своим HTTP, без официального SDK — D-81.

**Решение.** Аккаунт Claude в приложении — профиль одного из двух видов,
каждого — любое число. **API-профиль:** ключ API организации Console для
Messages и Models и, если автор даст, Admin-ключ только для отчётов
Usage, Cost и лимитов (только GET, по списку в коде). **Профиль
подписки claude.ai:** маршруты Claude Code с токенами API-триггера
`/fire`; входа в аккаунт claude.ai и OAuth-токенов подписки в приложении
нет. Вызовы Claude API — своим HTTP подсистемы «AI», без официального SDK
(D-81).

**Почему.** Политика Anthropic не разрешает сторонним продуктам
предлагать вход claude.ai и использовать OAuth-токены подписок; разрешена
аутентификация ключом API. Маршрут с API-триггером — документированный
способ запустить облачную сессию из своей программы по токену этого
маршрута (ТЗ, приложение В). Так аккаунты подписки и API используются
полностью и без риска блокировки аккаунта.

**Проверка.** С этапа 5: в `:core:claude` нет кода OAuth claude.ai; Admin
— только GET по списку (тест); маршрут — только `/fire` своего маршрута.

**Отклонено.** Вход claude.ai через встроенный браузер и перехват
токена — нарушение условий и риск блокировки аккаунтов; общий прокси с
одним ключом на все аккаунты — теряется раздельный учёт.

**Следствия.** Расход подписок не измеряется (ТЗ, L-03); сессии
открываются в приложении Claude или браузере (ТЗ, L-04).

### D-09 — Секреты — только на устройстве, под ключом Android Keystore

**Статус.** Принято — ответ автора 25 октября 2026. Предложено (этап 0),
5 октября 2026.

**Решение.** Токены GitHub, ключи API, токены маршрутов хранятся только
на устройстве: запись — AES-256-GCM с ключом записи как дополнительными
данными, ключ данных обёрнут ключом Android Keystore; для секретов ключ
требует аутентификации пользователя при показе секрета и действиях
уровня 2. Данные — в `noBackupFilesDir`, резервные копии Android
выключены. В коде секрет — тип `Secret` с `<redacted>` в `toString()`.
В репозитории секретов нет, даже «тестовых».

**Почему.** Телефон — самое уязвимое место пульта, у которого есть права
на все репозитории и аккаунты (ТЗ, T-01, T-02). Схема повторяет
проверенную в DPpass (`DPpass:D-19`, `DPpass:D-11`); правило «секретов в
репозитории нет — и это проверяется» — общее для экосистемы
(`DPmeta:E-09`).

**Проверка.** `tools/check/run.sh` — проверка `security.secrets` (токены и
файлы ключей); с этапа 3 — тесты `Secret` и журнала, проверка манифеста
(`allowBackup=false`, правила извлечения данных).

### D-10 — Без телеметрии; сеть — только по списку адресов

**Статус.** Принято — ответ автора 25 октября 2026, кроме отчётов о
падениях и телеметрии: их заменяет D-39. Предложено (этап 0), 5 октября
2026.

**Решение.** Никакой телеметрии, аналитики, отчётов о падениях,
идентификаторов устройства и рекламы — ни своих, ни в зависимостях.
Сетевой слой пускает запросы только к адресам из списка в коде:
`api.github.com`, `github.com`, `api.anthropic.com`, `dpsmpx.com`,
`www.dpsmpx.com`; остальные — отказ `HOST_NOT_ALLOWED`.

**Почему.** Приложение видит закрытые проекты; любой лишний канал
наружу — утечка (`DPmeta:C-05`). То же правило у DPpass (`DPpass:D-12`)
и DP-Verify («ничего не отправляет наружу»).

**Проверка.** С этапа 2: тест `:core:net` на отказ чужого адреса; проверка
зависимостей — нет библиотек аналитики и отчётов о падениях (ТЗ, A-10).

### D-11 — Сайт: мониторинг — в приложении; выгрузка — только системой SocialMediaImage через Termux

**Статус.** Заменено D-40 (ответ автора 25 октября 2026). Предложено
(этап 0), 5 октября 2026; «полный контроль сайта» — из постановки
автора.

**Решение.** Приложение наблюдает сайт `dpsmpx.com` (доступность,
заголовки, API сайта, рассинхрон с `main` SocialMediaImage) и запускает
выгрузку только ярлыком автора
`SocialMediaImage:tools/termux/dpsmpx-site-deploy.sh` на переднем плане
Termux — пробный прогон и «да» вводятся в терминале. Адреса и ключа
выгрузки у приложения нет; rsync, ssh, scp, sftp в коде нет; stdin
ярлыку не передаётся.

**Почему.** Выгружают только команды системы SocialMediaImage, ярлыки
лишь вызывают их (`SocialMediaImage:Д35`), а «да» на каждую выгрузку даёт
автор (`SocialMediaImage:Д36`). Инцидент 5 октября 2026 показал, что

### D-24 — Приложение личное: нигде не публикуется, ставится только на устройства автора

запрещено.

**Отклонено.** Магазин, закрытое тестирование в магазине или открытая
выкладка APK «на будущее» — других пользователей у приложения нет.

### D-33 — Ветки сборок — одна на платформу: `apk_debug`, `linux_debug`, `windows_debug`

**Статус.** Принято — ответ автора 25 октября 2026 на вопрос сессии
«Какое правило для веток сборок принять в DPmetaApp?» — «Одна на
платформу». Распространяет `DP_AI_Orcestrator:D-81` на весь репозиторий;
частично заменяет `DPpass:D-35` (ветка `apk`).

**Решение.**
- **Ветки репозитория:** рабочие — в них идёт работа; `main` — весь код,
  туда вливается проверенное; по одной ветке сборок на платформу:
  `apk_debug` — APK всех подсистем, у каждой свой каталог (`dpai/`,
  `dppass/`); `linux_debug` — сборки для Linux; `windows_debug` — для
  Windows, когда они появятся.
- **Новая сборка заменяет прежнюю** своей подсистемы: ветка сборок — один
  коммит без истории `main`, каждая сборка — коммит-сирота и
  принудительный пуш (иначе APK по десятки МБ копились бы в истории).

  коммита ветки без изменений; README ветки называет коммит `main`, из
  которого собран каждый каталог.
- **Ветки сборок по версии** (`apk-0.1.0-dev.1-2026-10-11`, `linux-debug`)
  удаляет автор (облачной сессии удаление веток запрещено), когда их
  сборки есть в новой ветке или уже не нужны.
- Хук начала сессии ветки сборок как невлитую работу не показывает.
- Сборки — только для устройств автора (D-24): ветка сборок — не выпуск
  и не публикация.

**Почему.** Слово автора: одна ветка сборок на платформу вместо ветки на
каждую версию; старые сборки не копятся.

**Проверка.** На GitHub — рабочие ветки, `main` и ветки `*_debug`;
`.claude/hooks/session-start.sh` их не выводит.

**Статус.** Принято — ответы автора 4 ноября 2026 (формы сессии): «Синхронизация

  лимит REST не тратит; первое клонирование — вне предела 60 с (ТЗ, A-02
  уточнено): долгое, в фоне, лучше по Wi-Fi; холодный старт (N-02) его не
  ждёт.

**Почему.** Слово автора: всё на телефоне, без лишних запросов, и
репозитории сразу готовы для работы с ИИ.

**Проверка.** Тесты модуля клонов на JVM с локальными репозиториями

неотмеченный репозиторий не клонируется и читается REST; на устройстве —

### D-72 — Уточнение D-70: клоны в Linux-среде — `/root/repos`; недостающий репозиторий модель клонирует git-ом среды

**Статус.** Принято 5 ноября 2026 — при исполнении D-70 (сессия): в D-70

**Проверка.** `ClonesTest` (каталоги `владелец/имя`, основная ветка клона без

  (строка для экрана), `timeout` — минуты, 1…30. Неизвестный ключ — отказ.

  ввода аргументов; новая команда — правка файла с проверкой `tools/check`

- **План.** В Linux-среде план запуска не меняет: команда идёт в процессе
  приложения, вывод — на экране по ходу, «Остановить» — всегда, уход с

- **Уровни** (D-07). 0 — чтение: проверки и отчёты по клону, запись —

- **`repo.ff` вместо `git pull`.** Вместо `git pull --ff-only` приложения
  Б — `git merge --ff-only @{upstream}`: рабочее дерево догоняет

### D-84 — Мост Termux: команды реестра и проба готовности; итог — через изменяемый явный `PendingIntent`

**Статус.** Принято 10 ноября 2026 — при исполнении D-83 (сессия): мост
Termux (F-41, F-42) делается, Termux у автора — из F-Droid, папка
проектов — настройкой. Уточняет F-41 (неизменяемый `PendingIntent` итога
не вернёт), F-42, T-03 и L-05 ТЗ; для приложения целиком дополняет
`DP_AI_Orcestrator:D-46` («только `sshd`» — о подсистеме «AI»).

**Решение.**
- **Что уходит в Termux.** Только две вещи, обе — из кода и APK, не от
  человека, модели или репозитория: команда реестра `config/commands.toml`
  (её программа, аргументы и каталог, D-82) и проба готовности `ls -1 -d
  -p -- <пути>` — только чтение. `stdin` не передаётся никогда; уровень 2
  — только на переднем плане (F-41; в реестре его нет). Подсистема «AI»
  по-прежнему шлёт Termux только `sshd` (`DP_AI_Orcestrator:D-46`).
- **Где.** Клон — в папке проектов Termux под именем репозитория (или им
  же строчными — как ищет DPmeta): `<папка>/<имя>`; у подсистемы — её
  каталог в клоне DPmetaApp. Папка по умолчанию —
  `/data/data/com.termux/files/home/Projects` (D-83); выбор — вводом пути
  на экране «Команды» (`~/` — домашний каталог Termux): каталог Termux
  приложению не виден, есть ли папка — говорит проба. Путь — абсолютный,
  без `.`, `..`, `//` и управляющих знаков.
- **Перевод команды.** Программа гостя из `/bin`, `/usr/bin`,
  `/usr/local/bin` — та же программа Termux из `$PREFIX/bin`; программа из
  клона — от каталога команды. Аргумент `/root/repos` (корень клонов
  Linux-среды) — папка проектов; другие пути гостя `/root/…` — отказ:
  команда не для Termux. Остальные аргументы — как есть, без оболочки.
- **Итог.** `PendingIntent` на свой приёмник `exported="false"`: явный,
  разовый и **изменяемый** — Termux кладёт итог в extras при отправке, а у
  неизменяемого их отбрасывает система (вики Termux, `RUN_COMMAND`).
  Подменить получателя нельзя: компонент задан, права `FILL_IN_COMPONENT`
  нет; у вызова — свой адрес, ответ одного не попадёт к другому. Итог —
  чужой текст: на экране — без ESC-последовательностей и управляющих
  знаков; Termux обрезал вывод (100 КБ на оба потока) — так и сказано; на
  диск и в журнал вывод не пишется. Итога нет за предел времени команды —
  «могла остаться идти в Termux»: Termux команду извне не останавливает,
  и «Остановить» у него нет.
- **Готовность по шагам** (F-42): Termux установлен; версия 0.109 или
  новее и разрешение `RUN_COMMAND` объявлено (сборка Google Play — нет);
  разрешение выдано («Разрешить» и «Настройки приложения» на экране);
  Termux принимает команды приложений (`allow-external-apps` — по ответу
  пробы, с готовой строкой для Termux); для переднего плана — «поверх
  других окон» у Termux (чужое разрешение отсюда не проверить — шаг
  только говорит); папка; клон; программа и скрипт — пробой; нет
  программы — строка `pkg install` с пакетами Termux.
- **Уровни** — как в Linux-среде (D-82): 0 — сразу; 1 — окно «что
  изменится» и журнал `command.run` с `place = termux` и каталогом Termux.

**Почему.** D-83 — слово автора. Вики Termux даёт для итога
`FLAG_MUTABLE` на Android 12+; с `FLAG_IMMUTABLE` итога нет, а
безопасность явного изменяемого `PendingIntent` держится на заданном
компоненте и неэкспортируемом приёмнике. Проба `ls` — единственный способ
узнать о папке Termux, не открывая его каталог, и не создаёт ничего

### D-85 — Каталог событий и правила тревог — данными; движок — первое подходящее правило

**Статус.** Принято 10 ноября 2026 — при исполнении F-37, F-51…F-53
(этап 7, D-83 — «дальше этап 7»; сессия): ТЗ называет файлы
`config/events.toml` и `config/alerts.toml`, но не их формат и не то, какое
правило решает, если подходят несколько. Уточняет F-37, F-51, F-52, F-53.

**Решение.**
- **`config/events.toml`**, `schema = 1`, таблицы `[[event]]`: `type` —
  латиницей, части через точку (`pr.opened`); `title`; `source` —
  `sync`, `push`, `listener`, `app` (С, М, Л, П §8.1); `channel` — вид
  канала F-38: `claude`, `dev`, `social`, `site`, `questions`, `sync`;
  `fields` — текстовые поля для условий, `numbers` — числовые. Первый
  каталог — все типы §8.1.
- **`config/alerts.toml`**, `schema = 1`, таблицы `[[rule]]` в порядке
  проверки: `id`, `title`, `on` — тип каталога или маска `часть.*`;
  `action` — `notify`, `feed`, `digest`, `silent`; `channel` (нет — канал
  типа), `importance` — `low`, `default`, `high`; `enabled`; условия —
  `project`, `contains` (текст, без учёта регистра), `regex`, число —
  `field` из `numbers` типа с `at_least` и/или `at_most`; `days` — дни
  недели (`mon`…`sun`); антидребезг — `limit` за `window` минут по правилу
  и проекту; `quiet = false` — правило звучит и в тихие часы. Числа —
  целые (подмножество TOML без дробных). Правило с
  неизвестным типом, полем или неверным `regex` — отказ разбора
  `RULE_INVALID` с местом.
- **Движок** (`:core:notify`) — чистая функция «события, каталог,
  правила, время, тихие часы, недавно показанное → решения»: событие
  неизвестного типа отбрасывается с `RULE_INVALID`; решает **первое
  подходящее включённое правило** (как список правил брандмауэра: частное
  «промолчать» ставится выше общего «уведомить»); не подошло ни одно —
  только лента. В тихие часы `notify` — без звука, кроме правил с
  `quiet = false`; предел `limit` за `window` — дальше лента. «Что
  сработало бы» (F-53) — тот же движок по сохранённым событиям за 7 дней
  с пустой историей показа.
- **Правила по умолчанию** (F-37) — в `config/alerts.toml`; правка их в
  приложении и экспорт файлом (F-52) — следующим шагом этапа 7, поверх
  этого же формата.

**Почему.** F-51 и F-52 требуют данных, а не кода; первое подходящее
правило — понятный автору порядок, без весов и неожиданных сочетаний.

**Следствия.** ТЗ: F-37, F-51, F-53 — ссылкой сюда. Код: типы событий и
правил — `:core:model`, разбор — `:core:formats` с корпусом, движок —
`:core:notify`; код `RULE_INVALID` — в ядро и реестр кодов (ТЗ, §6.9);
события ленты (D-34) — типами каталога (`main` → `main.commit`, `decision` →
`decision.new`, `roadmap` → `roadmap.step.done`).

**Проверка.** Корпус `events` и `alerts` («ловит / пропускает»), свои
`config/events.toml` и `config/alerts.toml` в `OwnDocumentsTest`, тесты
движка в `:core:notify`.

### D-99 — Фактический Git и запуск по сохранённым файлам

**Статус.** Принято 11 ноября 2026 при исполнении поручения автора

### D-106 — Редактор: полный вид и дзен, постоянные вкладки и запуск

**Статус.** Принято 12 ноября 2026 по поручению автора; работа последнего
PR подтянута, работоспособность редактора на смартфоне подтверждена автором.
**Решение.** Полный интерфейс и дзен переключаются явно. Дзен отдаёт
экран коду: без панелей приложения, заголовков, сведений о файле/черновике,
подсказок о контроллере и дополнительных инструментов. Остаётся одна
компактная строка вкладок и действий: выйти, сохранить, полный/дзен,
запустить в реальном терминале. Это исключение к постоянным панелям D-61.

нажатия. Открытые пути/активная вкладка и настройки вида восстанавливаются
после перезапуска, отдельно от зашифрованного текста черновиков D-101.

Выход/системный назад спрашивают о несохранённых изменениях: сохранить
или отменить изменения; закрытие диалога оставляет работу открытой.
Явная запись и проверки исходных байтов/owner сохраняются. Подсветка
просмотра и редактора включается отдельно, по умолчанию в обоих режимах;
её скрытие не выключает языковую службу и правила Enter/скобок.
Запуск — явная команда в новой вкладке реального Linux-терминала,
сначала сохранить/отменить правки выбранного дерева. Для C++/Kotlin
используется настроенная команда проекта, флаги сборки не угадываются.
Существующие ограничения ручных CHECK/BUILD и занятого дерева сохраняются.
**Почему.** Поле кода должно занимать максимум площади мобильного экрана;
скрывать панели и быстро просматривать файл можно без потери черновиков.
**Проверка.** Хранилище вкладок/настроек, переходы режимов и выход с правками,
запуск/кавычки/запрет несохранённого дерева; сборка/Lint и приёмка смартфона.

### D-107 — Недостающие библиотеки IDE скачиваются по подтверждению

**Статус.** Принято 12 ноября 2026 по сообщению автора об отсутствии
ncurses.h и поручению предлагать скачивание необходимых библиотек.
**Решение.** Выбран вариант докачки, а не включения всех библиотек в APK.
После неудачного запуска IDE предлагает известные пакеты Linux для
заголовков, библиотек компоновщика и инструментов. Транзитивные зависимости
решает пакетный менеджер установленной Alpine; установка — явным
подтверждением через существующий механизм Linux, не командой в PTY.
Чужой вывод не становится именем пакета: только проверенный каталог;
неизвестные заголовки показываются отдельно, пакеты можно назвать вручную.

команда проекта сама не переписывается. После установки запуск не
повторяется автоматически — остаются проверки D-106. Обновление пакетов
доступно прежней кнопкой Linux; версии берутся из репозиториев среды.
**Почему.** Заголовки и библиотеки нужны в среде компилятора; все возможные
библиотеки нельзя включить в мобильный APK. Для ncurses нужны и заголовки,
и флаг компоновки — одна установка не устраняет обе причины.
**Проверка.** Диагностика Clang/GCC/linker, пакетные предложения, границы
потокового вывода, ограничение памяти, установка/Lint и приёмка телефона.

### D-108 — C++: готовый одиночный запуск и понятное восстановление тулчейна

**Статус.** Принято 12 ноября 2026 по отчёту автора о компоновщике,
crt/libgcc, заголовках, Permission denied при apk и noexec внешней памяти.
**Решение.** Для новых C++-файлов есть начальная команда одного файла:
C++20, clang++, явный lld, проверка инструментов/crt и уникальный бинарник
во внутреннем /tmp, с уборкой после выхода. Это уточняет D-106: команда
пользователя и многофайлового проекта автоматически не заменяется.
По ошибке предлагается целый тулчейн: build-base, clang, lld, compiler-rt;
заголовки, libstdc++, libgcc и binutils приходят зависимостями Alpine.
Пакеты/виртуальные имена проверяются по реальной базе среды. Новая кнопка
проверки проверяет запись в системные каталоги и компилирует/запускает
минимальный C++ со стандартными заголовками, не меняя исходники проекта.
Частично установленный тулчейн восстанавливается отдельным подтверждением
apk fix --depends через механизм без /proc. Ошибки записи, noexec/доступа,
места, компоновки, кода и завершения программы получают разные объяснения.
Состояние readonly не выводится из одной строки Permission denied;
rootfs и данные приложения автоматически не сбрасываются.
**Почему.** Пользователь должен выбрать файл и запустить его либо получить
понятное решение. Полный набор устраняет цепочку ручных исправлений;
стартеры, библиотеки по умолчанию и защита стека остаются штатными.
**Проверка.** Образцы всего отчёта, команда одного файла, apk add/fix без
/proc, виртуальные пакеты, сборка/Lint; запуск на Redmi — приёмка автора.

### D-109 — Python и Kotlin получают тот же сценарий запуска и решений ошибок

**Статус.** Принято 12 ноября 2026 по поручению автора распространить
запуск/диагностику/установку C++ на Python и Kotlin.
**Решение.** Python-файлы, одиночные Kotlin/JVM .kt и скрипты .kts имеют
начальные команды и типизированные объяснения ошибок. Python-модули
ставятся по подтверждению из PyPI в отдельное внутреннее venv проекта;
системный Python и .venv исходников не изменяются. Каталог сопоставляет
import с дистрибутивом, неизвестное требует выбора имени вручную.
Kotlin/JVM 2.4.10 ставится официальным архивом JetBrains после проверки
закреплённого SHA-256, JDK 21 — пакетами Alpine. JVM-библиотеки для
одиночного файла разрешаются из Maven Central через официальный main-kts,
с транзитивными зависимостями и явными координатами/версиями; Gradle-файлы
не меняются. Android/Compose/KMP/Gradle-файлу предлагается команда/профиль
его проекта с SDK/target, вместо угадывания проектной сборки.
Есть подтверждённые подготовка/проверка/восстановление сред, понятные
ошибки кода, модулей, classpath, JVM, доступа, места и подключения.
Команды папки разделяются по языкам, прежние метаданные читаются.
Существующая пользовательская команда меняется только явным сохранением;
запуск после установки — снова из IDE с проверками D-106/D-108.
**Почему.** На телефоне библиотеки и окружения должны докачиваться без
ручной цепочки команд, с реальным PTY и без изменения системного Python
либо произвольного редактирования файлов зависимостей проекта.
**Проверка.** Диагностика и аргументы, обратное чтение метаданных,
настоящие Python/venv/pip и Kotlin/JVM/скрипт/Maven на хосте, build/Lint,
отдельная приёмка Alpine arm64 под Android.

### D-111 — Хранилище — одно для IDE, терминала и ИИ: разделы, карта, секреты по разрешению

**Статус.** Принято 12 ноября 2026 — поручение и ответы автора (форма
сессии): «Всё хранилище должно быть едино между IDE и ИИ… чётко разделено
на несколько разделов: секреты, инструменты+библиотеки+утилиты, проекты;
слоты ИИ — отдельная категория»; «Физически, со ссылками», «Список без
значений», «По разрешению на секрет», «~/STORAGE.md + ИИ читает».
Частично заменяет D-72 (клоны — `/root/repos`), `DP_AI_Orcestrator:D-108`
(у ИИ на телефоне нет токена GitHub) — теперь по разрешению на секрет;
D-69 и T-01 не меняются.

**Решение.**
- **Одно хранилище.** Терминал, IDE и ИИ in-app Linux работают в одной
  домашней папке гостя `/root` и видят одно и то же: что поставлено через
  терминал, кнопками IDE или ИИ, — видно всем. Инструменты IDE (службы
  языков, SDK) больше не прячутся вне `PATH`.
- **Разделы — физически**, в `/root`: проекты (клоны пульта и свои
  проекты), инструменты (службы IDE, SDK, библиотеки, утилиты, модели; их
  `bin` — в `PATH` терминала, IDE и ИИ), слоты ИИ. Прежние пути
  (`/root/repos`, `~/.claude-slot-N`, `~/.local/share/dpai`, `/root/models`)
  остаются символьными ссылками на новые места: старые команды, документы
  и ИИ не ломаются. Перенос — один раз, с проверкой места и отчётом; точные
  имена каталогов — по прототипу (D-112) и ответу автора.
- **Секреты** — раздел приложения, не папка: список имён, где секрет
  используется, когда задан; заменить или удалить; значения не
  показываются никогда, файлов-секретов на открытом диске нет (Keystore,
  T-01).
- **Секрет для ИИ — по разрешению на каждый секрет**: у секрета — отметка
  «давать ИИ»; разрешённый секрет попадает в окружение сессии ИИ in-app
  Linux при её запуске, каждая выдача — запись в журнал (кому, когда,
  какой). По умолчанию — не давать.
- **Карта хранилища** — короткий `~/STORAGE.md`, пишет приложение: разделы,
  проекты (ветка, изменения), инструменты с версиями, службы IDE, SDK,
  модели, слоты, имена секретов (без значений) и разрешённые ИИ.
  Обновляется после установки, удаления, клона и при запуске; инструкция
  каждого слота ИИ ссылается на неё.

**Почему.** Слово автора: ИИ, терминал и IDE не должны жить в разных
мирах; порядок в `/root` и карта — чтобы ИИ находил нужное без поиска.

**Проверка.** Тесты переноса со ссылками и карты (JVM); проба: инструмент,
поставленный кнопкой IDE, виден в терминале и ИИ по `PATH`; журнал выдачи
секретов; на телефоне — пункт «На устройстве» в `TODO.md`.

### D-113 — Хранилище: пути, предел объёма и запас 1 ГБ; вкладки — в верхней панели

**Статус.** Принято 12 ноября 2026 — ответы автора (форма сессии) на
вопросы по прототипам D-112 и разделам D-111: «Принимаю, реализуй, но с
поправками…», «~/projects/<владелец>/<имя>», «Переменной окружения»,
«Инструменты: ~/tools/models». Уточняет D-111 и D-112; заменяет в D-101
«бюджет студии 20 ГБ» настройкой.

**Решение.**
- **Пути разделов** в госте: проекты — `~/projects/<владелец>/<имя>` для
  клонов GitHub, `~/projects/local/<имя>` — для своих проектов без GitHub;
  инструменты — `~/tools` (`~/tools/bin` — в `PATH`; модели —
  `~/tools/models`); слоты ИИ — `~/ai/<исполнитель>-<N>`. Прежние пути —
  ссылками (D-111).
- **Предел объёма** — настройка «Предел хранилища, ГБ»: `0` — всё
  свободное место телефона, больше нуля — столько гигабайт занимает
  приложение целиком (данные, Linux, проекты, инструменты, кэш).
- **Защита места.** Любая загрузка, установка (пакеты, службы, SDK,
  модели), клон и сборка заранее оценивают размер и не начинаются, если
  после них по расчёту приложение выйдет за предел или **на телефоне
  останется меньше 1 ГБ** — жёсткий запас, настройкой не меняется. Отказ
  называет числа: сколько нужно, сколько есть, что освободить. Размер
  неизвестен заранее — берётся осторожная оценка вида работы (названа в
  отказе).
- **Секрет для ИИ** — переменной окружения сессии со стандартным именем
  (`GH_TOKEN`, `ANTHROPIC_API_KEY`, `HF_TOKEN`; у своего секрета имя
  задаёт автор); на диск не пишется.
- **Вкладки разделов** (IDE: код, файлы, терминал, Git; AI: запросы,
  задачи, слоты, модели) — в верхней панели вместо заголовка: места под
  содержимое больше; поиск настроек и справки — тоже в верхней панели.

**Почему.** Слово автора: у телефона своя память, жёсткие 20 ГБ ему не
подходят, а заполнить её до нуля нельзя; место на экране — для кода.

**Проверка.** Тесты расчёта места (предел, `0`, запас 1 ГБ, неизвестный
размер) на JVM; на телефоне — отказ загрузки при нехватке места (пункт
`TODO.md`).

### D-114 — Секреты для ИИ: какие, под каким именем, где и с каким входом

**Статус.** Принято 12 ноября 2026 — ответы автора (форма сессии):
«Другим именем», «Токен GitHub, Ключи API профилей, Токен Hugging Face»,
«Вход раз за запуск», «Только телефон». Уточняет D-111 и D-113.

**Решение.**
- **Кому можно «давать ИИ»:** токену GitHub (`GH_TOKEN`), ключам
  API-профилей (по провайдеру: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`,
  `GEMINI_API_KEY`, `OPENROUTER_API_KEY`, `DEEPSEEK_API_KEY`,
  `MISTRAL_API_KEY`), токену Hugging Face (`HF_TOKEN`). Admin-ключи,
  токены маршрутов, токен и пароль облачной копии — только в списке, без
  переключателя. Одна переменная — один секрет: включённый второй
  выключает первый.
- **Имя для слота.** Переменная, которая у слота перекрыла бы вход по
  подписке (`ANTHROPIC_API_KEY` у Claude, `OPENAI_API_KEY` у Codex,
  `GEMINI_API_KEY` у Gemini), у этого слота удаляется, как прежде (D-29), а
  ключ он видит как `DPMETA_<имя>` (`DPMETA_ANTHROPIC_API_KEY`): подписка не
  сбивается, скрипты и SDK проекта берут ключ явно. Остальные слоты и
  терминал получают стандартное имя.
- **Где.** Только телефон: окружение процессов Linux в приложении (ходы
  ИИ «в приложении» и терминал). ПК-target секретов не получают. Значения
  на диск не пишутся: ни в документы хода, ни в файлы гостя.
- **Токен GitHub** открывается входом (PIN или биометрия, D-59) раз за
  запуск и держится в памяти до остановки процесса или службы; без входа
  ИИ его не получает, а раздел секретов предлагает войти.
- **Журнал.** Включение, выключение и первая выдача за запуск — строкой в
  журнале приложения: имя и переменная, без значения.

**Почему.** Слово автора: подписка слота не должна переключаться на
оплату по API; секреты не покидают телефон; защита токена GitHub — как у
DP-Verify (D-95).

**Проверка.** JVM-тест имён и окружения (стандартное имя и `DPMETA_`,
одна переменная — один секрет); на телефоне — `env` в терминале и в ходе
Claude (пункт `TODO.md`).

**Почему.** Слово автора: проблема должна быть видна и объяснена, а

### D-125 — adb к самому телефону: ключ доступен терминалу и ИИ; logcat, запуск и отладка APK

**Статус.** Принято 13 ноября 2026 — ответы автора (форма сессии) на
вопросы D-124: ключ adb — «И в терминале, и ИИ»; первый объём — «logcat с
фильтрами», «Запуск APK на телефоне», «Отладка Kotlin/Java APK». Уточняет

**Решение.**
- **Подключение** — беспроводная отладка Android к самому телефону:

### D-126 — Отладка своих Kotlin/Java APK на телефоне: свой клиент JDWP

**Статус.** Принято 13 ноября 2026 — ответ автора (форма сессии) на вопрос
о способе отладки APK: «Свой клиент JDWP». Исполняет D-125 (отладка
Kotlin/Java APK — следующим шагом).

**Решение.**
- **Клиент JDWP — свой**, в ядре приложения, без новых зависимостей: JDI
  (`com.sun.jdi`) в Android нет, а адаптер DAP для Java требует в Linux
  приложения JDK и анализатор Java — сотни мегабайт и долгий старт.
- **Что отлаживается** — установленное отлаживаемое приложение (сборка
  `debug`) другого пакета. Сам DPmetaApp — нет: остановка его ВМ
  остановила бы и отладчик.
- **Подключение** — adb к самому телефону (D-125): приложение
  перезапускается с ожиданием отладчика (`am set-debug-app -w`, на один
  запуск), `adb forward tcp:0 jdwp:<pid>`; порт пересылки слушает adb
  гостя на `127.0.0.1`, DPmetaApp подключается к нему. Команда гостя
  держит сервер adb, пока идёт отладка.
- **Объём** — как у D-124: точки касанием номера строки в файлах `.kt` и
  `.java` (класс — по пакету и имени файла), стек, переменные кадра и
  `this`, «Шаг», «Войти», «Выйти» (системный код пропускается), «Пауза»,
  «Продолжить», остановка на непойманном исключении. Выражение — только
  имя переменной кадра: JDWP код не вычисляет. «Остановить» — отключение:
  приложение работает дальше.
- **Где** — «Отладка» у APK в «Сборка → Артефакты»; дальше — и кнопкой
  «Отладка» над файлом `.kt`/`.java` того же дерева.

**Почему.** Слово автора: отладка своих APK без ПК; свой клиент — малый,
без JDK в госте.
**Проверка.** `DP_AI_Orcestrator:D-161`; на телефоне — `TODO.md`.
