# Решения

Здесь записано, **что решено и почему**. Это источник истины: если другой
документ расходится с решением, прав этот документ, а расходящийся
исправляется. Решение меняется только правкой здесь — новым решением со
ссылкой «заменяет D-NN» и строкой в разделе «История», а не молча в
другом месте.

Правила журнала (как в журналах DP-Verify, DPlearn и DPmetaApp —
`docs/PROCESS.md`):

- номер — `D-NN` латиницей, не переиспользуется и не меняется;
- поля — «Статус», «Решение», «Почему», «Проверка»; решение без проверки
  — пожелание; «Отклонено» и «Следствия» — когда есть что сказать;
- чужой номер — с именем проекта: `DPmeta:C-05`, `DPmetaApp:D-15`.

Поля, сплошную нумерацию и ссылки держит `tools/check/run.sh` (проверки
`process.decisions` и `docs.refs`).

**Статус решений D-01…D-14.** Приняты сессией 5 октября 2026 по поручению
автора «полностью завершить разработку» (`docs/direction/REQUEST.md`) —
обычные решения, обратимые; автор может заменить любое новым решением.
D-01 стоит на допущении о цели до ответа на ТЗ, Q-01.

## Принятые

### D-01 — Назначение: интерактивная модель потоков и инфраструктуры; о проекте прав его репозиторий, о связях — DPmeta

**Статус.** Принято — сессия, 5 октября 2026; цель — допущение до ответа
автора на ТЗ, Q-01 (`docs/direction/REQUEST.md`, «Как установлена цель»).

**Решение.** DPvisualisation — интерактивная модель экосистемы dpsmpx:
узлы (репозитории, участники, сервисы, устройства, площадки, внешние
источники) и потоки информации между ними, наложенные на реальные данные
— историю git клонов и пробы сервисов. Её показывает свой просмотрщик и
должен суметь показать DPmetaApp (`DPmetaApp:docs/direction/REQUEST.md`,
Т15). Источник истины о проекте — его репозиторий (`DPmeta:M-02`), о
связях между проектами — контракты и карта DPmeta; модель — производное
знание со ссылкой на источник каждого узла и потока.

**Почему.** Так устроена вся экосистема: DPmeta — знание между
репозиториями (`DPmeta:M-01`), DPmetaApp — читатель, а не источник истины
(`DPmetaApp:D-01`). Модель, которая «знала бы лучше», стала бы ещё одним
устаревающим источником.

**Проверка.** Проверка модели требует ссылок у каждого узла и потока
(`model.valid`); сборщик сверяет модель с реестром и контрактами DPmeta
(D-11).

**Отклонено.** Модель без ссылок «по памяти сессии» — нечем проверить и
нечем обновить.

### D-02 — Модель — данные: TOML-источник → JSON-сборка

**Статус.** Принято — сессия, 5 октября 2026.

**Решение.** Модель пишется руками в `model/ecosystem.toml` и собирается
командой `python3 -m tools.dpvis model build` в `data/model.json`
(`dpvis-model/1`): детерминированно, с отпечатком источника. Виды узлов,
потоков, состояний, транспорта и сигналов — закрытые каталоги
(`tools/dpvis/model.py`, ТЗ §8). Собранный файл лежит в репозитории, и
проверка сверяет, что он не отстал от источника.

**Почему.** TOML — формат реестра DPmeta (`DPmeta:tools/ecosystem.toml`) и
читается стандартной библиотекой Python (`tomllib`); JSON читают браузер и
DPmetaApp без своего разборщика TOML. Каталоги — чтобы опечатка в виде
потока была ошибкой, а не новым «видом».

**Проверка.** `tools/check/run.sh`: `model.valid` и `model.compiled`;
тест детерминизма сборки (`tests/test_model.py`).

**Отклонено.** Модель в коде просмотрщика — DPmetaApp не смог бы её
прочитать; JSON как источник — без комментариев и неудобен для правки.

### D-03 — Наблюдения — чтение клонов и HTTP-пробы; сеть — только по ключу

**Статус.** Принято — сессия, 5 октября 2026.

**Решение.** Сборщик читает клоны репозиториев (только чтение, ветка по
умолчанию, а не рабочее дерево) и, только с ключом `--online`, делает
HTTP-пробы к адресам из списка `[allow] hosts` модели; `git fetch` — только
с ключом `--fetch`. Своего сервера в облаке, телеметрии и сторонних
сервисов нет.

**Почему.** Почти вся работа экосистемы оставляет след в git: CI нет
(`DPmeta:E-07`), сессии работают ветками и PR. Без ключей сборщик работает
без сети и годится для тестов и для сессии; ключи — для живого режима у
автора. Список адресов — как `DPmetaApp:D-10`.

**Проверка.** Тесты сборщика на синтетических клонах без сети; проба к
адресу вне списка — `HOST_NOT_ALLOWED` без запроса (`tests/test_probe.py`).

**Отклонено.** GitHub API для PR и веток — нужен токен в окружении
сборщика и лимит запросов; на 1.0 — ограничение ТЗ, L-01.

### D-04 — Детерминизм: срез — функция модели, клонов, времени среза и правил

**Статус.** Принято — сессия, 5 октября 2026.

**Решение.** `collect` не читает часы, если задан `--now`; дни считаются
в часовом поясе автора `+03:00`; ключи и списки упорядочены; все пороги и
окна — в `tools/dpvis/rules.py` с `RULES_VERSION`, который пишется в срез.
Пороги активности — как `DPmeta:M-08`: основная ветка — 6 ч, ветка с
невлитой работой — 24 ч; поток «идёт» — событие за 72 ч (как
`active_hours` набора `progress/v1`).

**Почему.** Детерминизм прежде скорости — правило экосистемы
(`DPmeta:E-12`); одинаковые наблюдения должны давать одинаковые числа и у
DPmetaApp (`DPmetaApp:D-04`).

**Проверка.** Тест: два сбора с одним `--now` — побайтно одинаковые
файлы; изменение смысла правил — новый `RULES_VERSION` (обзор).

### D-05 — Стек: Python без зависимостей; просмотрщик — HTML, CSS и JS без библиотек

**Статус.** Принято — сессия, 5 октября 2026.

**Решение.** Инструменты — Python ≥ 3.11, только стандартная библиотека.
Просмотрщик — `viewer/index.html`, `style.css` и ES-модули `src/*.js` без
библиотек, фреймворков и обязательной сборки; граф и графики — свой SVG.
Сборка одного файла (`tools/dpvis/build.py`) только склеивает модули и
встраивает данные. Тесты просмотрщика — встроенный `node --test`, без
пакетов npm.

**Почему.** Нужен только Python и git — как у DPmeta, DPmetaApp и
DP-Verify; просмотрщик открывается где угодно, включая WebView и телефон.
Свой код графики — свои правила подписей, таблиц и цветов
(`DPmetaApp:D-15`, `DPmeta:E-11`).

**Проверка.** `tools/check/run.sh`: `repo.layout` (нет `package-lock.json`,
`node_modules`); в `viewer/src` нет `import` извне каталога; в
`tools/dpvis` — только стандартная библиотека (`deps.python`).

**Отклонено.** D3, Cytoscape и подобные — внешний код и чужие решения о
доступности; Kotlin-библиотека для DPmetaApp — привязала бы модель к
одному читателю, а формат JSON читает и он.

### D-06 — Визуальный язык — токены автора; цвет потока — кто его движет

**Статус.** Принято — сессия, 5 октября 2026.

**Решение.** Цвета, шрифты и пределы контраста — из визуальной системы
автора (`SocialMediaImage:docs/brand/VISUAL_SYSTEM.md`,
`SocialMediaImage:assets/brand/tokens.json`): фон `ink`, панели
`graphite`, линии `line`, текст `paper` и `mist`; смысловые `human`,
`ai`, `verified`. Цвет потока — **кто его движет**: `human` — решение
автора, `ai` — сессии и автоматика, `check` (`verified`) — проверка,
`data` (`mist`) — данные и знание. Состояние — штрихом, активность узла
— формой (пульс, «?»), не только цветом. Светлая тема — свои оттенки тех
же смыслов (`docs/PROVENANCE.md`).

**Почему.** «Цвет — смысл, а не украшение» — правило визуальной системы
автора; одна и та же схема показывает метод работы (человек решает, ИИ
делает, проверка принимает) без подписей.

**Проверка.** Цвета заданы только переменными CSS в одном месте
(`viewer/style.css`, `:root`); тест контраста токенов текста
(`viewer/test/theme.test.js`).

### D-07 — Форматы `dpvis-model/1` и `dpvis-state/1` — контракт для читателей

**Статус.** Принято — сессия, 5 октября 2026.

**Решение.** Формат модели и среза описан в `docs/FORMATS.md` и
`schemas/`. В пределах версии `/1` поля только добавляются; читатель
игнорирует незнакомые поля; изменение смысла или удаление поля — новая
версия (`/2`) и строка в истории `docs/FORMATS.md`. Коды диагностики
только добавляются.

**Почему.** Главный читатель — DPmetaApp со своими разборщиками; так же
устроены `report.json` DP-Verify (`DP-Verify:docs/direction/TECHNICAL_TASK.md`,
N-09 там) и реестр DPmeta (`schema = 1`).

**Проверка.** Тест: срез и модель проходят проверку по схемам своим кодом
(`tests/test_formats.py`); проверка `state.valid`.

### D-08 — Личный инструмент: не публикуется; режим «показ»; в срезе нет содержимого

**Статус.** Принято — сессия, 5 октября 2026; по образцу
`DPmetaApp:D-24`. **Сужено D-15** (6 октября 2026): на сайт автора выходит
публичная выжимка — полная модель и срезы по-прежнему не публикуются.

**Решение.** DPvisualisation — инструмент автора: просмотрщик, модель и
срезы не выкладываются на сайт, в открытые репозитории и каталоги; сборка
`dist/` не коммитится. В срез попадают только счётчики, время, хеши и
имена веток — без текстов коммитов, почты и содержимого файлов. Режим
«показ» в просмотрщике скрывает имена узлов `undisclosed` и имена веток.

**Почему.** Модель раскрывает устройство закрытой экосистемы; закрытое не
выходит наружу (`DPmeta:C-05`), публичный образ правит только автор
(`DPmeta:C-07`); DPpass публично не называется
(`SocialMediaImage:data/progress/scope.yaml`).

**Проверка.** Тест сборщика: в срезе нет полей с текстом коммита и почтой;
`.gitignore` закрывает `dist/`; тест режима «показ»
(`viewer/test/privacy.test.js`).

### D-09 — Без GitHub Actions; проверка — командой в сессии

**Статус.** Принято — сессия, 5 октября 2026.

**Решение.** Workflow GitHub Actions нет и не добавляется. Проверка —
`tools/check/run.sh` (`static` после правки, `full` перед вливанием);
итог `full` — в разделе «Проверки» описания PR.

**Почему.** Правило всей экосистемы (`DPmeta:E-07`).

**Проверка.** `repo.layout`: каталога `.github/workflows/` нет.

### D-10 — Тексты по-русски, идентификаторы латиницей

**Статус.** Принято — сессия, 5 октября 2026.

**Решение.** Документы, интерфейс просмотрщика, сообщения диагностики,
комментарии и сообщения коммитов — по-русски; номера, коды, ключи и имена
в коде — латиницей.

**Почему.** Так во всей экосистеме (`DPmeta:E-10`); латинские номера не
путаются с кириллическими (`DPmeta:M-06`).

**Проверка.** Обзор; проверка `docs.refs` знает только латинские номера.

### D-11 — Расхождение с DPmeta — диагностика, а не автоматическая правка

**Статус.** Принято — сессия, 5 октября 2026.

**Решение.** Сборщик читает реестр (`DPmeta:tools/ecosystem.toml`) и
заголовки контрактов (`DPmeta:docs/CONTRACTS.md`) из клона DPmeta и
пишет расхождения в срез: `REGISTRY_DRIFT`, `CONTRACT_UNCOVERED`,
`CONTRACT_NOT_FOUND`. Модель правится только руками — с проверкой источника.
Отсутствие DPmeta и DPvisualisation в реестре DPmeta — ожидаемо до
ответа на ТЗ, Q-03; это показывается, но не считается ошибкой.

**Почему.** О связях прав DPmeta (D-01); автоматическая правка модели
переписала бы смысл без проверки — модель «как у DPmeta», но без ссылок.

**Проверка.** Тест сборщика на синтетическом клоне DPmeta: лишний
репозиторий реестра и непокрытый контракт видны в диагностике.

### D-12 — Живой режим — локальный `serve`; браузер опрашивает срез

**Статус.** Принято — сессия, 5 октября 2026.

**Решение.** «Онлайн» — это `python3 -m tools.dpvis serve` на устройстве
автора (компьютер или Termux): http-сервер на `127.0.0.1` отдаёт
просмотрщик и данные, фоновый цикл раз в N минут пересобирает срез
(при желании с `git fetch` и пробами). Просмотрщик опрашивает срез и
перерисовывает его без сброса вида. Push-каналов и облачных серверов нет.

**Почему.** Без своего сервера — как `DPmetaApp:D-18` и вывод
`DPmeta:RISK-09` о сервисах без владельца; опрос раз в минуту достаточен
для модели, которая меняется с коммитами.

**Проверка.** Тест `serve` на синтетических клонах: срез пересобран,
сервер отдаёт его и не отдаёт файлы вне `viewer/` и `data/`
(`tests/test_serve.py`).

**Отклонено.** WebSocket и события сервера — сложнее без выигрыша;
GitHub Pages — публикация, запрещена D-08.

### D-13 — Срез на дату хранится в репозитории

**Статус.** Принято — сессия, 5 октября 2026.

**Решение.** `data/state/latest.json` — срез реальной экосистемы на дату
его сборки, в репозитории; обновляется командой `collect` и коммитом
«Срез …». Срез — запись на дату, как отчёты `DPmeta:docs/reports/`: старые
значения не правятся руками.

**Почему.** Просмотрщик и DPmetaApp должны показывать реальные данные
сразу после клонирования, без клонов всей экосистемы; срез мал (счётчики).

**Проверка.** `state.valid`: срез проходит проверку формата и ссылается на
`sha256` текущей модели (иначе — «срез собран по старой модели»).

### D-14 — Сайт и сервисы — только внешние пробы; выгрузку и публикации не трогать

**Статус.** Принято — сессия, 5 октября 2026.

**Решение.** О сайте `dpsmpx.com` и других сервисах DPvisualisation знает
только то, что видно снаружи пробой без учётных данных. Адреса выгрузки,
ключи, журналы хостинга и команды SocialMediaImage он не читает и не
вызывает.

**Почему.** Выгружает только система SocialMediaImage и только после «да»
автора (`SocialMediaImage:Д35`, `SocialMediaImage:Д36`); инцидент
5 октября 2026 (`DPmeta:RISK-08`) показал цену обходов.

**Проверка.** В коде нет `rsync`, `ssh`, `scp` (проверка
`security.commands`); пробы — только `GET` и `HEAD`.

### D-15 — Публичная выжимка для сайта автора: белый список полей, закрытое — отказ сборки

**Статус.** Принято — поручение автора, 6 октября 2026 (сессия
SocialMediaImage): «На сайте должна быть готовая визуализация из
репозитория DPvisualise. Если она не закончена — доделай». Ограничения
автора: «не должно быть моего ФИО, не должно быть упоминания точного
названия и деталей DPpass, и прочих моих личных данных». Сужает D-08.

**Решение.**
- `python3 -m tools.dpvis build --site <каталог>` собирает комплект для
  сайта: `dpvis.js` (склейка модулей), `dpvis.css`, `dpvis-data.json`
  (`dpvis-public/1`) и `MANIFEST.json` с sha256. Скриптов и стилей внутри
  HTML нет: страница сайта работает под CSP `script-src 'self'`.
  `build --public` — то же одним файлом.
- Цель выжимки (уточнение автора 6 октября 2026): «Данные закрытых
  репозиториев добавь, но без лишних деталей и подробностей. Посетитель
  сайта должен в целом видеть мой прогресс и к какой системе я иду, а не
  смотреть на старые открытые проекты». Поэтому:
  - слой ранних и малых открытых проектов убирается целиком;
  - закрытые репозитории остаются с ролью, стадией и прогрессом (коммиты
    по дням ИИ и человек, первый и последний коммит, итог окна);
  - тексты — только публичные формулировки модели: `public_role`,
    `public_stage` узла, `public_what` потока. Рабочие `role`, `stage`,
    `what` (решения закрытых проектов, пути, коды контрактов, номера шагов)
    в выжимку не попадают никогда; нет публичной формулировки — нет текста;
  - убираются ветки, вливания, пути передачи, триггеры и дневная
    активность участников.
- В выжимку идут только поля из белого списка (`tools/dpvis/public.py`;
  формат — `docs/FORMATS.md`).
  - Узлы `undisclosed` убираются целиком, вместе с узлами, связанными
    только с ними. Остаётся только счётчик `hidden`, как «+ 1 проект без
    публичного имени» на странице прогресса.
  - Убираются устройства и личные каналы автора. Выгрузка через
    устройство схлопывается в поток «репозиторий → сайт».
  - Ветки — только числом, время событий — только датой.
  - Без ссылок на источники, контрактов, сигналов, проб, адресов,
    реестра и диагностики.
- После сборки весь текст выжимки проверяется по списку `FORBIDDEN`:
  имя проекта без публичного имени и признаки его назначения, устройства,
  адреса, почта, хеши, ветки сессий, точное время. Находка — отказ сборки,
  а не тихая правка.
- Полная модель, срезы и сборка с ними (`build` без `--public`) — как в
  D-08: только у автора.

**Почему.** Автор решил показать экосистему на своём сайте. Его три
ограничения выполняются устройством выжимки, а не вниманием сессии:
- белый список — новое поле не уйдёт наружу само;
- отказ сборки — проверяет каждую сборку.

Второй слой — фильтр сайта (`SocialMediaImage:Д39`).

**Проверка.** `tests/test_public.py`:
- закрытое не проходит;
- проверка ловит каждый вид утечки;
- схлопывание выгрузки работает;
- склейка однозначна.

`viewer/test/` — режим «показ» и публичный формат.
