# Решения DP_AI_Orcestrator

Журнал архитектурных решений. Код и документы ссылаются на них по номеру
(`D-05`); `tools/verify/check_docs.py` проверяет, что каждый номер,
упомянутый в репозитории, здесь определён. Из других репозиториев
экосистемы на них ссылаются с именем проекта: `DP_AI_Orcestrator:D-05`.

Правила журнала:

- Номер не переиспользуется и не меняется. Новое решение — следующий
  свободный номер (сейчас — **31**).
- Решение не переписывается задним числом: если оно меняется, старое
  получает статус «заменено D-NN», новое объясняет, что изменилось и
  почему.
- У каждого решения есть **проверка** — тест или шаг `tools/verify`,
  который ловит отступление от него. Решение без проверки — пожелание;
  если проверка появится на будущем этапе, это сказано прямо.
- Довод — требование ТЗ (`ТЗ, §N`), свойство, нужное пользователю, или
  датированный факт из `docs/research/`. «Так сделано в другом проекте» —
  не довод, а происхождение идеи; идеи экосистемы называются там, где
  ТЗ велит их взять (ТЗ, §5).

Все решения ниже приняты **6 октября 2026**: D-01…D-23 — на этапе 0,
D-24…D-25 — в начале этапа 2, D-26…D-30 — по ответам автора после этапа 2
(`docs/direction/ROADMAP/README.md`).

## Принятые

### D-01 — Что строится: control plane, а не launcher

**Решение.** DP_AI_Orcestrator — управляющий слой для AI-сессий
разработки: задачи, аккаунты, исполнители, рабочие деревья, контекст,
события, проверка и продолжение (ТЗ, §0, §1). Не список окон, не
WebView, не автоматизация интерфейса Claude, не обход ограничений.
Истинное состояние живёт в оркестраторе; сессия — заменяемый
исполнитель (ТЗ, §150). Имя репозитория пишется так, как его создал
автор (`DP_AI_Orcestrator`); в коде и командах — короткое `dpai`
(пакет `com.dpsmpx.dpai`, команда `dpai`, ссылки `dpai://`, ТЗ, §76).

**Следствия.** Всё, что нужно для продолжения работы, сохраняется вне
сессии (ТЗ, §3); любой сценарий начинается с состояния оркестратора, а
не с памяти окна Claude.

**Проверка.** Межмодульные сценарии «сессия умерла — другая продолжила»
(этап 14); до них — инварианты модели данных (`docs/DATA_MODEL.md`).

### D-02 — Ядро — чистый Kotlin/JVM; Android и cli — оболочки

**Решение.** Вся логика (планировщик, автоматы, контекст, сверка,
политики) живёт в модулях на чистом Kotlin/JVM без Android SDK.
Android-модуль — тонкая оболочка: интерфейс, Keystore, WorkManager,
уведомления (ТЗ, §72). `cli` — вторая оболочка над тем же ядром: режим
без интерфейса, `doctor`, сценарии на MockRunner. Байт-код — Java 17
(его принимает D8), инструменты — JDK 21.

**Следствия.** Ядро собирается и тестируется на любом JDK 21 без
эмулятора; модуль `android` подключается только при Android SDK.
Представление без платформы (состояния экранов, форматирование, deep
links) — модуль `ui`, его тоже проверяют тесты на хосте.

**Проверка.** `tools/verify/check_modules.py`: `android.*` и `androidx.*`
только в модуле `android`; направления зависимостей — по таблице
`docs/ARCHITECTURE.md`, §2.

### D-03 — Мобильный контроллер отдельно от исполнителя

**Решение.** Claude работает на execution target (Termux, Linux или
Windows по SSH, локальный помощник, будущий runner), а не внутри
процесса Android-приложения (ТЗ, §11). Встраивание CLI в Android-процесс
допускается только отдельным решением после доказанной стабильности на
целевых устройствах. Длительная работа на Android — только допустимыми
механизмами ОС (WorkManager, foreground service по правилам Android
14–16, ТЗ, §96, §97); надёжность не строится на вечном фоновом процессе:
её дают сохранённое состояние и сверка после перезапуска (ТЗ, §54).

**Следствия.** Между контроллером и исполнителем — протокол с
последовательными номерами событий (ТЗ, §56); его транспорт — отложенное
решение (этап 3).

**Проверка.** `check_modules.py`: запуск процессов (`ProcessBuilder`,
`Runtime.exec`) — только в модуле `execution`
(`tools/verify/check_forbidden_apis.py`, правило `process-spawn`).

### D-04 — Только официальные интерфейсы провайдера и только свои лимиты

**Решение.** С Claude оркестратор работает через официально
поддерживаемые интерфейсы: Claude Code CLI в неинтерактивном режиме
(`--print`, `--output-format stream-json`, `--resume`, `--session-id`,
`--max-budget-usd`, `docs/research/CLAUDE_CODE_CLI.md`) и Claude Agent
SDK. Запрещено: cookies и приватные эндпоинты приложения, разбор
внутреннего протокола клиента, обратная разработка, обход подписочных и
rate-ограничений (ТЗ, §1, §10).

Аккаунт — слот, который пользователь законно контролирует; число слотов
в модели не ограничено (ТЗ, §9), но параллелизм ограничен лимитами
провайдера, ресурсами и политикой. Переход работы на другой аккаунт —
распределение задач между доступными исполнителями в пределах лимитов
и условий каждого, а не способ обойти лимит: аккаунт в `RATE_LIMITED`
уходит в cooldown, идентичность не маскируется и не подменяется.

**Следствия.** Адаптеры провайдера живут в модуле `execution` и
вызывают только документированные команды и API; новая возможность
провайдера — запись в `docs/research/CLAUDE_CODE_CLI.md` с датой и
версией.

**Проверка.** `check_forbidden_apis.py`, правило `provider-private`
(адреса веб-приложения claude.ai и работа с cookies в коде);
обзор адаптеров при закрытии этапа 4.

### D-05 — Строгая семантика: неподдержанное — явная диагностика

**Решение.** Если оркестратор не может выразить действие точно, он
отказывает с диагностикой, а не делает «похожее» (ТЗ, §5.1, §5.11).
Ожидаемые отказы — значения (`Outcome` с `Diagnostic`), не исключения.
Диагностика несёт код, серьёзность, место, причины (цепочка `causes`,
ТЗ, §5.1) и класс повтора (`RETRYABLE`, `NON_RETRYABLE`, `UNKNOWN`,
ТЗ, §21). Код диагностики — публичный контракт: только добавляется.

**Следствия.** Сообщение диагностики не содержит секретов (D-14);
исключение превращается в причину-сводку без стека.

**Проверка.** `OutcomeTest`, `DiagnosticTest`; реестр кодов
`tools/verify/registry/diag_codes.txt` и `tools/verify/check_contracts.py`
(код нельзя удалить или переименовать).

### D-06 — Результат операции: `Outcome` для шагов, `OperationResult` для команд

**Решение.** Внутренний шаг возвращает `Outcome<T>`: `Success` со
значением и предупреждениями или `Failure` с ошибками; находки шагов
складываются. Команда оркестратора, видимая пользователю и журналу,
возвращает `OperationResult<T>` — конверт ТЗ, §5.1: `status`, `value`,
`diagnostics`, `warnings`, `causes`, `operationId`, `timestamp`,
`provenance`. Статус выводится из `Outcome`, а не задаётся отдельно —
противоречие «SUCCEEDED с ошибкой» невыразимо.

**Проверка.** `OperationResultTest`.

### D-07 — Время и случайность — только через `Clock` и `RandomSource`

**Решение.** Логика (планировщик, повтор, heartbeat, cooldown,
устаревание) берёт время у `Clock`, случайность — у `RandomSource` (ТЗ,
§5.1, §90). В тестах — `ManualClock.advance()` и источник с зерном; сна в
тестах нет. Время хранится как миллисекунды эпохи UTC (`Timestamp`);
длительности — монотонными часами там, где системные часы могут прыгнуть.

**Проверка.** `check_forbidden_apis.py`: системное время
(`System.currentTimeMillis`, `Instant.now`, `LocalDateTime.now` …),
`Thread.sleep`, `Random()` без зерна, `GlobalScope`, `runBlocking` вне
`cli` — только в разрешённых местах; `ClockTest`.

### D-08 — Типизированные идентификаторы с префиксом типа

**Решение.** У каждой сущности свой тип идентификатора (`TaskId`,
`SessionId`, `AccountId`, `ExecutionTargetId`, …). Строковый вид —
`<префикс>_<26 знаков Crockford base32>`: 48 бит времени создания и 80
бит случайности, сортируется по времени. Разбор проверяет префикс:
идентификатор задачи нельзя прочитать как идентификатор сессии.
`ProviderSessionId` (выдан провайдером) — отдельный тип, не связанный с
`SessionId` оркестратора (ТЗ, §28).

**Проверка.** `IdsTest` (формат, отказ чужого префикса, порядок по
времени, детерминизм при зерне).

### D-09 — Строгий JSON, канонический вид и версионированные форматы

**Решение.** Свой строгий JSON без сторонних библиотек: повтор ключа —
ошибка, глубина и размер ограничены до разбора, числа сохраняют
исходную запись, сообщение об ошибке без цитаты входа. Канонический вид
(ключи по порядку единиц UTF-16, как в RFC 8785; без пробелов;
минимальное экранирование; число — в нормальной записи, `1.0` и `1` —
одно число) — основа хешей. Каждый сохраняемый документ несёт
маркер `format: "dpai.<вид>"` и `version`; неизвестное поле — ошибка;
версия новее текущей — ошибка «создано более новой версией»; миграции —
только явные, между соседними версиями (ТЗ, §5.11, §62).

**Проверка.** `JsonTest`, `CanonicalJsonTest`, property-тест «разбор
канонического вида возвращает то же значение»; миграции — этап 2.

### D-10 — Хеш — SHA-256 канонического вида, с именем алгоритма

**Решение.** Содержимое (контекст, предложение на одобрение, снимок,
резервная копия) идентифицируется хешем `sha256:<64 hex>` канонического
JSON или байтов. Хеш — основа неизменности версий контекста (ТЗ, §24),
привязки одобрения к предложению (ТЗ, §5.4, §68) и проверки целостности
(ТЗ, §60).

**Проверка.** `HashingTest` (известные векторы, независимость от
порядка ключей).

### D-11 — Формальные автоматы состояний; недопустимый переход — отказ

**Решение.** Жизненные циклы сессии, задачи, аккаунта, свежести
heartbeat и предохранителя заданы таблицами переходов
(`docs/SESSION_MODEL.md`, `docs/DATA_MODEL.md`). Переход вне таблицы
отвергается диагностикой `INVALID_TRANSITION`; повтор того же перехода
не меняет состояние (идемпотентность). Из конечного состояния в рабочее
— только явной операцией продолжения (`continuation`), а не обычным
переходом (ТЗ, §8).

**Проверка.** `StateMachineTest`, `LifecycleTablesTest` (перебор всех
пар состояний, ТЗ, §101).

### D-12 — События: неизменяемые, идентифицируемые, упорядоченные в потоке

**Решение.** Каждое существенное изменение — событие с `EventId`,
типом, потоком (сущность), номером в потоке, временем, корреляцией и
причиной (ТЗ, §13). Журнал — только дописывание; производное состояние
пересчитывается из журнала и снимков (ТЗ, §57, §58). Повтор события с
тем же `EventId` идемпотентен; пропуск номера в потоке обнаруживается и
ведёт к сверке, а не к догадке (ТЗ, §56). Тип события — публичный
контракт: только добавляется.

**Проверка.** `EventsTest`, `SequenceTrackerTest`; реестр типов
`tools/verify/registry/event_types.txt` и `check_contracts.py`.

### D-13 — UNKNOWN ≠ 0

**Решение.** Наблюдаемая величина — `Measure`: известное значение с
источником (`OBSERVED`, `DERIVED`, `ESTIMATED`) или `Unknown` с причиной
(ТЗ, §5.7, §16, §49). Отсутствие heartbeat — «активность неизвестна», а
не «активности нет»; нет данных провайдера о токенах — `Unknown`, а не
ноль.

**Проверка.** `MeasureTest`; сумма с неизвестным слагаемым неизвестна.

### D-14 — Секреты защищены по умолчанию

**Решение.** Секрет — тип `Secret`: `toString()` не показывает значение,
`reveal()` разрешён в немногих местах. Свободный текст снаружи (вывод
процессов, сообщения провайдера, исключения) проходит `Redactor` перед
журналом и диагностикой. Секреты не попадают в журнал, диагностику,
контекст для Claude, Git, отчёты об ошибках и резервную копию без
шифрования (ТЗ, §5.1, §10, §65). Учётные данные хранятся в хранилище ОС
(Android Keystore и аналоги), в базе — только ссылка (ТЗ, §10).

**Проверка.** `SecretTest`, `RedactorTest`; `tools/verify/check_secrets.py`
(ключи и токены в репозитории); `check_forbidden_apis.py`, правило
`secret-reveal`.

### D-15 — Без GitHub Actions; проверка — командой в сессии

**Решение.** Проверка репозитория — `tools/verify/run.sh` с уровнями
ТЗ, §5.2: `static` (секунды, без сборки), `affected` (static и
затронутые модули), `full` (всё; пропуск недоступного шага — ошибка);
`plan` показывает, что и почему будет запущено, `report` — итог для
описания PR. GitHub Actions не используется и не добавляется — как во
всей экосистеме (`DPmeta:docs/PRINCIPLES.md`, E-07).

**Проверка.** `check_dependencies.py` считает каталог workflow GitHub
Actions ошибкой.

### D-16 — Своя система проверок, а не поставка DP-Verify

**Решение.** Репозиторий публичный (Apache-2.0, выбор автора при
создании), DP-Verify — закрытый и проприетарный (`DP-Verify:V-15`).
Поэтому код DP-Verify сюда не переносится и не поставляется
(`DP-Verify:tools/vendor.py` не применяется). Берётся словарь и устройство (ТЗ,
§5.2): уровни `static`/`affected`/`full`, `plan`, `report`, позже —
`baseline`, `explain`, `doctor`. Интеграция с DP-Verify как с
инструментом проверки проектов, над которыми работает Claude, — адаптер
к внешней команде `dpv` на execution target (этап 10), без его кода
здесь.

**Следствия.** То же для других закрытых репозиториев автора: в этот
репозиторий переносятся идеи с указанием источника, но не код и не
внутренние документы.

**Проверка.** Обзор при каждом переносе идеи; `check_secrets.py` не
пропускает ключи и токены, а внутренние пути других репозиториев в
тексте — только как ссылки `Проект:путь`.

### D-17 — Минимум зависимостей; ядро — только Kotlin stdlib

**Решение.** Модули ядра во время выполнения зависят только от Kotlin
stdlib; JSON, хеши, идентификаторы, property-тесты — свои. Тесты —
kotlin-test и JUnit Jupiter. Версии — только в
`gradle/libs.versions.toml`; новая зависимость или версия — по причине и
со строкой в `docs/PROVENANCE.md`. Gradle — через wrapper со сверкой
SHA-256 дистрибутива и `gradle-wrapper.jar`.

**Проверка.** `tools/verify/check_dependencies.py` (координаты мимо
каталога, версия без строки PROVENANCE, сумма wrapper не та);
`tools/verify/check_modules.py` (библиотека каталога вне тестовой
конфигурации модуля).

### D-18 — Тексты по-русски, идентификаторы латиницей

**Решение.** Документы, комментарии, KDoc, сообщения диагностики и
коммитов — по-русски; имена в коде, коды диагностики, типы событий,
ключи форматов — латиницей (`DPmeta:docs/PRINCIPLES.md`, E-10). Номера
записей — латиницей: решения `D-NN`, угрозы `T1`…, находки аудитов
`A-N`.

**Проверка.** `tools/verify/check_format.py` (невидимые и
двунаправленные символы); обзор.

### D-19 — ТЗ — контракт V1; ссылки на него — по номеру раздела

**Решение.** ТЗ лежит в `docs/direction/MASTER_TECHNICAL_TASK.md`
(перенесено из корня: в корне — только точки входа). Текст ТЗ не
правится ради удобства; меняется только вместе с решением здесь. Ссылка
на ТЗ — `ТЗ, §N`, где N — номер раздела («23. Context Manager» —
`ТЗ, §23`; подразделы — `ТЗ, §5.1`). Этапы плана нумеруются так же, как
фазы ТЗ, §139: этап N — Phase N.

**Проверка.** `check_docs.py`: раздел `§N` существует в ТЗ; этап N
есть в плане.

### D-20 — Объём V1 закреплён в начале

**Решение.** Что входит в V1 — `docs/direction/V1_SCOPE.md` (ТЗ, §143,
§144): пять основных сценариев и то, что для них необходимо. Всё
остальное — список FUTURE там же; оно не мешает закрытию V1 и не
начинается без решения.

**Проверка.** Обзор при закрытии каждого этапа: новая работа вне V1 —
только с записью в FUTURE или новым решением.

### D-21 — Модули и границы — по таблице архитектуры

**Решение.** Модули Gradle повторяют подсистемы ТЗ, §6: `core`,
`storage`, `execution`, `accounts`, `sessions`, `tasks`, `contexts`,
`git`, `monitoring`, `notifications`, `verification`, `ecosystem`,
`security`, `analytics`, `connectors`, `ui`, `android`; плюс сборка
системы `orchestrator`, оболочка `cli`, общие средства тестов `testkit`
и межмодульные наборы `tests/…`. Таблица `docs/ARCHITECTURE.md`, §2 —
единственный источник допустимых направлений зависимостей; новый модуль
или направление — правка таблицы в том же изменении. Пустой модуль
допустим: он закрепляет границу до появления кода.

**Проверка.** `check_modules.py` сверяет `settings.gradle.kts` и каждый
`build.gradle.kts` с таблицей; `testkit` — только в тестовых
конфигурациях.

### D-22 — Детерминированное ядро; LLM не принимает решений планировщика

**Решение.** Планировщик, приоритеты, зависимости, автоматы, повтор,
дедупликация уведомлений, выбор контекста и рабочего дерева,
восстановление — детерминированы: одинаковые вход и время дают
одинаковый результат (ТЗ, §4.3). Локальная модель (ТЗ, §77) может только
подсказывать; подсказка проходит политику, как любое предложение (ТЗ,
§78). Порядок при равенстве — по устойчивому ключу (идентификатор), а не
по порядку хеш-таблицы.

**Проверка.** Property-тесты устойчивости порядка (этап 7);
`check_forbidden_apis.py` (время и случайность, D-07).

### D-23 — Заявление AI — не завершение

**Решение.** «Готово» от Claude переводит задачу в `IMPLEMENTED`, а не
в `DONE`. Дальше — `VERIFYING` по профилю проверки; `DONE` — только после
`VERIFIED` или явного исключения политики, иначе
`COMPLETION_UNVERIFIED` (ТЗ, §5.5, §32, §151). Наблюдение, вывод,
решение и проверка хранятся раздельно.

**Проверка.** Таблица переходов задачи не содержит перехода в `DONE`
мимо `VERIFIED` и исключения (`LifecycleTablesTest`); сценарии этапа 10.

### D-24 — Источник истины — файлы журнала и документов; индексы — производные

**Решение.** Сохранённое состояние — собственные файлы без сторонних
библиотек (D-17), одинаковые на JVM и Android:

- журнал событий — строки канонического JSON `dpai.journal-record`: событие
  `dpai.event`, номер записи, хеш предыдущей и своей записи (цепочка);
  запись подтверждается только после fsync;
- документы (снимки, реестры, настройки) — атомарная замена: временный
  файл → fsync → переименование, прежняя версия остаётся last known good;
- снимок производного состояния — документ с позицией в журнале и хешем
  записи на этой позиции.

SQLite или другой индекс для поиска и списков (ТЗ, §75) — производное,
перестраиваемое из журнала, а не источник истины; нужен ли он — по
замеру на этапе 11. Работа с файлами — только через `Vfs` модуля
`storage`; в тестах — модель сбоев: незафиксированное fsync теряется,
хвост дописывания может оборваться на любом байте.

**Почему.** Журнал только на дописывание с пересчётом состояния (D-12,
ТЗ, §57) естественно ложится на файлы; каждая запись проверяется хешем
(D-10); копия переносится как есть; поведение при сбое проверяется
моделью без нативного драйвера. На хосте SQLite требует JDBC с нативной
частью — зависимость, которой ядро избегает (D-17).

**Следствия.** Недописанный хвост журнала (запись без fsync) отрезается
при открытии и сохраняется в карантине; повреждение в середине журнала —
отказ открытия, пока пользователь явно не подтвердит карантин хвоста
(`docs/RECOVERY.md`, §4). После отказа записи журнал не принимает новых
записей до повторного открытия (ТЗ, §80).

**Проверка.** Тесты прерывания на каждом шаге записи по модели сбоев;
property-тест «снимок + хвост журнала = полный пересчёт»;
`check_forbidden_apis.py`, правило `file-write` (запись в файлы — только
в `storage`).

### D-25 — Резервная копия не содержит секретов

**Решение.** В хранилище оркестратора секретов нет: учётные данные — в
хранилище ОС, в документах — ссылки (D-14). Поэтому резервная копия —
документы и журнал как есть, с манифестом (формат, версия, время, версия
схемы, файлы с размером и SHA-256, хеш манифеста; ТЗ, §60) и без
шифрования. Экспорт секретов — отдельная операция по явному согласию с
шифрованием, вместе с хранилищем учётных данных (этап 5). Копия
применяется, только если манифест и каждый файл сошлись; восстановление
возобновляемо: прерванное — довершается при следующем запуске (ТЗ,
§61).

**Проверка.** Тесты набора ТЗ, §61 (годная, старая схема, частичная,
повреждённая, после прерванного восстановления); модуль `storage` не
использует `Secret` (`check_forbidden_apis.py`, правило
`storage-secret`).

### D-26 — Targets V1: Termux, Linux и Windows; транспорт — SSH для всех

**Решение.** Execution targets V1 — те, что есть у автора: Termux на
телефоне разработчика, Linux-хост по SSH, Windows-хост по SSH (OpenSSH
Server). Транспорт контроллер ↔ target один — SSH: к Termux приложение
подключается к его `sshd` на `127.0.0.1`, к хостам — с проверкой ключа
хоста (T2). На target работает агент оркестратора — `dpai agent` из
модуля `cli` (JVM 17+): запускает Claude Code, пишет события в свой
журнал с номерами, переживает обрыв SSH и отдаёт пропущенное при
переподключении (ТЗ, §56).

**Почему.** Один транспорт на три вида targets; SSH даёт шифрование,
ключи и поток вывода. Запуск команд Termux через намерения Android
(`RUN_COMMAND`) не даёт потока и есть только на Android.

**Следствия.** На Android нет клиента `ssh`: нужна библиотека SSH —
выбор с лицензией и проверкой на Android 11 в начале этапа 3
(«Отложено»). Claude Code официально поддерживает macOS, Windows и
Linux (glibc и musl), Android в списке нет
(`docs/research/CLAUDE_CODE_CLI.md`, §5): работает ли он в Termux
нативно или только в окружении Linux поверх Termux — проверка на
устройстве в начале этапа 3; не работает — телефон остаётся
контроллером, а Claude — на Linux и Windows.

**Проверка.** Критерии этапа 3: запуск и полная остановка процесса на
каждом виде target; `doctor` проверяет `claude --version` на target.

### D-27 — Аккаунты — подписки Claude через собственный вход Claude Code

**Решение.** Слоты аккаунтов V1 — подписки Claude (Pro, Max). Слот —
это target и свой каталог настроек Claude Code (`CLAUDE_CONFIG_DIR`):
пользователь входит в аккаунт сам, запустив Claude Code с этим
каталогом, через вход Anthropic. Оркестратор учётных данных claude.ai
не читает, не копирует, не хранит и не передаёт: не трогает
`.credentials.json`, не использует `claude setup-token` и
`CLAUDE_CODE_OAUTH_TOKEN`. Ссылка на учётные данные (`credentialRef`) —
путь к каталогу настроек на target, а не секрет. Запуск —
`CLAUDE_CONFIG_DIR=<каталог> claude -p …`, без `--bare` (он не читает
вход по подписке). Пределы подписки (окно пять часов и недельный
предел) — пределы провайдера: достигнут — слот в `RATE_LIMITED` и
`COOLDOWN` до сброса, обходов нет (D-04). Оркестратор не создаёт
аккаунты и не скрывает, какой аккаунт работает; сколько подписок
использовать — решение автора в рамках условий Anthropic
(`docs/ACCOUNT_MODEL.md`, §6).

**Почему.** Условия Claude Code на 6 октября 2026: вход по подписке
предназначен для обычного использования Claude Code; сторонним
разработчикам нельзя собирать, хранить и передавать учётные данные и
токены claude.ai — вход проходит только через поток Anthropic. Несколько
аккаунтов на одной машине — документированный `CLAUDE_CONFIG_DIR`
(`docs/research/CLAUDE_CODE_CLI.md`, §4).

**Следствия.** Android Keystore хранит ключи SSH для targets, но не
вход claude.ai. Здоровье слота — по ответам Claude Code: ошибка входа —
`AUTH_REQUIRED`, сообщение о пределе — `RATE_LIMITED`. Уточняет D-04
для подписок; строка «изоляция учётных данных» из «Отложено» закрыта.

**Проверка.** `check_forbidden_apis.py`, правило `provider-private`:
`.credentials.json`, `CLAUDE_CODE_OAUTH_TOKEN` и `setup-token` в коде
запрещены; тесты слотов — этап 5.

### D-28 — Android: minSdk 30; основное устройство — Redmi Note 13

**Решение.** Минимальная версия — Android 11 (API 30). Основное
устройство проверки — Redmi Note 13 автора (Xiaomi, HyperOS/MIUI):
приёмка этапов 11 и 19 и проверки жизненного цикла (ТЗ, §96, §97) — на
нём.

**Следствия.** Оболочки Xiaomi ограничивают фоновую работу сильнее
обычного Android (автозапуск, экономия батареи) — проверить на
устройстве; надёжность и так не строится на живучести процесса (D-03).
Разрешение на уведомления (Android 13+) и типы foreground service
(Android 14+) учитываются, если устройство на этих версиях.

**Проверка.** `minSdk = 30` в модуле `android` (этап 11); записи о
проверке на устройстве — в `TODO.md` и файлах этапов 11 и 19.

### D-29 — Только вход через форму Claude; ключей API нет

**Решение.** Единственный способ входа слота — вход аккаунтом Claude
через форму Anthropic внутри Claude Code (`claude auth status` сообщает
`authMethod = "claude.ai"`). Ключи API, `apiKeyHelper`, токены
`setup-token`, облачные провайдеры в V1 не поддерживаются (слово
автора, 6 октября 2026). Слот, у которого Claude Code сообщает другой
способ, — в `ERROR` с диагностикой `ACCOUNT_AUTH_METHOD_FORBIDDEN` и
уведомлением.

**Почему.** Ключ API в окружении или `apiKeyHelper` в настройках
перекрывают вход по подписке (`docs/research/CLAUDE_CODE_CLI.md`, §4):
без проверки сессия молча ушла бы на другой способ и другую оплату.

**Следствия.** Окружение процесса `claude` собирается из разрешённого
набора: переменные, перекрывающие вход (`ANTHROPIC_API_KEY`,
`ANTHROPIC_AUTH_TOKEN`, токен `setup-token`, переключатели облачных
провайдеров, профили Anthropic), удаляются, `CLAUDE_CONFIG_DIR` слота —
задаётся (`SlotEnvironment`). Способ входа проверяется по `claude auth
status` перед первым запуском слота и после каждого отказа входа.

**Проверка.** `AccountsTest` (запрещённые способы входа),
`SlotEnvironmentTest` (удаление переменных).

### D-30 — Подписка и слот; одна подписка — основной режим

**Решение.** Подписка (аккаунт Claude с общими пределами) и слот
(подписка, вошедшая в Claude Code на конкретном target в своём каталоге
настроек) — разные сущности: одна подписка может быть слотами на
Termux, Linux и Windows, и её пределы общие для всех её слотов.
Основной режим — **одна подписка**: весь контроль работает в нём
полностью — пределы окна пяти часов и недели, ожидание сброса,
отложенные новые сессии у предела, параллельные сессии до предела
подписки, cooldown после серии ошибок, вход и его истечение,
уведомления. Несколько подписок — тот же механизм плюс защиты от
пересечения (`docs/ACCOUNT_MODEL.md`, §4):

- один каталог настроек на target — не больше одного слота;
- отпечаток аккаунта слота (хеш `orgId` и email из `claude auth status`;
  сам email не хранится) совпадает с отпечатком его подписки; иначе —
  `ACCOUNT_IDENTITY_MISMATCH`, слот остановлен;
- один аккаунт Claude не может быть двумя подписками —
  `ACCOUNT_DUPLICATE_SUBSCRIPTION`;
- предел, замеченный любым слотом, действует на все слоты подписки;
- сессия арендует ровно один слот на всё время жизни;
- задача продолжает на другой подписке, только если автор явно
  разрешил это у принимающей подписки (`rotationAllowed`), только между
  сессиями (через handoff) и не чаще заданного числа раз за сутки —
  иначе `ACCOUNT_SWITCH_LOOP` (ТЗ, §22).

Состояние аккаунтов — события в журнале (D-12, D-24); состояние слота
по автомату `AccountLifecycle` выводится из фактов (вход, пределы,
ошибки, занятость) и меняется только допустимыми переходами.

**Почему.** Автор просит упор на одну подписку и полный контроль в
ней; несколько подписок — по его решению и с риском
(`docs/ACCOUNT_MODEL.md`, §6). Отдельная подписка как сущность нужна,
потому что пределы общие для всех машин, где выполнен вход.

**Проверка.** `AccountsTest`, property-тест инвариантов аккаунтов
(аренда — не больше одного слота на сессию, не больше предела
параллельности на подписку, не на остановленный или упёршийся слот,
переходы — только по таблице); уведомления —
`AccountNotificationsTest`.
