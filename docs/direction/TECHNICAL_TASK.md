## 0. О документе

**Обязательность.** «Должен» — требование 1.0; его проверяет критерий
готовности (§15). «Может» — допустимо, но не обязательно. «Не делает» —
граница версии (§3, §16).

**Нумерация.** Цели — `G-NN`, сценарии — `S-NN`, решения — `D-NN`,
функциональные требования — `F-NN`, нефункциональные — `N-NN`,
интеграции — `I-NN`, угрозы — `T-NN`, критерии готовности — `A-NN`,
ограничения — `L-NN`, риски — `R-NN`, вопросы автору — `Q-NN`. Номера —
латиницей (`DPmeta:M-06`). Чужой номер пишется с именем проекта —
`DPmeta:C-04`, `DPmetaApp:D-15`; чужой путь — `DPmeta:docs/CONTRACTS.md`
(`DPmeta:C-06`). Свои номера сверяет `tools/check/run.sh` (проверка
`docs.refs`).

**Неизвестное** не додумывается: недоступное и непроверенное помечено
**UNKNOWN** с тем, чем и когда это проверить.

**Словарь.**

| Термин | Значение |
|---|---|
| экосистема | репозитории автора `dpsmpx`, описанные в `DPmeta:docs/ECOSYSTEM.md`, и инфраструктура, на которой они работают |
| модель | описание экосистемы данными: **узлы** (репозитории, сервисы, устройства, площадки, участники) и **потоки** между ними; источник — `model/ecosystem.toml`, сборка — `data/model.json` (`dpvis-model/1`) |
| узел | то, между чем течёт информация: репозиторий, сервис, устройство, площадка, участник (автор, сессии Claude), внешний источник |
| поток | направленная связь «от → к»: что передаётся, каким путём, по какому контракту, в каком состоянии, чем наблюдается |
| сигнал | способ наблюдать узел или поток в реальных данных: история git клона, изменения путей (HTTP-проб нет — D-19) |
| наблюдение | то, что сборщик получил из источника на момент `as_of` |
| срез | состояние на момент `as_of` — `dpvis-state/1`; экран всегда показывает, на какой |
| сборщик | `python3 -m tools.dpvis collect` — строит срез из модели и клонов |
| просмотрщик | интерактивная страница `viewer/`; одним файлом — сборка `dist/dpvisualisation.html` |
| живой режим | `python3 -m tools.dpvis serve`: локальный сервер на устройстве автора, который пересобирает срез по расписанию, и просмотрщик, который его опрашивает |

Выводы, на которых стоит ТЗ:

1. **Связи уже описаны словами, но не данными.** Контракты, карта и
   принципы DPmeta — текст; потоки инфраструктуры (сессии, выгрузка,
   площадки) разбросаны по репозиториям. Модель собирает их в одно

2. **Реальные данные — в git.** CI нет, своего сервера нет; почти вся

   ИИ и человека по дням, ветки с невлитой работой, вливания, изменения
   путей, через которые идут потоки. Сайт не опрашивается: он сам забирает
   схему перед выгрузкой (D-19).
3. **Потребитель — DPmetaApp**, у которого свои графики (`DPmetaApp:D-15`),
   список адресов (`DPmetaApp:D-10`) и опрос без своего сервера
   (`DPmetaApp:D-18`). Значит, главный продукт — **форматы** модели и
   среза; просмотрщик — эталонный показ тех же данных.
4. **О проекте прав его репозиторий, о связях — DPmeta** (`DPmeta:M-02`).
   Модель — производное со ссылками; расхождение с источником — находка
   сборщика, а не повод модели «знать лучше».

## 3. Что не входит (non-goals)

- **Не источник истины о проектах и связях.** Модель ссылается на
  репозитории и DPmeta; при расхождении исправляется модель (D-01).
- **Не правит другие репозитории** и не пишет в их клоны: только чтение
  (`DPmeta:M-04`).
- **Не управляет**: не запускает сессии, выгрузку сайта, публикации, не
  вливает PR. Это пульт DPmetaApp и системы проектов (`DPmetaApp:D-06`,
  `SocialMediaImage:Д35`).
- **Без своего сервера в облаке и без телеметрии** (D-03): живой режим —
  локальный процесс на устройстве автора.
- **Не публикуется** в открытых каталогах (D-08): модель раскрывает
  устройство закрытой экосистемы (`DPmeta:C-05`). На сайт автора — только
  публичная выжимка по его поручению (D-15, 6 октября 2026).
- **Без сторонних библиотек** графиков и фреймворков (D-05).
- **Не хранит содержимое** чужих репозиториев: в срезе нет текстов
  коммитов, почты, содержимого файлов — только счётчики, время, имена
  веток и хеши (D-08).

## 4. Пользователи и сценарии

Пользователь — автор: с компьютера или телефона (браузер, Termux), позже
— внутри DPmetaApp. Второй пользователь — сессия ИИ, которая ведёт этот
репозиторий. Третий — DPmetaApp как программа-читатель форматов.

| | Сценарий | Что происходит |
|---|---|---|
| S-01 | Посмотреть, как живёт экосистема сейчас | открыть просмотрщик → граф: где идёт работа (узлы с яркой рамкой), по каким потокам течёт информация (толщина линии — события за неделю), что запланировано (пунктир); время среза вверху |
| S-02 | Разобраться в одном проекте | нажать узел → роль, стадия со ссылкой, активность за 30 дней с таблицей, ветки с невлитой работой, входящие и исходящие потоки |
| S-03 | Разобраться в одной связи | нажать поток → что передаётся, каким путём, контракт DPmeta, состояние, последнее событие, события по дням |
| S-04 | Увидеть историю | шкала времени: воспроизвести 30 дней — как появлялись репозитории и где шла работа |
| S-05 | Следить вживую | `serve` на компьютере или в Termux → просмотрщик обновляется сам; показывает, когда собран срез |
| S-06 | Новый репозиторий или контракт | сборщик сообщает: «в реестре DPmeta есть, в модели нет» или «контракт C-NN не покрыт потоком»; модель дополняется правкой `model/ecosystem.toml` |
| S-07 | Показать экран другому | режим «показ»: имена закрытых-неназываемых проектов и веток скрыты (D-08) |
| S-08 | Подключить к DPmetaApp | DPmetaApp читает `data/model.json` и срез по `docs/FORMATS.md` и показывает их своим кодом (Q-04); сборка просмотрщика без сети — только отступлением с ответом автора |

## 6. Архитектура

### 6.1 Части

```
model/ecosystem.toml ──compile──► data/model.json ─────────────┐
        (узлы, потоки, ссылки)        dpvis-model/1             │
                                                                ▼
клоны экосистемы ──┐                                     viewer/ (ES-модули)
DPmeta (реестр, ───┴──collect──► data/state/latest.json ──► просмотрщик
  контракты)                       dpvis-state/1               ▲
                                                                │
                                                                │
serve: пересборка среза по расписанию + http-сервер ───опрос────┘
build: viewer + model + срез ──► dist/dpvisualisation.html (один файл, без сети)
```

- `tools/dpvis/` — пакет Python (только стандартная библиотека):
  `model` (чтение, проверка, сборка модели), `gitlog` (чтение клонов),
  `collect` (срез), `registry` (сверка с DPmeta),
  `rules` (пороги), `serve` (живой режим), `build` (сборка одного файла),
  `__main__` (команды).
- `viewer/` — просмотрщик: `index.html`, `style.css`, модули `src/*.js`,
  тесты `test/*.test.js` (`node --test`).
- `schemas/` — JSON Schema обоих форматов (описание для читателей;
  проверку ведёт свой код, D-05).

### 6.2 Модель

Модель — список узлов и потоков с каталогами видов (§8). У узла — `id`,
имя, вид, слой, группа, видимость, роль, ссылки на источники; у
репозитория — `repo` (slug GitHub).
У потока — `id`, `from`, `to`, вид, состояние по модели (`active`,
`planned`, `blocked`, `off`), что передаётся, транспорт, триггер,
контракт DPmeta (если есть), ссылки и сигнал. Модель сверена с
источниками на дату `as_of`.

### 6.3 Срез

`collect(модель, клоны, as_of, правила) → срез`:

- **узел-репозиторий**: ветка по умолчанию, последний коммит и его время,
  коммиты по дням окна (ИИ, человек, вливания), ветки с невлитой работой
  (сколько коммитов впереди, когда обновлялась), признак неполной
  истории; **активность** — `working` / `idle` по порогам
  `DPmeta:M-08` (основная ветка — 6 ч, ветка — 24 ч);
- **участники**: автор — по вливаниям и коммитам человека, сессии
  Claude — по коммитам ИИ во всех репозиториях;
- **поток**: события по дням окна по его сигналу, время последнего
  события; состояние — `flowing` (событие за 72 ч), `quiet`, `planned`,
  `blocked`, `off`, `unknown` (сигнал есть, наблюдение не удалось),
  `unobserved` (сигнала нет по устройству);
- **сверка**: репозитории реестра DPmeta без узла модели и наоборот;
  контракты DPmeta без потока и ссылки потоков на несуществующие
  контракты;
- **диагностика**: каждая неудача — запись с кодом (§6.7), субъектом и
  текстом; остальное собирается дальше.

Срез не зависит от рабочего дерева клонов: читается ветка
`origin/<по умолчанию>` (или локальная `main`/`master`), а не то, что
сейчас выписано.

### 6.4 Просмотрщик

Одна страница: граф (SVG) по ширине экрана — на широком узлы по слоям
слева направо, на узком слои полосами сверху вниз; потоки — прямые со
стрелкой, толщина растёт с числом событий за 7 дней; без анимаций (D-16);
панель подробностей; фильтры; шкала времени; таблицы. Данные — из
встроенного в сборку JSON, из адресов `?model=`/`?state=` или из
`../data/` рядом со страницей. Подробно — §9.

### 6.5 Живой режим

`serve --root <клоны> --every <минуты>`: http-сервер только на
`127.0.0.1` (по умолчанию) отдаёт `viewer/` и `data/`, а фоновый цикл
раз в N минут делает `git fetch` клонов (ключ `--fetch`) и пересобирает
срез во временный файл с атомарной заменой. Просмотрщик опрашивает
`state` раз в 60 с (настройка) и перерисовывает состояние, не сбрасывая
выбор и фильтры.

### 6.6 Сеть и приватность

- Сеть нужна только `--fetch` (`git fetch` клонов). К сайту и сервисам
  сборщик не обращается (D-19): `[allow] hosts` модели пуст, модель с
  адресами не проходит проверку.
- Просмотрщик сам в сеть не ходит: только к своему источнику данных
  (тот же адрес, что страница, или встроенные данные). Шрифты — системные
  или установленные, без загрузки.
- В срез не попадают тексты коммитов, почта, содержимое файлов (D-08).

### 6.7 Ошибки

Ожидаемые отказы — записи `diagnostics` среза `{code, subject, message}`;
коды — публичный контракт, только добавляются: `MODEL_INVALID`,
`CLONE_NOT_FOUND`, `CLONE_SHALLOW`, `REF_NOT_FOUND`, `GIT_FAILED`,
`FETCH_FAILED`, `REGISTRY_NOT_FOUND`, `REGISTRY_SCHEMA_UNSUPPORTED`,
`REGISTRY_DRIFT`, `CONTRACT_UNCOVERED`, `CONTRACT_NOT_FOUND`,
`HOST_NOT_ALLOWED`, `PROBE_FAILED`, `PROBE_STATUS_UNEXPECTED`,
`PROBE_HEADER_MISSING`, `SIGNAL_UNSUPPORTED` (коды проб с D-19 не
пишутся, но остаются в контракте). Код возврата сборщика: 0 —
срез построен (диагностика бывает и тогда), 2 — неверный вызов или
модель, 3 — сбой.

## 7. Функциональные требования

### 7.1 Модель

| | Требование |
|---|---|
| F-01 | Модель **должна** описывать каждый репозиторий реестра `DPmeta:tools/ecosystem.toml`, а также DPmetaApp и DPvisualisation, узлом вида `repo` со slug GitHub — кроме архива, который автор исключил из текущей системы: он перечислен в `[registry] exclude` с причиной и виден в сверке (D-20). |
| F-02 | Модель **должна** описывать инфраструктуру узлами: сессии Claude Code, GitHub, сайт `dpsmpx.com` на хостинге, телефон автора с Termux, площадки из `SocialMediaImage:data/platforms/destinations.yaml`, запланированные сервисы (онлайн-компилятор DPlang, мгновенный канал ntfy) и внешние источники сборки. |
| F-03 | Каждый контракт `DPmeta:C-NN` **должен** быть покрыт хотя бы одним потоком с полем `contract` — кроме контрактов архива из `[registry] exclude_contracts` (D-20); поток без контракта ссылается на документ, где связь записана. |
| F-04 | У узла и потока **должны** быть ссылки на источники в форме `Проект:путь` или `Проект:номер` (`DPmeta:C-06`); утверждение без источника — `UNKNOWN` в тексте. |
| F-05 | Виды узлов, потоков, состояния, транспорт и сигналы — только из каталогов §8; неизвестное значение — ошибка проверки модели с местом. |
| F-06 | `python3 -m tools.dpvis model check` проверяет модель: уникальность `id`, ссылки `from`/`to` на существующие узлы, каталоги, обязательные поля, адреса проб в списке разрешённых. |
| F-07 | `python3 -m tools.dpvis model build` собирает `data/model.json` (`dpvis-model/1`) детерминированно: одинаковый источник — побайтно одинаковый файл; в файле — `sha256` источника. |
| F-08 | Узел может задать положение на схеме (`col`, `row`); без него положение выводит раскладка по слою и порядку в модели. |

| | Требование |

| F-15 | Сигналы потоков (§8.5): `git-commits` (коммиты репозитория по виду автора), `git-path` (коммиты основной ветки, затрагивающие пути), `probe` (проба узла). Поток получает события по дням, время последнего события и состояние (§6.3). |

| F-18 | Сверка с DPmeta: реестр читается из клона DPmeta (`DPmeta:tools/ecosystem.toml` основной ветки, `schema = 1`); репозиторий реестра без узла — `REGISTRY_DRIFT`; контракт из `DPmeta:docs/CONTRACTS.md` без потока — `CONTRACT_UNCOVERED`; поток со ссылкой на несуществующий контракт — `CONTRACT_NOT_FOUND`. |
| F-19 | `--fetch` перед сбором делает `git fetch --prune` каждого найденного клона; неудача — `FETCH_FAILED`, сбор идёт по уже скачанному. |
| F-20 | Срез детерминирован: при одинаковых модели, клонах, `--now` и правилах — побайтно одинаковый файл; ключи и списки упорядочены. |

## 8. Каталоги модели

### 8.1 Виды узлов

| Вид | Что | Пример |
|---|---|---|
| `repo` | репозиторий GitHub | Galdhold, DPmeta |
| `actor` | участник, который двигает потоки | автор, облачные сессии Claude Code |
| `service` | сетевой сервис | сайт `dpsmpx.com`, GitHub, ntfy |
| `device` | устройство | телефон автора с Termux |
| `platform` | внешняя площадка публикаций | Telegram, YouTube, VK |
| `upstream` | внешний источник сборки | Xray-core |

### 8.2 Слои (колонки схемы)

`control` — управление экосистемой (DPmetaApp); `actors` — участники;
`product` — продукты; `engineering` — инструменты и обеспечение;
`knowledge` — знание и публикация; `meta` — синхронизация (DPmeta, D-21); `infra` —
инфраструктура; `outside` — площадки и внешние источники. Слоя ранних
проектов нет: в схеме только текущая система (D-20). Слои — данные
модели (`model/ecosystem.toml`), а не каталог кода.

### 8.3 Виды потоков

| Вид | Что течёт | Кто движет по умолчанию |
|---|---|---|
| `work` | работа сессий: ветки, коммиты, PR | `ai` |
| `decision` | решения, ответы, вливание PR, «да» на выгрузку | `human` |
| `knowledge` | решения и правила, повторённые или перенесённые между репозиториями | `data` |
| `facts` | факты о проектах со ссылкой на коммит | `data` |
| `metrics` | числа истории и счётчики | `data` |
| `format` | формат данных, который один пишет, другой читает | `data` |
| `delivery` | поставка кода копией | `check` |
| `check` | проверка: чтение чужого для сверки | `check` |
| `read` | чтение клонов или API для показа | `ai` |
| `deploy` | выгрузка сборки на хостинг | `human` |
| `publish` | публикация на площадку | `human` |
| `service` | вызов сетевого сервиса | `data` |
| `notify` | события и уведомления | `ai` |
| `build` | внешний код или данные при сборке | `data` |
| `host` | где живёт: хранение, хостинг, исполнение | `data` |

**Кто движет** (`driver`) — цвет потока (D-06): `human` — коралловый
(решение автора), `ai` — бирюзовый (ИИ и автоматика), `check` — зелёный
(проверка), `data` — серый (данные и знание без участия).

### 8.4 Состояния

По модели (`status`): `active` — работает; `planned` — записан план;
`blocked` — ждёт решения или доступа (с причиной в `note`); `off` —
выключен.

По данным (в срезе): у потока — `flowing`, `quiet`, `planned`,
`blocked`, `off`, `unknown`, `unobserved`; у узла — `working`, `idle`,
`up`, `down`, `planned`, `blocked`, `off`, `unknown`, `unobserved`.

### 8.5 Сигналы

| Сигнал | Поля | Событие |
|---|---|---|
| `git-commits` | `repo` (узел), `who` = `ai` / `human` / `merge` / `any` | коммит основной ветки репозитория указанного вида |
| `git-path` | `repo` (узел), `paths` (префиксы путей) | коммит основной ветки, который меняет путь с одним из префиксов |

### 8.6 Транспорт

`git` (ветки, PR, вливание), `clone` (чтение клона), `copy` (копия
файлов), `http` (запрос), `rsync` (выгрузка), `intent` (вызов
приложения Android), `push` (мгновенный канал), `api` (API площадки),
`manual` (руками автора), `knowledge` (решение, записанное с двух
сторон, без передачи данных).

## 10. Интеграции

Правило для всех интеграций с репозиториями экосистемы: DPvisualisation
**подстраивается** под их форматы и не просит менять их ради себя без
решения в том репозитории (`DPmeta:M-02`). Нераспознанное — диагностика
с местом, а не догадка.

| | Интеграция | Что берёт или отдаёт | Устойчивость | Что ломает |
|---|---|---|---|---|
| I-01 | DPmeta: реестр | `DPmeta:tools/ecosystem.toml`, `schema = 1` — slug репозиториев | схема с номером | новая схема — `REGISTRY_SCHEMA_UNSUPPORTED`, сверка пропускается |
| I-02 | DPmeta: контракты | заголовки `## C-NN — …` в `DPmeta:docs/CONTRACTS.md` | формат уже держит `DPmeta:C-10` | другой уровень заголовков — контракты «не найдены» |
| I-03 | Git: клоны репозиториев | история основной ветки, ветки `origin/*` | стабильный формат git | неполная история — пометка `CLONE_SHALLOW` |
| I-04 | Сайт `dpsmpx.com` | ничего не опрашивается (D-19): сайт сам забирает комплект схемы перед каждой выгрузкой (D-18, `SocialMediaImage:Д43`) | копия файлов | — |

| I-07 | Браузер и WebView | HTML5, SVG, ES2020, `fetch`, `postMessage` | стандарты | — |
| I-08 | Termux | `serve` на телефоне: Python ≥ 3.11 и git из пакетов Termux | документированные пакеты | нет клонов на телефоне — срез из `unknown` |

**Что стоит записать в DPmeta** (решает DPmeta, `DPmeta:M-02`; Q-03):
строку DPvisualisation в `DPmeta:tools/ecosystem.toml` и поток «DPmeta →
DPvisualisation: реестр и контракты читаются как данные» — как
`DPmeta:C-10` для страницы прогресса: изменение формата заголовков
контрактов молча изменит модель.

**Что предлагается DPmetaApp** (решает он сам; Q-04 — решено): разбор
Т15 по `docs/FORMATS.md` — нативный показ своими графиками
(`DPmetaApp:D-15`, `DPmetaApp:D-26`). WebView со сборкой
`dist/dpvisualisation.html` из ресурсов приложения, без сети, — только
отступлением с ответом автора: мастер-ТЗ DPmetaApp называет WebView тем,
чем приложение быть не должно.

## 11. Безопасность и приватность

| | Угроза | Мера |
|---|---|---|
| T-01 | Устройство закрытой экосистемы утекает наружу | личный инструмент, не публикуется (D-08); сборка `dist/` не коммитится; на сайт и в открытые репозитории не выкладывается |
| T-02 | Содержимое закрытых репозиториев в срезе | в срез — только счётчики, время, хеши и имена веток; текст коммита читается только для признака ИИ и не сохраняется (D-08) |
| T-03 | Сервер живого режима доступен из сети | `127.0.0.1` по умолчанию (F-46); сервер только отдаёт файлы `viewer/` и `data/`, без записи и без листинга каталогов |
| T-04 | Сборщик обращается к посторонним адресам | обращений к сайту и сервисам нет (D-19); `[allow] hosts` пуст, модель с адресами не проходит проверку |
| T-05 | Секреты в репозитории | секретов нет и не нужно: `git fetch` — учётными данными окружения автора; проверка `security.secrets` |
| T-06 | Чужая страница внедряет данные через `postMessage` | сообщение принимается только от родительского окна и только с `type: "dpvis:data"` и `schema` `dpvis-*/1`; данные отображаются как текст, не как HTML |

## 13. Процесс разработки

Как во всей экосистеме (`DPmeta:docs/PRINCIPLES.md`, E-01…E-13):
журнал решений — источник истины; `CLAUDE.md` — правила, `docs/PROCESS.md`
— зачем они; `TODO.md` — только незаконченное; одна команда проверок
`tools/check/run.sh` (`static` — после правки, `full` — перед вливанием,
итог — в описании PR); без GitHub Actions; хук начала сессии показывает
ветки с невлитой работой; шаблон PR «Сделано / Осталось / Проверки».
Происхождение идей — `docs/PROCESS.md`, чужого — `docs/PROVENANCE.md`.

## 14. План внедрения

Этапы — `ROADMAP/ROADMAP.md`: 0 — постановка и процесс; 1 — модель; 2 —
сборщик; 3 — просмотрщик; 4 — живой режим, сборка, выпуск 1.0.0. Версия
растёт с этапами: этап N — `0.N.0`, выпуск — `1.0.0`.

## 16. Ограничения первой версии

| | Ограничение |
|---|---|
| L-01 | Открытые PR и сессии без коммитов не видны: GitHub API и состояние облачных сессий не читаются (нет токена и публичного API); «работает» — только по следам в git. |
| L-02 | Потоки без следа в git (публикация на площадку руками, «да» автора в терминале) — `unobserved` или по косвенному сигналу; их точность ограничена. |

| L-05 | Модель сверена вручную на дату `as_of`; состояния адресатов площадок и планы сервисов обновляются правкой модели. |
| L-06 | Нет уведомлений: тревоги — дело DPmetaApp по его каталогу событий. |
