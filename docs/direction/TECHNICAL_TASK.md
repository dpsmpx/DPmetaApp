## 0. О документе

**Обязательность.** «Должен» — требование 1.0; его проверяет критерий
готовности (§16). «Может» — допустимо, но не обязательно. «Не делает» —
граница версии (§3, §17).

**Нумерация.** Цели — `G-NN`, сценарии — `S-NN`, решения — `D-NN`,
функциональные требования — `F-NN`, нефункциональные — `N-NN`,
интеграции — `I-NN`, угрозы — `T-NN`, критерии готовности — `A-NN`,
ограничения — `L-NN`, риски — `R-NN`, вопросы автору — `Q-NN`. Номера —
латиницей: на них ссылаются код и тесты, а латинская `P` и кириллическая
`Р` на глаз неразличимы (`DP-Verify:docs/direction/TECHNICAL_TASK.md`,
R-06 там). Чужой номер пишется с именем проекта — `DPpass:D-12`,
`DPmeta:C-05`; чужой путь — `SocialMediaImage:docs/platforms/WEBSITE.md`
(`DPmeta:C-06`). Номера сверяет `tools/check/run.sh` (проверка
`docs.refs`).

**Неизвестное** не додумывается: недоступное и непроверенное помечено
**UNKNOWN** с тем, чем и когда это проверить
(`SocialMediaImage:CLAUDE.md`, «Факты и утверждения»).

**Словарь.**

| Термин | Значение |
|---|---|

| проект | репозиторий экосистемы с записью в реестре (§7.1) |

| действие | операция, меняющая что-то вне приложения (комментарий, слияние, запуск маршрута, выгрузка сайта) — с уровнем по D-07 |

| событие | факт «что-то произошло» с типом из каталога (§8.1): открыт PR, новый комментарий, Claude закончил ответ, сайт не отвечает |
| правило уведомления | условие над событиями и что делать, когда оно выполнено: уведомить, собрать в сводку, промолчать (F-52) |
| мгновенный канал | доставка событий от внешних источников на телефон сразу, без ожидания опроса: UnifiedPush через ntfy (D-23) |
| набор хуков уведомлений | скрипт для хуков Claude Code (`Stop`, `Notification` и др.), который шлёт подписанное событие в мгновенный канал (F-56) |

Выводы, на которых стоит ТЗ:

1. **Знание о проектах уже машиночитаемо — приложение его читает, а не
   заводит второе.** Реестр репозиториев есть в DPmeta
   (`DPmeta:tools/ecosystem.toml`), стадии — в блоках README, которые
   пишут скрипты (`DPmeta:E-13`), решения — в журналах с шаблонами
   номеров, история — в наборах `progress/v1` SocialMediaImage, публичное
   — в `/api/v1/` сайта, задуманном в том числе «для своих клиентов —
   приложения и бота» (`SocialMediaImage:docs/platforms/WEBSITE.md`).
   О себе прав сам репозиторий (`DPmeta:M-02`); приложение — читатель и
   пульт, а не источник истины.
2. **CI нет — состояние проверок живёт в описаниях PR.** GitHub Actions
   не используются нигде (`DPmeta:E-07`); итог полного прогона пишется в
   раздел «Проверки» описания PR. Красный `main` без CI никто не замечает
   (`DP-Verify:docs/direction/TECHNICAL_TASK.md`, §1, вывод 3) —
   приложение должно делать это видимым.
3. **Работу делают облачные сессии Claude Code.** Рычаги автора —
   поручить работу сессии, посмотреть PR, ответить на вопрос, влить.
   Официальный способ запустить облачную сессию из своей программы —
   API-триггер маршрута (`/fire`, приложение В).
4. **Телефон автора — Android с Termux, и выгрузка сайта уже идёт с
   него** — ярлыком Termux:Widget, который вызывает систему
   SocialMediaImage (`SocialMediaImage:tools/termux/dpsmpx-site-deploy.sh`).
   Инцидент 5 октября 2026 (ярлык выгрузил весь рабочий каталог,
   `DPmeta:RISK-08`) показал цену обхода: приложение повторно использует
   этот вход и не строит второй.
5. **Процесс во всех проектах одинаков по сути** (`DPmeta:docs/PRINCIPLES.md`,
   E-01…E-13) — разборщики форматов могут быть общими, а различия
   (шаблоны номеров, пути журналов) берутся из реестра.
6. **Границы закрытого:** код закрытых проектов не выходит наружу
   (`DPmeta:C-05`); DPpass публично не называется
   (`SocialMediaImage:data/progress/scope.yaml`); без телеметрии
   (`DPpass:D-12`); публичный образ правит только автор (`DPmeta:C-07`).
7. **Подписочные аккаунты claude.ai нельзя подключить входом в стороннем
   приложении** — политика Anthropic разрешает сторонним продуктам только
   ключи API (приложение В). Подписку приложение использует через
   маршруты и их токены.
8. **Соцсети неравны по API.** Подписчиков, комментарии и ответы
   официальные API дают по-разному: где-то полностью, где-то после
   запроса прав или аудита, где-то никак (приложение Г). Приложение
   работает только официальными API, без скрейпинга и входа под
   паролем; где API нет — ручной ввод, импорт выгрузки и честная
   пометка «нет API» (D-20).
9. **«Claude закончил ответ» знает только сама сессия.** Публичного API
   состояния облачных сессий нет; событие даёт хук Claude Code `Stop`
   (с текстом ответа), «ждёт ввода» — хук `Notification`. Облачная
   сессия читает хуки только из `.claude/settings.json` своего
   репозитория (приложение В) — поэтому событие требует набора хуков в
   репозиториях, по их решению (D-23).

## 3. Что не входит (non-goals)

Из постановки и решений экосистемы:

- **Не источник истины о проектах.** Приложение не хранит решений,
  стадий и задач проектов как своих; оно показывает их из репозиториев
  и меняет только через процесс репозитория (D-06).
- **Не правит журналы решений, `CLAUDE.md` и `main` других репозиториев
  напрямую**; не делает force-push, не переписывает историю `main`
  (`DPmeta:C-04`, неявное допущение «история не переписывается»).
- **Не выгружает сайт само** и не хранит адрес и ключ выгрузки;
  прямой rsync/ssh/scp в обход системы SocialMediaImage — никогда
  (`SocialMediaImage:Д35`, D-11).
- **Не публикует контент на площадки** и не одобряет версии за автора
  (`SocialMediaImage:Д12`, `SocialMediaImage:Д26`): публикации идут
  через систему SocialMediaImage. Ответ на комментарий — другое: его
  пишет и отправляет сам автор (D-21).
- **Без скрейпинга, автоматизации браузера и входа в аккаунты площадок
  по паролю** — только официальные API (D-20); где API нет — ручной ввод
  и ссылка в приложение площадки.
- **Без автоответов и массовых действий** на площадках: ни одного
  ответа без нажатия автора, никаких рассылок, подписок и отписок
  пачкой (D-21).
- **Не входит в аккаунт claude.ai** и не использует OAuth-токены подписок
  (D-08); не повторяет интерфейс сессий Claude Code — сессия открывается
  в официальном приложении Claude или в браузере.
- **Без телеметрии, аналитики и отчётов о падениях** (D-10).
- **Без своего сервера** в 1.0 и без FCM: данные — опросом; мгновенные
  события — через UnifiedPush и сторонний ntfy, в событии — только
  подписанный минимум без содержимого (D-18, D-23).
- **Не IDE и не git-клиент:** код не редактируется, клоны на устройстве
  ведёт Termux, не приложение.
- **Не собирает проекты на телефоне** (Galdhold, DPlang и др.); запускает
  только команды из реестра команд (§7.10).
- **Не распространяется через Google Play, RuStore и App Store** в 1.0
  (§12).
- **Не для iOS, веба и компьютера** в 1.0 (D-02).
- **Не многопользовательское:** один пользователь — автор; общего доступа
  и ролей нет.

## 4. Пользователи и сценарии

Пользователь один — автор, с телефона. Второй — сессия ИИ, которая
разрабатывает приложение (её процесс — §14). Третий — сессии Claude Code
в репозиториях экосистемы: они получают поручения из приложения и
отчитываются через PR.

| | Сценарий | Что делает приложение |
|---|---|---|
| S-01 | Утренний обзор | сводка на срез: что изменилось за ночь, кто работает, PR ждут автора, красные и неизвестные проверки, вопросы автору, сайт, расход Claude (F-04, F-05) |
| S-02 | Ответить на вопрос автору | список вопросов из всех проектов → ответ → поручение сессии того репозитория маршрутом → слежение за PR с записью решения (F-24, F-25) |

## 6. Архитектура

### 6.1 Платформа и стек

- **Android**, телефонная раскладка; `minSdk` 28, `targetSdk` и
  `compileSdk` 36, JDK toolchain 21 (N-10; `minSdk` — Q-02).
- **Kotlin**, сборка Gradle с wrapper, каталог версий
  `gradle/libs.versions.toml`, правила модулей — convention-плагины в
  `build-logic/` (образец — `DPpass:build-logic/`, `DPpass:gradle/libs.versions.toml`).
- **Ядро** — модули на чистом Kotlin/JVM: собираются и тестируются в
  облачной сессии без Android SDK (D-03). Android-модуль `:app`
  подключается, только если SDK найден, а полный режим проверок называет
  его отсутствие ошибкой (образец — `DPpass:settings.gradle.kts`).
- **Интерфейс** — Jetpack Compose (D-15), фон — WorkManager (D-18),
  биометрия — `androidx.biometric`, виджет — Glance. AndroidX — только в
  `:app`.

Кандидаты в зависимости — каждая входит только со строкой в
`docs/PROVENANCE.md` и проверкой контрольных сумм (N-14); окончательный
выбор — на этапе, где зависимость нужна:

| Назначение | Кандидат | Лицензия | Модуль | Этап |
|---|---|---|---|---|
| корутины | `kotlinx-coroutines` | Apache-2.0 | ядро | 1 |
| JSON | `kotlinx-serialization-json` | Apache-2.0 | ядро | 1 |
| HTTP | OkHttp | Apache-2.0 | `:core:net` | 2 |

### 6.2 Модули

```
:core:diagnostics  Outcome, Diagnostic, реестр кодов (только добавляются)
:core:model        типы предметной области: ProjectId, RepoRef, Observation, Snapshot, ActionLevel …
:core:formats      разборщики: подмножество TOML, реестр DPmeta, журнал решений, TODO,
                   ROADMAP, блок состояния README, разделы описания PR, progress/v1,
                   item.yaml; у каждого — корпус «ловит / пропускает»
:core:store        хранилище наблюдений (только добавление) и журнал действий; шифрование — через интерфейс
:core:net          HTTP с условными запросами (ETag), бюджет запросов, список разрешённых адресов (D-10)
:core:github       GitHub REST и GraphQL поверх :core:net
:core:claude       Claude API (Messages, Models), отчёты Usage & Cost и лимиты (только GET), маршруты /fire
:core:site         пробы сайта, политика заголовков, API сайта
:core:social       площадки: каталог возможностей, адаптеры официальных API (подписчики,
                   комментарии, ответы), ручной ввод и импорт CSV
:core:metrics      выводимое состояние и метрики; Rules.kt — все пороги и веса с RULES_VERSION
:core:notify       каталог событий, события из наблюдений, движок правил уведомлений,
                   проверка подписи мгновенного канала
:core:actions      модель действий: уровни, политика подтверждений, исполнитель, запись в журнал
:core:sync         план синхронизации: источники → наблюдения; не знает о расписании
:cli               dpmeta-cli (JVM): синхронизация с корпуса или вживую, состояние, метрики, дым
:tests:corpus      синтетический корпус форматов и межмодульные тесты
:app               Android: Compose, Keystore, биометрия, WorkManager, мост Termux, виджет,
                   приём UnifiedPush, вход в площадки, слушатель уведомлений (по желанию)
```

Направления зависимостей: `diagnostics ← model ← formats ← {github,
claude, site, social} ← sync`; `net` — под `github`, `claude`, `site`,
`social`; `metrics`, `notify` и `actions` зависят только от `model` и
`diagnostics`; `:app` и `:cli` — от всех. Компилятор проверяет зависимости, допустимые направления —
проверка модулей в `tools/check/` (образец — `DPpass:tools/hostcheck/check_modules.py`).
Android-типы — только в `:app` (как `DPpass:CLAUDE.md`, «Правила кода»).

Раскладка в корне репозитория — точки входа и файлы Gradle; модули ядра —
в `core/`, CLI — в `cli/`, приложение — в `app/` (`DPmeta:E-06`).

### 6.3 Модель данных

- **Наблюдение** — `{id, source, subject, kind, as_of, schema, payload,
  raw_sha256}`: что получено, откуда и когда; `payload` — нормализованный
  JSON, `raw_sha256` — отпечаток исходного ответа. Наблюдения только
  добавляются; одинаковое содержимое не дублируется (по отпечатку).
- **Выводимое состояние** — `derive(наблюдения ≤ as_of, правила)`:
  «кто работает», открытые вопросы, метрики, тревоги. Хранится только как
  кэш, который можно удалить без потерь (образцы — `DPlearn:D-01`,
  `DP_game_market_analytic_system:docs/ARCHITECTURE.md`, INV-01 там;
  `DPmonetization:tools/dpmon/__init__.py`).
- **Правила** — все пороги, окна, веса — в одном файле `Rules.kt` с
  `RULES_VERSION`; изменение смысла — новая версия и строка в
  `docs/CHANGELOG.md` (что, почему, как проверить; образец —
  `DPlearn:CLAUDE.md`, «Новая версия правил»).
- **Время** — UTC в хранении; через `Clock` в коде (`DPpass:D-21`);
  часовой пояс показа — настройка, по умолчанию `+03:00` (как
  `SocialMediaImage:data/progress/scope.yaml`).
- **Журнал действий** — отдельный поток записей только на добавление
  (F-44).

### 6.4 Синхронизация

- План строится из реестра: для каждого проекта — источники (PR и ветки
  одним запросом GraphQL, файлы процесса — по содержимому с ETag, сайт —
  пробы, Claude — отчёты); порядок детерминирован.
- Условные запросы (`If-None-Match`): ответ 304 — наблюдение «без
  изменений», лимит GitHub не расходует (N-03).
- Отказ источника — `Diagnostic` этого источника; остальные идут дальше;
  старые наблюдения не удаляются и не перекрываются пустыми.
- Бюджет: перед синхронизацией — остаток лимита GitHub; меньше нужного —
  синхронизация по приоритету (сводка → открытые PR → файлы процесса →
  история), остальное — на следующий раз, с пометкой на экране.

### 6.5 Действия и уровни

Каждое действие — типизированная команда `{id, level, target, params}`,
которая проходит политику уровня (D-07), выполняется и пишется в журнал.

| Уровень | Что | Подтверждение | Примеры |
|---|---|---|---|
| 0 | чтение | нет | синхронизация, просмотр, фоновые команды Termux только для чтения, черновик ответа от Claude (пока не отправлен), ручной ввод числа подписчиков |
| 1 | обратимое, видимое | одно нажатие с показом, что уйдёт | комментарий, ревью, issue, перевод PR из черновика, запуск маршрута, `git pull` клона в Termux, ответ на комментарий в соцсети |
| 2 | значимое | экран «что изменится» + биометрия или PIN устройства | влить PR, закрыть PR, удалить влитую ветку, выгрузка сайта ярлыком Termux, скрыть или удалить комментарий на площадке |
| 3 | запрещено | в коде отсутствует; проверка ищет признаки | force-push и перезапись ссылок, удаление репозитория, изменение настроек репозитория и защиты веток, мутирующие вызовы Admin API, rsync/ssh/scp, одобрение контента за автора, автоответы и массовые действия на площадках, публикация постов в обход SocialMediaImage |

### 6.6 Хранение и секреты

- Данные — в `noBackupFilesDir`; резервные копии и перенос Android
  выключены (`allowBackup=false`, правила извлечения данных пустые).
- Запись шифруется AES-256-GCM со случайным nonce и ключом записи как
  дополнительными данными; ключ данных обёрнут ключом Android Keystore
  (StrongBox, если есть) — образец `DPpass:D-19`.
- Секреты (токены GitHub, ключи API, токены маршрутов) — отдельное
  хранилище; ключ Keystore для него требует аутентификации пользователя
  для показа секрета и для действий уровня 2.
- В коде секрет — тип `Secret`: `toString()` даёт `<redacted>`, значение
  выдаётся только в разрешённых местах; журнал — только через `Logger` с
  редактированием по умолчанию (`DPpass:D-11`).
- Экраны с секретами — `FLAG_SECURE` (нет снимков экрана и превью в
  списке задач).

### 6.7 Фон, события и уведомления

- Периодическая синхронизация — WorkManager, по умолчанию раз в 30 минут
  (не чаще 15 — предел системы), ограничения «есть сеть» и «не низкий
  заряд»; ручное обновление — срочной задачей. Интервал можно задать
  отдельно для групп источников (соцсети, GitHub, сайт).
- **События** появляются тремя путями: из разницы наблюдений после
  синхронизации (новый PR, комментарий, изменение подписчиков);
  мгновенным каналом (D-23); слушателем уведомлений других приложений,
  если автор его включил (F-57). Все три ведут в один каталог (§8.1).
- **Движок правил** (`:core:notify`) — чистая функция «события + правила
  + время → что показать»: уведомление, строка ленты, пункт сводки.
  Тот же движок проверяет правило на прошлых событиях (F-53).
- **Мгновенный канал:** приложение регистрируется у дистрибьютора
  UnifiedPush (приложение ntfy) и получает адрес; источники (хуки Claude
  Code, F-56) шлют туда событие из минимума полей с подписью
  HMAC-SHA256 общим ключом; приложение проверяет подпись, а подробности
  достаёт само. Постоянного сервиса на переднем плане у приложения нет:
  соединение держит дистрибьютор.

### 6.8 Сеть

- Список разрешённых адресов в коде: `api.github.com`, `github.com`
  (device flow), `api.anthropic.com`, `dpsmpx.com` и `www.dpsmpx.com`;
  для площадок — адреса их официальных API, и только для площадок,
  которые есть в списке соцсетей (приложение Г: `www.googleapis.com`,
  `youtubeanalytics.googleapis.com`, `oauth2.googleapis.com`,
  `api.telegram.org`, `api.vk.com`, `oauth.vk.com`,
  `open.tiktokapis.com`, `discord.com`); остальные — отказ на уровне
  `:core:net` (D-10). С мгновенным каналом приложение по сети не
  говорит — его держит дистрибьютор UnifiedPush.
- Только TLS с системными корневыми сертификатами; свой `TrustManager` и
  `HostnameVerifier` запрещены (`DPpass:docs/SECURITY_MODEL.md`, T5 там).
- **Исключение на время:** сайт сейчас отвечает по http (сертификата нет —
  `SocialMediaImage:tools/termux/dpsmpx-site-deploy.sh`, переменная
  `SITE`). Пробы сайта по http разрешены только для `dpsmpx.com`
  (`network_security_config` по домену), без секретов в запросах.
  Когда у сайта появится сертификат, исключение удаляется (A-09).

### 6.9 Ошибки

Ожидаемые отказы — `Outcome` с `Diagnostic`, а не исключения; причина —
цепочкой; код `DiagCode` — публичный контракт, только добавляется
(образец — `DPpass:D-22`). Пользователь видит причину и что сделать.

`FORMAT_UNRECOGNIZED`, `GITHUB_AUTH_EXPIRED`, `GITHUB_RATE_LIMITED`,

`ROUTINE_TOKEN_INVALID`, `ROUTINE_LIMIT_REACHED`, `SITE_UNREACHABLE`,
`SITE_STATUS_NOT_OK`, `SITE_HEADER_MISSING`, `TERMUX_NOT_READY`,
`TERMUX_COMMAND_FAILED`, `HOST_NOT_ALLOWED`, `STORE_CORRUPTED`,
`SOCIAL_AUTH_EXPIRED`, `SOCIAL_QUOTA_EXCEEDED`, `SOCIAL_NOT_SUPPORTED`,
`SOCIAL_RIGHTS_MISSING`, `PUSH_SIGNATURE_INVALID`, `PUSH_NOT_REGISTERED`,

**Что стоит записать в DPmeta** (решает DPmeta, `DPmeta:M-02`):
DPmetaApp становится первым репозиторием, который **читает форматы
процессов всех проектов**. Как страница прогресса (`DPmeta:C-10`),
приложение молча покажет другие числа, если формат заголовков или
меток изменится. Предложение — контракт в `DPmeta:docs/CONTRACTS.md`
«DPmetaApp читает форматы процессов» и строка DPmetaApp в
`DPmeta:tools/ecosystem.toml` (Q-11).

**Что предлагается репозиториям экосистемы** (решает каждый сам):

- набор хуков уведомлений (F-56) — строка в `.claude/settings.json`
  репозитория и скрипт; это поставка кода автора в его же репозитории,
  как у DP-Verify (`DPmeta:C-03`): копия с записью происхождения и только
  по решению принимающего репозитория (Q-15);
- SocialMediaImage — источник истины о публичных ссылках: новые и
  изменённые аккаунты из приложения доходят до `links.yaml` поручением
  его сессии (F-60), а не правкой из приложения (D-19).

## 12. Подпись, сборка и распространение

### 12.1 Что такое подпись на Android

Каждый APK подписан — без подписи система его не установит. Подпись
говорит системе, **кто** выпустил приложение: обновление ставится поверх,
только если подписано тем же ключом (или ключом из цепочки ротации схемы
v3). Ключ разработчик создаёт сам, бесплатно; это и есть подпись
разработчика в техническом смысле.

«Официальная подпись разработчика» в обиходе — это одно из другого:

1. **Подпись магазина** — Google Play App Signing (нужен аккаунт Play
   Console и проверка личности), RuStore, App Store.
2. **Верификация разработчика Android** — регистрация личности
   разработчика и пары «имя пакета + ключ» у Google; с 30 сентября 2026
   без неё приложение не ставится на сертифицированные устройства в
   Бразилии, Индонезии, Сингапуре и Таиланде, в 2027 — шире (приложение В).
3. **Apple Developer Program** — для iOS (не в 1.0, D-02).

### 12.2 Нужна ли она для заявленной функциональности

| Функция | Что нужно | Официальная подпись или регистрация |
|---|---|---|
| установка на телефон автора | APK, подписанный своим ключом | **не нужна** (APK; при обязательной верификации — ADB или «расширенный путь», §12.3) |
| обновление приложения | тот же ключ | **не нужна**; нужна дисциплина ключа (§12.4) |
| GitHub: чтение, PR, слияние, issues | GitHub App с device flow или PAT (D-17) | **не нужна** (регистрация GitHub App — не подпись приложения) |
| Claude API: чат, расход, лимиты | ключи API Console | **не нужна** |
| маршруты Claude Code | токены `/fire` | **не нужна** |
| несколько аккаунтов Claude | профили (F-17) | **не нужна**; вход claude.ai в стороннем приложении запрещён политикой Anthropic, подпись этого не меняет |
| мост Termux | разрешение `RUN_COMMAND`, `allow-external-apps` | **не нужна**: общая подпись с Termux не требуется (приложение В) |
| биометрия, Keystore | системные API | **не нужна** |
| уведомления, WorkManager, виджет | системные API | **не нужна** |
| мгновенные push (FCM) | проект Firebase | **не нужна**, но в 1.0 не используется (D-18) |
| проверенные ссылки App Links на `dpsmpx.com` | `assetlinks.json` с отпечатком **своего** ключа на сайте | **не нужна**; в 1.0 не нужны — device flow обходится без перенаправления |
| распространение через Google Play / RuStore | аккаунт магазина, проверка личности | **нужна** — не входит в 1.0 |
| установка на чужие устройства в странах с обязательной верификацией | верификация или аккаунт ограниченного распространения | **нужна** — не входит в 1.0 (Q-08) |
| iOS | Apple Developer Program | **нужна** — не входит в 1.0 |

### 12.3 Вывод

**Для всей функциональности 1.0 официальная подпись разработчика не
нужна.** Нужна и достаточна собственная подпись ключом выпуска автора —
с дисциплиной ключа (§12.4). Ни одна функция приложения не обращается к
API, которые требуют регистрации разработчика у Google или Apple (D-12).

Что может это изменить, и что тогда делать:

- **Верификация разработчика Android дойдёт до региона автора** (2027).
  По сообщениям на август 2026 (приложение В), резиденты России не
  смогут пройти верификацию из-за санкций США, а устройства в России
  Google исключит из проверки — **UNKNOWN**, официального документа
  Google об этом нет; сверить при каждом шаге развёртывания Google.
  Если проверка коснётся телефона автора, остаются пути без регистрации:
  установка через ADB и «расширенный путь» для опытных пользователей
  (однократно: включить, перезагрузить, подождать 24 часа). Аккаунт
  ограниченного распространения (до 20 устройств, без документа и платы)
  — доступен ли он резиденту России, **UNKNOWN**.
- **Нужна установка на чужие устройства или магазин** — тогда
  регистрация (Q-08); это меняет D-12 новым решением.
- **Нужен iOS** — платная программа Apple (D-02).

### 12.4 Ключ и порядок выпуска

Образцы — `Galdhold:app/build.gradle` («Релиз — только своим ключом») и
`DPpass:docs/direction/ROADMAP/05-release.md`.

- Ключ выпуска — RSA 4096 (`keytool -genkeypair`), создаётся автором
  один раз; в репозитории его нет — `tools/check` запрещает файлы
  `*.jks`, `*.keystore`, `*.p12`, `*.pfx`, `*.key`.
- Схемы подписи v2 и v3 (v1 не нужна при `minSdk` ≥ 24); v3 — чтобы
  можно было сменить ключ, не теряя обновлений.
- Сборка релиза без ключа и паролей в окружении останавливается с
  объяснением, а не подписывается отладочным ключом молча.
- **Ключ не покидает устройств автора.** Предлагаемый порядок: облачная
  сессия собирает **неподписанный** релизный APK и файл с его SHA-256
  (`tools/release/` — этап 8); автор сверяет сумму и подписывает APK
  `apksigner` в Termux своим ключом (есть ли пакет `apksigner` в
  репозитории Termux — UNKNOWN, проверить на этапе 8; запасной путь —
  компьютер автора с Android SDK). Источник выпуска — только артефакт
  сборки, не рабочий каталог (`DPmeta:RISK-08`).
- Отпечаток SHA-256 сертификата ключа — в `docs/RELEASE.md` (публичная
  часть, не секрет) и в «О программе» (F-50); проверка APK
  (`check_apk`, образец — `DPpass:tools/hostcheck/check_apk.py`): схемы
  v2+v3, отпечаток совпадает с записанным, `debuggable=false`, нет
  cleartext, кроме исключения §6.8.
- Две резервные копии ключа и паролей — в разных местах, зашифрованно
  (T-10); без ключа обновить установленное приложение нельзя.
- `applicationId` фиксируется до первой установки (Q-10): после установки
  его смена — новое приложение без данных старого.

## 14. Процесс разработки

Подробно и с источником каждой практики — `docs/PROCESS.md`; правила
для сессий — `CLAUDE.md`. Главное:

- **Источник истины** — `docs/direction/DECISIONS.md`; старшинство:
  решения → `CLAUDE.md` → ТЗ → ROADMAP → `TODO.md` → `docs/`. `README.md`
  — не источник истины; его блок состояния пишет скрипт (`DPmeta:E-13`).
- **Запрос автора сверяется с решениями** до работы; решённое не
  переспрашивается; мелочи решаются и называются в отчёте (`DPmeta:E-02`).
- **Сначала проверить нужду; готово — остановиться** (`DPmeta:E-03`).
- **Сбой инструмента — не сбой кода; красное до правки — не своё**
  (`DPmeta:E-04`).
- **Работа не теряется:** коммит и пуш после каждого законченного куска и
  не реже раза в полчаса; незаконченное — `WIP:`; PR черновиком сразу
  после первого пуша с «Сделано / Осталось / Проверки»; в начале сессии
  — ветки с невлитой работой (`DPmeta:E-08`; хук
  `.claude/hooks/session-start.sh`).
- **Классы задач** — обычная, системная, рискованная; проверяющий только
  для чтения — на контрольных точках (`Galdhold:CLAUDE.md`, «Работа над
  задачей»).
- **Другие репозитории экосистемы — только чтение**: клоны — чтобы
  сверить форматы; находка — в PR и `TODO.md` этого репозитория, правка
  там — их сессией (`DPmeta:M-04`).

**Уровни проверок** (`tools/check/run.sh`, D-13, D-16):

| Уровень | Что | Когда |
|---|---|---|
| `static` | структура, текст, секреты и файлы ключей, ссылки, номера, решения, `TODO`, ROADMAP, блок README, скрипты — секунды | после любой правки |
| `full` | `static` + самотесты проверок; с этапа 1 — сборка и тесты ядра Gradle без Android SDK, дым `dpmeta-cli`; с SDK — `:app`: сборка, Lint, проверка манифеста | перед переводом PR из черновика, перед вливанием |
| `full --strict` (этап 1) | `full`, где пропуск (нет SDK, нет JDK) — ошибка | перед вливанием правок `:app` и перед выпуском |

Коды возврата: 0 — пройдено, 1 — есть находки, 2 — неверный вызов,
3 — сбой самой проверки (`DP-Verify:V-10`). Пустая проверка — провал
(`DP-Verify:V-07`). Итог `full` — в описании PR. GitHub Actions нет.

**DP-Verify** подключается по его правилам интеграции, когда выйдет 1.0
и автор решит вопрос лицензии (Q-01, `DPmeta:RISK-01`); тогда общие
проверки `tools/check/` заменяются его обязательным набором, а

## 16. Критерии готовности 1.0

| | Критерий | Чем проверяется |
|---|---|---|
| A-01 | Все проекты реестра DPmeta на одном экране; неизвестная схема — явная ошибка, работа на последнем распознанном реестре | тест разборщика на корпусе; ручная проверка на устройстве |

| A-10 | Сеть — только адреса §6.8; телеметрии нет | тест `:core:net`; проверка зависимостей и манифеста |
