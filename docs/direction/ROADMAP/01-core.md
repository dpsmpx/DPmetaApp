# Этап 1 — Основа ядра

Состояние: **в работе**.

## Цель

Модуль `core`: примитивы, на которых держатся все подсистемы, — с
модульными и property-тестами (ТЗ, §139, Phase 1; ТЗ, §126).

## Объём

| Пакет `com.dpsmpx.dpai.core.…` | Что | Решения |
|---|---|---|
| `result` | `Outcome`, `OperationResult`, `Provenance` | D-05, D-06 |
| `diagnostics` | `Diagnostic`, `DiagCode`, причины, класс повтора, `Secret`, `Redactor` | D-05, D-14 |
| `ids` | типизированные идентификаторы, генератор | D-08 |
| `clock` | `Clock`, `ManualClock`, `Timestamp`, `RandomSource` | D-07 |
| `hashing` | `ContentHash`, SHA-256 | D-10 |
| `serialization` | строгий JSON, канонический вид, чтение полей с путём | D-09 |
| `state` | автомат с таблицей переходов; жизненные циклы сессии, задачи, аккаунта, heartbeat, предохранителя | D-11, D-23 |
| `events` | конверт события, типы, отслеживание последовательности | D-12 |
| `measure` | `Measure`: известное с источником или неизвестное | D-13 |

Средства тестов — модуль `testkit`: property-тесты с зерном и
генераторы (`docs/TESTING.md`, «Свойства»).

## Критерии выхода

- [ ] Все пакеты таблицы реализованы; модульные тесты на каждый.
- [ ] Property-тесты: недопустимые переходы отвергаются; разбор
      канонического JSON возвращает то же значение; повтор события
      идемпотентен; порядок идентификаторов по времени устойчив.
- [ ] Каждый код диагностики и тип события — в реестре
      (`check_contracts.py`).
- [ ] Перебор всех пар состояний каждого жизненного цикла: переход либо
      в таблице, либо отвергнут (ТЗ, §101).
- [ ] Ядро без сторонних зависимостей времени выполнения (D-17).
- [ ] `tools/verify/run.sh full` зелёный.

## Что не делалось

Хранение — этап 2; сущности подсистем (задача, сессия, аккаунт как
данные) — в своих модулях на своих этапах.
