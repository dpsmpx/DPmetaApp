# Адаптация в Zapret и Zapret2: что переносится в DPpass

Дата исследования: **5 октября 2026**. Вопрос: как Zapret и Zapret2
учатся на ограничениях сети и что из этого применимо к клиенту прокси
на Android без root (решение D-44). Источники — документация и исходники
открытых проектов, прочитанные в этот день; код не берётся, только
сведения о подходах (`docs/direction/RESEARCH_SCOPE.md`, §3, правило 5).

## 1. Что это за проекты

- **Zapret** (bol-van/zapret, лицензия MIT по `zapret/docs/readme.en.md`) —
  средство против DPI на Linux и Windows. Программы `nfqws` (пакеты из
  NFQUEUE/WinDivert) и `tpws` (прозрачный прокси) меняют собственный
  трафик пользователя так, чтобы фильтр не узнал запрещённое: поддельные
  пакеты, разбиение и перестановка сегментов, манипуляции TTL и
  контрольными суммами («десинхронизация»).
- **Zapret2** (bol-van/zapret2, `nfqws2`/`winws2`) — тот же подход, но
  стратегии и автоматизация написаны на Lua (`lua/zapret-auto.lua`,
  `zapret-antidpi.lua`); последняя запись журнала изменений на дату —
  1.0.6 (`zapret2/docs/changes.txt`). Лицензию zapret2 по файлу в репозитории
  сверить не удалось (файла `LICENSE` по ожидаемому пути нет) — это не
  важно: код не берётся.
- Обоим нужен доступ к пакетам до ядра сети: на Linux — правила
  iptables/nftables и NFQUEUE (права root), на Windows — драйвер
  WinDivert.

## 2. Автолист Zapret (autohostlist)

Zapret сам решает, к каким доменам применять десинхронизацию: домен
попадает в автолист после нескольких неудач подряд.

**Признаки неудачи** (по `zapret/docs/readme.en.md`):

- несколько ретрансляций первого запроса в TCP-сессии с известным
  именем (`nfqws`);
- RST в ответ на первый запрос (`nfqws`, `tpws`);
- HTTP-перенаправление на первый запрос на домен второго уровня, не
  совпадающий с исходным (`nfqws`, `tpws`);
- клиент закрыл соединение после первого запроса, не получив ответа
  (`tpws`).

**Порог:** `--hostlist-auto-fail-threshold` (по умолчанию 3) неудач в
окне `--hostlist-auto-fail-time` (60 с); попытка считается неудачной
после `--hostlist-auto-retrans-threshold` (3) ретрансляций. Домен
пишется и в память, и в файл; список исключений проверяется первым.
Документация прямо называет ложные срабатывания: сайт, который сам
сбоит (перегрузка, DDoS), тоже попадёт в автолист — его убирают руками.

## 3. Zapret2: детекторы и оркестратор

По `zapret2/docs/manual.en.md` и описанию `lua/zapret-auto.lua`:

- **`standard_failure_detector`** — неудача, если в пределах первых
  `--hostlist-auto-retrans-maxseq` (32768) байт исходящего потока
  случилось `--hostlist-auto-retrans-threshold` (3) ретрансляций; RST в
  начале входящего потока (`--hostlist-auto-incoming-maxseq`, 4096);
  перенаправление HTTP 302/307 на чужой домен второго уровня; для UDP —
  много исходящих пакетов (`--hostlist-auto-udp-out`, 4) при малом числе
  входящих (`--hostlist-auto-udp-in`, 1). Одно соединение даёт не больше
  одной неудачи.
- **`standard_success_detector`** — успех, если исходящий поток прошёл
  дальше `maxseq`, входящий — дальше `inseq`, или по UDP пришло больше
  `udp_in` пакетов. Успех сразу сбрасывает счётчик неудач («прежний сбой
  был временным»).
- **Оркестратор `circular`** — стратегии пронумерованы с 1 без пропусков;
  после `fails` (3) неудач в окне `time` (60 с) переходит к следующей,
  после последней — снова к первой; аргумент `final` останавливает
  перебор на заданной. Состояние — по ключу хоста (`standard_hostkey`)
  в таблице Lua в памяти процесса. Комментарий в исходнике: оркестратору
  нужно перенаправление и входящего трафика (иначе он не видит RST и
  ответы).
- **Профили по сети:** `--filter-ssid` (имя Wi-Fi) и `--nlm-filter`
  (сети Windows Network List Manager, различаемые по MAC шлюза) —
  разные стратегии для разных сетей задаются руками.
- **blockcheck2** — активный перебор стратегий против выбранных доменов;
  в 1.0.6 добавлен `CURL_PAD` (большой запрос, чтобы вызвать ограничение
  «16 КБ» без большой загрузки) и сводка COVERAGE.

## 4. Чего у Zapret нет

- **Качества пути.** Детекторы отвечают «работает или нет»; задержка,
  её разброс и «замерзания» после части данных не оцениваются.
- **Памяти между запусками и сетями.** Состояние оркестратора — в
  памяти процесса; автолист — файл, общий для всех сетей. Различие сетей
  — только ручные профили (`--filter-ssid`).
- **Порядка по опыту.** `circular` перебирает по кругу: после неудачи
  следующей идёт стратегия с соседним номером, а не та, что лучше
  работала раньше.
- **Защиты от «залпа».** blockcheck2 — сознательно активный перебор; для
  клиента, который работает постоянно, такие пробы сами становятся
  сигналом для фильтра (L7, `docs/research/RUSSIA_NETWORK_RESTRICTIONS.md`).

## 5. Перенос в DPpass

DPpass — не средство десинхронизации, а клиент прокси: путь наружу
создаёт сервер из конфигурации пользователя. Поэтому «стратегия»
Zapret у DPpass — **кандидат плана** (сервер с его транспортом и
защитой), а не параметры пакетов.

| Zapret / Zapret2 | DPpass (D-44) |
|---|---|
| стратегия десинхронизации | кандидат плана (D-15); параметры сервера DPpass не меняет (D-05, D-11) |
| ретрансляции первого запроса, RST, тишина в ответ | пассивно, по соединениям ядра с сервером: отказ установки TCP (сброс, отказ, тайм-аут), ретрансляции и «замерзание» по `TCP_INFO` (данные отправлены, ответа нет); плюс проба D-32 |
| успех: поток прошёл дальше `maxseq`/`inseq` | соединение с сервером получило больше 32 КиБ (порог «16–20 КБ», L4/L7) или проба прошла |
| 3 неудачи за 60 с | гистерезис наблюдателя сессии: 2 проваленные пробы подряд или «замерзание» с проваленной пробой — переключение сразу; ухудшение задержки — только при заметно лучшем кандидате |
| `circular`: по кругу | порядок по опыту **в этой сети** (оценка устойчивости), разнообразие классов транспорта (D-15) |
| состояние по хосту в памяти | книга устойчивости по паре «сеть, сервер», хранится зашифрованной (D-19) и переживает перезапуск |
| профили по SSID руками | непрозрачный ключ сети: соль установки и грубые признаки сети, без SSID и адресов |
| blockcheck: активный перебор | не делается: учёт исходов настоящих попыток и одна маленькая проба по расписанию (D-14) |
| десинхронизация пакетов | не делается: нужен доступ к пакетам до ядра сети (root); отложенный вопрос «Локальная DPI-десинхронизация» (`docs/direction/DECISIONS.md`, «Отложено») |
| автолист доменов | автоматического списка «напрямую не открывается» в 0.5.0 нет — `TODO.md` |

## 6. Что DPpass добавляет к подходу

Детекторы Zapret дают сигнал «сработало / нет»; DPpass по этому сигналу
и по пассивным замерам строит оценку, нужную пользователю, — устойчивость
важнее скорости:

- **Забывание.** Свидетельства стареют (полураспад сутки): блокировки
  меняются неделями, и опыт прошлого месяца не должен перевешивать
  вчерашний.
- **Обнаружение смены режима.** Последовательный тест Пейджа — Хинкли по
  исходам проб: когда отказов внезапно становится больше, уверенность в
  сервере сбрасывается за 2–3 наблюдения, а не за дни забывания.
- **Задержка и её разброс.** Сглаженный RTT и его отклонение — как у TCP
  (RFC 6298), разброс соседних замеров — как джиттер RTP (RFC 3550);
  пассивно — по `TCP_INFO` ядра, без отдельных пакетов.
- **Обобщение.** Однослойная модель (логистическая регрессия — нейросеть
  из одного нейрона) по признакам сервера и сети переносит опыт на
  серверы без своей истории: «в этой сети UDP не проходит» относится ко
  всем серверам Hysteria2 новой подписки сразу.
- **Пессимизм.** Порядок — по нижней границе доверия к доле успехов:
  сервер с 3 удачами из 3 не обгоняет сервер с 95 из 100.
- **Без «дребезга».** Переключение — по подтверждённому отказу, с паузой
  и пределом переключений в час: сама смена сервера — нагрузка и сигнал
  для фильтра.
